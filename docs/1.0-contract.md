# 1.0 acceptance contract — reopened

The previous readiness score is withdrawn. Karl requires a stricter review of
usefulness, readability and ease of use; passing tests alone does not establish
that the product is ready. [Current rework](product-rework.md) adds agent-facing
MCP and real source scaffolds with fail-fast stubs by default. No new product score is assigned.

Authorised target: a near-feature-complete local design workbench, with a reviewed
plan and a separately reviewed implementation. A score is a transparent checklist
judgement, not mathematical proof. No core feature below may be deferred at final
review while claiming 9.5/10. Public publishing remains separately authorised.

Finite scopes, primitive/record/tagged/list data and bounded structured control are
the 1.0 execution boundary. Unbounded recursion, arbitrary shared mutable aliases,
universal SMT/proofs, production conformance, cloud collaboration and general
latency/peak-memory inference stay outside it. Those are not substitutes for F01–F13.

## Resolved architecture choices

- One TypeScript package. Existing parser/typed IR/analysers and process owner remain
  authoritative. The GUI never infers verdicts, costs or ownership itself.
- Local React interface, CodeMirror editor, Vite build. Loopback Node host; CLI
  `studio PATH` binds to one canonical project root. No cloud account or desktop
  shell needed. Source/output HTML is escaped, never evaluated.
- Unsaved content enters the existing loader through explicit buffer overlays.
  Each run captures a deep-copied overlay revision and snapshot, never temporary
  overwrites of source files. Disk saves compare expected content hash.
- HTTP requests use a random per-session token and origin checks. Every path is
  canonicalised and checked against the root, including imports and symlinks.
  One active analysis at a time; superseding cancels it and marks history clearly.
- Typed run events contain run ID, buffer revision, request configuration and report
  snapshot. A completed old run remains inspectable as historical evidence.
- Structured execution uses one small-step source semantics with finite environment
  outcomes. Backend lowering preserves the same observable steps and validates
  witnesses. Explicit machines remain for advanced environmental protocols.
- Text is authoritative; diagrams are views. Bounded node/row materialisation and
  search prevent a large project from creating a quadratic GUI layout.

## Two ratings

Plan readiness is reviewed across 20 equal criteria: scope, current-state honesty,
feature traceability, GUI workflows, shared semantics, buffer identity, save conflict,
stale-run ordering, cancellation, root confinement, token/origin isolation, resource
semantics, environment contracts, cost/constraint boundaries, backend correspondence,
accessibility, deterministic tests, reproducible setup, exports/privacy, and delivery
loops. At least 19/20 must have a concrete decision and an observable check before
construction. An unresolved data-loss/false-assurance/security blocker overrides the score.

Product review weights: F01–F06 usable GUI 30%, F07–F10 semantic capabilities 35%,
F11–F12 complete workflows 15%, F13 correctness/lifecycle/security 20%. Every mandatory
feature must be implemented, integrated and evidenced. A critical failing test,
missing flow lowering, missing editor/save workflow or false evidence claim blocks
9.5 regardless of weighted arithmetic. GUI quality is also a non-compensable gate: a polished first-open experience, clear hierarchy, accessible interaction and smooth authoring must each pass review. Engine strength cannot compensate for a poor interface. Remaining deductions may only be minor UX,
documentation or optional-scope issues. Report untested/manual items honestly.

## Initial plan review

The earlier roadmap was directionally sound but not implementation-ready: it left
buffer loading, per-run versioning, save races, local host security, finite flow
semantics, exact release scope and score interpretation underspecified (8/10).
This contract resolves those decisions and defines checks for all 20 criteria.
Plan readiness: 19/20 = 9.5/10, with visual usability requiring actual implementation
and review rather than paper confidence. This is permission to build, not a product
rating. The final implementation must earn its own score against F01–F13.

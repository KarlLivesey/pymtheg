# C-64: What is stored beside a source file holds nothing of a program

Found while measuring C-52 (pull request 66) on microsoft/TypeScript: a heap
snapshot near the default heap limit held six TypeScript programs at once,
where the analysis needs one. The shortest path from the roots to four of
them was:

```
stack root → libCache (or the new build's lib files) → a lib SourceFile
  → keyNames entry (WeakMap, symbols.ts) → closure context → program
```

## The leak

C-49 stores, beside every source file of a program, how its compiler text
spells names back (`setKeyNames` in `symbols.ts`, a `WeakMap` from the
source file to a `restore` function). `extractFile` made that function as an
arrow inside itself:

```ts
setKeyNames(source, (text) => restoreNames(text, fresh));
```

A closure made there shares the function's context, which holds the
program, the checker and everything else `extractFile`'s inner closures
use. The map is weak in its key, but its keys include the lib files, and
lib files live for the whole analysis: the module keeps one parse of each
in `libCache` (project.ts), shared by every program. So every program that
stored an entry on a lib file stayed alive, with its checker, until the
analysis ended. Programs are replaced during an analysis: per project
group, and on every rebuild after a checker stack overflow or a compiler
exception. On microsoft/TypeScript that kept up to six programs (each about
14,500 files and a checker) alive at once.

## The fix

`nameRestorer(fresh)` (rename.ts) makes the stored function at module level,
over a copy of the fresh names: three strings per table, checked to be
strings. Its closure holds that copy and nothing else, so an entry on a lib
file keeps no program alive. `extractFile` makes one per program and stores
it for each of the program's files, as before. No stored row changes, so no
module version changes.

## Other values stored beside compiler objects, checked

Every module-level `WeakMap`/`WeakSet` of the TypeScript module keyed by a
source file, node, symbol or declaration, and the per-analysis ones whose
keys can be lib files:
- `identities` (symbols.ts): node → string. Holds nothing.
- `fileKeys` (symbols.ts): source file → its own nodes' keys (strings).
  Holds only that file.
- `keyNames` (symbols.ts): fixed here.
- `libraryReader` (library.ts, one per analysis): `declarationUnits`,
  `declarations` and `exportedOwners` hold plain data (units, targets,
  names). `qualifiedKeys` maps a result's library target object to a
  symbol or declaration; it is keyed by the target, not by a source file,
  lives as long as the result, and no root path in the snapshot went
  through it.
- Maps keyed by a program or a checker (`judges`, `programNodeEvidence`,
  `programTestSetups`, `producerReaders`, `receiverCache`, `programTypes`,
  the taint and judge budgets): an entry dies with its key, so they keep
  nothing beyond it.

No other value stored beside a source file, a lib file or the parse cache
closes over a program, checker, type or symbol.

## Not fixed here

- **A cached source file pointing at an old checker's type.** One of the
  six programs was reached through the live parse cache: a cached source
  file's node → its binder symbol → that symbol's `parent`, a symbol the
  checker created (with `links`) → a type of the old checker → that
  checker → its program. The checker writes this onto the shared parse
  itself; it is TypeScript's state, not something this module stores, so
  this fix does not cover it. The parse cache is left as it is. (C-52's
  draft measured that a fresh parse per rebuild avoids it.)
- **V8's allocation-site feedback.** One program was held by the engine's
  feedback for the object literal in TypeScript's `createProgram`, from the
  stack roots. That is V8's, not ours.

## Test

`test/graph-index-memory.test.mjs`, without timing (`v8.queryObjects`
counts live objects after a full collection):
- "a program replaced during an analysis does not stay alive through what is
  stored beside its files": a six-file project whose extraction meets one
  injected stack overflow per file (the module's `checkerFault` hook), so
  the session rebuilds its program six times. At the first checker call of
  each rebuilt program it counts the live checker types. With the closure
  made inside the extraction they grow by about 99 per rebuild (176, 275,
  374, 473, 572, 671); with the fix they settle (the last three equal). It
  also checks that every file's stored restorer was made by `nameRestorer`.
  [mutation.mjs](../../evidence/c-64/tools/mutation.mjs) puts the old
  closure back and shows the test failing.
- "the stored name restorer copies the fresh names and accepts only
  strings".

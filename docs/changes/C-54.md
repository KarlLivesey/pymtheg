# C-54: The server owns its toolchain processes

Cancelling an MCP job now ends the processes the job started. This covers a
`code_graph` index and a `requirement_links` job that indexes. A server that
exits with a job running ends them too, as does a CLI index stopped by
SIGINT, SIGTERM or SIGHUP.

Before this change, both MCP job managers cancelled by terminating the job's
worker thread. The worker's abort signal never fired, so the toolchain it
was waiting on kept running: the Go route's `go`, and anything a build runs.
The route's own clean-up never ran either. Taken out of the C-43 review
(pull request 62), so that the other pull requests that start child
processes from a worker can use the same piece.

## The registry

`src/backends/child-groups.ts` records the process groups this process has
started. They are kept in memory that the main thread shares with its
worker threads and owns.

- `runProcess` already starts every child as the leader of its own process
  group. It now records the group as soon as the child has a pid, and
  forgets it once the group is killed.
- The main thread has its own registry. A job manager gives each job a new
  one (`jobChildGroups`) and passes it to the job's worker, which records
  into it (`useChildGroups(workerData.childGroups)`).
- `killChildGroups(buffer)` sends SIGKILL to every recorded group and
  forgets it. The owner calls it itself, so it needs nothing from the
  worker, which may be terminated or stuck.
- When the process exits, it kills every group in its own registry and in
  every job's.
- A full registry (256 live groups) refuses to start the child. The child
  is killed at once, and `runProcess` answers `spawn_failed` saying the
  registry is full. The Go route then reports `unavailable` with that
  reason in the job's result (`toolchain.go.reason`), so the job says why
  and no child ever runs untracked.

## Which paths start children

`runProcess` is reached from three places:

- the Go toolchain route (`go env`, `go build`, the helper);
- `git`, in trusted checkouts (`src/shared/safe-git.ts`);
- registered emitter plugins.

An import trace from every worker entry finds two workers that reach it.
Both now record into their job's registry:

- the graph worker (`code_graph`);
- the links worker (`requirement_links`). Its link actions sync the graph
  first, so the Go route runs there too.

The other workers (architecture, behaviour, query, the Rust phases and the
CLI check worker) start no child process. `git` and plugins run on the main
thread, whose registry is killed when it exits.

## Cancelling a job

**`code_graph`** (`GraphJobs`) cancels in four steps:

1. It kills the job's recorded process groups itself, at once, so no child
   outlives a cancel whatever the worker does (a worker blocked in
   synchronous code included). It asks the worker to abort (`{kind: "abort"}`). The worker aborts the
   command's signal, which kills the process groups it is waiting on
   (`runProcess`) and lets the route remove its folders as it unwinds. The
   Go route rethrows the signal's own reason, so the index is cancelled
   whole rather than recorded as an analysis error.
2. When the command has settled, the worker answers `aborted`. The server
   waits for that answer only while the job has a live child group. A
   group is live only while the worker awaits it, so the answer normally
   comes at once. A worker that does not answer within a grace period
   (`CANCEL_GRACE_MS`, 30 s, on an injectable clock) is terminated all the
   same. The grace bounds only how long clean-up may take; the children
   are already dead. A bound with no clock would need a sign from the
   worker that it is blocked, which a blocked worker cannot give, so the
   clock it is: injectable, and deciding nothing but clean-up time.
3. The worker is terminated.
4. Any group still recorded is killed by the server.

**`requirement_links`** (`LinkJobs`): the link library takes no abort
signal, so a cancel terminates the worker and the server kills the job's
groups. The Go route's run folder is not removed then.

## Signals and the true limits

- The CLI (and so `pymtheg mcp`) turns SIGINT, SIGTERM and now SIGHUP (a
  closed terminal, which is how a server dies when its client's terminal
  closes) and SIGQUIT into the same orderly end. A client that vanishes
  closes the server's stdin, which ends it the same way; a write to a
  closed stdout fails with EPIPE (Node ignores SIGPIPE), an uncaught error,
  after which the exit hook still runs. The command's signal is aborted, the MCP server closes
  its jobs, and the exit hooks run. Before, SIGHUP killed the process at
  once and nothing it started.
- The true limit: only a death the process cannot observe leaves children
  behind. That means SIGKILL, a crash of the runtime itself, or another
  signal that ends Node with no handler (none that a terminal or client
  sends). Its
  children are in their own process groups, so a signal to the parent's
  group does not reach them, and they run until they end on their own.
  Their folders are left behind. The Rust route's stale-run sweep (C-43,
  pull request 62) removes such a run's folder the next time. The Go
  route's `build-*` and `run-*` folders have no sweep yet.
- After an uncaught exception the exit hook still kills the processes, but
  the route's `finally` never ran, so the Go route's `build-*` folder (in
  the user's cache folder) is left behind, as after SIGKILL. The next build
  uses a new folder; nothing reads the old one.
- After a child exits, `runProcess` waits up to 120 ms for its pipes before
  it kills the group and forgets it, so a reaped pid can stay recorded for
  that long. A kill in that window reaches the pid as a process group: only
  a new process that reused the pid and leads a group of its own would be
  hit. That cannot happen within that window in practice, and the reviewers
  found no such case.
- A child recorded in the instant between `spawn` returning and the record
  (a worker terminated in exactly that window) is not killed by the server.
  Its own abort still ends it while the worker runs.
- **Windows** has no process groups, so `process.kill(-pid)` is not used
  there. The registry and `runProcess` kill the recorded process itself
  (`process.kill(pid)`, which terminates it). Its own children are not
  killed: nothing kills a grandchild on Windows, which is the gap.
- **macOS** behaves as Linux: `detached` children lead their own process
  groups, and `kill(-pid)` reaches the whole group.

## Tests

`test/mcp-graph-children.test.mjs` runs on a trusted checkout with the Go
route on. A fake `go` whose `go build` starts a child that never finishes
writes both pids, and the test reads them as its readiness handshake.
Every test's `finally` kills the fake's process group, so a failing test
leaves nothing running.

- A `code_graph` cancel ends both processes, and the build folder is
  removed.
- A server process that exits with the job running ends both.
- A CLI `graph index` stopped by SIGTERM, SIGINT or SIGHUP exits 130 and
  ends both.
- A `requirement_links` job (a `list` by symbol, which syncs the graph) that
  is cancelled ends both.
- An MCP server (`pymtheg mcp`) sent SIGHUP while a `code_graph` index runs
  ends both.
- A worker that never answers the abort is terminated when the grace,
  fired by a controlled clock, ends, and its child is killed.
- A full registry refuses to start a child, and says why.

On main's job manager the first test fails with "a toolchain process is
still running", and the second with "a toolchain process outlived the
server". The Go route's cancellation test now expects the index to reject
with the signal's reason; before, it expected an analysis error.

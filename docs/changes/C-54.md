# C-54: The server owns its toolchain processes

Cancelling a graph job over MCP now ends the processes the job started. A
server that exits with a job running ends them too. Before this change, the
job manager cancelled by terminating the job's worker thread: the worker's
abort signal never fired, so the toolchain it was waiting on (the Go route's
`go`, or anything a build runs) kept running, and the route's own clean-up
never ran. Taken out of the C-43 review (pull request 62), so that the
other pull requests that start child processes from a worker can use the
same piece.

## The registry

`src/backends/child-groups.ts` records the process groups this server has
started. They are kept in memory shared by the main thread and its worker
threads, which the server owns.

- `runProcess` already starts every child as the leader of its own process
  group. It now records the group in the registry as soon as the child has a
  pid, and forgets it once the group is killed.
- `killChildGroups(buffer)` sends SIGKILL to every recorded group and
  forgets it. The server calls it itself, so it needs nothing from the
  worker, which may be terminated or stuck.
- A worker records into the server's registry when it is given one
  (`useChildGroups(workerData.childGroups)`). The main thread has its own
  registry, killed when the process exits.
- A full registry (256 live groups) records no more. Such a child runs as
  before this change: its own abort still kills it.

## The MCP job manager

Each job gets its own registry (`GraphJobs`, `src/mcp/graph-jobs.ts`). A
cancel now runs in four steps:

1. It asks the worker to abort (`{kind: "abort"}`). The worker aborts the
   command's signal, which kills the process groups it is waiting on
   (`runProcess`) and lets the route remove its folders as it unwinds.
2. When the command has settled, the worker answers `aborted`. The server
   waits for that answer only while the job has a live child group. A group
   is live only while the worker awaits it, so the worker's event loop is
   free and the answer comes; no clock decides. With no live group the
   worker is terminated at once, as before.
3. The worker is terminated.
4. Any group still recorded is killed by the server.

When the server process exits, it kills every group its jobs recorded.

## The CLI

The CLI already ended its toolchain children: SIGINT and SIGTERM abort the
command's signal, and `runProcess` kills the process groups it is waiting
on. A test now keeps it so (below). The main thread's registry adds a
backstop: a CLI process that exits kills every group it recorded.

## Limits

- A process killed with SIGKILL runs no code, so nothing it started is
  killed by this: its toolchain processes run until they end on their own.
  Their folders are left too. The Rust route's stale-run sweep (C-43, pull
  request 62) removes such a run's folder the next time; the Go route's
  `build-*` and `run-*` folders have no sweep yet.
- A group recorded in the moment between `spawn` returning and the record
  (a worker terminated in exactly that window) is not killed by the server.
  Its own abort still ends it while the worker runs.

## Tests

`test/mcp-graph-children.test.mjs` runs the production `GraphJobs` and
graph worker on a trusted checkout with the Go route on. A fake `go` starts
a child in its process group that can never finish, writes both pids and
waits; the test reads them as its readiness handshake.

- A cancel ends both processes, and the route's build folder is removed.
- A server process that exits with the job running ends both.
- A CLI `graph index` stopped by SIGTERM, and one stopped by SIGINT, exits
  130 and ends both.

Both tests fail on main's job manager ("a toolchain process is still
running") and pass with this change. The existing MCP job tests pass
unchanged.

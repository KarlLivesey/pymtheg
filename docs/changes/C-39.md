## 1. Const assertions

`x as const` and `<const>x` parse as a type reference named `const`. The
module stored them as unresolved `references` links: 2,719 across 19 pins.
A const assertion is not a reference, so it now stores no link
(`ts.isConstTypeReference`). `as Point` and `satisfies Point` still link to
`Point`.

## 2. Configs extended by package name

Every package-name `extends` (`astro/tsconfigs/strict`,
`@turbo/tsconfig/library.json`, `@repo/typescript-config/nextjs.json`) was
marked "from an external package". The marker was cleared only when the
compiler read the config from an installed path. Two things kept it in
place:

- **Not captured.** The extended files lie in the checkout behind a
  workspace link (`packages/turbo-workspaces/node_modules/@turbo/tsconfig →
  ../../../tsconfig`, `examples/ssr/node_modules/astro → packages/astro`). Their
  names (`strict.json`, `library.json`) match no context pattern, so they
  were never captured.
- **Not counted.** A config the compiler read through `node_modules` that
  turned out to be a captured checkout file did not clear the marker.

The fix has two parts.

- **Capture.** JSON files directly in a directory whose name contains
  `tsconfig`, or in a `typescript-config` directory, are now captured
  (`**/*tsconfig*/*.json`, `**/typescript-config/*.json`).
- **Resolution.** A package-name `extends` that the compiler reads through
  `node_modules` clears the marker, whether the file is installed or a
  captured checkout file behind a workspace link. It still does so only
  when the compiler reports no unreadable extended config. An `extends` of a
  package that is absent keeps the marker and its `incomplete-config`
  reason.

This capture is a static pattern. Capturing exactly the file that any
`extends` chain names would need a second capture pass: the module would
resolve each chain over the inventory and ask the core to capture what it
names. That pass would have to stay consistent across full and incremental
indexing and context-change detection. It is listed as further work.

A base reached by package name whose JSON has a syntax error keeps the
marker. The compiler reports it (1005) and drops what it cannot parse,
exactly as for an unreadable base (6053 or 5083).

Turborepo gains 12,273 Level 2 links from read configs, Astro 368 and tRPC
15. A further 602 Turborepo library links now name their symbol under the
read configs. As the review predicted, some links behind the read configs
now stop at their next blocker, such as missing build output or
uninstalled packages.

## 4. Library targets beside an unread file: split out to C-51

This item kept an installed library target beside an unread (failed) file
when no unread file could change it. Three review rounds found four
distinct holes in that rule. Its gain was +3,602 Level 2 links (0.25
points, all Vitest). By the manager's ruling it is removed from this pull
request and continues as C-51 (draft pull request 59, from this branch's
pre-removal head `675ac88`, with the review's open findings).

Here, a program with an unread file withholds library targets exactly as on
main (`no-unseen-declarations`). The module-link identity fix for a dynamic
import of a pattern ambient module (`import("./App.css")`) is removed with
it. It existed only because item 4 kept targets beside unread files;
without item 4, main's behaviour returns and there is nothing to fix.

## Links that changed or were lost

Every definite link on main was compared with the candidate on all 19 pins.
The same comparison is used for identities
([changes](../../evidence/c-39/changed-definite-installed.jsonl.gz),
[kinds](../../evidence/c-39/changed-kinds.json)). All changes are on
Turborepo and Astro, and all follow from reading the real configs:

- **181 renamed library links, same package** (Turborepo). Under the
  now-complete settings, the checker proves the declaration (for example
  `node:path:path`) where main named the import binding as spelled
  (`node:path:default`). 157 of the 251 changed or lost links have the
  identical name and kind linked to the identical target elsewhere on main.
- **6 now name the declaring package.** For example, `eslint/config`'s
  `defineConfig` is declared in `@eslint/config-helpers` (the C-23
  ownership rule).
- **46 Astro `getCollection` links became `external-package`.** On main the
  example's config could not be read, so its files fell to the inferred
  project, which contains every ambient `astro:content` declaration in the
  checkout. With the example's own config read, the program, like `tsc`
  there, does not see those files. They reach a real Astro project only
  through the generated `.astro/types.d.ts`, which `astro sync` writes and
  the checkout lacks.
- **18 lost, and 12 symbol identities gone, in 4 Turborepo Svelte example
  files that now fail.** `@repo/typescript-config/svelte.json`, now read,
  sets `allowJs`. The example configs therefore include their JavaScript
  files, and they also extend the generated `.svelte-kit/tsconfig.json`,
  which is missing. The existing rule fails every file of a broken config;
  on main these files fell to the inferred project.
- **`with-nextjs-elysia/packages/contract`** (fixed). The first version
  of this note blamed a TypeScript assertion on the real config. The
  cause is ours, and it predates this chunk. `registryDependency`
  (`library.ts`) passes the manifest range `^1.0.0-beta.9-8d6992`
  (drizzle-orm's published beta form) to the compiler's
  `VersionRange.tryParse` (`workspace.ts`), which throws on it instead
  of returning nothing. The throw was reported as a compiler failure of
  the importing file. Every parse of manifest input now catches the
  throw:
  - a range it cannot read is an unknown range, which still identifies
    the registry dependency by its unit but never yields a version pin;
  - a version or range that cannot be parsed proves no workspace version
    match.

  The five files now index.

These are the only symbol keys that change. Every other symbol on all 19
pins is unchanged ([removed](../../evidence/c-39/turborepo-removed.txt)).
The 22 link sites removed with the Svelte files, and the 2,719 `as const`
links, are the only sites that disappear (2,741). None is added.

**Item 4 is fully removed.** On the four pins whose unread files passed
item 4's rule (tRPC, Vitest, Astro, Turborepo), every link that main
computed in a program with an unread file (marked `no-unseen-declarations`,
75,071 links) was compared with this branch
([check](../../evidence/c-39/unread-equal.json),
[tool](../../evidence/c-39/tools/unread-equal.mjs)):

- 74,420 are identical;
- 571 are in files whose owning project changed, because their own config
  is now read (item 2). Astro has 534 and Turborepo 37;
- 66 are `as const` links, now not stored (item 1);
- 10 are in the four Svelte files that now fail (item 2);
- 4 keep the same unresolved outcome with another reason. These are
  Turborepo's `with-vitest` imports of `@repo/vitest-config`: their
  example's extended config is now read (item 2), and
  `workspace-entry-unavailable` became `workspace-build-output-missing`.

## Checks

The new tests each fail on main and pass here:

- const assertions;
- the shared config behind a workspace link and through package
  `exports`;
- a manifest range the compiler's parser throws on
  (`^1.0.0-beta.9-8d6992`). The importing file indexes, and the three
  range outcomes are checked directly.

The negatives hold on both builds: an absent extended package, and a base
config whose JSON has a syntax error (the marker stays).

The tests and test changes for item 4 moved to C-51 with it. The conformance
sample, the W2-D differential harness, K3 and `written imports can be
independent of …` are as on main.

Build, type check, format check, the TypeScript graph tests (234), the sweep
tests and the full `npm test` pass.

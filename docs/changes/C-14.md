# C-14: Go links to standard-library, builtin and dependency symbols

Support items `go-external-targets`, `go-external-import`,
`go-external-result` and `go-external-fields` in the coverage plan, and the
owner's decision that Go builtins the graph identifies count at level 2.
Go module version 29 → 30: stored links gain library targets and a reason,
so older stores re-index. The opt-in toolchain helper (`golinks.go`) changed
too; it is rebuilt from its source hash. No symbols and no link sites are
added.

## What Go now records

On the C-5 core (`library` outcome, `graph uses`), only where a link has no
checkout target, candidate set or failure:

- **Imports** of a package outside the checkout: the unit is the import path
  as written, evidence `import-path` (level 1). Blank and dot imports too.
- **Package-qualified names**: an exported name selected from such an
  import's qualifier, as a call, value, embedded field or written type
  (`strconv.Quote`, `http.MethodGet`, `time.Duration`, `require.NoError`,
  `sync.Mutex` embedded): unit and name, evidence `import-binding`.
- **Builtins** (`len`, `append`, `make`, `new`, `delete`, `copy`, `close`,
  `panic`, `recover`, `print`, `println`, `min`, `max`, `clear`, `complex`,
  `real`, `imag`, `cap`): unit `builtin`, ecosystem `go-std`, evidence
  `declared-builtin`, when nothing can shadow the name: no package-level
  declaration of it in any file or build variant of the package, no import
  of that name, no failed file of the package, no same-package test-file
  declaration (the test build would see it), no local (bound at parse).
  Predeclared types and values (`error`, `int`, `nil`, `true`) have no link
  site unless shadowed (then they resolve inside), so nothing changes there.

**Standard library or dependency.** `go-std` when the path's first element
has no dot and is a standard root (a fixed list, so a GOPATH-style
`import "a"` under `testdata/src` is not taken for the standard library),
and no module of the checkout provides or declares the path. `go` when a
module of the build provides it and every destination is outside the
checkout: the module cache, or a `replace` to another module path or to a
directory outside the project. Never a library: a main or nested module of
the checkout, a local `replace` (with or without a captured go.mod), an
uncertain or ambiguous destination (C-8's provider rules in `gomod.ts`), a
module whose `vendor/` directory has captured files (Go builds the vendored
copy, which is checkout code), `import "C"`. In a pruned build (go 1.17 or
later) a module no main module requires is not in the build, so nothing
through it is a library either.

**Version.** Only when exactly one module provides the package, no
`replace` applies, and C-8's `selectedVersion` proves the selected version
from the main go.mod; `versionSource` is that go.mod. A replaced module
gets no version (the import path stays the unit: it is the package
identity). The `go` directive is the language version, not a standard
library version: `go-std` targets have none.

**Which import binds a qualifier.** Imports are per file. The qualifier
must not be a package-level or local declaration (locals are bound at
parse, so `http := newClient(); http.Get()` is the local), and exactly one
of the file's imports must be able to bind it: an explicit import name; a
standard-library package's last path element (before `/vN`); or, for an
unnamed dependency import, its conventional name, the last path element
without a `/vN` or `.vN` suffix or a `go-` prefix. The package clause of a
dependency is not in the checkout, so the conventional name is an
assumption, kept narrow: a qualifier that matches no import's conventional
name (`minio.New` through `github.com/minio/minio-go/v7`, `v1.Pod` through
`k8s.io/api/core/v1`) or more than one is not followed. The shape it would
get wrong is two unnamed imports whose package clauses are each other's
conventional names; goimports writes a name wherever clause and path
differ. A dot-imported name is not followed source-only (the name may be a
package-level declaration elsewhere; the evidence kind for it, `glob-import`,
is for candidate sets only).

**Build variants.** An import is per file, so the unit holds in every build
of the file. A selected name that exists only on some platforms
(`syscall.Kill`, `unix.*`) cannot be checked without the library: it is
recorded as written; the import proves the unit and the written name. The
builtin rule counts a declaration in any build variant as a shadow.

## Methods and fields on library types

`buf.Write(p)` on `var buf bytes.Buffer`, `resp.Body`, `t.Format(...)` on a
library call's result: the member's declaring owner is not provable from the
checkout. A method may be promoted from an embedded type of another package
(`exitErr.ExitCode()` on an `*exec.ExitError` is declared by `os`'s
`ProcessState`), and a library call's result type is not written in the
checkout at all. Source-only, such a link stays unresolved with
`data.uncertainty: "library-member-unproven"`. The task suggested recording
the receiver's unit at level 1; that is not done, because the receiver's
unit is not always the member's (the `os/exec` example), and level 1 does
not count for the plan. The written type itself (`bytes.Buffer` where a
variable, field, parameter or result is declared with it) is a reference
site with its own level 2 target.

With the opt-in toolchain route (`graph.toolchain.go`) and a clean run,
go/types' selection proves the member: the helper's C and U records now
carry the selected field's or concrete method's declaring named type
(after promotion), and the resolver records `Owner.Name` with
`declaring-owner` (`Buffer.Write` in `bytes`, `Mutex.Lock` in `sync` for a
promoted `g.Lock()`, `ProcessState.ExitCode` in `os`, `Response.Body` in
`net/http`). Interface methods are dispatch and get no library symbol either
way. A builtin and a package-level object the toolchain names are recorded
as the source-only route would; the toolchain's answer wins where both
exist. These decisions hold for the toolchain's one configuration, like its
checkout targets.

A member promoted from a library type embedded in a checkout struct
(`g.Lock()` with `struct{ sync.Mutex }`) gets no reason source-only yet;
only a library-typed receiver does.

## The measure

`coverage-export.mjs` credits stored targets on Go graphs of module 30 and
later and does not run its Go reconstruction there, so nothing is counted
twice; older graphs (0.1.0, and module 29) keep the reconstruction, so the
committed baseline scores as before.

## Results

All 20 Go pins, a build of `main` against this branch
([evidence](../../evidence/c-14/README.md)):

- **Go level 2 77.81% → 84.87%** (default, source-only route; 1,512,998
  stored Go links at 1,512,591 sites). All sites and like-for-like are the
  same figure: no site or row added or removed. The plan's Go section:
  79.11% → **84.99%**, source-only ceiling 94.30%.
- Builtins 48,840 links; package-qualified names newly credited 58,152
  (mostly unnamed dependency imports, which the reconstruction did not
  credit); 153,749 the reconstruction credited are now stored; 32,531
  import units at level 1; 111,406 members of library-typed values carry
  `library-member-unproven`.
- Every checkout-definite row kept (1,023,393, none lost or retargeted),
  no candidate set changed, all 200,941 symbols kept. Of the 153,868 sites
  the old reconstruction credited, **119 are withheld**, all golang/tools
  `go/ssa/interp/testdata` imports of the harness's own `fmt`, `reflect`,
  `strings` and `errors` from `testdata/src` (checkout code).
- 40 library links hand-checked at seed `c-14` across restic, cli/cli,
  pebble, gin and samber/lo: all true.
- Toolchain route on restic: 84.40% → **91.08%**. Of 13,930 sites with a
  library target on both routes, go/types decided 10,524 itself (recorded
  provenance) and agreed on all of them; the other 3,406 were the
  source-only decision on both routes.
- A shipped standard-library member table (not built) would hold about
  4,000 methods and 2,500 fields of 1,169 types, about 200 KB per Go release,
  and could recover at most about 66,000 links (4.4 pp), only where the
  receiver's type is written in the checkout.
- Cost: user CPU +8% (restic) and +16% (bbolt) in a cold index, all of it
  in the store writing the new library rows; wall time within noise; peak
  memory unchanged.

`pymtheg graph uses fmt Errorf`, `graph uses github.com/spf13/cobra` and
`graph uses builtin append` answer on Go graphs (restic: 222, 186 and 421
links; output in the evidence).

## Review round 1

- A `replace` to any filesystem path, relative or absolute (`/src/mod`,
  `../up`, `C:\x`), may be checkout code: nothing through it is a library.
- In a `go.work` workspace a version is recorded only when every workspace
  module that requires the module names the same version (another module
  can raise the selection); otherwise unit and symbol without a version.
- An unnamed import whose package clause is not captured may bind any
  plausible name of its path: the last element, or the one before `/vN`,
  without `.vN`, a `go-` prefix or a `-go`/`.go` suffix, hyphens dropped or
  as underscores. One import that can declare the qualifier: its target
  (`minio.New` through `minio-go/v7` is now definite); several
  (`example.org/client-go` and `example.net/client` for `client`): a
  candidate set of their units. None occurs on the 20 pins. A captured
  clause binds as before.
- A file under a `testdata` directory whose tree holds `src/<import path>`
  (golang/tools' `go/ssa/interp` harness supplies a fake `fmt`) imports
  checkout code: no library target.
- Evidence counts every stored row (the first head's comparison keyed by
  site and so collapsed distinct `implements` rows) and the toolchain's
  recorded provenance.
- Cost was not re-measured: the review changes touch import binding and
  module layout only, not the store writes the cost comes from.

## Found, not built

- A reason for members promoted from a library type embedded in a checkout
  struct (`g.Lock()` on `struct{ sync.Mutex }`): unresolved without one.
- A standard-library member table (above).
- Dot-imported library names: provable only by showing no package-level
  declaration of the name can exist; left unresolved source-only.
- The store's per-link write cost for library rows (core, C-5).

# C-36: Rust re-index proportional to the edit

A Rust edit that leaves every fact other files read unchanged now re-decides
only the edited file's links. Comment, whitespace and many body edits qualify.
Before this change both Rust passes, analysis and resolution, decided every
link of the project after any edit. Every other edit still uses the full Rust
pass. The change reuses the C-27 scoped analysis contract unchanged and adds
no setting, dependency or stored field. The Rust module version is 47
(main was 46). The cache rules below can change cold answers in shapes
whose result depended on the order in which files were decided.

## What another file reads

The Rust resolver receives every file's facts and decides links in one
pass. Links are read across files only through indexes built from
`ctx.links` in `resolve.ts`, and no other Rust file reads link lists. There
are twelve such reads. Nine select `imports`, `contains` or `macros` links:

- the function-region and macro-use maps;
- the extern crate list;
- the import tables by scope;
- the contains index;
- the macro sites;
- the visible prefixes;
- the trait imports in scope;
- the edition 2015 extern check;
- the attribute sites.

The other three touch only the links being decided: the cfg annotation, the
main decision loop and the macro-body calls.

`calls`, `values`, `types`, `patterns` and `implements` links are only
decided, so no other file can observe them. Everything else another file reads
comes from symbols and file data. The trait/impl relation, method names,
receiver forms, field types, signatures, aliases, variants and constants are
symbol facts. Inherited conditions, attribute contexts and macro scopes are
file data.

A file's **surface** is therefore its parse status and diagnostics, its file
data, every symbol with its data, and every `imports`, `contains`, `macros` and
`modules` link with its data. A link kind the list does not name counts as
surface. This covers each fact on the task's list:

| Fact | Where it is in the surface |
| --- | --- |
| Items, namespaces, visibility, enum variants, constants, traits and their items, impl heads, method names and receivers, written field and signature types, type aliases | Symbols and their data |
| `use` trees, re-exports, globs, `extern crate` and its macro-use requests | `imports` links and their data |
| `mod` declarations, `#[path]`, `#[macro_use]` on modules | `modules` links, module symbols and their data |
| `macro_rules!` definitions, bodies, `#[macro_export]` and textual order | Macro symbols, macro profiles and their ranked positions |
| Attributes and derives on items | `macros` links of attribute and derive flavour, and the file's opaque attribute list |
| `cfg` conditions | The file's attribute contexts and each fact's conditions |
| Crate-root attributes such as `no_std`, edition and crate kind | Root file data and the file symbol's unit data, set from Cargo |
| Cargo manifests, lockfiles and configuration | Not in the surface: any change uses the full pass |

Source offsets are replaced by their rank among the file's surface offsets.
Ranks preserve their order and equality. The resolver orders and matches a
file's positions and never measures them or compares them with another
file's. The ranked fields are ranges, `item:` keys, `libraryAttributeStart`,
and the starts of opaque attributes and standard macro scopes. Any other
number is hashed as written, so an offset the list misses can only cause a
fallback.

The file symbol always spans the whole text and only stands for the file's
own scope. Its range is hashed as a fixed marker rather than ranked, so a
leading comment does not change the rank of a first item at offset 0.

Since C-24, the Rust phases meet symbols and links in path and position
order, not in store id order. The surface lists them in that same order,
computed from the written values. A file's own symbol is now always first
in that order. Before, it tied with a first item at offset 0 and moved
behind that item once a comment preceded it. If an edit reorders surface
facts, including a tie broken by written data, the fingerprint changes. A
link's index in the file's list fixes only its store id. Other files'
decisions do not contain that id, and within one run it serves only as a
key. An edit that adds a call before a later `use` or derive therefore keeps
the surface.

## Argument and evidence

This section argues that a scoped pass decides the edited file's links as a
cold index does, names the steps the argument does not prove, and lists
every fuzz and seeded run with its counts.

### The argument

The resolver caches answers across links: lookup memos, and lazily filled
caches of helper shadowing, attribute shadowing, item presence, trait risk,
traits implemented outside the checkout, receiver typing and path calls. A
cold index decides the edited file's links after other files' lookups have
filled those caches. A scoped pass decides them after setup alone.

**Setup is the same computation in both.** Setup builds the module tree,
places, bindings and import facts from the snapshot, then fixes the opaque
scopes and clears every cache. It then builds the captured macro and
derive-helper exports afresh (`captureExports`; round 4), so no decision
reads a map built part-way through setup. In the analysis pass it then asks
every symbol's presence (`itemPresence`) and conditions (`conditionsFor`),
and every link's conditions where an implicit gate applies, in path and
position order (C-24), whatever the decision scope. The decision scope only
limits which of those answers are reported (`markPresence`,
`markConditions`). The caches after setup are therefore the same in both
passes.

A cut is a lookup cycle cut, a depth cut, a helper re-entry or a lazy
re-entry. The scoped path rests on three rules.

1. **No cached answer depends on its caller.** A lookup memo entry never
   contains a cut met at an ancestor of the cached lookup (C-24). Its
   recorded height means a hit that a fresh lookup could not finish within
   the depth limit is not used.

   Every lazily filled cache follows one rule (`lazyHit`, `lazyCompute` and
   `lazyFresh`; path calls carry their trace on the answer). A hit and a
   fresh computation give the caller the same answer, scope reads and
   height. They differ in two ways. A fresh computation adds the cuts it
   meets to the cut counter and a hit adds none; for a cycle-free key that
   is zero either way. And a fresh computation can run the conditional
   clears of the incomplete-lookup memo, which a hit does not (unproved
   step U2). The global state such a computation can read is:

   | State | Why it cannot make the answer depend on the caller |
   | --- | --- |
   | The lookup stack `seen` and the caller's lookup `activeLookup` | Set aside: each lookup the computation starts begins with an empty stack and no parent, so it neither absorbs into nor invalidates the caller's trace. Only a re-entry, whose answer does depend on the caller, invalidates it (round 4) |
   | Lookup mode (scope mode, macro-identity probe, library lookup settings) | In every lazy cache key (`lookupMode()`, a length-prefixed concatenation since round 4) |
   | `helperBusy` (helpers being decided) | A re-entry counts as a cut, and nothing computed under one is stored |
   | `importExpansions` (imports being expanded) and `activeMacroImports` (macro imports being resolved) | Set aside when the computation starts and restored when it ends, so it starts from nothing and meets its cuts within itself |
   | Lazy computations under way (`lazyBusy`) | Reaching a key already being computed is a re-entry. Like a helper re-entry, it counts as a cut, answers with the caller's state, and neither it nor the computation it re-entered is stored |
   | Scope-read bits (`scopeChanges`, and `scopeReads` in the audit) | Captured while computing, stored with the answer and replayed on a hit, as a lookup memo hit replays its own. The proven/assumed retry decision is then the same for a hit and a fresh computation |
   | Depth reached (`deepestLookup`) | The computation's lookups start from an empty stack, so the depth they reach does not depend on the caller. It is stored with the answer (`lazyHeights`, `pathCallHeights`) and added on a hit, as a fresh computation adds it (round 4) |
   | `capturedMacroExports`, `capturedHelperExports` | Built at the end of setup in both passes, from facts fixed by the end of setup. While the helper map is being built, helper questions answer `true`, and no lazy answer computed meanwhile is stored |
   | Incomplete-lookup memo and `lookupRevision` | See unproved step U2 |
   | `scopeEffectsReady`, `preparingScopes` | Set by `prepareIsolatedScopeEffects` before the first decision, after setup's presence loop; identical in both passes (below) |
   | The other caches | By induction, below |
   | Opaque scopes, lookup-facts-final, the module tree, places, bindings | Fixed by setup before any decision |

   The note used to say the caches are cleared whenever setup changes these.
   That is not quite so: `prepareIsolatedScopeEffects` sets
   `scopeEffectsReady` after the presence loop has run, without clearing the
   caches it filled. This is harmless because it happens at the same point,
   with the same caches, in both passes: before it, every scope read with an
   opaque origin marks the read as needing both retries (`scopeChanges |= 3`),
   in both; after it, the same reads are classified.

   `helperShadowed` no longer clears the incomplete-lookup memo when it
   computes an answer (round 4). That clear ran on a fresh computation and
   not on a hit. It was not needed to keep an answer met under a re-entry
   out of the memo: an incomplete entry met under a
   re-entry has an invalid trace (`LookupTrace.fits()` requires a valid
   one) and is never stored, and the entries computed under `helperBusy`
   are keyed by it. So it now runs on neither. Removing it does change
   which stored incomplete answers a later lookup replays; that those
   replays equal fresh lookups is unproved step U2.

   `importHeads` is resolved inside an import chain, so it is cached only
   when no cut occurred. Retry answers are not evicted. `unprovedImports` is
   stored only when its proof was cycle-free.
2. **Every limit that depends on the caller is gone or counted.** Trait
   risk and receiver typing had limits that depended on their caller. Both
   now depend only on the facts. Helper and lazy re-entries count as cuts and
   invalidate the enclosing lookup trace.
3. **A scoped pass is used only if no cut occurs while deciding the edited
   file's links.** The check runs with the file's new facts and with its
   old ones, in both passes. For an edit that keeps every fact up to offset
   ranks, before and after analysis, the old check is the new one.

**Why these rules give cold's answer.** Call a cached key cycle-free if
computing it from the post-setup caches meets no cut. Take a cycle-free key
and any answer its computation hits in some history.

That answer was stored by a computation of another key that met no
re-entry and started with an empty lookup stack, no caller lookup, no import
expansion and no macro import. It was therefore computed from the
post-setup caches and other stored answers alone, with the same mode. Its
scope reads and height travel with it. Either it is a setup answer, which is
the same in both passes, or it is the answer of another reachable key. That
key is cycle-free too; otherwise its cycle is reachable from the first key,
whose own fresh computation would meet it.

By induction, a cycle-free key has the same answer, the same scope reads,
the same height, and meets no cut, in every history. A non-cycle-free key
meets a cut whenever it is computed fresh. The scoped pass computes every
key it uses fresh unless setup supplied it.

So with no cut in the scoped pass, every answer the edited file's decisions
use is cold's, with cold's scope reads, and so are the decisions and the
retries.

**Why other files keep their stored decisions.** Adding or removing the
edited file's lookups adds or removes stored answers to cycle-free
keys. A cycle-free answer is the same whether it is computed or hit, and it
lies on no cycle another lookup could cut. The lookup memo's and lazy
caches' recorded heights keep their hits from changing whether another
lookup reaches the depth limit. One further effect is not covered by this
argument: the edited file's own lookups can run the conditional clears of
the incomplete-lookup memo without meeting any cut (a new call written
inside an existing workspace macro's arguments reaches `macroLookup`, which
clears it when a complete macro path includes a symbol that is not
visible), and that changes which incomplete answers later files replay.
That those replays equal fresh lookups is unproved step U2.

**Termination.** Every lookup adds its guard to
`seen`; a guard already there is cut, and a stack deeper than 128 is cut,
so a chain of nested lookups is finite. A lazy computation is in `lazyBusy`
(a helper also in `helperBusy`) while it runs. Reaching a busy helper again
returns `true` without computing. Reaching any other busy lazy key again
does compute it again, under the caller's state, nested inside its
own earlier computation, and that can happen more than once for one key
(an item whose presence has two helper origins can be reached again
through the second while the first is busy). The nesting is still
bounded. From inside a lookup the only lazy computations
that can be reached are item presence and attribute or helper shadowing.
Presence calls itself only for a module's file symbol, which cannot call
it again, and attribute shadowing does no lookups; only a `helperShadowed`
call that actually computes does (a busy helper or a cached answer does
none). So each path from a presence key back to itself passes through a
`helperShadowed` computation of a helper that was not yet busy, and that
helper stays busy until the path returns. Every nested re-run of a key
therefore happens under a strictly larger set of busy helpers, and the
nesting is bounded by the number of helper origins; `helperBusy` is keyed
by the origin alone, so different lookup modes do not loosen the bound.
Typing, path calls, trait risk and `implementedOutside`
are called only from decisions and from each other, along a chain with no
cycle, and typing calls itself only on a strictly shorter part of the
recipe. The lazy keys are drawn from a finite set (the snapshot's origins,
items and sites, times finitely many modes), each computation with its own
bounded lookup stack. The captured-exports fixpoint and the trait-risk closure only
add names or scopes to finite sets, with a visited set, and stop when
nothing changes. Receiver typing is bounded by the recipe's own chain
length. Every computation therefore ends, in any order of decisions.

### Unproved steps

- **U1. `unprovedImports` hits record no height.** Unlike a lookup memo or
  lazy hit, a hit there does not add the height of the proof that stored
  it. Two histories that differ only in such a hit could disagree only for a
  lookup that reaches the 128-deep limit. On the ten pins, no stored Rust
  link carries the depth limit's reason.
- **U2. Conditional clears of the incomplete-lookup memo.** Three clears run
  inside lookups when an observation changes (a complete answer preempting
  an observed incomplete one, a macro path whose visible symbols differ, an
  import proof that was observed before it was proved). Inside a fresh lazy
  computation they can run; on a hit they do not. They can also run in the
  edited file's own lookups, with no cut: an edit that adds or removes
  such a lookup changes what later files find in the memo in a cold index
  of the edited tree, which the kept decisions are compared against. They empty the
  incomplete-lookup memo and bump `lookupRevision`, which changes only which
  incomplete answers are later replayed and whether a lookup under way may
  store its own. C-24 replays an incomplete answer only under the same
  ancestor tests and depth, which should make a replay equal to a fresh
  lookup; that equality is not proved here.
- **U3. The decision order of the later phases.** The fuzzer permutes the
  order of the first decision loop. The retry and macro-assessment phases
  after it run in link order in every test; their order is not varied.

### Fuzzing

`scripts/reindex/fuzz-order.mjs` is a seeded, deterministic differential
fuzzer, bounded by an edit count. It generates small workspaces from these
shapes:

- glob cycles;
- mutual `pub use`;
- globs shadowed by a textual macro;
- `#[macro_use] extern crate`;
- serde derive helpers through aliases;
- cfg siblings, including C-24's cfg-alternative files globbed back by
  their parent;
- the review's method call through a three-module glob chain, with zero to
  seven other callers.

For each workspace, it compares cold indexes made with the first decision
loop in forward, reversed and shuffled order. Then it applies seeded edits:
comments, whitespace, body calls, and surface edits such as uses, globs,
functions, macros and cfg variants. After each edit it compares the
incremental re-index with a cold index of the tree, decided in a different
order, row for row. The order hook (`rustDecisionOrder`) is unset in
production.

### Cache audit

| Cache or limit | Depends on the caller? | Now |
| --- | --- | --- |
| Lookup memo `memo` | Only through ancestor cuts or depth | Stores no result with a cut at an ancestor (C-24). A hit is ignored when its recorded height would pass the depth limit. |
| Retry memo `retryMemo` | Through eviction at 8,192 entries | Same rule as `memo`. No eviction. |
| Incomplete lookups (`LookupMemo`) | Replayed only under the same ancestor tests and depth (C-24) | Unchanged. A replay of an answer that had a cut counts a cut. |
| `unprovedImports` | Stored only when the proof was cycle-free | Unchanged. Hits record no height (U1). |
| `importHeads` | Resolved inside an import chain; was stored even when it met a cut | Stored only when cut-free |
| `helperShadowed` with `helperBusy` | A re-entry returned `true`, and the answer was cached | A re-entry counts a cut and invalidates the lookup trace. An answer computed under a re-entry is not cached. The computation starts with no import expansion or macro import. A hit replays the stored scope reads and height. No longer clears the incomplete-lookup memo (round 4). Keyed by the lookup mode. |
| `attributeShadowCache`, `itemPresenceCache` | Through helper re-entries, the caller's expansions, scope reads and the lookup mode | The lazy-cache rule: starts from no expansion; not cached under a re-entry; scope reads replayed; keyed by the lookup mode. Setup asks every symbol's presence in both passes. |
| `riskCache` (`traitRisk`) | Stopped at three nested globs, and wrote a provisional answer for a scope being walked | Union over the whole glob closure with a visited set. The lazy-cache rule. |
| `typingCache` (`typing`) | Stopped at a call depth of 32 | The limit is the recipe's own chain length. The lazy-cache rule. |
| `pathCallCache`, `outsideCache` | Through helper re-entries, the caller's expansions, scope reads and the lookup mode | The lazy-cache rule (path calls carry their trace on the answer). |
| `expandType` alias chain (32), macro proofs (16), macro-body calls (8), `summarize` (16) | No: each starts with an empty `seen` at its root and caches nothing | Unchanged |
| `ownerCache`, `reachableCache`, `failureCache`, `unknownCache`, implication and possibility caches | No: pure functions of the module tree, crate graph or conditions | Unchanged |

The first review fix cached lazy answers only when no cut at all occurred
inside. That kept a cut met inside the computation, which does not depend
on the caller, from being cached, and it cost the cold index of dioxus
about 60% more CPU. The measurements below compare the current rule with
main.

The full-pass cold index is affected as well. On main, one file's answer
could depend on which other file first computed a shared module's trait
risk. In the review's case, a call `r.area()` through a three-module glob
chain resolved to `Rect::area` with no other caller and stayed unresolved
with six. It now resolves to `impl Rect::area` either way. That is rustc's
answer: an owned `Rect` with no trait in scope calls its inherent method.
`cargo check` accepts the case. The ten-pin comparison below shows what
the change did to the corpus.

## When it uses the full Rust pass

- The indexer gives no previous records. This covers a Rust file that was
  added, deleted or renamed, or whose module ownership changed. It also
  covers a previous run that is unfinished or did not record completed Rust
  analysis, a direct graph write, and a Rust module version change. The
  first index after this change rebuilds Rust once to record it.
- A Cargo manifest, lockfile or `.cargo/config` changed.
- An edited file was not clean before or after the edit. Making a file
  unparseable and repairing it both use the full pass.
- An edited file's surface changed, before or after analysis.
- A cut occurred while an edited file's links were decided. A cut is a
  lookup cycle cut, a depth cut, a helper re-entry or a lazy re-entry. The check uses the
  file's new facts and, unless the edit is isomorphic, its old ones, in
  either pass.

A changed surface re-decides the whole Rust module, not only the crate and
its dependents. That is the conservative end of the scope the task allowed.

## Proof

`test/graph-reindex-equality.test.mjs` adds 19 Rust shapes. Each one compares
every store row with a cold index after the edit and after its revert. Each
cross-file shape must also leave stale rows under a test-only module that
re-decides only the edited files. The test-only fixture is one crate whose
modules read each other:

- add, remove and rename a `pub fn`;
- rename a private crate-root function a sibling module calls;
- rename an impl method and a trait method with implementors;
- rename an enum variant matched elsewhere;
- rename a struct field read through a receiver;
- change a return type used in a method chain;
- remove a `use` a child module imports;
- remove a `pub use` re-export;
- add a glob import that shadows the prelude's `drop`;
- move a `#[macro_use]` module after its user;
- change a `macro_rules!` body;
- add an attribute macro and a `cfg`;
- remove a `mod` line;
- make a file unparseable, then repair it.

A separate two-crate workspace renames the function the dependent crate
calls, and its narrowed run also differs. The fixture's first two-crate
version had no resolvable cross-crate links, which is described below.

The scoped cases assert the work counters. A leading comment and a no-link
statement re-decide one file through the isomorphic check. A body edit that

and a manifest change use the full pass. A body edit falls back on a lookup
cut in a module that publicly globs its parent while the parent publicly
globs it back. Since C-24, a private glob back no longer closes that cycle.

- the cold answer for `widget.rs` with no other caller and with six.

The kill test has scoped Rust cases for a leading and a trailing comment.

### Changes to existing tests

The Rust module now declares incremental analysis. As for Go since C-27,
the indexer writes an edited Rust file after its analysis instead of
before. In `test/graph-rust-finishing.test.mjs`, the analyze-phase signal
cases stop an edited index while its Rust analysis worker is busy. That
run has written nothing, so the store is still the previous complete graph.

Previously, the stopped run left its unfinished mark, and `graph file
--no-sync` returned `incomplete` with exit code 2. It now returns `ok` with
exit code 0, `sync.complete: false` and the `index-incomplete` warning. That
is what main returns for an edit that has not been indexed yet, which a
probe checked on both builds. The resolve-phase cases still expect
`incomplete` and exit code 2. Every other assertion is unchanged, including
exit code 130, the incomplete status, the retry and the clean comparison.

The busy-worker fixture matched the worker's phase name exactly. An edited
index now starts its analysis worker as `analyzeScoped`, so the fixture
matches the phase as a prefix.

The equality helper now gives each step's check the work counters of its
incremental index. The existing checks ignore the extra argument. The kill
test's child process now also prints how many Rust files the unkilled run
re-decided alone. The existing pattern that reads its write count is
unchanged.

## Remaining cost per edit

On the scoped path, the Rust module runs its setup three times. Setup builds
the module tree, name tables, impl indexes and macro scopes from all stored
facts. The analysis pass and the dry resolution pass run inside analysis, and
the real resolution pass runs again. A non-isomorphic edit adds the two
old-fact passes.

For the ripgrep body edit, analysis took 3.4 CPU s and resolution 2.4 s of
11.4 s. The rest went to startup, inventory, parsing and SQLite. For helix,
analysis took 6.6 s and resolution 5.3 s of 15.5 s. Deciding one file's
links costs little next to setup, so setup dominates after scoping. Keeping
the global tables between the phases or between runs would need a durable
key over every surface. The dry run and the resolve phase repeat the same
work, and sharing it between phases would break C-2's rule that module
input does not outlive its phase.

## Found, not built

- **Setup on large workspaces.** A scoped dioxus edit still costs 250 to
  290 CPU s. Each of its three passes rebuilds the module tree, name tables
  and macro scopes over 884 files. Keeping that setup between the passes
  would need an identity for the whole fact set.
- **Crate scope.** A changed surface could re-decide the edited crate and
  its dependent workspace crates instead of the whole module. Proving that
  needs the macro-export, glob and `#[macro_use] extern crate` reach across
  crates.
- **Body macro sites.** Macro invocations in function bodies, such as
  `println!` and `vec!`, are `macros` links and so part of the surface.
  Showing that only their own file reads them would let more body edits
  qualify.
- **Opaque workspace fixture.** In the first version of the test fixture, a
  binary crate depended on a crate whose root has `#[macro_use] mod macros;`.
  Every cross-crate `use` in the binary stayed unresolved with "namespace,
  import or alias structure is unknown". The minimal workspace in the
  dependent-crate test resolves. This looks like a coverage gap.
- **Fixed cost.** SQLite close took 0.95 CPU s in the ripgrep body edit,
  parser start 0.95 s and module import 0.5 s.

grammars and the Go standard-library table beside it.


The second batch's seeds are 36311 and 36312 for ripgrep, with 30 edits
each, and 36313 and 36314 for helix, with 10 each. The first batch used
36301 to 36304 with the scoped mix as committed at `1343984`. The scoped mix
weights body statements, new calls and comments and keeps one of each other
Rust edit: signature renames, imports,

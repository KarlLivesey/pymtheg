# C-36: Rust re-index proportional to the edit

A Rust edit that leaves every fact other files read unchanged now re-decides
only the edited file's links. Comment, whitespace and many body edits qualify.
Before this change both Rust passes, analysis and resolution, decided every
link of the project after any edit. Every other edit still uses the full Rust
pass. The change reuses the C-27 scoped analysis contract unchanged and adds
no setting, dependency or stored field. The Rust module version stays 45.

## What another file reads

The Rust resolver receives every file's facts and decides links in one
pass. Links are read across files only through indexes built from
`ctx.links` in `resolve.ts`, and no other Rust file reads link lists. There
are twelve such reads. Nine select `imports`, `contains` or `macros` links:

- the function-region and macro-use maps;
- the extern crate list;
- the import tables by scope;
- the contains index;
- the macro sites;
- the visible prefixes;
- the trait imports in scope;
- the edition 2015 extern check;
- the attribute sites.

The other three touch only the links being decided: the cfg annotation, the
main decision loop and the macro-body calls.

`calls`, `values`, `types`, `patterns` and `implements` links are only
decided, so no other file can observe them. Everything else another file reads
comes from symbols and file data. The trait/impl relation, method names,
receiver forms, field types, signatures, aliases, variants and constants are
symbol facts. Inherited conditions, attribute contexts and macro scopes are
file data.

A file's **surface** is therefore its parse status and diagnostics, its file
data, every symbol with its data, and every `imports`, `contains`, `macros` and
`modules` link with its data. A link kind the list does not name counts as
surface. This covers each fact on the task's list:

| Fact | Where it is in the surface |
| --- | --- |
| Items, namespaces, visibility, enum variants, constants, traits and their items, impl heads, method names and receivers, written field and signature types, type aliases | Symbols and their data |
| `use` trees, re-exports, globs, `extern crate` and its macro-use requests | `imports` links and their data |
| `mod` declarations, `#[path]`, `#[macro_use]` on modules | `modules` links, module symbols and their data |
| `macro_rules!` definitions, bodies, `#[macro_export]` and textual order | Macro symbols, macro profiles and their ranked positions |
| Attributes and derives on items | `macros` links of attribute and derive flavour, and the file's opaque attribute list |
| `cfg` conditions | The file's attribute contexts and each fact's conditions |
| Crate-root attributes such as `no_std`, edition and crate kind | Root file data and the file symbol's unit data, set from Cargo |
| Cargo manifests, lockfiles and configuration | Not in the surface: any change uses the full pass |

Source offsets are replaced by their rank among the file's surface offsets.
Ranks preserve their order and equality. The resolver orders and matches a
file's positions and never measures them or compares them with another
file's. The ranked fields are ranges, `item:` keys, `libraryAttributeStart`,
and the starts of opaque attributes and standard macro scopes. Any other
number is hashed as written, so an offset the list misses can only cause a
fallback.

Each surface link also keeps its index in the file's link list. A link's
store id hashes that index, and the resolution pass meets links in id order.
Inserting a `calls` link before a surface link would renumber it, so the
index stays in the surface. The parser appends attribute and derive `macros`
links after all other links. In a file with `#[derive]`, an edit that adds
or removes any link changes the surface. On these pins, an edit that adds a
call usually uses the full pass.

## Why the edited file's decisions equal a cold index's

The resolver keeps lookup memos across links. C-24 (pull request 33) showed
that answers met in glob cycles can depend on which lookup ran first. A cold
index decides the edited file's links after other files' lookups have
filled those memos. A scoped pass decides them after setup alone. Setup reads
only surface facts and is identical in both. A memo entry can differ between
the two histories only if its computation met a cycle against a lookup still
on the stack, which is a cut.

If no cut occurs while the edited file's links are decided from the post-setup
state, every lookup they reach is acyclic. Such a lookup has the same answer
in any history, so the scoped decisions equal the cold ones. The resolver now
counts cuts, including those in its isolated scope probes, and reports the
count met while deciding. A scoped pass that meets any cut falls back. The
cold indexes met 53 to 15,302 cuts per pass on the four pins, so the
whole-project version of this test would never pass. Among sampled single
files, 18 of 18 on ripgrep, 7 of 8 on redb and 5 of 8 on helix had none.
[Probe](../../evidence/c-36/probe.json)

Other files keep their stored decisions. Their cold decisions could still
change if removing or adding the edited file's lookups changed the memos they
meet. The check therefore runs with the file's new facts and with its old
ones. Both sets of lookups are then acyclic and context free, so neither
their presence nor their absence changes another answer. When all of the
file's facts, before and after analysis, are the same up to offset ranks,
the old lookups are the new ones. One check then covers both. Such edits
include comments, whitespace and statements without links.

The check runs in both passes. The analysis pass decides the edited file
with its new and old facts. The resolution pass runs dry inside analysis,
with the exact input the resolve phase will read, in the store's id order.
After analysis, the edited file's annotated surface must also equal its
stored one, because other files' resolution reads those annotations. The
resolve phase then rebuilds every link from the stored records, decides the
edited files and stops with an error if it meets a cut. That error cannot
happen after the dry run, and if it did, the unfinished mark would force a
full repair.

## When it uses the full Rust pass

- The indexer gives no previous records. This covers a Rust file that was
  added, deleted or renamed, or whose module ownership changed. It also
  covers a previous run that is unfinished or did not record completed Rust
  analysis, a direct graph write, and a Rust module version change. The
  first index after this change rebuilds Rust once to record it.
- A Cargo manifest, lockfile or `.cargo/config` changed.
- An edited file was not clean before or after the edit. Making a file
  unparseable and repairing it both use the full pass.
- An edited file's surface changed, before or after analysis.
- A lookup cut occurred while an edited file's links were decided, with its
  new facts or, unless the edit is isomorphic, its old ones, in either pass.

A changed surface re-decides the whole Rust module, not only the crate and
its dependents. That is the conservative end of the scope the task allowed.

## Proof

`test/graph-reindex-equality.test.mjs` adds 19 Rust shapes. Each one compares
every store row with a cold index after the edit and after its revert. Each
cross-file shape must also leave stale rows under a test-only module that
re-decides only the edited files. The test-only fixture is one crate whose
modules read each other:

- add, remove and rename a `pub fn`;
- rename a private crate-root function a sibling module calls;
- rename an impl method and a trait method with implementors;
- rename an enum variant matched elsewhere;
- rename a struct field read through a receiver;
- change a return type used in a method chain;
- remove a `use` a child module imports;
- remove a `pub use` re-export;
- add a glob import that shadows the prelude's `drop`;
- move a `#[macro_use]` module after its user;
- change a `macro_rules!` body;
- add an attribute macro and a `cfg`;
- remove a `mod` line;
- make a file unparseable, then repair it.

A separate two-crate workspace renames the function the dependent crate
calls, and its narrowed run also differs. The fixture's first two-crate
version had no resolvable cross-crate links, which is described below.

The scoped cases assert the work counters. A leading comment and a no-link
statement re-decide one file through the isomorphic check. A body edit that
adds calls in a file without later surface links re-decides one file with
both checks. A new export, a new file and a manifest change use the full
pass. Body edits in a module that globs its parent, with the parent globbing
it back, fall back on a lookup cut. The kill test adds a scoped Rust case,
and one index after a kill at every commit boundary equals cold.

### Changes to existing tests

The Rust module now declares incremental analysis. As for Go since C-27,
the indexer writes an edited Rust file after its analysis instead of
before. In `test/graph-rust-finishing.test.mjs`, the analyze-phase signal
cases stop an edited index while its Rust analysis worker is busy. That
run has written nothing, so the store is still the previous complete graph.

Previously, the stopped run left its unfinished mark, and `graph file
--no-sync` returned `incomplete` with exit code 2. It now returns `ok` with
exit code 0, `sync.complete: false` and the `index-incomplete` warning. That
is what main returns for an edit that has not been indexed yet, which a
probe checked on both builds. The resolve-phase cases still expect
`incomplete` and exit code 2. Every other assertion is unchanged, including
exit code 130, the incomplete status, the retry and the clean comparison.

The busy-worker fixture matched the worker's phase name exactly. An edited
index now starts its analysis worker as `analyzeScoped`, so the fixture
matches the phase as a prefix.

The equality helper now gives each step's check the work counters of its
incremental index. The existing checks ignore the extra argument.

## Remaining cost per edit

On the scoped path, the Rust module runs its setup three times. Setup builds
the module tree, name tables, impl indexes and macro scopes from all stored
facts. The analysis pass and the dry resolution pass run inside analysis, and
the real resolution pass runs again. A non-isomorphic edit adds the two
old-fact passes.

For the ripgrep body edit, analysis took 3.1 CPU s and resolution 2.8 s of
9.0 s. The rest went to startup, inventory, parsing and SQLite. For helix,
analysis took 7.1 s and resolution 5.5 s of 16.2 s. Deciding one file's
links costs little next to setup, so setup dominates after scoping. Keeping
the global tables between the phases or between runs would need a durable
key over every surface. The dry run and the resolve phase repeat the same
work, and sharing it between phases would break C-2's rule that module
input does not outlive its phase.

## Found, not built

- **Link order after C-24.** C-24 makes the Rust phases take links in an
  order fixed by file, position and kind instead of id. Once it merges, the
  link index can leave the surface. Most body edits that add or remove calls
  or macro invocations would then re-decide one file, subject to the cut
  check.
- **Crate scope.** A changed surface could re-decide the edited crate and
  its dependent workspace crates instead of the whole module. Proving that
  needs the macro-export, glob and `#[macro_use] extern crate` reach across
  crates.
- **Body macro sites.** Macro invocations in function bodies, such as
  `println!` and `vec!`, are `macros` links and so part of the surface.
  Showing that only their own file reads them would let more body edits
  qualify.
- **Opaque workspace fixture.** In the first version of the test fixture, a
  binary crate depended on a crate whose root has `#[macro_use] mod macros;`.
  Every cross-crate `use` in the binary stayed unresolved with "namespace,
  import or alias structure is unknown". The minimal workspace in the
  dependent-crate test resolves. This looks like a coverage gap.
- **Fixed cost.** SQLite close took 0.95 CPU s in the ripgrep body edit,
  parser start 0.95 s and module import 0.5 s.

## Reproduce

Run on the dev server from the mirrored tree. Each build's `dist/` needs its
grammars and the Go standard-library table beside it.

```sh
node scripts/reindex/fetch.mjs "$PYM_SCRATCH" BurntSushi/ripgrep helix-editor/helix cberner/redb fjall-rs/fjall
node scripts/reindex/measure.mjs <dist> "$PYM_SCRATCH" <pin> "$PYM_SCRATCH/out/<label>"
node scripts/reindex/random-edits.mjs <dist> "$PYM_SCRATCH" BurntSushi/ripgrep 36201 30 out.json --store-dir /dev/shm/c36 --cache-pages 131072 --command
node scripts/reindex/cold-cost.mjs <store dir> out.json 1 main-1=<main dist> after=<dist> main-2=<main dist> --exact -- "$PYM_SCRATCH/pins/<pin>"
```

The seeds are 36201 and 36202 for ripgrep, with 30 edits each, and 36203
and 36204 for helix, with 10 each. The Rust edit mix weights signatures,
imports, `macro_rules!`, `mod` lines with new files, file deletion, `cfg`,
`#[derive]`, comments, bodies and new exports.

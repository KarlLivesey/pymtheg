# C-42 TypeScript environment globals declared by several typings

C-42 handles SW-6's largest candidate-set group: globals such as `URL`,
`Request`, `console.log` and `setTimeout`, which several environment
typings declare at once (the DOM library and `@types/node`, and also
`bun-types` and `@cloudflare/workers-types`). The graph stored them as
candidate sets, because the declarations live in different library units.

The TypeScript module version moves from 49 to 51. The number is
provisional; the manager assigns the final one at merge. Old stores re-index.

## 2. Merged environment globals

The module marks a candidate set `mergedGlobal` only when all of these hold:

- every declaration that gave a library candidate resolves, through
  `checker.getSymbolAtLocation` on its name, to one and the same compiler
  symbol. That is the compiler's own merge: one `ts.Symbol` with several
  declarations. Nothing decides which typing "wins";
- every such declaration is in the global scope: in a script file such as
  `lib.dom.d.ts`, or inside `declare global` / `global {}`. A declaration
  inside an ambient `declare module "x"` or a module file is not;
- the candidates come from at least two library units;
- there is no checkout candidate, and no target synthesised by the
  bare-checkout Node fallback;
- no unit is a test framework or a competing test package (narrowed D23;
  `isTestPackage`: jest, mocha, vitest and their scoped parts, chai,
  jasmine, qunit and the like). Their globals are alternatives: a file runs
  under one of them;
- no two of the units are in conflict on a shared global (narrowed D23;
  reviews N1, N1b, round 2). Conflict is what the compiler itself reports
  between declarations of one global name in two units:
  - TS2403, subsequent variable declarations must have the same type;
  - TS2717, subsequent property declarations must have the same type;
  - TS2300, duplicate identifier;
  - TS2451, cannot redeclare a block-scoped variable;
  - TS2428, all declarations must have identical type parameters;
  - TS2687, all declarations must have identical modifiers.

  TS2403 and TS2717 compare the declared types for identity
  (`isTypeIdenticalTo`), which is stricter than mutual assignability:
  `{ n: any }` and `{ n: number }` are each assignable to the other, but
  not identical.
  - **How the module asks the compiler.** The checker does not export its
    identity relation, and `skipLibCheck` suppresses these checks in
    declaration files. So a second checker of the same program, told that
    `skipLibCheck` is off (`ts.createTypeChecker` over the program, with
    only `getCompilerOptions` replaced), checks every declaration of each
    global name that two or more units declare, through
    `getDiagnostics(file, token, nodes)`. That covers variables, functions,
    classes, interfaces with their members, type aliases, enums and
    namespaces. It reads them in every global scope: script files,
    `declare global`, and `global {}` inside an ambient `declare module
    "x"`, which is how `@types/node` declares `URL`, `Buffer`, `console` and
    `process`.
  - **Which units a diagnostic pairs.** A conflict pairs exactly the two
    units whose declarations disagree: the unit of the declaration the
    diagnostic names, and the unit of the other declaration.
    - The other declaration is the diagnostic's related "was also declared
      here" location: the first declaration for TS2403 and TS2717, the
      other declaration for the duplicates TS2300 and TS2451.
    - TS2403 and TS2717 compare with the first declaration, so a
      declaration of the same symbol that the compiler does not report
      agrees with the first. The reported one then disagrees with it too:
      A and B agree and C differs gives A–C and B–C.
    - TS2428 and TS2687 carry no related location; the compiler reports
      them on the declarations themselves. There the other declarations are
      the ones its own comparison finds different: type parameter names,
      and constraints and defaults where both have one; `?` and the
      modifiers it compares (private, protected, async, abstract, readonly,
      static).
    - Only where none of these names another declaration is the unit
      paired with the units that declare the name and are not themselves
      reported for it.
    - Two units are never paired because both were reported against a
      third. With Workers' `Request` first, the DOM and Node both differ
      from it and agree with each other: Workers–DOM and Workers–Node are
      pairs, DOM–Node is not.
  - **A conflict inside one unit key makes no pair.** A link's target
    names the unit key, and both sides of such a conflict name the same
    key, so the stored target is the same named thing either way. Nor is
    the conflict attributed to another unit: a declaration that disagrees
    with one of its own key pairs with no unit, and with no other
    declaration known, a unit that declares the name twice is not paired.
    This is a limit of the unit key. Two cases on the pins:
    - Dexie installs four versions of `@types/node`. They disagree with
      each other (the compiler reports TS2300 between them), and all are
      the one key `@types/node`. Paired with another unit, this conflict
      unmarked 86 links there before the ruling; MEASURE-DEXIE after it.
    - vitest's `packages/web-worker` loads the DOM and WebWorker libraries
      together, both the unit `dom`; the compiler reports TS2403 between
      them. Paired with Node, it unmarked 28 links there before the ruling;
      MEASURE-VITEST after it.
  - **Units are typings packages.** A declaration's unit is the one its
    library candidate names, so conflicts and link unit sets use one key.
    Every `node:*` unit counts as the one package `@types/node`.
  - **Units, not symbols, are the alternatives.** Two units in conflict on
    any one shared global are alternatives. Every merged global whose units
    include that pair is left unmarked, whatever kind of symbol it is:
    `fetch`, `setTimeout`, `RequestInit`, `x.text()` and `reader.cancel`,
    not only `Request`.
  - **Cost.** The pairs are computed once per program, cached by program,
    the first time a merged global is met. Before round 2 they were
    computed again in every extracted file. The counted work is under
    [Cost](#cost).

The link stays a candidate set in the core. Its library candidate rows name
each declaring unit with its own symbol path (for example
`dom:dom:Console.prototype.log` and `node:console:Console.prototype.log`),
and the mark says that the rows are one symbol.

**Identity.** The rows are stored sorted and keyed by ecosystem, unit,
symbol, version and evidence, as every library target is. The identity is
therefore the same in every file, program and run, and after any re-index.
A file in several programs keeps the mark only when every program gives the
same set and no reason; otherwise the mark is dropped. Wherever the module
drops a link's library facts, it drops the mark with them.

**Unread files.** Main's rule is kept: in a program with an unread file,
library targets are withheld, so no merged global is marked there. This
does not depend on PR 49.

**The coverage rule (D23).** A link counts at Level 2 when:

- it is marked `mergedGlobal`;
- it has no checkout candidate;
- it has at least two library candidates from different units, each naming
  a symbol.

It then names the symbol and every declaring unit.

The alternative was to change the core, so that a definite `library` link
could carry several units. That would change the store, the queries and the
conformance kit for every language. It was not built.

**Member links.** A marked member link such as `console.log` is one
compiler symbol across the units. The mark requires that the name of every
declaration of the member resolves to the same symbol, which is the merged
interface member, with declarations in each listed unit. The 13,540 marked
links are:

| Kind | Links |
| --- | ---: |
| Calls (`fetch(…)`, `new URL(…)`, `console.log(…)`, `x.text()`) | 9,554 |
| References (`URL`, `Request` as types; member references) | 3,963 |
| `extends` | 16 |
| Imports | 7 |

The existing rule for a member merged from several declarations of one
receiver type (`selectedMergedDeclaration`) runs before the mark, and
applies to library declarations too. It narrows a member call to the
declaration whose signature the checker selects, as an ordinary definite
library link, when no declaration from another body could also accept the
arguments. A marked member call is one that rule did not narrow, for any of
its reasons:

- another unit's declaration also accepts the arguments (both units declare
  `log(...data: any[])`, so the checker's pick is declaration order);
- the receiver's apparent type is a union or an intersection, which the
  rule never narrows;
- the receiver's property for the name is not the member's symbol;
- the checker's selected signature is not one of the member's declarations
  (for example a signature of an instantiated or synthesised type).

In every case the mark itself still requires one compiler symbol, whose
declarations are in each listed unit.

Extending that narrowing to bare global calls was tried and not kept. A
bare global's runtime value is not decided by which declaration's
signature fits. Two existing tests show this:

- two test frameworks both declaring `expect` stay a candidate set
  (competing test globals);
- two `function twice()` declarations in a JavaScript script stay a
  candidate set, because the later one wins at run time.

## 3. Group (b)

No sound rule makes the rows of (b) definite, except perhaps the
augmentation row, which is the manager's to rule on:

- **Two units in conflict (570).** These are alternatives under the
  narrowed D23: the compiler itself says the two typings cannot both
  describe one global environment.
- **One symbol merged by a module augmentation (241).** A plugin's
  `declare module "fastify" { interface FastifyRequest {…} }` merges with
  fastify's own interface: one compiler symbol, in two units. By D23's
  reasoning it is one named target, but it is not a global, so the mark
  does not cover it. Extending the mark to it would add 241 links on these
  pins, 0.02 points. That is not built.
- **A synthesised Node target present (112).** The Node target is the
  module's own guess for a program without `@types/node`, so the set does
  not name the compiler's declarations.
- **Test packages (31).** Alternatives under the narrowed D23.
- **Not one compiler symbol, or no rule above (1,613).** A union receiver
  (`Window | Element`) really can be either at run time, so it stays a
  candidate set.

A link is computed in its own program. So the case where a program's `lib`
or `types` settings select exactly one typing never reaches (b): such a
program sees one declaration and stores a single library target. Where a
file belongs to several programs whose sets differ, the mark is dropped, as
above.

## Seeded edits

**The first run was unsound evidence.** `scripts/reindex/random-edits.mjs`
copied each pin with `cpSync`, which turns pnpm's relative `node_modules`
symlinks into absolute ones pointing outside the copied tree. On a pnpm pin
the copy's installed packages then do not resolve inside it. Library links
fall, marks vanish, and the run still reports "equal" over the emptier
sets. The tool now:

- copies with `verbatimSymlinks: true`;
- prints, for every step, how many links, library links and marked links
  the compared store holds (`held` in the results);
- with `--readable`, draws a TypeScript edit again, from the same seeded
  sequence, when its result would not parse. Then no file's failure
  withholds its program's library targets.

**The run.** Thirty seeded edits on pmndrs/zustand (a pnpm pin), seed 911,
with `--readable`
([results](../../evidence/c-42/seeded-edits-zustand-readable.json)):

- every incremental store is identical row for row to a cold index;
- no file failed;
- the compared stores hold 15 marked links and 3,311–3,315 library links at
  every step, as the pin does (3,313).

Without `--readable`, five seeds broke a file within seven steps, and the
marks fell to two or none.

The earlier oclif/core run ([results](../../evidence/c-42/seeded-edits-oclif.json))
used the old copy, and is superseded by this one.

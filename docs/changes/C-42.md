# C-42 TypeScript environment globals declared by several typings

C-42 handles SW-6's largest candidate-set group: globals such as `URL`,
`Request`, `console.log` and `setTimeout`, which several environment
typings declare at once (the DOM library and `@types/node`, and also
`bun-types` and `@cloudflare/workers-types`). The graph stored them as
candidate sets, because the declarations live in different library units.

The TypeScript module version moves from 50 (main, after C-60) to 51. The
number is provisional; the manager assigns the final one at merge. Old
stores re-index.

## 2. Merged environment globals

The module marks a candidate set `mergedGlobal` only when all of these hold:

- every declaration that gave a library candidate resolves, through
  `checker.getSymbolAtLocation` on its name, to one and the same compiler
  symbol. That is the compiler's own merge: one `ts.Symbol` with several
  declarations. Nothing decides which typing "wins";
- every such declaration is in the global scope: in a script file such as
  `lib.dom.d.ts`, or inside `declare global` / `global {}`. A declaration
  inside an ambient `declare module "x"` or a module file is not;
- the candidates come from at least two library units;
- there is no checkout candidate, and no target synthesised by the
  bare-checkout Node fallback;
- no unit is a test framework or a competing test package (narrowed D23;
  `isTestPackage`: jest, mocha, vitest and their scoped parts, chai,
  jasmine, qunit and the like). Their globals are alternatives: a file runs
  under one of them;
- no unit is in conflict (narrowed D23; reviews N1, N1b, rounds 2 and 3).
  **Deny by default (round 3):** any diagnostic, whatever its code, that the
  compiler reports in a unit's global declarations, or whose related
  information lies in that unit's declaration files, makes that unit
  conflict with every other unit.
  No code is listed and no spelling is compared.
  - **How the module asks the compiler.** `skipLibCheck` suppresses these
    checks in declaration files. So a second checker of the same program,
    told that `skipLibCheck` is off (`ts.createTypeChecker` over the
    program, with only `getCompilerOptions` replaced), checks every
    statement declaring a global name that two or more units declare,
    through `getDiagnostics(file, token, nodes)`. That covers variables,
    functions, classes, interfaces with their members, type aliases, enums
    and namespaces. It reads them in every global scope: script files,
    `declare global`, and `global {}` inside an ambient `declare module
    "x"`, which is how `@types/node` declares `URL`, `Buffer`, `console` and
    `process`.
  - **A diagnostic with related locations, all in one unit key, is
    dropped; one with no related location always counts against its
    unit.** "All" is the diagnostic's own location and each related one; a
    location in no unit (a checkout file) is not counted. A link's target names the unit key, and both
    sides of such a diagnostic name the same key, so the stored target is
    the same named thing either way: two installed versions of
    `@types/node` (Dexie), or `lib.dom` and `lib.webworker` (vitest's
    web-worker package), both the unit `dom`. A diagnostic with no related
    location is never dropped. That is the common case (tRPC's 164 TS2687 in `@types/node` and 150 TS2428
    in the TypeScript library, each with no related information;
    `evidence/c-42/conflict-diagnostics.json`). Any
    diagnostic that touches two units counts for both, including one
    between typings that one package splits over two files.
  - **Units are typings packages.** A declaration's unit is the one its
    library candidate names, so conflicts and link unit sets use one key.
    Every `node:*` unit counts as the one package `@types/node`.
  - **Units, not symbols, are the alternatives.** A unit in conflict is an
    alternative on every global it declares. Every merged global whose
    units include it is left unmarked, whatever kind of symbol it is:
    `fetch`, `setTimeout`, `RequestInit`, `x.text()` and `reader.cancel`,
    not only `Request`. A set whose units are all one unit key (only
    `node:*` units, such as `node:globals` + `node:process`) is never
    unmarked by a conflict: a unit conflicts only with other units.
  - **Rounds 1 and 2** used a list of six codes and paired the two units a
    diagnostic named. Each review found another code or another way to
    pair, so round 3 denies by default.
  - **Cost.** The check runs once per program, cached by program, the first
    time a merged global is met. The counted work is under [Cost](#cost).

The link stays a candidate set in the core. Its library candidate rows name
each declaring unit with its own symbol path (for example
`dom:dom:Console.prototype.log` and `node:console:Console.prototype.log`),
and the mark says that the rows are one symbol.

**Identity.** The rows are stored sorted and keyed by ecosystem, unit,
symbol, version and evidence, as every library target is. The identity is
therefore the same in every file, program and run, and after any re-index.
A file in several programs keeps the mark only when every program gives the
same set and no reason, and every program marks it; otherwise no mark is
stored anywhere in the link's data, its per-program entries included. Wherever the module
drops a link's library facts, it drops the mark with them.

**Unread files.** Main's rule is kept: in a program with an unread file,
library targets are withheld, so no merged global is marked there. This
does not depend on PR 49.

**The coverage rule (D23).** A link counts at Level 2 when:

- it is marked `mergedGlobal`;
- it has no checkout candidate;
- it has at least two library candidates from different units, each naming
  a symbol.

It then names the symbol and every declaring unit.

The alternative was to change the core, so that a definite `library` link
could carry several units. That would change the store, the queries and the
conformance kit for every language. It was not built.

**Member links.** A marked member link such as `console.log` is one
compiler symbol across the units. The mark requires that the name of every
declaration of the member resolves to the same symbol, which is the merged
interface member, with declarations in each listed unit. The 11,938 marked
links are:

| Kind | Links |
| --- | ---: |
| Calls (`fetch(…)`, `new URL(…)`, `console.log(…)`, `x.text()`) | 8,528 |
| References (`URL`, `Request` as types; member references) | 3,389 |
| `extends` | 16 |
| Imports | 5 |

The existing rule for a member merged from several declarations of one
receiver type (`selectedMergedDeclaration`) runs before the mark, and
applies to library declarations too. It narrows a member call to the
declaration whose signature the checker selects, as an ordinary definite
library link, when no declaration from another body could also accept the
arguments. A marked member call is one that rule did not narrow, for any of
its reasons:

- another unit's declaration also accepts the arguments (both units declare
  `log(...data: any[])`, so the checker's pick is declaration order);
- the receiver's apparent type is a union or an intersection, which the
  rule never narrows;
- the receiver's property for the name is not the member's symbol;
- the checker's selected signature is not one of the member's declarations
  (for example a signature of an instantiated or synthesised type).

In every case the mark itself still requires one compiler symbol, whose
declarations are in each listed unit.

Extending that narrowing to bare global calls was tried and not kept. A
bare global's runtime value is not decided by which declaration's
signature fits. Two existing tests show this:

- two test frameworks both declaring `expect` stay a candidate set
  (competing test globals);
- two `function twice()` declarations in a JavaScript script stay a
  candidate set, because the later one wins at run time.

## 3. Group (b)

No sound rule makes the rows of (b) definite, except perhaps the
augmentation row, which is the manager's to rule on:

- **A unit in conflict (2,172).** Alternatives under the narrowed D23: the
  compiler itself finds a fault in a unit's global declarations, alone or
  against another unit's.
- **A declaration outside the global scope (364).** A plugin's
  `declare module "fastify" { interface FastifyRequest {…} }` merges with
  fastify's own interface: one compiler symbol, in two units
  (`FastifyRequest` 67, d3's `Selection` 43, `Readable` 30, `FastifyReply`
  27). By D23's reasoning it is one named target, but it is not a global,
  so the mark does not cover it. Extending the mark to it would add 364
  links on these pins, 0.03 points. That is not built.
- **Distinct symbols (180).** The candidates are two or more compiler
  symbols (`toString` 68, `setTimeout` 44, `clearTimeout` 28). A union
  receiver (`Window | Element`) really can be either at run time, so it
  stays a candidate set.
- **A synthesised Node target present (112).** The Node target is the
  module's own guess for a program without `@types/node`, so the set does
  not name the compiler's declarations.
- **Test packages (5).** Alternatives under the narrowed D23.
- **Fewer than two library units on this branch (1,336).** Not a set the
  rule applies to.

A link is computed in its own program. So the case where a program's `lib`
or `types` settings select exactly one typing never reaches (b): such a
program sees one declaration and stores a single library target. Where a
file belongs to several programs whose sets differ, the mark is dropped, as
above.

## Seeded edits

**The first run was unsound evidence.** `scripts/reindex/random-edits.mjs`
copied each pin with `cpSync`, which turns pnpm's relative `node_modules`
symlinks into absolute ones pointing outside the copied tree. On a pnpm pin
the copy's installed packages then do not resolve inside it. Library links
fall, marks vanish, and the run still reports "equal" over the emptier
sets. The tool now:

- copies with `verbatimSymlinks: true`;

## Stated limits (further work, not built)

- **A conflict on a statement whose name only one unit declares is never
  checked.** The second checker checks only statements declaring a global
  name that two or more units declare. A diagnostic between units reported
  on another statement (for example TS2430 or TS2420, an interface that
  incorrectly extends or implements another unit's) is therefore not seen,
  and review fixtures of that shape left their marks in place. It was not
  seen in 41 combinations of published typings, nor on four of the pins.
- **A checkout global that conflicts with a typings package does not count
  against that package.** Units are typings packages; a conflict between a
  checkout declaration and a package's does not make the package a unit in
  conflict. (A set with a checkout candidate is never marked.)

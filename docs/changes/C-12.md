# C-12 Rust names that a macro in scope cannot define

The Rust code graph can resolve a written name beside an opaque macro
expansion when the expansion cannot introduce that name. The same check
applies to checkout targets, library paths and edition prelude names. It uses
existing link sites and preserves the ordinary checkout and library lookup
order. Calls on a receiver continue to use their existing declaring-owner
checks.

## Proven name bounds

For a captured `macro_rules!` definition, the parser records literal item
names across all arms. A metavariable in a name position can contribute an
identifier from the invocation. When an arm invokes a second captured macro,
the resolver checks that definition too and includes names passed through
the outer macro. A literal `let` identifier is hygienic. A `let` name taken
from the invocation still matters. An emitted glob, arbitrary item or token
fragment, generated macro definition, or macro with an unproven identity can
keep the scope opaque. A cyclic or unreadable expansion also stays opaque.
The check also leaves foreign declaration blocks and repetitions that can
change an item header opaque.

An `ident` fragment can also supply an item keyword. In the compiler control,
`item_with_keyword!(struct)` emits `struct Option`. The old macro-neutrality
rule credited the standard `Option` at the following use. The graph now keeps
that use unresolved because the expansion can introduce a nearer type.

The standard expression macros and token-consuming builtins have documented
outputs. The checks cover `print!` and its variants, `format!`, `format_args!`,
`write!`, `writeln!`, `vec!`, assertions and debug assertions, `matches!`,
`dbg!`, `panic!`, `todo!`, `unreachable!`, and `unimplemented!`. They also
cover `cfg!`, `line!`, `column!`, `file!`, `module_path!`, `concat!`,
`stringify!`, `env!`, `option_env!`, `include_str!`, `include_bytes!`, and
`compile_error!`. `thread_local!` can introduce statics named in its
input. A recognised invocation only clears names outside its input.
`include!` can insert Rust items into its caller's scope and stays opaque.
Nested calls retain leading `::` and `$crate::`. An unreadable or
unidentified nested invocation keeps its wrapper opaque.
[Standard library macros](https://doc.rust-lang.org/std/index.html#macros)

Built-in attributes such as `#[cfg]`, `#[allow]`, `#[inline]`, and `#[test]`
use the existing attribute rules. Proven built-in derives such as `Debug`,
`Clone`, `Copy`, `PartialEq`, `Eq`, `PartialOrd`, `Ord`, `Hash`, and `Default`
generate implementations. The surrounding scope still has to clear any
external derive on the same item.
[Derive attribute](https://doc.rust-lang.org/reference/attributes/derive.html)

## External macro assumption

The stored `rust-external-macro-name` assumption requires an external
function-like macro to receive an identifier that could name an item.
Literal-only and file-path inputs can load names from elsewhere, as with
`tonic::include_proto!` or `sqlx::migrate!()`. Eligible expansions are
assumed to introduce only names present in their input. Derives and
attributes can also introduce names made from whole case-insensitive
components of an input item name. For example, `Config` blocks
`ConfigBuilder`, `config_builder`, and `CONFIG_X`. It leaves `Option`
eligible. Field and variant names count only on exact equality.
Procedural macros can synthesize arbitrary identifiers. The bound is an
assumption about unrelated names.
The assumption is recorded on the link and appears separately in coverage.
Graph JSON exposes it in `data.assumes`, and the MCP graph-result legend
includes the same identifier.
[Procedural macros](https://doc.rust-lang.org/reference/procedural-macros.html)

An attribute's input includes the attached function, type or module and its
attribute tokens. Names in that input remain protected. A derive sees the
name of its type. The ordinary explicit binding continues to resolve uses of
that type where it already supplies the same namespace. Derive inputs follow
the same name check as other inputs. A captured `#[macro_use] mod` still uses
its textual and module resolution rules. An unread module cannot be made
readable by this assumption.

Known identifier generators such as `paste`, `concat_idents`, `seq_macro` and
`duplicate` stay opaque. So do `automod::dir!`, `include!`, and unresolved
macro definitions. A glob in scope still needs its own binding proof.
The assumption also leaves a macro that receives a glob or layout directive
opaque, since a macro can pass those tokens through to its caller. The
assumption applies only after the macro's Cargo origin is established.

Rust module version 35 reindexes earlier facts. The parser distinguishes
item identifiers in function-like input and item names in attribute input.
Empty function-like inputs are implicit in the stored parse. The resolver marks the ordinary
lookups whose macro guards can change, skips retries that cannot change a
decision, and shares ordinary lookup entries when their guards are stable.
The retry still considers cases where the original associated-call fallback
hid the ordinary path result. See the [pinned comparison and source
audit](../../evidence/c-12/README.md) and the [remaining
blockers](../../evidence/c-12/remaining.md).

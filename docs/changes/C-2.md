# C-2: indexing stays within the default Node heap

`pymtheg@0.1.0` ran out of Node's default heap (about 4 GB) on three large or
mixed-language checkouts: the TypeScript compiler repository, Turborepo, and
T3 Code at `b387e3a1`. Memory grew much faster than the source did. This
change removes the copies of the graph that indexing kept alive. All three
now index to completion with the default heap. On repositories that already
finished, the stored files, symbols, links and candidates are identical.
Measurements are in [`evidence/c-2/`](../../evidence/c-2/summary.md).

## What held the memory

Measured first, with heap snapshots and a program-lifetime probe on the dev
server (method and findings in the evidence):

1. **Whole-graph copies at resolution.** The indexer read every file, symbol
   and link once, then deep-copied all of them (`structuredClone`) for each
   module's `resolve`. It also validated against its own copy, and the store
   read every file and symbol again to validate a second time. Turborepo's
   crash stack was in that clone.
2. **Decoded files held for the whole run.** The store cached every decoded
   file record, including each record's stored text, for the life of the
   store. It handed out clones on every read.
3. **Captured sources and parse results after they were written.** The
   indexer kept every file's captured text and parse result until it
   returned. A module's analysis input and results also survived in the
   suspended async frame into the resolution phase.
4. **Native memory from per-row statements.** The store prepared a new SQLite
   statement for every link it wrote: target updates, candidate rows and
   link inserts. Each one holds native memory that V8 does not see, with this
   schema's triggers compiled in. It is freed only when a full collection
   happens to run. In one module's analysis write on a large checkout,
   hundreds of thousands piled up. On the TypeScript compiler repository,
   writing Go's results raised RSS from 4.2 to 8.9 GB while the V8 heap
   stayed near 3.3 GB. In isolation, rewriting cli/cli's 198,234 Go link
   targets in one transaction grew RSS by 4.0 GB with a statement per row,
   and by 60 MB with one statement reused. The released build has this too.
5. **Compiler programs.** These were **not** the leak. The probe shows each
   program and checker released after its group's facts are extracted. Live
   heap falls back to about 550 MB between later groups of T3 Code. The
   remaining peak inside TypeScript analysis is the current group's program.
   About half of its checker is TypeScript's own deferred-diagnostic
   callbacks; see "Not built".

## What changed

- `SqliteGraphStore` keeps no decoded file between reads. Every read decodes
  fresh, independent records. `files()` decodes one row at a time. New light
  reads, `fileSummaries()` (path, module, status) and `moduleLinks(module)`,
  decode no source records. They are optional `GraphStorage` capabilities, as
  is `counts()`. The indexer falls back to the old reads when a store lacks
  them.
- `indexProject` reads the graph afresh for each module's `resolve`. The
  records are freshly decoded, so the module still gets its own copy, and
  nothing is kept between modules. Validation reads only the files that
  receive added links. `resolutionFacts` takes a file lookup instead of the
  whole file list. A storage error inside that boundary still propagates
  unchanged; it is never reported as a module failure.
- Captured texts and parse results are released once written. Only the set
  of unreadable paths is kept. The cache check keeps hash, module, version
  and a failed flag instead of the previous record. Each module's analysis
  and resolution run in their own function frame. The closing report counts
  rows instead of decoding every symbol and link.
- Each store write operation (`replaceFile`, `replaceAnalysis`,
  `resolveLinks`) prepares each statement once and reuses it for every row,
  including the file lookups in added-link validation.
- No TypeScript module change was needed. No module version changes and no
  stored format changes: nothing re-indexes.

## Contract change

W2-I promised that a store instance reused for a second index decodes no
stored file when nothing changed. That came from the cache this change
removes. Each phase that needs records now decodes them again:
- one cache-check read per file;
- per module, its analysis input and its resolver input;
- for a module that adds links, one validation read and the store's lookups
  of the files that receive them.

The count is linear in files and modules, and nothing is kept between
phases. The CLI opens a new store per command, so it never had the reuse.
For the one-module synthetic workload, `test/graph-core-scaling.test.mjs` now
asserts at most three decodes per file on a cold run and four on an unchanged
one, instead of zero. Recorded in `docs/decisions.md`; `docs/support.md` and
`docs/runtime-map.md` are updated.

## Tests

`test/graph-index-memory.test.mjs` is a behaviour proxy for retained memory,
not a size limit. It marks every decoded stored file record and counts live
ones with `v8.queryObjects`, which forces a full garbage collection first, so
the count is exact and independent of machine speed. It indexes synthetic
projects of 20 and 80 files with two modules (one with a project-wide
`analyze`), cold, unchanged and after an edit. It asserts:
- no file record is passed to `structuredClone`;
- while each module resolves, exactly one decoded record per file is alive
  (its own input: no store cache, no earlier phase's copy);
- no decoded record is alive after the run.

On the previous main it fails: 100 file records are cloned on a cold
20-file run. Without the per-module frames it also fails, with 40 live
records during resolution instead of 20.

A second test counts the statements prepared while the store writes one
module's resolution. The synthetic module resolves 10 links per file and adds
20 more. For 20 and 80 files the count must be the same and small. The
previous main prepares 1,403 and 5,603 statements; this change prepares a
fixed seven (the test allows at most 12).

## Evidence

Full tables are in [`evidence/c-2/summary.md`](../../evidence/c-2/summary.md).
Every run is a cold index with Node's default heap (4,288 MiB here) on the
dev server.

| Checkout | Before | After | Largest heap after a full GC, before → after |
|---|---|---|---|
| microsoft/TypeScript | out of heap | done | 4,092 → 2,580 MiB |
| vercel/turborepo | out of heap | done | 4,069 → 1,614 MiB |
| T3 Code `b387e3a1`, own code | out of heap | done | 4,079 → 2,553 MiB |

- **Headroom.** All three also finish under a 3 GB cap, with stored records
  identical to their default-heap runs. Under a 2 GB cap they do not.
- **Identity.** On the 12 repositories that already finished, every stored
  file, parse-failure marker, context, symbol, link and candidate row is
  byte-identical before and after, in two rounds. They are 6 TypeScript,
  3 Go and 3 Rust, including nestjs/nest, excalidraw, cli/cli and helix.
  The exported coverage breakdowns are identical too, and Level 2 is
  unchanged on each. The old build, given a 16 GB heap, stores exactly what
  this build stores for the TypeScript repository.
- **Peak RSS** falls on all 15: for example cli/cli 4.5 → 1.4 GB, astro
  3.1 → 1.2 GB, nestjs 3.6 → 2.3 GB, restic 1.9 → 0.6 GB. Most wall times
  fall too, because fewer statements are prepared.
- **Coverage plan.** The script now marks microsoft/TypeScript and
  vercel/turborepo finished (55 of 60).
- **The TypeScript repository's TS and JS are not analysed.** The
  TypeScript module throws a compiler assertion there ("Debug Failure. False
  expression."), on the old build too. All 27,194 TS and JS files are stored
  as failed. That repository's coverage counts only its Go port.

## Not built

- **A safety net (proposal).** A re-exec with a larger heap was not built,
  as the task asked. It may still be worth having: the largest checkouts now
  need between 2 and 3 GB of heap against Node's default of about 4.2 GB,
  and a bigger checkout will cross it again. A conservative form: when
  `graph index` exits with V8's fatal heap error and no heap flag was given
  (in `NODE_OPTIONS` or argv), the CLI says so and runs the same index once
  more with `--max-old-space-size` set from physical memory (for example
  half of it, capped). An environment marker would stop it looping. Stored
  results would be unchanged; only whether a huge checkout finishes.
- **TypeScript's deferred-diagnostic callbacks.** In a T3 Code group's
  checker these held about 500 MB. The checker queues a closure for each
  name it resolves with diagnostics enabled. It runs them only when
  diagnostics are requested, which analysis never does. Draining them would
  run extra checking, and the checker's answers could then depend on query
  order. The module's warm-up exists to prevent exactly that. Left as is.
- **Narrower resolver input.** Each module's `resolve` still receives every
  file in the checkout, as the interface documents. In mixed checkouts that
  is the peak: the Rust resolve over the TypeScript repository's 32,448
  files. Passing a module only its own files would cut it. The Rust resolver
  reads other modules' files without a module filter, though. That code is
  in C-1's directory, and the change would need its own identity proof.
- **The TypeScript repository's compiler assertion.** The TypeScript module
  throws "Debug Failure. False expression." while analysing that checkout,
  and the exception fails the whole module's 27,194 files. It reproduces on
  the old build with a large heap. Localising it to one group or file and
  failing only those files is separate robustness work.
- **Store writes.** One synced commit per file dominates wall time on a busy
  disk (W3-P1 left it that way on purpose). Speed is out of scope here.

# C-26: a file whose analysis does not return fails with a reason

microsoft/TypeScript never finished the sweep. One TypeScript checker call,
on a 273-byte conformance test, ran without returning. This change makes
the TypeScript module recognise such a file before asking the compiler
anything about it, and fail it with a reason. The check is deterministic:
it reads the file's control-flow graph and needs no clock.

## What the call was doing

The file is `tsc/testdata/tests/cases/compiler/unreachableFlowAfterThrowingForHead1.ts`:
a `for` head made of immediately invoked, throwing (generator) functions,
and `console.log("1")` in the body. Measured on the dev server
([`evidence/c-26/`](../../evidence/c-26/README.md)):

- **Which call.** Replaying the module's queries one at a time
  (`tools/hang-probe.mjs`), warm-up returns. `getSymbolAtLocation` on `log`
  in `console.log` never returns.
- **What it does** (`tools/prof.sh`, 30 s under V8's tick profiler):
  - 51% of ticks are in `getTypeAtFlowNode` and 43% in the property loads
    it makes;
  - the only caller is `getFlowTypeOfReference`, from `checkIdentifier` on
    `console`, and there is no deeper frame;
  - memory stays flat.

  So it is not deep recursion and not exponential type work. It is
  `getTypeAtFlowNode`'s own `while (true)` loop following a cycle.
- **Why it loops.** That loop follows a flow node's single successor
  without counting:
  - an assignment, call or array mutation that yields no type;
  - a label with one antecedent;
  - from a function's start to its container's flow node.

  `flowDepth` counts only recursive entries, not these steps. The
  throwing calls in the `for` head make the binder build a loop of exactly
  such steps.
- **No hook to bound it.** The loop polls no cancellation token: the
  checker polls one only inside `getDiagnostics`. It touches no
  instantiation or flow-loop limit, and no counter we could read. TypeScript
  5.9's own `getPreEmitDiagnostics` overflows the stack on the same file.
  A cheaper query would not help either: any type query on `console` there
  enters the same loop.

## The design answer

AGENTS.md asks for two things that pull apart here:
- correctness must not depend on machine speed;
- a real resource limit is reported as unresolved evidence, never as a
  passed result.

A watchdog is a time limit, so it would make results depend on the machine
for exactly the files it stops. It is the right tool only where nothing
deterministic exists. Here something does:
- the cycle is a property of the binder's graph, which exists once the
  program is bound and before any checker query;
- following the same single-successor steps from each flow node, with a
  record of nodes already passed, finds every cycle that loop could
  follow;
- every step that might continue is taken (worst case), so the check
  reports any file where the compiler could loop. It may report a file
  that would in fact have stopped at an assignment that yields a type.
  That is an over-approximation in the safe direction: the file fails with
  a reason, never a guess.

So the module fails such a file, in the same place and the same way as a
file the compiler throws on (C-13):
- the reason is `The TypeScript compiler failed while analysing this file:
  its control-flow analysis would not return (the compiler follows a cycle
  of flow nodes from line L, column C without a limit)`;
- it counts toward the 100-file cap;
- the file is absent from the program, which is rebuilt without it, and
  the failed-file rule withholds the links that depend on it.

The outcome depends only on the source.

**What it covers.** Exactly this loop in the pinned compiler: a cycle of
single-successor flow steps.

**What it does not cover:**
- another compiler loop;
- exponential type work;
- a grammar or resolver loop in the Go or Rust modules.

For those the only bound is a watchdog. It was not built here, because no
such case is known on the corpus: every pin that finishes analyses all its
files. Its shape is below. Building it means running each module's
analysis in a worker thread, so isolation costs memory on every pin; that
should be measured against a real case.

## The watchdog that was not built (for the record)

- **Isolation.** Per module phase, a worker thread that reports the file
  it is on. The main thread terminates the worker past the deadline.
- **What is lost.** The TypeScript program; it is rebuilt without the
  file, and counted under the same cap.
- **The deadline.** Minutes per file, at least 100 times the slowest
  legitimate file measured on a loaded server. Configurable, and able to
  be turned off.
- **The reason.** `analysis-deadline-exceeded`, a failed file, shown in
  `graph status` as a budget stop.
- **Tests.** An injected clock and a worker that cannot finish.
- **The cost of honesty.** It is the one mechanism that could make results
  differ between machines, and only for files that would otherwise stop
  the index for good.

## Two more stops found on the way

With the non-returning file failed, microsoft/TypeScript stopped twice more,
on main too. Each was found by tracing and fixed.

- **The judge under a stopped walk.** On main the analysis ran out of heap
  at 1,166 s, extracting `packages/typescript/lib/getExePath.js`.
  - **The call.** The last checker call was the judge's `reaches` on the
    global `Object` (`Object.keys(pkg.bin)`).
  - **Why it explodes.** When the taint walk stops at its budget, C-13
    keeps its direct causes in a map that never reports itself empty. So
    extraction no longer skips `reachedFrom`, and the judge builds its
    dependence graph from `Object`'s declarations. Many test scripts
    redeclare `Object`, so that graph is nearly the whole 27,000-file
    program, with failed-file sets copied along it.
  - **The fix.** Under a stopped walk the judge's two graphs answer
    nothing. Every link they could clear becomes `taint-budget-exhausted`
    anyway, and direct bindings of a failed file are still answered from
    the direct causes.
- **The failed-file map in every result.** With the judge fixed, the
  analysis completes: 1,508 s, 2.8 GB live with its results. But the
  indexer then ran out of heap storing them.
  - **The cause.** Every result's `data.failedFiles` held the module's
    whole map of failed files: 12,473 paths with hashes, about 1.9 MB. In
    memory it is one shared object. The store writes each result on its
    own, so it was serialised 27,190 times: about 52 GB of JSON.
  - **The fix.** Each result now stores `failedFilesDigest`, a SHA-256 of
    the sorted map, instead of the map. The unchanged re-index shortcut
    rebuilds the map from the stored invalid results and the changed
    files, and compares digests. That accepts the same cases or fewer,
    never more.

The module version moves from 38 to 39, so stores index again: the
stored result format changes from `failedFiles` to `failedFilesDigest`.

## Two rules from C-13's review

- **A file the compiler throws on in a later project.** If an earlier
  project already read or published it, it is failed for the store (one
  status per file). Earlier results' links that target it become
  `target-unavailable`. Every other link of a project whose program read it
  is flagged `no-unseen-declarations`: it was computed with a file the store
  now calls unreadable. Within one project, C-13 already extracts the
  project again.
- **The 100-file cap** now counts compiler failures that a program imports
  from another project, not only its own.

## Tests

`test/graph-typescript-large.test.mjs`:

- **A non-returning file.** The reduced fixture, a `for` head of throwing,
  immediately invoked (generator) functions, fails with the reason and
  position; another file still resolves. The test has a generous timeout
  only so that a regression fails instead of hanging; nothing is asserted
  about time.
- **Loops that return are not failed.** These are the variants measured
  next to it (`tools/variants.mjs`): a throwing update or condition only,
  an ordinary loop, `for … of` over a throwing generator, and an immediately
  invoked function in the body.
- **The cross-project rule**, with an injected compiler assertion in a
  later project. It fails with the old rule.
- **The cap** counts the 60 failed files a second project imports: 40 of
  its own get the compiler's message and 20 the cap's. It fails with the old
  count.
- **A clean file's stored result** has the same size with 2 and 200 failed
  files beside it. On main it grows from 918 to 17,154 characters.
- **An unchanged re-index** still reuses stored results when files failed.

## Known limits and not built

- **No general watchdog** (see the design answer). A non-returning loop
  other than this flow loop still stops the index.
- **Compiler exceptions that are not assertions.** A `TypeError` thrown
  inside the compiler during extraction is still reported as a pymtheg
  internal error, not as a compiler failure. `for ((function () { throw 1;
  })(); ; ) { … break; }` makes the checker throw one (`tools/variants.mjs`).
- **The judge under a completed walk** is as on main. On a program that
  completes its walk within budget, its dependence graph has no budget of
  its own.
- **microsoft/TypeScript's time** within the sweep limit; see above.

# W2-C2 Rust recall: macros

Rust module version 23 improves recall for standard statement macros and textual
macros inherited by child module files. Core and the source snapshot contract are
unchanged. Macro expansion is still outside this structure-level fallback.

## Scope-neutral standard expansions

The explicit set is `print`, `println`, `eprint`, `eprintln`, `assert`, `assert_eq`,
`assert_ne`, `debug_assert`, `debug_assert_eq`, `debug_assert_ne`, `vec`, `format`,
`write`, `writeln`, `panic`, `todo`, `unreachable`, `unimplemented`, `dbg`, and
`matches`. Their standard expansions do not introduce items or bindings in the
caller's enclosing scope. Bare invocations and qualified `std::`, `core::`, and
`alloc::` invocations can therefore preserve name and receiver-type evidence.
This does not create semantic links to uncaptured standard-library definitions.

The exemption requires no captured competing binding. Project macro definitions
are checked conservatively across the captured project; explicit import names
and captured glob/re-export chains are checked in the lexical module, even when
the imported macro target is uncaptured. Named `macro_use`
requests are visible bindings even when their crate is uncaptured; readable
captured bare requests also count. Qualified paths require an unshadowed standard
crate prefix. A disabled implicit prelude defeats the bare-name assumption.
Unseen macro output, uncaptured bare `macro_use` exports, and failed/unverified
textual module entries are assumed not to rebind these standard names, following
the owner's extended E4 ruling for this chunk. This assumption is not a claim
about arbitrary macro expansion.

The parser retains conservative fallback flags only where binding evidence
changes. If a candidate is not proven standard, the resolver restores the old
scope opacity and binding fallback. Unknown macros remain opaque. In particular,
a captured project `println!` that rebinds a typed parameter cannot prove the
parameter's original inherent method.

## Textual inheritance

A child module file inherits its parent's textual macro environment at the
`mod child;` declaration. Earlier definitions and earlier `macro_use` modules
flow through nested file/inline module chains. Later parent definitions do not.
A child's own unconditional textual definition wins. An unverified declaration
or module layout cannot prove an inherited environment. Conditional definitions and
unseen failed-module entries keep all visible alternatives and remain uncertain.
Path-qualified invocations continue to use path lookup only.

## Known limits

- Under extended E4, failed/unverified textual entries are assumed not to bind
  any of the 20 standard names. The exact counterexample is:

  ```rust
  // src/main.rs
  pub fn helper()->u32{10}
  #[macro_use] mod macros;
  pub fn b()->u32{ println!(); helper() }
  mod later;
  // src/macros.rs (fails parsing)
  macro_rules! println { () => { fn helper() -> u32 { 20 } }; }
  pub fn broken( {
  // src/later.rs is empty
  ```

  The fallback intentionally retains the visible `helper` link (10). Making
  macros.rs readable lets rustc use the generated helper (20). This is a known
  limit pinned by labelled tests and a compiler-checked readable replacement.
  Visible captured macro definitions/imports still defeat the exemption;
  failed/unverified entries still make OTHER bare macro names uncertain.

- Workspace cross-crate macro exports (`dep::bail!`, macro imports, and external
  `macro_use` target resolution) remain a separate follow-up. Priorities 1 and 2
  already require changes to binding evidence and textual environments; adding a
  dependency macro resolver would broaden this chunk.
- Project macro bodies are not classified as scope-neutral: metavariable splicing
  and nested macros make a shallow absence-of-`let` check insufficient.
- An unrelated captured project macro with a standard name can conservatively
  disable that standard-name exemption. Explicit standard macro imports and
  aliases of standard crate prefixes may also lose recall; they are treated
  conservatively as competing imports.
- Child files whose failed parent erased their declaration cannot inherit a
  proven textual environment. Existing unverified-layout and grammar limits
  remain as documented in W2-C.

## Round-2 correctness and cache fixes (version 22 history)

Captured explicit import spellings are competing-binding evidence even when the
macro definition is outside the snapshot. That evidence follows captured
re-export and glob chains, including aliases, nested globs, restricted public
imports, and extern-crate aliases. It does not invent a semantic target for an
uncaptured macro. Known non-macro namespaces and unrelated imports retain the
standard-macro exemption.

Version 22 also made a failed or unverified module in the site's textual macro
environment prevent the standard-name exemption. The owner rejected this guard
in round 3; the following cost figures preserve the rejected variant. That guard
used textual lookup source-order/cfg rules and inherited environments. The guard
is absent in version 23; ordinary textual macro lookup remains strict.

Parse facts now intern their original source conditions separately from derived
module/file conditions. Analysis restores those source gates before recomputing
the derived conditions, and resolution produces fresh de-duplicated arrays.
Neither analysis nor resolution mutates the core's input; regression tests pass
deeply frozen inputs through both hooks. Re-index tests cover unchanged cfgs,
changed inner cfgs, a failed child, and restoration, comparing complete file,
symbol, and link records with a separate cold store.

## Round-3 ruling: extended E4

The standard-macro exemption now ignores failed/unverified textual entries,
just as it ignores other unseen output under E4. The ordinary textual lookup
rules are unchanged. Captured unresolved import spellings still count through
re-export/glob chains, and source conditions remain immutable and repeat-index
stable. Version 23 removes only the additional unseen-textual-entry guard.

The failed-entry tests are now explicitly labelled known-limit tests, recording
the intentional visible-helper link separately from the native replacement's
answer. Readable competing macros, visible unresolved re-exports, unrelated
imports, known non-macro namespaces, and ordinary macro uncertainty remain
covered. The unverified-layout control preserves the standard exemption too.

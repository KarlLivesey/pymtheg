# C-4: Go member links through element types and struct fields

Support items `go-container` and `go-fields` in the coverage plan. Go module
version 25 → 28 (26 and 27 were earlier pushed heads: identities, then the
stored build constraint, changed): stores built by an older version
re-index. `FileFact.build` can now hold several legacy `+build` lines.

## What changed

**Every anonymous struct type with a field is now a symbol.** Before, an
anonymous struct type became a local struct symbol only when it embedded
something, so a field of `[]struct{ args []string }` had no declaration in
the graph to link to. Now every anonymous struct type with at least one
field (a table-test literal, a nested `mu struct{…}` field of a named
struct, a `var x struct{…}`, a map key or value type) is a local struct
symbol with its field symbols and `embeds` links, exactly like a
function-local struct. A field-less `struct{}` (sets, `chan struct{}`,
`struct{}{}`) is not a symbol. The struct's value description records the
symbol (`Desc` `local.sym`), and selectors on its values go through the
existing selector rule, so depth, promotion, the equal-depth rule,
unexported names and the failed-file backstop all apply unchanged.

**Identities are anchored to the owning declaration**, as in 0.1.0: the
identity is fixed when the walk reaches the struct, under the declaration
that owns it (a package variable, a struct field, a type, or the enclosing
function), never under the file or the enclosing type.

- One that embeds something keeps its 0.1.0 identity
  `<file>:<owner>.struct#<n>`, numbered among the embedding structs of that
  owner; inside field-only anonymous structs (which were not symbols in
  0.1.0) its owner is still the 0.1.0 one (cli/cli
  `queries_repo.go:LastCommit.struct#1`). Every such symbol of the base
  graph keeps its identity (see the evidence).
- One with named fields only is `<file>:<owner>.anon#<n>`, numbered among
  those, so it cannot shift a 0.1.0 number. Examples:
  `args_test.go:TestMatchAll.anon#1.args`,
  `settings.go:Settings.Local.anon#1.FS` (the file name once); an embedding
  one: `checker.go:Checker.blobRefs.struct#1`.
- Inserting a declaration elsewhere leaves an owner's identities as they
  are, and a requirement link to such a field keeps its anchor; renaming
  the owner makes it missing, as for named symbols.
- **Limit:** inside one owner (a function with several tables) the structs
  are numbered in source order. Inserting another anonymous struct of the
  same kind above a linked one in the same owner shifts the numbers
  (`struct#n` or `anon#n`), and `link check` then stays ok on the new
  struct's field of the same name instead of the one that was linked.
  0.1.0 did the same for `struct#n`.
- These symbols and their fields carry `data.anonymous`. Graph search (CLI
  and MCP) and file listings put them after every named declaration rather
  than leaving them out, so they are still found when asked for, but a page
  of table-test `name` fields no longer hides `(*worker).name`. The ordering
  is one `ORDER BY` term in `store.ts` (`searchSymbols`, `symbolsForFile`);
  no stored-format change.

**Values of function-local struct types resolve.** `type row struct{…}` in a
function was already a symbol, but values of it were opaque. A local type
name in a type position now refers to that symbol (`TypeRef.l`), so
`var l row; l.Y` and `for _, r := range []row{…} { r.Y }` resolve.

**A named type over a container is a container.** An element or key of a
value whose type is a defined type over a container literal
(`type HeaderRouter map[string][]HeaderRoute`) is the literal's element or
key, also through defined types over it (`type S R`), including a generic
defined type over a non-generic container (`type Gen[T any] Rows` with
`type Rows []Row`: `g[0].N` is `Row.N`, whatever `T` is). A generic
container literal (`type L[E any] []E`) is not followed: its element is the
type parameter, which is not instantiated. Build variants of the type must
agree.

**Build variants are searched one configuration at a time.** A type
declared in several build-variant files is a different type in each
configuration. The selector rule now:

- keeps only the variants that can be built with the referencing file
  (inside `netns_linux.go`, a `NetNS` declared under `//go:build !linux`
  is not a candidate); a variant declared in the referencing file itself,
  or the one every build of that file includes, is the only one (two
  declarations of a name are never in one valid build);
- searches each remaining choice of variant separately, choosing only when
  a variant set is reached (at the top or as an embedded type), at most 32
  configurations;
- is definite only when every configuration that finds the name finds the
  same declaration. A configuration that finds nothing is one in which the
  referencing code does not compile (a `!cgo` mock `SQLiteConn` without
  `Exec`), so it does not count. When they find different declarations,
  the answer is the candidate set of their answers (the module's existing
  rule for build variants); ambiguous, unknown or failed anywhere makes the
  whole that.

A variant's own fields are only those of its declaration. A method counts
for a variant when, in the referencing file's builds, the variant's
constraint implies the method file's; it is absent when the method's file is
never built with the variant in those builds (also when only the
referencing file's own constraint excludes it: a `!fast` caller never sees
a `fast` method); otherwise its presence is one more choice of
configuration. Constraints are read from `//go:build` and legacy `+build`
lines and `_GOOS`/`_GOARCH` filename suffixes, and `import "C"` means
`cgo` (`constraints.ts`). Without a `//go:build` line every legacy line
holds (Go ANDs them), but only one followed by a blank line before the
package clause (one directly above `package` is not a constraint, as in
Go); with a `//go:build` line, it alone holds. GOOS and GOARCH values,
also for filename suffixes, are Go's own known lists (`go/build`). One
GOOS and one GOARCH per configuration, `android`→`linux`, `ios`→`darwin`, `illumos`→`solaris`,
`unix` for the Unix GOOS values, release tags cumulative (`go1.23` implies
`go1.22`), other tags free (more than 10 free tags, or an unreadable line:
not known). The solver does not know which GOOS/GOARCH pairs Go supports
(`windows && wasm` counts as possible).

Before, a field at depth 0 in one variant won over a promoted field in
another: `items[0].Name` was definite to the Windows `Item.Name` while the
Linux build selects `forwarded.Name`. This applies to every route of this
chunk: element types, anonymous and local structs and named containers all
select through the same rule.

Typed slices, arrays, maps, channels, range variables, index expressions and
receives of checked-in element types were already resolved; they now also
work when the element is an anonymous or local struct or comes through a
named container type.

**The resolver's outcome no longer depends on the order it is given the
graph.** The candidate corpus run found 28 links that lost their target
although the code they need had not changed. Running the same build three
times on the same fiber checkout gave 58,163, 58,163 and 58,184 unresolved
links. Two causes, both older than this chunk and made visible by it:

- *A cut-short answer was cached.* `typeFromRef` (and `view`) memoised
  `unknown` when the recursion depth limit cut the computation short. If
  the first route to reach a type was a long one (fiber's
  `cand.idx` in `router_skip.go`), every later, shallow lookup of the same
  type got `unknown` (fiber's `app.skip.enabled`). Answers cut short by the
  depth limit or by a cycle guard are no longer cached (`cutoffs`), in
  `memo`, `views`, `hiddenMemo` and `externalMemo`.
- *Which route came first depended on the store's order.* A cached good
  answer still lets a long route finish where it would otherwise reach the
  depth limit. The resolver now sorts files, symbols and links by file and
  position before it starts, so every run gives the same answer.

Sorting exposed a third order dependence: an interface embedding two
interfaces that declare the same method with different signatures
(`interface{ I; X }`, `M()` and `M() int`, which Go rejects) kept whichever
it met first, so it had implementers or not depending on the order.
`graph-go-review2` case 4 only passed because of the store's order. Now a
provably different duplicate makes the method set unknown: no implementers,
in any order.

## Kept as it was

- **Same-depth ambiguity.** Two embedded types supplying the same name at
  the shallowest depth (`struct{ A; B }`, both with `N`) is a compile error
  in Go when selected. The module's documented rule is a candidate set of
  both, never one pick; this chunk keeps that rule for anonymous structs
  too. Changing it to unresolved-with-a-reason would change the rule for
  every struct and add a reason value; listed below.
- **Interface-typed elements** stay dispatch candidate sets.
- **External types.** An element, field or embedded type from a package
  outside the checkout stays unresolved, including an exported name at a
  depth where an external embedded type could also supply it (golang/tools
  `macho/file.go:166`, `s.Maxprot` beside an embedded `io.ReaderAt`).
- **Build variants of an anonymous field.** A field reached through an
  anonymous struct type declared in several build variants of its enclosing
  type (`t_linux.go`/`t_windows.go` each with `mu struct{…}`) is
  unresolved: the variants' anonymous structs are different types and the
  value is not one type.
- **Type parameters.** An element of `[]T` with `T` a type parameter
  resolves only through its constraint, as before.

## Toolchain agreement (opt-in route)

On restic `c734245` with `graph.toolchain.go` on, there were 0 disagreements
before and after the change (`evidence/c-4/toolchain-agreement-restic.json`).
Links the toolchain confirmed from a source-only definite answer rose from
31,115 to 32,525. Links only the toolchain could decide fell from 834 to
461: 373 of them are now found by the source-only route, with the same
target.

`evidence/c-4/README.md`: the candidate run of all 20 Go repositories
against a build of `main`, level 2 before → after, the site and identity
comparison, the hand-check of 20 newly definite links, toolchain agreement,
timings and memory.

- Go level 2: 74.16% → **77.10%** counting every link; **76.67%** with the
  27,977 links at new sites removed from both sides.
- Gross additions 65,297 newly definite Go links: 37,348 at sites that
  already had a link, 24,698 new `contains` links of the new symbols and
  3,251 new references. Replaced keys 0, lost or retargeted 0: net 65,297.
  (The first head's figures were 65,270 gross, 351 replaced `contains`
  keys of re-scoped identities, 64,919 net.)
- All 176,250 Go symbols of the base graph keep their identity.
- 20 newly definite links drawn at a fixed seed: all true.
- Reference sites: `go-container` 29/33, `go-fields` 14/21. The rest need

  restic 62.4 s → 63.9 s, peak 0.69 → 0.70 GiB.

  pins, not this chunk), Rust unchanged.

## Not built

- The constraint solver accepts GOOS/GOARCH pairs Go does not support
  (`windows && wasm`); it never makes a link definite on its own, but it can
  keep an impossible configuration in a candidate set.
- Same-depth ambiguity as unresolved with its own reason, module-wide.
- Joining build-variant anonymous structs into a candidate set.
- Library identity for elements and fields of external types (later chunk).
  The type facts are recorded where they already were: `data.expr` keeps the
  full description, and an external element is an `external` type value.
- A missing toolchain helper source (`golinks.go`) under the package makes
  every Go file fail when the opt-in route is on, instead of reporting the
  toolchain unavailable. Seen while building the evidence; not changed.

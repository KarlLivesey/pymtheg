# W3-M2: stable content failures on warm queries

Branch starts at main `0e632c9c49e924fd9d25fcd8225e19c89d1d7ada`.
PR 40's branch is untouched. No MCP, schema, command settings/toolchain wiring or
language-interface changes. The implementation touches the indexer and TypeScript
module only; command completion already admits stored content failures.

## Contract

An analyze-only module may now explicitly return `failureKind: "content"` for a
validated failed result. The core stores the existing self-validating failure
marker (file hash, module ID, module version). An absent failureKind from analysis
is insufficient; the existing parser-origin marker may still be preserved.
Thrown analysis, bad/invalid output and explicit transient failures do not acquire
a marker. Failure lists and incomplete-answer warnings are unchanged.

TypeScript module version 16 becomes **17**, also keyed by installed compiler
version. It certifies only an entire failed diagnostic set reproduced by the
existing standalone `syntaxFailure(path, text)` helper. That helper uses the
compiler parser with Latest syntax, extension-selected script kind, BOM-adjusted
ranges, and existing file-local heritage grammar checks. No config, imports,
Program, checker or other source is consulted. Whole diagnostic sets are compared
independent of order (tied configs may reorder them). A pure file syntax failure
is therefore a property of the same file bytes and module/compiler version.

Diagnostics added only by Program syntax checks (for example TS-only annotations
in a JS file), config/ownership errors and tied-config structure disagreements
are conservatively not cached. Neither are internal exceptions, parser/binder/
checker resource limits or an explicit transient result, even if the file also
has a local syntax error. They continue to block completion and force retries.
This deliberately does not turn every failed TypeScript analysis into a content
failure. Content failures retain all diagnostics and contribute no symbols/links.

Completion stays in graph.sqlite, with the existing invalidation triggers,
module/configuration/inventory/settings fingerprint and publication checks. Once
all failed files have content markers and no operational/module error occurred,
automatic queries hash the snapshot then answer without entering indexProject.
This is a complete index of a partly unreadable project, **not** a complete answer:
every failed file remains named, and answers still carry the failed-files warning.
Content/context/module changes invalidate the checkpoint. An edited file is the
only newly indexed source; project analysis/resolution can still revisit other
files because a source edit changes their lookup context. This is no speed fix
for actual changed projects or operational failures.

## Validation

Six deterministic tests cover mixed Go/Rust/JS/TS failed files; zero progress
phases/report on warm queries; byte-identical cold/warm answers excluding the
sync observation; one newly indexed source for each fix; version/context changes;
real TypeScript extraction faults and recovery; thrown/unclassified/transient/bad
analysis output; and config/Program-only diagnostics. No elapsed-time assertions.

The separate clean mixed-project comparison serializes stored files, symbols and
links with a fixed namespace against main. Bytes are identical after normalizing
only the deliberate TypeScript module-version/analyzer provenance (16 to 17).
Literal version-bearing output necessarily changes with the required version
bump; source, identities, diagnostics, certainty, link data and targets do not.
The two snapshots and SHA-256 comparison are in evidence/w3-m2/.

Fixture baseline (one failed JS, Go and Rust file plus clean TS): three unchanged
queries all synced, indexed the failed JS again (1), analyzed 2 TS files, entered
all 3 analyze and all 3 resolve phases. TS's own existing reuse avoided rebuilding
a Program but did reparse the failed JS for diagnostics. Wall times observed:
33.4 / 34.0 / 29.1 ms. After: all three report unchanged, no index report, no module
phases, no Program/extraction/reuse activity; 9.3 / 6.6 / 6.6 ms. These are
observations on the dev server, not guarantees or acceptance thresholds.

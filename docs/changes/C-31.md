The table counts 138,933 distinct stored links on the ten source-only pins.
One of the four reasons was first on 136,951 links. A further 1,982 carried one
of them later. The refreshed replay on main `ecc0c2d` keeps the same stored
cohort and shifts a few owner-evidence cells from the original
`e291a60` measurements. The groups above use the receiver syntax and
the recorded typing stop. A chain or field can stop earlier at an unresolved producer. A
constructor-shaped checkout call has a definite producer and a name such as
`new`, `with_capacity` or `default`. The written return type supplies the
receiver when the resolver can read it.

“Checkout inherent candidate” counts a method read from an impl of the
identified type. “Checkout trait evidence” includes an impl candidate or a
trait found as the owner. “Core or std type” and “third-party type or prefix”
record only lookup evidence for the receiver or associated path. A type such
as `Arc<T>` can lead to a trait, an inherent member or a method on a deref
target. None of those three follows from the type name alone. A standard or
third-party **producer** says where a value came from. It does not establish
the value's type.

neither a written receiver nor a recipe all came from macro argument tokens.

## What the diagnosis supports

- **Associated paths already spell the prefix.** All 18,392 in the
  unknown-owner cell have a written prefix. Of those, 12,801 (69.60%)
  carry `opaque-item-may-shadow-name`. For 9,633 (52.38%) opacity is
  the sole recorded blocker once the path category and target-list
  truncation are set aside. For 5,759 (31.31%) the list contains no other
  reason beside opacity and the path category. Start with the opaque
  macro proof for these written paths.
- **Macro argument receivers and chain heads.** All 16,226 calls without
  a recipe were captured in macro arguments. Of those, 15,063 (92.83%)
  have an `assert!` family name in the enclosing macro chain, and 9,199
  (56.69%) have a definite sysroot target for one of those macros on
  main. Of the 26,715 chains, 16,478 stop before the first inner method
  and another 9,180 stop at that method. Together they make up 96.04%.
- **Written `from` and `default` producers.** Of the 10,793 unresolved
  call results, 217 spell `T::from` and 816 spell `T::default` (9.57%
  combined). The standard traits declare a `Self` return. A link still
  needs proof that the spelling selects that trait method, because
  inherent methods can share the name.
- **Known receiver, core declaration at the first probe.** This is low risk.
  The receivers that match the small catalog on main are a few hundred sites
  across the ten pins. The lookup must still prove the written type binding,
  its receiver form and method availability.
- **Checkout inherent candidates.** There are 6,259 links
  with an inherent candidate. That includes 873 direct `self`, 717 written
  receiver types and 885 constructor-shaped receivers. Many have a later
  receiver form, a bounded impl or a build-dependent declaration. Only 253
  sites got as far as an autoref check with a checkout trait name whose captured
  receiver forms could not be earlier. That is an upper bound on narrowing
  that single blocker. Further checks on those sites can still withhold.
- **Library producers and written library types.** There are 1,613 direct
  results of calls with a named standard producer and 582 with a third-party
  producer. This is a boundary where a small signature catalog can help
  specific families. A method call on a third-party type can need its impls,
  bounds, re-exports and deref behavior as well as the signature.
- **General receiver inference.** Chains, patterned bindings, iterator items,
  closure parameters and generic or trait-object receivers need facts about
  the prior operations and Rust's trait selection. Their counts bound the work
  population. They do not estimate how many sites have a definite source-only
  answer.

## Implemented

A small catalog checked against Rust 1.98.1 names selected inherent methods
of primitive types, `Option` and `Result`. The [catalog check](../../evidence/c-31/core-catalog.tsv)
records the declarations, receiver forms, argument counts and first releases
supplying them in `core`. The compiler floor is the higher of the edition
minimum and the declared package `rust-version`, including a value inherited
from the workspace. Edition floors are Rust 1.0, 1.31, 1.56 and 1.85.
Compiler verification for edition 2015 goes down to Rust 1.31.

When the compiler floor falls below a catalog entry, the graph records
`core-method-owner-version-unverified`. Inherent `str` and `char` methods
moved into `core` in Rust 1.27. Float `abs` and `signum` require Rust 1.85
for the `core` declaration. Older `std` builds use the method declared in
`std`. On Rust 1.56 and 1.83, the `no_std` control with a local extension
trait selects the trait methods instead. The catalog proof compiles
`no_std` calls on 1.31 (editions 2015 and 2018), 1.56 and 1.83 (2021), and
1.85 (2024).

A direct string, character or suffixed numeric literal contributes its type
from syntax, including integer-shaped float literals such as `1f32` and
`1f64`. The written-type route uses captured annotations and the existing
checkout receiver recipes, including their declaration scopes. A single
checkout alias can supply an outer standard type written in its declaration.
Conditions, imports, opaque items and namespace shadowing can withhold either
route. Library lookup of the type uses the same binding checks as other Rust
library paths. The first receiver form must exactly match the catalog. For a
shared `str` method that means `&str`. For an owned `Option::unwrap` call it
means `Option<T>`. Rust chooses an inherent method over a trait method at the
same probe. Method-level argument bounds are checked by Rust against the
selected declaration. The selected impl itself must apply to all type arguments.

The graph stores `core` and the declaring symbol with `declaring-owner`
evidence. It needs no installed library metadata or compiler at indexing time.
The Rust module version rises from 42 to 44 to refresh cached receiver facts.

The fixture uses the `read(&[]).unwrap()` receiver from the Turborepo coverage
sample. Cargo compiled it under both feature settings. Type assertions check
which receiver form Rust chooses when a trait can win before an inherent
`&mut self` method, when a wrapper competes with its deref target, when two
traits are in scope, when a blanket impl is available, and when the receiver
is `&T`. Byte strings, C strings and byte characters exercise literal
distinctions that share parser node kinds.

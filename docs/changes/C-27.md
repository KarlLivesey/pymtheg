# C-27: Go re-index proportional to the edit

A source-only Go edit that leaves declaration and import facts unchanged
re-decides links in the edited file. An ordinary function change can also
re-decide callers without visiting links in unrelated packages. Both passes
use the same Go resolver as a cold index. Go module version 32 rebuilds older
Go records once to save the new fingerprints.

## What is fingerprinted

The parser saves two hashes with each clean file. One records its package,
imports and aliases, test-file flag, build expression, filename platform,
non-function declarations and embedding facts. It includes `init` in these
facts. The other records ordinary functions. Both include names, identity,
kind, source order and the full stored symbol data. This includes unexported
declarations, local and anonymous types, owners, receivers, signatures, type
references and descriptions of declaration values. Extraction places the
type information used across files on these symbols and on embedding links.

| The resolver reads | What proves reuse |
|---|---|
| File membership, package names, import bindings, type and method variants | Paths and ownership must match. The global hash covers parse status and package, test, import and build facts. Go manifests are captured separately and must match. |
| Package and dot-import lookups, type references, declaration values, return and function signatures | Hashes include every declaration consulted by these lookups. A change confined to ordinary functions follows every possible directory from Go's import layout, in reverse and transitively. A changed name read by a type, method, field, variable or embedding fact makes the module fall back. |
| Predeclared names | Analysis uses the package-level declaration names from the same snapshot. The reader's predeclared use and its range come from its own parse. Ordinary function changes include all files in the declaration's directory, including tests and package variants. |
| Promoted members, interface method sets, implementers, hidden methods and candidates | The resolver rebuilds these from all symbols, imports, constraints and embedding facts. Global changes use the full Go pass. Unknown receivers can consult a project-wide method list, even when the reader never imports the package that declares a method. |
| Failed-file causes, uncertain membership, vendoring and test-data providers | Paths, module ownership and statuses remain valid across a scoped run. A failed or repaired edited file, changed manifest or changed vendored Go source or metadata uses the full pass. |
| Source links, local use ranges and generated-link ranges | Each re-decided file supplies its own links. Outside a file, source-only Go uses stable symbol IDs, declaration order, and whether embedding sites share an offset. Absolute ranges are only written to links belonging to the declaration's own file. The opt-in toolchain can look up declarations by offset and always uses the full pass. |

The store's symbol IDs use identity and ordinal. A comment that moves a
declaration changes its range and draft key, while the ID survives. The
fingerprint preserves the source order used for ordinals and for embeddings.
Unknown embeddings use their offset to distinguish sites in one file, so
the hash preserves ties between those offsets. The Go resolver reads symbols
by range only for toolchain positions. It uses the new ranges on derived
links owned by the edited file.

Some bounded lookups can use facts already worked out for another link.
The global pass seeds those lookups from the declarations. A file can then
reuse work done for its own earlier links, in source order, with the same
starting state in a cold or scoped run. The resolver drops that file's
temporary cache when it moves on to another file. Selection also keys by
the actual reader file, because that lookup can prefer a declaration in
the reader's file over another build variant.

On main, the selector cache reused one standalone example's `Options`
fields for the next file in `cli/cli`'s CodeQL examples. Each file
declares its own `Options` and takes that type as the `opts` parameter.
Four stored field references now link to the declarations in their own
file. The example fixture checks both targets after moving one file's
declarations. The evidence lists each correction and both target lines.
[cli/cli cold corrections](../../evidence/c-27/cli-cold-corrections.json)

## When it uses the full Go pass

- A Go file was added, deleted, renamed or changed language ownership, or
  another claimed path changed the captured set used for vendor and test-data
  lookups.
- A file has no comparable fingerprint, changed package, imports, build
  facts, non-function declarations or embedding, or became unreadable or
  readable again. Changes to methods and interface members are global.
- A changed function name is read by a global declaration or embedding fact,
  or the changed file is under `vendor/`.
- The captured `go.mod`, `go.work` or `vendor/modules.txt` changed, the Go
  module version changed, a previous index was unfinished, or the store
  cannot safely write a scoped result.
- The store cannot show that the module version finished its last owned
  index run. A direct graph write invalidates that evidence even when source
  hashes match. The next index restores the module's parsed rows and decisions.
- The Go toolchain is enabled or the store still holds toolchain facts from
  a previous run. The opt-in configuration and toolchain input checks still
  run on the full path.

The shared indexer validates a scoped result before it writes anything
from it. It writes edited files with their final analyzed symbols in one
replacement. Writing a raw parse result first would temporarily remove a
package's derived symbol and allow SQLite to clear incoming links that
should survive. File-by-file link replacement uses the existing validation
and target rules. All writes keep the existing run ownership and unfinished
mark. A subsequent run rebuilds every record if an earlier run stopped
after a commit or could not complete Go analysis or resolution.

After review, the store records the completed module versions in the same
transaction that clears the run's mark. The next run reads the record in its
opening SQLite snapshot alongside the mark and the data version. Graph-row
writes invalidate both this record and the command checkpoint through SQLite
triggers. The CLI and direct indexer calls use the same proof. Older stores
acquire it after a full index.

## Remaining work per edit

The shared indexer still inventories and hashes claimed files by content.
The command checks the inventory before and after the run, and the indexer
captures the bytes it passes to language modules. Content checks also catch
edits that preserve timestamps. Go loads project file and
symbol facts to rebuild the name and method-set indexes for the two passes.
The method-set pass can compare types and interfaces across all packages.
The store keeps one copy of the facts. No second durable index is needed
to reuse link decisions.

The global rebuild used 0.6 to 8.7 CPU seconds across the four body edits.
golang/tools took another 5.4 seconds reading previous records and loading
the two Go phase inputs, and 3.7 seconds on inventory and source capture.
The shared inventory still hashes by content and the resolver still decodes
whole file records for global facts. Mixed-language projects also run the
other modules through their existing analysis and resolution routes.

## Found, not built

For one fresh restic index on memory-backed storage, setting the test
database header's `PRAGMA default_cache_size = 131072` reduced observed wall
time from 221 to 123 seconds. Both indexes executed 261,622 SQL statements.
With 4 KiB pages that setting allows up to 512 MiB of SQLite page cache per
connection, compared with the default 2,000 KiB. This is a cache capacity,
and actual resident memory depends on the pages the connection touches.
The product keeps its existing SQLite settings.

## Reproduce

Run on the dev server. Each build's `dist` needs its matching grammar and
Go standard-library assets in the checkout.

```sh
node scripts/reindex/fetch.mjs "$PYM_SCRATCH" restic/restic cli/cli golang/tools labstack/echo
node scripts/reindex/measure.mjs <dist> "$PYM_SCRATCH" restic/restic "$PYM_SCRATCH/out/<label>"
node scripts/reindex/cold-cost.mjs /dev/shm/c27 "$PYM_SCRATCH/cold-restic.json" 1 main-1=<main-dist> after=<after-dist> main-2=<main-dist> --go-surface --cache-pages 131072 -- "$PYM_SCRATCH/pins/restic_restic"
node scripts/reindex/random-edits.mjs <after-dist> "$PYM_SCRATCH" restic/restic 27201 200 "$PYM_SCRATCH/random-restic.json" --store-dir /dev/shm/c27 --cache-pages 131072
node scripts/reindex/random-edits.mjs <after-dist> "$PYM_SCRATCH" cli/cli 27202 60 "$PYM_SCRATCH/random-cli.json" --store-dir /dev/shm/c27 --cache-pages 196608
node scripts/reindex/random-edits.mjs <after-dist> "$PYM_SCRATCH" cli/cli 27204 12 "$PYM_SCRATCH/random-cli-extra.json" --store-dir /dev/shm/c27 --cache-pages 196608
node scripts/reindex/random-edits.mjs <after-dist> "$PYM_SCRATCH" golang/tools 27203 20 "$PYM_SCRATCH/random-tools.json" --store-dir /dev/shm/c27 --cache-pages 196608
node scripts/reindex/random-edits.mjs <fixed-dist> "$PYM_SCRATCH" restic/restic 27301 20 "$PYM_SCRATCH/review-random-restic.json" --store-dir /dev/shm/c27 --cache-pages 131072
```

The seeded harness checkpoints the completed comparisons. Add `--resume` to
the same invocation to continue after a time limit. Keep the source and the
intermediate warm database under the same scratch path.

# C-15 Rust failed files: name them only where they could change the answer

The 0.2.0 coverage plan's largest Rust item, "keep independent Rust links
resolvable after a different file fails" (`rust-taint`, 308,480 links, 13.27
points in five repositories), assumed that a Rust file the parser rejects
withholds many links in other files that it cannot affect. This chunk
measured that assumption first. It is not what happens. The resolver already
withholds very few links because of a failed file; what reaches far too wide
is the **reason** it records. Every unresolved link in a crate whose
dependency closure contains a failed file was labelled
`failed-file-unseen-declarations`, whatever actually stopped it, and the
coverage plan counts every link with that label as a taint miss.

This change makes the recorded reason exact. It changes no link's outcome,
target, candidates or library row. The plan's taint row now shows the real
size of the failed-file problem, and the links it held are counted under the
items that actually block them.

## How much the failed files really withhold

To bound what any rule could recover, the five repositories were indexed a
second time with a diagnostic build that treats every failed file as an empty
file (the resolver's failed-file set forced empty; not committed). Nothing a
failed file contains is visible either way, so any link that resolves only in
that build is the most a failed-file rule could ever release, and it is an
upper bound because an empty file is a guess, not a reading.

| Repository | Rust links | Labelled failed-file on main | Level 2 links released when the failed files are emptied |
| --- | ---: | ---: | ---: |
| vercel/turborepo | 683,584 | 280,527 | 408 (352 macros, 56 calls in macro arguments; 1 link lost) |
| DioxusLabs/dioxus | 149,592 | 13,298 | 44 (macros and calls in their arguments) |
| rustls/rustls | 69,929 | 18,141 | 10 (calls in macro arguments) |
| alacritty/alacritty | 30,965 | 11,222 | 1 (`vec!`) |
| rust-lang/mdBook | 12,557 | 347 | 5 (`assert!`) |
| **Total** | | **323,535** | **468** |

So the 308,480 figure was almost entirely a label, not withheld links. The
few links the diagnostic build releases are macro lookups (`vec!`, `format!`,
`assert!`, `include_str!`, a `to_owned!` macro) that sit after a failed
sibling module in textual macro scope, and calls inside their arguments. A
failed file's own `#![macro_use]` or `macro_rules!` cannot be ruled out, so
those stay withheld; textual macro scope belongs to C-12, and this chunk does
not touch it.

## The old rule

Resolution itself (unchanged by this chunk):

- A path into a failed file's module, including inline child modules and
  modules it declares with `mod`, is failed (`invalid-code`, with the file as
  `data.cause`).
- A name looked up in a scope whose body is a failed file, a glob import of a
  failed module, and a textual macro scope that passes a failed module are
  unresolved with `failed-file-unseen-declarations`.
- A method call at the C-10 autoref step is never definite when any crate the
  caller's crate can reach has a failed file.
- A file below a failed module file has no known module path.

The label (what this chunk changes): `methods()` appended
`failed-file-unseen-declarations` to every unresolved method or associated
call reason when any crate in reach had a failed file, and the final step of
the resolver appended it to every unresolved link with no target in such a
crate. Neither looked at what stopped the link.

## The new rule

A failed file only ever **adds** declarations, imports, impls and macros; it
cannot remove anything visible. So a link that is stopped by something
visible stays stopped whatever the failed file holds, and the failed file
is not its reason. The label is now recorded only where the unseen content
could change the answer:

1. **A lookup reached the failed file** (a path into it, a glob of it, a scope
   it is the body of, a textual macro scope through it, a binding check that
   met it): unchanged, as above.
2. **Method and associated calls** on a type the resolver found:
   - autoref step blocked only because a crate in reach failed: labelled
     (an unseen trait impl could add an earlier by-value candidate);
   - no visible inherent method of that name: labelled only if a failed file
     is in the **type's own crate**, because only that crate can declare an
     inherent impl, and a trait method is never definite here anyway;
   - a visible inherent method whose applicability, probe step or receiver
     form is unproved, or a candidate under an opaque attribute: not labelled
     (more impls cannot remove the visible doubt);
   - the type could not be found or is a trait, alias or outside type: not
     labelled unless its own lookup reached a failed file or an alias
     expansion was unknown (an alias lookup can reach one unseen).
3. **Receivers with no type:** a receiver the parser cannot type (a closure
   parameter, pattern binding, literal, macro, index, …) and a receiver whose
   type the resolver found but whose written shape stops it (a generic field
   or return, `impl Trait`, `dyn`, reference to reference, a missing or
   private field on a found struct, …) is not labelled. A receiver gap that a
   lookup could cause (an unresolved callee or method in the chain, an
   unknown field owner, a non-local value) keeps the label.
4. **Local bindings:** a parameter or `let` binding is unproved when a
   constant or unit item of its name could be in scope. That check now
   carries the failed-file reason when it reached a failed file (a glob of a
   failed module); otherwise a failed file elsewhere is not its reason.
5. **Other unresolved links** keep the label only when the resolver has no
   other reason for them (a name found nowhere). Macro links, and links
   inside the arguments of a macro whose arguments are unproved, keep the
   wider rule as before: the macro itself may be one a failed file declares
   in textual scope (C-12 owns macro scope). The first version of this
   change dropped the reason on two `serde_json::to_string` calls inside
   `format!` in dioxus; the cross-check against the diagnostic build caught
   it.

## Why each kind of dependence is or is not sound

The task asked for each case to be thought through:

- **Names the failed file declares in its module and inline child modules**
  are reachable only by a path through that module or a glob of it. Both
  lookups reach the failed file and are withheld (cases 1).
- **`mod` declarations it may contain** create modules below it; a path to
  them goes through its module (withheld), and a file below it has no known
  module path, so its own `super::` paths stay unresolved.
- **`use`, `pub use` and globs it contributes** reach importers only through
  a path into its module, which is withheld; an importer's own items and
  explicit imports still beat a glob of it (a local `fn k` beside
  `use crate::bad::*` resolves).
- **Impl blocks for any type.** An explicit path to a free function, type,
  const or module never consults impls, so it is unaffected. For a method or
  associated call an unseen impl can only add a candidate. An added inherent
  method at the first probe step would duplicate a visible one with an
  overlapping impl (rustc E0592) or apply to a different instantiation,
  which the applicability check already rules out, so the first step stays
  definite as on main. At the autoref step an unseen trait impl in any
  reachable crate could add an earlier candidate, so the step stays withheld.
  An inherent impl must be in the type's crate, so a failed file in another
  crate cannot answer a call that has no visible inherent candidate.
- **`macro_rules!` with `#[macro_export]` or textual scope:** unchanged.
  Exported names collide at the crate root, so a visible exported macro is
  definite; an absent one stays unresolved and labelled. A sibling declared
  after a failed module could see its textual macros and stays withheld.
- **`#[path]`:** a failed file could mount any file a second time elsewhere.
  That second copy's items are reachable only through the failed module
  (withheld); impls in it would conflict with the first copy's.
- **A failed file in another crate:** affects only crates that depend on it,
  through paths into it (withheld), trait impls (autoref withheld) and
  exported macros (macro rule unchanged). It is never named for a type it
  cannot declare inherent methods for.
- **Partially parsed files:** the parser gives no reliable recovery regions,
  and the owner's rule is that the unit of failure is the file, so the whole
  file stays unreadable, including the lines before the error.

## Why these repositories have failed files at all

Every failed file is valid Rust (or valid nightly Rust) that the vendored
grammar rejects, except two mdBook documentation snippets:

| Shape the grammar rejects | Valid Rust? | Failed files |
| --- | --- | --- |
| `str` as a macro name (`str![[r#"…"#]]`, snapbox) or a path with generics (`&str<u8, el>` in a proc-macro DSL) | yes (syntax) | 18: mdBook `tests/testsuite/*.rs` (17), dioxus `interpreter/src/unified_bindings.rs` |
| A lifetime first in `dyn` bounds (`Box<dyn 'a + Display>`, `dyn 'static + for<'a> FnMut…`) | yes | 3: turborepo `turborepo-wax/src/{encode,rule}.rs`, dioxus `desktop/src/config.rs` |
| Attributes on function or closure parameters (`#[rustfmt::skip] #[cfg(…)] x11_visual: …`, `\|#[allow(unused_variables)] use_native: bool\|`) | yes | 2: alacritty `display/window.rs`, turborepo `turborepo-api-client/src/lib.rs` (a crate root) |
| `box` patterns | nightly (`box_patterns`) | 2: turborepo `turborepo-cache/src/multiplexer.rs`, `turborepo-lsp/src/lib.rs` (a crate root) |
| `where dyn Trait: Bound` | yes | 1: rustls `server/hs.rs` |
| A turbofish in a struct pattern (`let ErrorPayload::<Value> { … }`) | yes | 1: dioxus `fullstack/src/request.rs` |
| Documentation snippets with hidden `#` lines | no | 2: mdBook `guide/src/format/example.rs` and its copy under `tests/` |

The plan's later row "parse Rust snapshot macros with nested bracket token
trees" is this `str` row: the parser fails at the `!` because it reads `str`
as the primitive type, not because of the nested brackets.

These are grammar changes (patches to `grammars/rust` and a rebuilt `.wasm`
under the W2-S procedure), not small, contained fixes inside this chunk, so
they are listed for the manager. Fixing the parser is the only way to
recover the links that really depend on these files.

## Results

Main (`5ec4baa`) against this branch, every stored link of 19 Rust pins and
vercel/turborepo compared ([evidence](../../evidence/c-15/README.md)). After
main moved to `ef149b7` (C-11, TypeScript only; no Rust module file changed)
it was merged and alacritty, mdBook and rustls re-run: their Rust links are
identical to the pre-merge candidate.

- **Nothing lost or changed:** all 530,168 links definite on main keep their
  target on the 18 pins whose runs are deterministic and on turborepo; symbol
  keys, link sites, candidate sets and library rows are identical; no link
  changes outcome. On embassy (no placed failed file, no label on either
  build) 4 definite imports swap with 4 unresolved ones between cfg
  alternative sibling files; a second main run shows the same kind of swap
  (main's own run-to-run variation, see the evidence).
- **swc** does not finish on main (out of memory in TypeScript analysis
  after 46 minutes), as in C-10, so it has no like-for-like comparison.
- **Level 2 is unchanged by design.** Rust Level 2 in the regenerated plan:
  **38.88% → 38.88%** (same sites on both builds, so all-sites and
  like-for-like agree). Main's committed plan says 35.80% because its Rust
  section used release 0.1.0 results for turborepo and left out embassy;
  re-measured on main with this chunk's inputs it is 38.88%.

## For the manager

- Retire or re-scope `rust-taint`: at most 468 links (all macro-scope, C-12's
  area) can be released by any failed-file rule; the remaining 110,623 L2
  misses that keep the label are where a failed file could matter, and only
  parsing those files recovers them.
- Grammar work (table above): `str` as a macro name or path (18 files,
  including all 17 mdBook test modules), lifetime-first `dyn` bounds (3),
  attributes on parameters (2, one a crate root), `box` patterns (2,
  nightly, one a crate root), `where dyn Trait:` (1), turbofish in struct
  patterns (1).
- Refresh the SW-3 sample labels for the Rust taint stratum.
- Main resolves some imports in cfg-alternative sibling module files
  nondeterministically: two main runs of embassy differ on 7 definite
  imports (`use super::…` in `ppi/ppi.rs` and `dppi.rs`, `time_driver/tim.rs`
  and `lptim.rs`, and others).
- The remaining labels are deliberately conservative in two places that a
  later chunk could narrow with provenance: receiver gaps from lookups
  (an unresolved callee or chained method) and unresolved links with no
  other reason.

## Tests

`test/graph-rust-failed-scope.test.mjs` indexes small projects with the real
indexer and reads the stored links. For each case a link the failed file
could change stays withheld, and its twin resolves (or stays unresolved for
its own reason without naming the failed file): names, inline and `mod`
children; the whole file failing; a file below a failed module; globs and
re-exports; explicit paths beside an unseen impl; autoref and first-step
method calls with a failed file in the same crate, a dependency and an
unrelated crate; a call with no inherent candidate when the failed file is
in the type's crate or in a dependency; receivers typed from the failed file
(from alacritty's `display/window.rs`, which fails on attributes on a
parameter) against a closure parameter; textual macro scope; exported
macros; and parameter bindings beside a failed glob, a readable glob and an
outside import (from alacritty's `display/mod.rs:784`). The three label
cases fail on main; the others pin behaviour main already had.

`graph-rust-round7` "B3 S1": the expected reason for `A::from` with a failed
file only in a dependency is now `trait-dispatch` alone (the dependency
cannot declare an inherent `from` for `A`).

The Rust module version moves to 34 (C-12 uses 33), so stored graphs
re-index and drop the old labels.

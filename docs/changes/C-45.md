# C-45: What a one-file edit costs, and a session that can keep the rest

A one-file edit re-indexes through a new process every time. This chunk
measures where that time goes on six pins, says what a process that stays
alive could keep and what would invalidate it, and builds the
language-independent part: an in-process index session that keeps the
language modules and gives each module a place for proved state between
runs. No language module uses that place yet; the TypeScript and Rust
modules are being changed by other pull requests.

What each language does with one edited file:

- **TypeScript** builds every program again (24 on Hono, 50 on Vitest) and
  extracts every file of them again (650 and 3,815), whichever file changed.
  That is 83 to 89% of the edit.
- **Rust** analyses and resolves the whole module again: 82% of helix's
  body edit and 96% of dioxus's (413 of 429 s).
- **Go** re-decides only the edited file after a body edit (C-27), but
  still decodes every stored record and rebuilds its global lookups. A
  surface edit re-decides most files (545 of 559 on restic).
- **Every edit** hashes every source three times (two command inventories
  and the indexer's own reads; "files hashed" is three times the files) and
  decodes every stored record of the edited module.

## What a resident process could keep, and what invalidates it

| Stage | Keepable? | Invalidated by |
|---|---|---|
| Process start and module load (0.5–0.6 s) | Yes, by any process that stays alive | A different build (module versions) |
| Tree hash (0.3–2.7 s) | No: hashing every source on each request is the proof that nothing else changed (C-33 does not trust timestamps). The three passes could become one if the run took its snapshot from the command, which needs the ownership baseline handled (C-33 explains why the first capture is not shared now) | — |
| Stored inputs read (1.2–12.4 s) | Yes: decoded records and summaries, re-reading only the changed files | Any write to the store by anyone (the completion record), a module version or configuration change |
| Parse | Already only the edited file | — |
| TypeScript programs and extraction | Yes, as programs reused through the compiler's own `oldProgram`, re-extracting only files whose facts can change. Needs PR 50 (per-file TypeScript re-index) | A changed source in the program, tsconfig or compiler options, installed declarations (C-22's dependency inputs), the compiler version |
| Rust resolver setup | Yes: crate graph, name and macro tables. Needs PR 45 | A changed Cargo manifest or lockfile, a changed file set, a changed declaration that feeds the tables |
| Go global lookups and resolver input | Yes for a body edit; a surface edit changes them | Any change to a file's global fingerprint (C-27 already computes it) |
| Resolution of the edited files | Edit work | — |
| Store writes and completion | Edit work; the completion record is the proof for the next run | — |

## What stays alive today

- **The CLI** is a new process per command: it discovers the modules, opens
  the store, hashes the tree, runs the index and exits.
- **The MCP server** lives for the whole session, but each graph request
  runs `executeGraph` in a new worker thread (`src/mcp/graph-jobs.ts`,
  `graph-worker.ts`) with its own module graph, so it loads the modules
  again each time. Cancelling a job terminates the worker. It runs one
  graph job at a time.
- **Studio** does not index the graph.
- **Run ownership** is per index run, whichever process runs it: the run
  begins (`beginIndexRun`), its first commit writes the unfinished-run
  mark, every commit proves no other run wrote since (else
  `GraphIndexTakenOver`), and the completion record is written last. Nothing
  is held between runs. A worker terminated mid-run leaves the mark, and the
  next run, in any process, takes it over and repairs the store.

## What a one-file edit could cost

From the tables: "without start, load and stored inputs" is what a resident
process gains by keeping only the language-independent state. "Floor" also
keeps the per-language setup the edit does not change. It counts the tree
hash, parse and store writes, plus the share of analysis and resolution the
edit's files need. That share is counted for Go (files re-decided, of the
module's files). For TypeScript and Rust it is assumed to be the edited
file alone, which is a lower bound: a surface edit's dependents are not
counted.

| Pin | Edit | Now CPU s | Without start, load and stored inputs | Floor (estimate) |
|---|---|--:|--:|--:|
| honojs/hono | body | 50.9 | 47.0 | 3.1 |
| honojs/hono | surface | 46.2 | 42.5 | 1.6 |
| vitest-dev/vitest | body | 122.6 | 116.2 | 5.0 |
| vitest-dev/vitest | surface | 128.3 | 121.7 | 4.9 |
| restic/restic | body | 5.2 | 3.5 | 0.9 |
| restic/restic | surface | 13.8 | 9.5 | 9.0 |
| cli/cli | body | 13.0 | 7.6 | 1.8 |
| cli/cli | surface | 33.8 | 20.8 | 13.0 |
| helix-editor/helix | body | 54.6 | 48.1 | 2.7 |
| helix-editor/helix | surface | 51.8 | 45.4 | 2.5 |
| DioxusLabs/dioxus | body | 429.1 | 417.6 | 3.9 |
| DioxusLabs/dioxus | surface | 446.4 | 434.2 | 3.6 |

So the language-independent state is worth 1.7 to 13.0 s per edit. The rest
of the gap is in the TypeScript and Rust modules rebuilding everything per
edit. A resident process is the place to keep that state, but only those
modules can keep it. A Go surface edit is close to its floor already.

## Design

**Where the state lives.** In a long-lived process that runs index runs
in-process: first the MCP server, then Studio. The MCP server would keep
one graph worker for its session, holding an `IndexSession`, instead of a
new worker per request. A job is cancelled through the abort signal that
`executeGraph` already takes, not by terminating the worker; terminating it
remains the fallback and only drops the session. A separate index daemon
that the CLI, MCP and Studio all talk to would also let the plain CLI
benefit. But it adds a process to start, find and stop, and an IPC
protocol, and it brings nothing that one process per tool cannot keep. It
is not proposed now.

**Coexistence.** The session holds no store connection or lock between
runs. Every run is an ordinary index run with its own ownership checks, so
a second process, a plain `graph index` and a resident session can
interleave exactly as two CLI runs do today. The rules stand: one owner per
run, every store after any run equal to a cold index row for row, and a
killed process leaving a store the next run repairs.

**Learning what changed.** Hash on request against the snapshot, as now.
No file watcher is needed for correctness. A watcher may only be a hint to
start a run early, or to hash the hinted files first.

**Proving kept state still valid.** Three keys, all of which must hold:

1. **The store** is as the session's last completed run left it: its
   completion record (fingerprint) is the one that run wrote. Every graph
   write by anyone deletes the record (C-22, C-27 triggers). A record
   written by another completed run proves the store equals a cold index
   of the inputs it records. So a store changed by anyone else drops
   everything.
2. **The scope** is unchanged: project root, store path, project id, module
   ids, versions and claims, and the index settings (toolchains).
3. **The module's own key** covers every input the value was computed from:
   content hashes of the files and context files, dependency inputs,
   compiler options. The module computes it; the session only compares it.

A run that does not complete keeps nothing it set, and drops what was kept.

**Memory.** Each module keeps at most a few named values (four by
default); setting another drops the oldest. A process drops a whole session
when it is idle or under memory pressure; nothing is lost but time. Kept
TypeScript programs can be large: C-40 measured a 2.7 GB program on
microsoft/TypeScript. So a module should keep a program only below a size
it can afford, and say so when it does not.

**Waits on other pull requests.** Keeping TypeScript programs and
re-extracting only changed files belongs with PR 50 (TypeScript per-file
re-index). Keeping the Rust resolver setup belongs with PR 45. Both would
use the hook built here (`context.kept`).

## What was built

- **`src/graph/session.ts`: `IndexSession`.** It discovers the modules once
  and keeps state per module and version. A value is returned only under
  the validity key it was kept with. Values set during a run are staged,
  and kept only if the run writes its completion record. A run that does
  not complete drops everything. Everything is dropped when the completion
  record found at the start of a run, or the one its ownership baseline
  reads, or the scope, is not what the session last recorded (review,
  below).
- **`executeGraph`** takes `session` (a process that indexes more than once
  passes the same one).
- **`indexProject`** passes each module its `kept` state.
- **`ProjectAnalysisContext` and `ResolutionContext`** gain an optional
  `kept`.
- **A session with an injected registry** is treated like an injected
  registry: no verified shortcut.
- **No production module uses the kept state yet.** Go was not wired.
  Keeping its decoded resolver input needs a proof that the C-27 global
  fingerprints cover the global lookups, and the indexer writes analysed
  records before resolution, so a kept input would have to be patched with
  them. On cli/cli that would save up to 4.8 s of stored-input reads on a
  body edit. It is left with these numbers.

`test/graph-index-session.test.mjs` uses a synthetic module that keeps a
name-to-symbol map between runs and resolves its links through it, so a
stale map would show as a difference from a cold index:

- **Reuse:** the map is reused across a content edit and rebuilt when the
  symbols change; every store equals a cold index.
- **Drops:** a module version change, a direct write by another connection,
  and a failed run that set a wrong value each drop what was kept; the next
  store equals a cold index.
- **No edit:** in a production session an unchanged second index runs no
  index, parses nothing, hashes each source once and executes at most 20
  statements.
- **Production equality:** five seeded TypeScript and Go edits through one
  production session each equal a cold index.

The kill, race and re-index equality tests are unchanged and pass.

### Review (first round)

- **B1, a stale "store unchanged" proof.** The completion record was read
  when the command began, before the run's ownership baseline. A run by
  another process that started and completed between the two was seen by
  neither check: the session kept everything. Now the run's baseline
  (`beginIndexRun`) reads the completion record in the same snapshot as its
  data version and mark (`baselineCommandState`), and the session run is
  confirmed against it (`SessionRun.confirm`). Nothing kept is readable
  before that. A run by another process after the baseline is caught by
  the run's own ownership checks, as for any index run. The reviewer's
  race is a test: another process's complete `graph index` runs inside the
  inventory event just before the run begins (`spawnSync`, no sleeps); the
  session drops and the stores equal a cold index.
- **The kept contract.** A confirmed run takes what was kept; only what it
  `set`s again is kept after it. A module must treat a kept value as
  immutable or `set` the value it changed: a value changed in place and not
  set again is forgotten, and a run that fails keeps nothing, so a
  violation never reaches a later run. Kept state is bounded by count
  (`maxValuesPerModule`), not by bytes; an embedder must bound the memory
  of its process (the MCP server ends a worker above its resting bound,
  C-48).
- **Each drop rule has a test that fails without it** (checked by removing
  each from the built code): the baseline comparison (the race test), the
  scope check (trust source-only → trusted → revoked, a drop each time),
  taking kept state at the baseline (the in-place change, the failed run
  and the race), and the drop when a run is abandoned (the failed run).

## Things to know

- **Hashing three times:** every edit hashes every source three times, on
  Vitest 7,926 file reads for 2,642 files. One pass is the proof; two are
  the price of not sharing the command's capture with the run (C-33).
- **Stored-input reads:** they cost more than the Go analysis itself on a
  cli/cli body edit (4.8 s against 2.8 s).
- **Hono's body edit (measured on main at `60d4f2b`, 22 November 2026) writes
  18 files and executes 17,659 statements (the review measured 17,545 on a
  later main), against
  2 files and 1,425 for its surface edit.** The body edit changes inferred
  facts in other files of the program. Not investigated further here.

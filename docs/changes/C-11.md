# C-11 TypeScript and JavaScript library links

The TypeScript graph now names the outside library at existing import, call,
heritage and type-reference sites. `graph uses es Map.prototype.delete` finds
uses of the method behind Vitest's `openingSessions.delete(sessionId)`.
`graph uses fs readFileSync` accepts calls through either `node:fs` or `fs`.

The checker supplies the declaring interface, class or namespace when its
declaration is available. Compiler declarations use `typescript-lib` / `es`
for ECMAScript and `dom` / `dom` for the web platform, including worker libs.
Instance members use `Owner.prototype.member` (for example
`Map.prototype.delete`), static members use `Owner.member` and globals use
their declared names. `document.querySelector()` names
`ParentNode.prototype.querySelector` because `Document` inherits it. A
checked-in Node type package uses `node` with the
declaring builtin module or `globals`. Other captured `@types` packages name
the package they describe, and declaration-only vendored packages can name
their manifest package. The root package and packages linked from the
checkout retain project identities, including those named `@types/*`.
The graph follows inherited members, typed return
values and re-exports using the selected declaration. A mixed union can show
checkout and library candidates together. Checkout declarations and local
augmentations still participate in the existing declaration resolution.

Without declaration files, a literal import can name a written export when
its package route is proven. A bare npm name needs a dependency in the
importer's manifest chain up through its workspace root. An explicit
`npm:` or `jsr:` route supplies its own registry evidence. Namespace
selections name the export, as does a direct selection from a proven
CommonJS module object. Node's builtin default export
exposes its CommonJS exports under Node's ESM convention. For example,
`fs.readFileSync()` can identify `readFileSync` through a default import of
`node:fs`. [Node.js built-in modules](https://nodejs.org/api/esm.html#built-in-modules)

An explicit `node:` import selects its builtin. A bare builtin with a
declared npm dependency retains the Node and npm routes as candidates.
Bare unresolved framework aliases and virtual module names keep their
existing unresolved reason in the absence of package-route evidence.

`import { z } from "zod"` proves the export `z`, while `z.string()`
identifies the unit `zod` at Level 1. The member declaration is unknown. A
package subpath prefixes a written export with `subpath:`, for example
`@scope/pkg` and `client:open`. Checkout module and `paths` resolution take
precedence. An unambiguous exact pin in the manifest that owns the import
supplies the version. A checker-selected declaration can arrive through
another package or a typed return, so it carries no inferred version.
If a workspace member's manifest is unreadable, a missing npm specifier in
that workspace can name the unreadable package. The link stays unresolved.

Unconfigured JavaScript uses `lib.esnext.full.d.ts`, the existing ESNext
compiler default. It includes ECMAScript, DOM, Worker `importScripts`, Script
Host, DOM iterable and DOM async iterable declarations.
Type packages need explicit captured declarations, such as configured local
type roots. If the importer declares `@types/node` or the compiler expects
Node through its types options or references, missing declarations can
leave a bundled global open. Node 24's documented globals supply the list
of possible overlaps. It includes timers, console, Web APIs such as
`fetch`, `Request`, `AbortController` and `URL`, and the other documented
global names in `global-types.ts`. The graph can name documented console
methods and timers under `console` and `timers`, and documented global
names under `globals`. An overlapping member without specific Node
evidence stays unresolved. A missing configured or referenced global
types package with an unknown surface also leaves DOM targets open.
This applies when the checker also finds a checkout declaration in the
same merged member set.
Array, Map, Promise and JSON retain their ECMAScript proof. [Node.js globals](https://nodejs.org/docs/latest-v24.x/api/globals.html)

Missing configuration, failed input, unverified receivers and
ambiguous ownership can leave links unresolved. The graph still excludes
installed `node_modules`; it performs no dependency installation or lookup
outside the snapshot.

A `typeof` query can use a type-only import's written binding, and a
namespace-qualified JSX tag can identify an export selected from a module
object. A qualified `import =` can name a module's written export. Ambient
class heritage can identify a type-only import. Version provenance
currently uses exact manifest pins.

The review revision selects Deno's nearest captured `deno.json` or
`deno.jsonc` map before choosing a package ecosystem. Inline imports and
scopes, and a configured map captured as `import_map.json`, `import-map.json`,
`importMap.json` or the corresponding supported JSONC names, can identify
Node, npm, JSR and relative checkout routes. The checker resolves an alias to
its mapped file while import diagnostics still refer to the written name.
When named Deno configurations such as `deno.precompile.json` and
`deno.react-jsx.json` share an owning directory, a definite route requires
agreement across the captured choices. Unavailable, conflicting and remote
URL routes stay unresolved. Deno registry routes carry no inferred version.

CommonJS object patterns use the written property key. Rest and nested
extraction can establish the unit alone. A defaulted binding use needs
independent proof of the resulting value. Direct same-file assignment,
deletion or reflective writes to the module object withhold the affected
member name. Explicit const aliases of the object share this check.
Interprocedural writes remain outside the proof, as in
[C-7](C-7.md).

Declaration-only packages in the checkout need an installed location or an
external dependency declaration from the importer. Checked-in `@types/*`
declarations outside `node_modules` retain their checkout identity.
Captured external top-level exports use import-binding evidence. A paths
mapping and a same-named manifest can identify a checkout
declaration. A literal outside binding with a known module route can retain
its source-proved identity when an unrelated declaration is unreadable.
Explicit `node:` routes also retain this evidence under an incomplete
compiler configuration when the captured project gives no conflicting
route.

TypeScript module version 28 triggers re-indexing. The schema and existing
symbol keys, listings and search are unchanged. Release 0.1.0 coverage still
uses its historical reconstruction. The measure credits the stored targets
directly for TypeScript module 23 onward.

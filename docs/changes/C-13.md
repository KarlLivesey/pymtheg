# C-13: TypeScript analysis on very large checkouts, compiler exceptions, and manifests with a byte-order mark

Three problems in the TypeScript module each lost whole repositories or
packages:

1. swc-project/swc ran Node out of its default heap.
2. The TypeScript compiler's internal assertion failed every TS and JS file
   of microsoft/TypeScript.
3. A `package.json` that starts with a UTF-8 byte-order mark failed every
   file of its package.

The causes are fixed in `src/graph/languages/typescript/index.ts` and
`project.ts`. On the pins that already finished, every stored row is
unchanged apart from the module version. The one exception is Vite, whose
byte-order-mark package is now read. Neither swc nor microsoft/TypeScript
finishes the sweep yet, for causes outside these files; see "Outcomes".
Measurements are in [`evidence/c-13/`](../../evidence/c-13/README.md).

## What ran out of memory on swc

Measured with a TypeScript-only probe and heap snapshots on the dev server
(`evidence/c-13/tools/`).

- **One program over 160 MB of source.** swc has 50,187 TS and JS files.
  50,117 of them, mostly test fixtures and benchmark inputs, are in no
  tsconfig or jsconfig, so they form one inferred program: 159,816,112
  characters. Parsing and binding that program alone holds about 4.2 GB of
  live heap, which is Node's whole default limit. The largest inferred group
  on the other pins measured is 48.1 million characters
  (microsoft/TypeScript); excalidraw, vitest, trpc, astro, hono,
  redux-toolkit and vite stay under 5 million per program.
- **Splitting the inferred program cannot keep every link.** Files with no
  config share one global scope: a script's top-level names are visible to
  every other loose file, and lib interfaces can be augmented from any of
  them. A prototype split that joins files by imports, references, ambient
  modules and shared global names (`tools/components.mjs`) still leaves one
  component of 44,933 of swc's 50,117 loose files. The names alone do it:
  `a`, `foo`, `b`, `x`, `console`. A further 174 files augment lib globals
  such as `Array`, `File` or `Generator` and join everything. Main's links
  for these files depend on that shared scope, so no split can be identical.
- **Every rebuild kept the previous program alive.** A program is rebuilt
  without a file the compiler throws on. Two things kept the old programs
  reachable:
  - `ts.createProgram` replaces the host's `realpath` with a wrapper over
    the new program. Its completion hook restores `fileExists`,
    `directoryExists` and `getDirectories`, but not `realpath`. Every
    program built on the same host wrapped the previous wrapper.
  - The caught exception's stack frames held the old checker during the
    rebuild.

  On a 2,022-file fixture with 20 failing files, live heap rose from 607 MB
  to 2,499 MB, about 100 MB per rebuild. With the fix it stays at 609 MB.
  The same retention ran microsoft/TypeScript out of heap once its
  assertion no longer stopped the module.

## What changed

- **A program budget.** One program is given at most 50,000,000
  characters of the captured source it owns (`MAX_PROGRAM_SOURCE` in
  `project.ts`). A project with more leaves out its largest files, then by
  path, until the rest fits. Each one left out is a failed file with the
  reason:

  > Not analysed: its TypeScript project (the files no tsconfig or jsconfig
  > includes) holds 159,816,112 characters of source, more than one
  > compiler program is given (50,000,000); its largest files, this one
  > (14,102,710 characters) among them, are left out until the rest fits

  Such a file is absent from every program, like any failed file. Its
  global names count as a failed file's names, so an unresolved name only
  it declares is `invalid-code`, never an ordinary miss. Every other link
  of its program carries `assumes: ["no-unseen-declarations"]`, which the
  W2-D rule defines as unverified. The number is fixed, so the outcome
  depends only on the snapshot. No pin that already finished comes near it.

  The bound also holds for what a program actually loads. A program counts
  every checkout file the compiler asks it for, roots and imported files
  alike, in the order the compiler asks. A file that would take it past
  the bound is not loaded in that program. There it is absent, an unseen
  failed file whose global names are recorded, and failed with the reason
  if it is one of that program's own roots. Its own project's program may
  still read it. That order is the compiler's, fixed by the snapshot, so
  this is deterministic too. Installed declarations (C-20) are not counted
  here; they have their own budget.

  **Unavailable, not invalid.** A file left out by the budget, or failed by
  a compiler exception, has no syntax error. Links that reach it are
  `target-unavailable`, as for a file whose parse or bind failed, not
  `invalid-code`, which means a syntax error. In each case the file is
  readable code that this analysis could not take in. Its names still count
  as unread, so an unresolved name only it declares is failed.
- **Compiler exceptions fail files, not the module.** An exception from
  the compiler that is not a stack limit fails one file, with the
  compiler's message as the reason (`The TypeScript compiler failed while
  analysing this file: Debug Failure. False expression.`). The program is
  then rebuilt without that file. This covers binding, the syntax phase,
  warm-up and extraction:
  - **Which file.** The checker records the last node the module asked
    about, and the exception is charged to that node's file. That is the
    file being analysed, unless a whole-program walk was reading another
    file's declaration: taint.ts reads every file's declarations at a
    file's first lookup. Then that other file fails and the current file
    is extracted again.
  - **Binding.** An exception while binding is charged to the file the
    binder left unfinished. Failing that, the root list is bisected to the
    first root whose addition makes the build throw.
  - **Warm-up after a rebuild.** A rebuild for this reason resumes the
    warm-up with the files no earlier checker of the session warmed.
    Repeating it from the start would cost a full warm-up per failing
    file. Rebuilds for stack limits still warm from the start.
  - **Exceptions inside taint.ts's walk.** Five lookups in the walk no
    longer read an exception as "no symbol": a stack limit leaves the walk
    unknown, as at its budget, and a compiler assertion is charged to the
    file being read, like any other. Known limit, unchanged from main: the
    alias-chain lookups (`aliasChain`, also called from extraction) and the
    contextual-type rule still catch an exception and carry on as if there
    were no answer. In injected-fault runs over 18 fixtures this never
    produced a definite link; the affected links stay unresolved, and some
    read `external` or `no-symbol` where `invalid-code` would be right.
  - **A file dropped late.** If it was extracted earlier in the run, it
    still fails everywhere. Its own project is extracted again from its
    first file, so files extracted before and after the drop agree. Each
    round needs a further drop, so the cap bounds the rounds. If the file
    belongs to an earlier project, its published result is replaced by the
    failed result, and published links that target it become
    `target-unavailable`.
  - **A cap.** After 100 such files in one program, its remaining files fail
    with that reason. The cap counts every contained exception the same
    way: binding, the syntax phase, warm-up, extraction and the taint walk.

  These files are failed files under the W2-D rule: absent from later
  programs, their global names known, and the other links of the program
  flagged. They are not cached as content failures, so the next index tries
  them again.
- **Programs are released on rebuild.** The host's own `realpath` is put
  back before every build, and exceptions become plain data before the
  rebuild. A rebuilt session drops its old program before building the
  next.
- **taint.ts's whole-program walk is bounded.** In a program with a failed
  file, taint.ts reads every file's declarations to find which links depend
  on the failed files. Three changes:
  - **Seeds come from declarations only.** The seed walk asked the checker
    for the symbol of every named node, member accesses in function bodies
    included. On the 8.9 KB conformance test
    `crossProductUnionIntersectionRepeatedPropDeclarationsNoOOM1.ts`, one
    such query (`newShapePartial.props?.w`, on a cross-product of unions and
    intersections) exhausted the heap. Aliases are what the seed walk looks
    for, and the binder puts each alias on its declaration, so the walk now
    reads the binder's symbol (or a CommonJS export assignment's). The file
    now takes 2,256 steps.
  - **Cause sets are shared until they grow.** The fixpoint handed every
    dependent its own copy of a symbol's failed-file causes. On
    microsoft/TypeScript, with about 12,000 failed files, the copies
    exhausted the heap: 13,135 strongly and 10,509 weakly tainted symbols
    after 20,000 iterations, growing 1 GB. A set is now shared and copied
    only before it grows; the contents are the same. Adding an edge no
    longer copies the edge list.
  - **A deterministic budget** (`TAINT_BUDGET`, 8,000,000 steps): a node
    visited, an edge followed, a cause stored, compared or copied. A walk
    that reaches it stops. Its taint is unknown, so every link of a file
    extracted with that checker is unresolved with reason
    `taint-budget-exhausted`, with no target or library fact. The
    exceptions are structural links, and links that bind a failed file
    directly: an import, `import * as`, `import =` or `require` binding,
    and the names reached through it (`value()`, `b.value()`). Those are
    still `invalid-code` with that file as the cause, computed for the one
    binding asked about. Later checkers of the same session skip the walk
    and are treated the same way; a rebuild per failing file had repeated it
    each time. Exhaustion is recorded before any rebuild, so it is
    inherited whether the extraction that met it succeeded or threw. Pins
    that walk use at most 826,220 steps (vitest), about a tenth of the
    budget.
- **Byte-order marks in package manifests.** `package.json` is read with
  a leading U+FEFF removed. TypeScript's own readers for tsconfig and
  jsconfig, and for package.json during module resolution, already ignore
  it, and the pnpm workspace reader already removed it. Source text and
  offsets are unchanged: a source file's mark stays in its stored text.
- The module version moves from 37 on main to 38, so stores index again.

## Tests

`test/graph-typescript-large.test.mjs`:

- **A compiler assertion fails only the file it was analysing.** The
  fixture is reduced from microsoft/TypeScript's `tests/cases`: script
  files declare one global enum in two files, and a third reads a member
  whose initialiser indexes a member of the other declaration (`a.ts`:
  `enum E { A = E["B"] }`, `b.ts`: `enum E { B = 1 }`, `c.ts`:
  `const v = { x: E.A };`). Only `c.ts` fails, with the compiler's message,
  on two consecutive indexes. Unrelated and imported links still resolve.
  On main every file fails.
- **Rebuilds release earlier programs.** With 8 failing files, the count of
  live checker types (`v8.queryObjects`, which collects first) when the 9th
  program is built is less than twice the count at the 2nd. It fails with
  the `realpath` reset removed: the count grows by one program per rebuild.
- **A global that only a failed file declares** is `invalid-code`, never a
  guess.
- **The byte-order mark.** A manifest from Vite's
  `playground/resolve/utf8-bom-package` is read, and its package's links
  resolve. On main every file in the package fails. A source file with a
  mark keeps its text and offsets. A mark anywhere but the start still
  makes the manifest unreadable.
- **The taint budget.** A program with a failed file, through the test hook
  `taintLimits`:
  - within the budget, a call resolves as before and a link into the
    failed file stays `invalid-code`;
  - with the walk stopped at its first step, the program's links are
    unresolved `taint-budget-exhausted` and never resolved, the failed
    link keeps `invalid-code`, and a program with no failed file is
    unaffected.

  Treating a stopped walk as "no taint" resolves the call, and the test
  catches that.
- **The budget.** Through a test hook (`programBudget`), a project over the
  budget leaves out its largest file with the reason. A name only that file
  declares is `invalid-code`, and other links are flagged. A config's
  project under the budget is untouched, and a project within it is
  analysed whole.

## Outcomes

- **The BOM package.** Read; see Vite above.
- **microsoft/TypeScript.**
  - **On main.** The assertion fails all 27,194 TS and JS files, and only
    Go is analysed. In this session the cold index completed after about
    34 minutes, but the run met the 60-minute limit during the repeat index
    and queries (wall limit, 3,610 s).
  - **With this change.** It still does not finish: the sweep meets the
    60-minute limit (3,611 s), where main finishes in 2,246 s.
  - **Where it went, step by step.**
    1. The assertion is contained: 28 files fail with the compiler's
       message.
    2. taint.ts then exhausted the heap twice. First on the memory-stress
       test above, which with any failed file beside it exhausts the heap
       on main too (100 s); fixed. Then in the fixpoint's cause copies;
       fixed.
    3. The walk now reaches the budget, deterministically, and later
       rebuilds no longer repeat it. Memory stays near 2.8 GB of RSS.
  - **Where the time now goes.** Extraction reaches
    `tsc/testdata/tests/cases/compiler/unreachableFlowAfterThrowingForHead1.ts`
    and does not return:
    - the file is 273 bytes, a `for` head of throwing, immediately invoked
      (generator) functions;
    - TypeScript 5.9's own `getPreEmitDiagnostics` overflows the stack on
      it, in `isReachableFlowNodeWorker`;
    - in the module, the one checker call on it had not returned after
      590 s, alone and on main as well;
    - main never reaches it, because the assertion stops its module first.

    No count bounds a single compiler call, so it is not contained.
  - **Also slow.** The walk spends about 5 minutes on
    `tsc/testdata/baselines/reference/compiler/manyConstExports(target=es2015).js`.
    Its 5,000-link `exports.x =` chain costs the checker time per query,
    not walk steps: 95,315 steps and 340 MB alone.
  - **The checklist row** moves from finished (Go only, 94.21% Level 2 over
    485,580 links) to open.
- **swc-project/swc.**
  - **The sweep.** With both builds, swc meets the 60-minute limit while
    Rust analysis is still running (`graph analyze rust: 0/1523` at
    3,601 s on this loaded server). It never reaches TypeScript.
  - **TypeScript alone on main.** It runs out of the default heap after
    246 s, while building the no-config program. This was measured on
    `8ca29ac`; program construction is the same on main.
  - **TypeScript alone with this change.** The build and warm-up fit:

    growth across rebuilds. Neither makes swc's TypeScript fit; the
    extraction of one 50,000-file program does not fit either.

## Known limits

- **Narrowed candidate sets.** The budget leaves out files rather than
  splitting a project. A left-out file is an unread file under the W2-D
  rule. A name it declares that the program resolves elsewhere is flagged
  `no-unseen-declarations`, not turned into a candidate set. That limit
  already applies to every failed file.
- **Characters, not memory.** The budget counts characters, which bounds
  parsing and binding. Extraction memory grows with the number of files and
  what the checker computes for them: swc's 50,028 remaining files need more
  than 13.9 GB. A file-count bound, or extraction that holds less, would be
  needed. It was not calibrated here, because swc's Rust phase alone already
  outlasts the sweep's allowance.
- **The checker's state after a contained exception.** A contained
  exception rebuilds the program. Files extracted before it saw the failed
  file. Their links into it are unresolved, because a failed file has no
  symbols.
- **The cap.** After 100 compiler-failing files, a program's remaining
  files fail. The number bounds the time spent rebuilding.

## Not built

- **A compiler call that does not return.** One checker call on
  `unreachableFlowAfterThrowingForHead1.ts` does not finish in TypeScript
  5.9. Only a separate process with a deadline could contain it, and
  correctness must not depend on time, so it was not built. This is what
  keeps microsoft/TypeScript from finishing.
- **taint.ts's walk scope.** Even bounded, the walk reads every declaration
  of a program with a failed file. Reading only what a file's links reach
  would be cheaper.
- **swc and the 60-minute allowance.**
  - Rust analysis of swc's 1,523 Rust files alone outlasts the allowance on
    this server.
  - The TypeScript extraction of swc's no-config files is long too.
  - No speed work is in this chunk.
- **Splitting the no-config program.** Splitting by import components would
  narrow candidate sets that span loose scripts (see above). A semantics
  for unrelated loose scripts, such as one program per test fixture
  directory, is a product decision.
- **A self-reported 7,974 links for Vite** (C-11's builder) is now 10,558:
  the BOM manifest blocked C-11's workspace boundary for all of Vite.

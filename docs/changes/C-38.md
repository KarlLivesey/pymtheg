# C-38: TypeScript re-index proportional to the edit

A one-file TypeScript edit that other files cannot see now extracts only
the edited file, in the projects that own it, and keeps every other stored
result. A comment or a body edit on Hono, tRPC, Vite and Excalidraw takes
this path, and so does a body edit in a project that has broken
configurations or deliberately invalid fixtures elsewhere. An edit other
files can see, such as a new export, still runs the full analysis. Every
re-index still leaves the store equal, row for row, to a cold index of the
same tree. TypeScript module version 44 → 45, so stores index again once.

## Where an edit's time went

On main a one-line body edit rebuilt every TypeScript project. On Hono that
is 24 programs, 650 file extractions for 460 files, and 53.3 CPU seconds. A
CPU profile of that edit, main thread, 28.9 s sampled:

| Part | Seconds |
| --- | ---: |
| TypeScript analysis | 20.5 |
| of which: building 24 programs (parse and module resolution) | 3.1 |
| of which: the warm-up of each program | 5.3 |
| of which: extracting every file | 10.6 |
| resolution | 2.1 |
| store, inventory and start | about 6 |

The compiler has no cheap per-file checker, and the module warms each
program in program order. The warm-up is what makes one file's answers
independent of which files were extracted before (W2-D). So the honest
saving is not a faster checker. It is building only the programs that own
the edited file, extracting only that file, and proving that no other
file's result can change.

## What a scoped re-index does

The indexer offers the module the edited file's previous record when the
store's completion record (C-27) says the last owned run of this module
version finished. The module then:

1. checks that exactly one file was edited (failed files the core retries
   on every index, with unchanged content, do not count; see below), and
   that its previous result can be stood on;
2. compares the file's syntactic surface, old text against new;
3. builds the projects that own the file, as a full analysis would (same
   host, same warm-up), and extracts only that file there;
4. in every program that loaded the file (recorded as `loadedBy` on its
   stored result), builds the program with the old text and with the new,
   and compares the checker surface;
5. re-keys other files' stored target facts that point into the file: its
   declarations keep their identities, and positions move (the store's
   symbol IDs are identity and ordinal);
6. returns the edited file's result, the re-keyed files and the retried
   failures as a C-27 scoped result. Only those files' decisions are
   replaced.

No fingerprint is stored. The old text is in the store, so both texts are
compared in the same run, in programs built the same way. A printed type
can depend on the order the compiler created types in, which differs
between runs and makes a stored fingerprint unreliable.

## What is compared

| Other files' analysis reads | What proves it unchanged |
|---|---|
| Declarations, signatures, written types, aliases, interfaces, enums, initialisers outside functions, exports and re-exports, imports | The syntactic surface: every token outside function bodies, comments left out and JSDoc kept, old against new. In a JavaScript file, every token and JSDoc of every body too. |
| Inferred types (a body edit can change a return type) | The checker surface, in a program with each text and in every program that loads the file. For each declaration outside bodies without a written type, it records the printed inferred type and every declaration that type reaches: its symbol and alias, type arguments, union and intersection members, signatures, base types, and the members of anonymous types and of types the file declares. A named declaration inside a body, a printed type cut at a million characters, or the step budget means the full analysis. (With no truncation the printer elides only cycles, which the reach walk follows.) |
| Whole-program scans of bodies without the checker: object producers' returned values, writes and initialisers; module references (`require`, `import()`, import types); side-effect imports (test setups); the hashbang; the CommonJS test | Recorded from inside bodies in the syntactic surface. |
| Which programs exist and what they load | Configs, manifests and installed declarations unchanged (otherwise the indexer offers no previous facts); the file's module references unchanged; its stored `loadedBy`. |
| The file's own positions in other files' target facts | Re-keyed when the file's symbols pair up by identity and order; otherwise the full analysis. |
| Failed files and the failed-file walk (taint) | A program the scoped path relies on may ask only for a "quiet" failed file: its own syntax errors, no global name, read by no stored link other than an import with no bindings. Then the walk is empty before and after. |
| Fresh rename names, chosen from every text | Recomputed with the old text: must be equal. |

## When the full analysis runs

The module counts each reason (`statistics.declined`):

- more than one edited file, a file added, removed or renamed;
- a changed config, manifest, lockfile or installed declaration;
- an unfinished run, a missing completion record, a version change;
- the edited file is a declaration file, has `declare global` or `declare
  module`, is a script, or is renamed for the compiler;
- a changed syntactic or checker surface, or symbols that do not pair up;
- a stored result with a compiler limit, or a failed file other than a
  quiet one, in a program the scoped path relies on;
- the edited file's extraction reads object producers, before or after;
- a drop, rebuild, rename, assumption pass or exception in the attempt.

### What a function body can contribute to another file's links

The C-38 review found three ways an edit inside a body changed another
file's links while both surfaces stayed equal. Two rules close the
families they belong to, rather than the three cases.

- **JavaScript: every token of a body is compared.** The JavaScript binder
  declares members from statements inside bodies. JSDoc on any statement
  can type them. Rather than track which statements the binder treats as
  declarations, a JavaScript file's syntactic surface includes every token
  and every JSDoc of its bodies. Any token change in a JavaScript body takes
  the full path; comment-only edits stay scoped.
- **An inferred type is compared by what it reaches, not only as printed.**
  A printed name does not prove the declaration behind it is the same:
  same-named locals, a local class whose members changed, `Item` from two
  modules. So the checker surface also records every declaration the type
  reaches (see "What is compared").
  - A named declaration inside a body of the edited file (class,
    interface, enum, type alias, function) means the full path: it can
    change while its name prints the same.
  - An anonymous one (an object or type literal, a function or arrow
    expression, their members and parameters) is recorded by its place, and
    its members and signatures are compared recursively.
  - Elision. The surface prints with no truncation. Then the compiler
    elides only a cycle: a type already printed further out comes back as
    `any`, and the reach walk still follows it. Past a million characters
    the text is cut and ends in `...`, which means the full path.
    - A first version declined on any `...` in the printed text. That
      caught rest parameters and spread bindings (`(...args: T) => void`,
      `({ label, ...rest })`). Excalidraw's `packages/common/src/utils.ts`
      (`debounce`, `throttleRAF`) and most of its components then took the
      full path on every edit, the measured case included. The edit
      measurements found it, and a test covers it.
    - The same file then declined twice more on anonymous parts in its
      bodies: an expando member (`ret.flush = () => …`), then a function
      type inside `ret as typeof func & { clear: () => void }`. Both are
      now compared as anonymous parts (the audit's two expando and
      written-type rows).

The audit below lists every way a body can contribute to what another file
links to.

| How a body can contribute | Rule |
|---|---|
| Inferred return type of a function declared outside bodies | Compared: printed type and the declarations it reaches. |
| Inferred type of an exported or module-level variable or property initialised from a body (an IIFE, a callback's result, a generic's inferred argument) | Compared, as above, for the variable or property. |
| A named class, interface, enum, type alias or function declared in a body and reached by an inferred type (a returned local class, a mixin, a generic argument) | Declines. |
| An object literal, type literal, arrow or function expression in a body reached by an inferred type | Compared by its place and, recursively, its members and signatures. Their own positions are re-keyed. |
| Narrowing or flow analysis inside a body changing an inferred type | Compared: it changes the inferred type or what it reaches. |
| Returned values, writes, initialisers and module references read by whole-program scans (object producers, test setups, module references) | Compared: recorded from bodies in the syntactic surface. Any edit to a return expression takes the full path. |
| JavaScript `this.x =` in constructors, methods, nested functions or arrows; `X.prototype.m =`; expando properties; `exports.x =`, `module.exports =`; `Object.defineProperty` | Compared: every token of a JavaScript body. |
| JSDoc in a JavaScript body (`@type`, `@typedef`, `@param` on inner functions, `@this`, `@returns`) | Compared: every JSDoc of a JavaScript body. |
| JSDoc in a TypeScript body | Cannot affect other files: TypeScript files take no types from JSDoc. A JSDoc `@internal` (C-25's stripped declarations) belongs to a declaration outside bodies, whose JSDoc is compared. |
| `this.x =` in a TypeScript class body | Cannot declare a member: TypeScript classes declare members outside bodies, which are compared. |
| An expando property in TypeScript | Compared: TypeScript accepts an expando only beside its declaration, in the same scope. For a module-level function that is outside bodies. On an arrow or function expression in a body (excalidraw's `debounce`) it is a member of an anonymous type: recorded by place, its type compared. On a named function declared in a body, that function declines when reached. |
| A type written in a body (`x as T & { clear: () => void }`, an annotation on a local) reached by an inferred type | Anonymous parts (type literals and their members, function and constructor types, mapped types, signatures, their parameters and type parameters) are compared by place and recursively. A named one (a local type alias or interface) declines. |
| `declare global`, `declare module`, augmentation in a body | Declines: no syntactic surface at all. |
| A body's object-producer lookups filling the shared memo | Declines when the edited file makes any (see below). |
| A body's statements changing union order by type creation | Not compared. The warm-up runs in program order as in a full analysis (W2-D). The reviewer's case `union-order-by-creation` and the random edits found no difference. This is the remaining assumption, stated also under "Order". |

Return-expression edits always take the full path, because returns are
recorded in the syntactic surface. The weighted random mix below inserts
statements and comments and never edits a return expression. So these runs
do not measure the share of real edits a return-expression change is.

### Order: the lesson from C-36

C-36's review found that a memo whose value depends on which lookup ran
first breaks a scoped path even when the fingerprint is right. Two such
memos are in the TypeScript module:

- **Compiler stack limits.** Whether a lookup overflows depends on what the
  checker computed before. A stored result with a compiler limit, or any
  limit, drop or rebuild in the scoped attempt, means the full analysis.
- **The object-producer memo** (`object-producers.ts`). It is shared by all
  files of a program, caches complete answers, and cuts a lookup at depth
  32 or on a cycle. A deep lookup is answered when a middle link is
  already cached, and cut otherwise. The fixture shows it: `v40.m()`
  through 41 bindings is cut on its own, and would be answered if another
  file had already looked up `v20`.

  Which lookups a file makes does not depend on the memo; only their
  answers do. So the full analysis records `objectProducers` on each
  result whose extraction made one. The scoped path is used only when the
  edited file made none, before or after. Then the memo every other file
  sees in a full analysis is the same before and after the edit.

The checker itself is taken as order-independent after the warm-up, as
W2-D does. The random-edit runs below test that on real code.

### Two runs at once (C-22)

Making TypeScript incremental means its parsed placeholders wait for
analysis (C-27's deferred writes), so a run paused in analysis has written
nothing yet. A second run then found the store unchanged and answered
without writing (C-33), and the first run's later writes went unnoticed.
C-22's race tests caught it. The indexer now writes the run's mark
before analysis whenever a module's writes are deferred, as writing parse
results first did, and a run that begins meanwhile takes over as before.
The same applies to Go's deferred writes since C-27, which no test
exercised.

### Failed files and C-39

C-39 (pull request 49, not merged when this was measured) keeps library
targets beside a failed file, which depend on that file's text. Two rules
here already cover that:
- An edit to a failed file takes the full path, because its previous result
  cannot be stood on.
- A program that asks for any failed file other than a quiet one makes the
  scoped path decline.
A quiet failed file can't change from an edit to another file, since its
text is the same. The five failed-file tests in
`test/graph-typescript-reindex.test.mjs` each add an edit inside the failed
file. Each is asserted full and equal to cold. When C-39 merges, this branch takes the next module version and
repeats that edit beside a library target that C-39 keeps.

## Stored format

- `loadedBy`: on every result, the names of the programs that loaded the
  file; on a failed file, the programs that asked for it.
- `objectProducers: true`: on a result whose extraction read object
  producers.

Both are deterministic, and a cold index writes them. TypeScript module
version 45.

## The floor, and what remains

The Hono body edit after this change, main thread, 17.9 s sampled:

| Part | Seconds |
| --- | ---: |
| building and warming the two owning projects' programs | 8.1 |
| of which: the warm-up | 5.3 |
| store writes (17 rewritten files and their decisions) | 4.5 |
| surface programs (8 loading programs, old and new) | about 1.5 |
| extracting the file, and both surfaces | 0.3 |
| start, module load, inventory, store input | about 1.4 |

So the floor is building and warming the owning projects' programs. It is
seconds on Hono and tens of seconds on Excalidraw, where one project owns
almost the whole tree. A one-file edit is not "almost immediate" yet. The
next steps, in order of what they would save:

1. **Keep programs between edits.** A long-lived process (the MCP server,
   a watch mode) holding each project's program and warmed checker could
   rebuild a program from the old one, which reuses every unchanged parsed
   file. A one-shot CLI run cannot. This is the step that would reach
   about a second.
2. **Position-free target facts.** Facts point at declarations by offset,
   so a body edit near the top of a widely imported file rewrites every
   importer (184 files on Excalidraw). Facts keyed by identity and ordinal,
   as the store's IDs already are, would leave them alone. That is a
   stored-format change for every TypeScript row.
3. **A persisted parse cache.** Parsing is about a third of program
   building here. A cache across CLI runs would save that part only, and
   it would need its own invalidation rules. It is worth a later chunk
   only after step 1, if one-shot runs stay important.

The warm-up cannot simply be dropped: it is what makes the edited file's
answers equal a full analysis's.

  JSDoc types" shape: its body-only edit is now asserted full, not scoped
  (every token of a JavaScript body is compared). Its comment edit is still
  scoped.
- `test/graph-index-runs.test.mjs`: `pausing` takes the module to pause
  (TypeScript by default), so the existing cases are unchanged.
- `test/graph-stable-failures.test.mjs`, after a direct `replaceFile` of a
  failed JavaScript file: `indexed` is now 2, not 1. The direct write also
  clears the analysis completion record, so the TypeScript module, which
  reuses stored results only under that record, restores its clean file
  too (C-27's rule, now applying to TypeScript). The other assertions are
  unchanged.

## Tools

- `scripts/reindex/install.mjs` passes the sweep's package-manager prefix
  to corepack, as `scripts/sweep/run.mjs` does. Without it every install
  failed.
- `scripts/reindex/edit-equals-cold.mjs` compares one case edit's store
  with a cold index of the edited tree; `measure.mjs` compares only after
  the revert.
- `scripts/reindex/random-edits.mjs --weighted` is a TypeScript mix of
  comment and body edits with reverted exports and line deletions. It
  records whether each step was scoped.
- `scripts/reindex/dump.mjs` `withoutTypeScriptLoadedBy`, and
  `cold-cost.mjs --ts-loaded-by`.
- `scripts/reindex/cases.json` adds vite and excalidraw.

## Found, not built

- The three steps under "The floor".
- An export edit always runs the full analysis, even when no file uses the
  new name. A file's export list could be compared with the names other
  files' stored links read.
- trpc and vite fail files on every index for configs that extend missing
  generated files (`.nuxt`, a deliberately broken playground config). Their
  results are re-delivered now, but they still make the store incomplete.
- With a syntax error in Hono's `src/utils/jwt/jwt.ts`, three files that
  use it fail with "An invalid-code link must name its cause", an internal
  error in `extract.ts`. Cold and incremental agree on it. It is a defect
  in the failed-file walk, found by the random edits.

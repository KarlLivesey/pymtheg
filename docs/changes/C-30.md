The two provable classes have the same cause: a *shared base*. A shared
base is a config file such as `tsconfig.base.json` that other configs
`extend`. It names no `files` or `include` of its own. Without a file
selection, the compiler would select every file under its directory. On
main, the module ranked such a file like any other config. When it sat
in the same directory as the real config, it tied with it (Hono, Vite,
Vitest). When it sat deeper, it won by depth (Nest's
`packages/tsconfig.build.json`, Excalidraw's `packages/tsconfig.base.json`,
Vite's `packages/vite/tsconfig.base.json`).

## The rule

A config is a shared base when all of these hold:

- another config extends it;
- it names no `files` or `include` itself;
- it is not named `tsconfig.json` or `jsconfig.json`;
- no project reference names it;
- no package script names it. A script path such as `tsc -p tsconfig.check.json` is resolved from the script's package directory, following any `cd` earlier in the script.

A shared base does not compete for a file that a project config also
includes. When nothing else includes the file, the base still owns it, as
on main. The ranking among project configs is unchanged, and so are ties
between them.

The rule matches how the tools treat these files:

- **The editor** opens only `tsconfig.json` and `jsconfig.json` files found
  by walking up from the file, and the projects they reference. In
  TypeScript 5.9 the language server takes the nearest such config when
  its own file list includes the file. Otherwise it tries that config's
  references in order, and then continues to ancestor configs (TypeScript
  5.7 release notes, "Searching Ancestor Configuration Files for Project
  Ownership"; the pinned compiler's `forEachConfigFileLocation` and
  `tryFindDefaultConfiguredProject`). If nothing includes the file, it
  creates an inferred project.
- **`tsc --build`** builds only referenced projects (TypeScript 3.9 release
  notes, "Solution Style" config files).

A shared base is neither discoverable nor referenced, so no tool compiles
it as a project.

What the graph now matches, pin by pin:

- **Hono test files:** the editor reaches the root solution config, skips
  `tsconfig.build.json` (it excludes `*.test.ts[x]`) and takes
  `tsconfig.spec.json`. The graph now does the same.
- **Hono non-test `src` files:** both `tsconfig.build.json` and
  `tsconfig.spec.json` include them, and `tsc -b` compiles them under both.
  The editor shows the first reference. The graph keeps the tie and merges
  both. It does not pick.
- **Excalidraw tests:** each package config excludes `tests`, so the editor
  walks up to the root `tsconfig.json`, which includes them. The graph now
  does the same.
- **Nest's `platform-node` and `platform-ws` spec files:** no `tsconfig.json`
  the editor opens includes them, so the editor uses an inferred project. The
  graph does not follow the editor here. The configs that include these files
  are root `tsconfig.spec.json` (`types: ["vitest/globals"]`) and the
  eight `packages/*/test/tsconfig.json` files, each of which only extends it.
  They are identical, so they bind the same declarations. The project's
  Vitest config (`globals: true`, `include: ["packages/**/*.spec.ts"]`) runs
  these files with those globals.
- **Vite's `src/types/*.d.ts`:** these go to the two `__tests_dts__`
  configs that include them. They are analysed under both and merged, and
  they agree.

## Links that changed

All links that were definite on main were compared on all nine pins in
both modes ([installed](../../evidence/c-30/changed-definite-installed.jsonl),
[bare](../../evidence/c-30/changed-definite-bare.jsonl)). Each change follows
from the new owner's compiler options:

- **Nest, 12 installed and 12 bare:** `.call` and `.bind` change from
  `CallableFunction.prototype.call` to `Function.prototype.call`.
  `packages/tsconfig.build.json` sets `strict`, and with it
  `strictBindCallApply`. `tsconfig.spec.json`, which extends the root
  `tsconfig.json`, does not. The new target is what the spec config binds.
- **Nest, 4 installed:** `Readable` from `stream`, and its `once`, become a
  candidate set of `node:stream` and `@fastify/busboy`. The spec program also
  contains the Fastify spec files, and `@fastify/busboy`'s installed types
  `declare module 'stream'`, so two packages declare the symbol.
  `node:stream` remains a candidate.
- **Vite, 7 installed:** `Plugin` from `postcss`, and `Duplex` and `DuplexOptions` from `stream`,
  in `src/types/*.d.ts` change name only. The old names were `Plugin`, `Duplex` and
  `DuplexOptions`, with evidence `import-binding`. The new names are
  `postcss.Plugin`, `Stream.Duplex` and `Stream.DuplexOptions`, with evidence
  `declaring-owner`.
  Main's base program contained failed fixture files, which allow only the
  lexical binding name. The `__tests_dts__` programs let the checker prove
  the declaring namespace. It is the same declaration.

Symbol identities are unchanged. On all nine pins in both modes, every
symbol's file, kind, identity and key is the same set before and after.

## Cost

The work the module does is deterministic. On every pin it is equal or
lower: compiler programs fall by at most one (Excalidraw 13 → 12, Nest
102 → 101, Vitest 49 → 48). File analyses, counting a tied file once per
tied config, fall on Hono (965 → 650), Vitest (2,566 → 2,536) and Vite
(1,710 → 1,705), and are unchanged elsewhere ([work.tsv](../../evidence/c-30/work.tsv)).

Timings were unusable as a comparison. The server's load average was 30–40
during the runs. Two main runs of Hono's cold bare index in one session took
96 and 200 CPU seconds, and Nest's took 271 and 514. The candidate,
measured between them, took 142 and 507 ([cost-1-main.json](../../evidence/c-30/cost-1-main.json),
[cost-2-candidate.json](../../evidence/c-30/cost-2-candidate.json),
[cost-3-main.json](../../evidence/c-30/cost-3-main.json)). Peak memory
was:

- Hono: 1,585 and 1,263 MiB on main, 841 MiB on the candidate;
- Nest: 1,556 and 1,485 MiB on main, 1,499 MiB on the candidate.

## Found but not built

- **The editor rule in general.** The graph still ranks project configs by
  containing directory, depth and name, and does not follow the editor's
  nearest-config walk and reference order. On these pins the two differ only
  where the graph keeps a tie that the editor resolves by reference order
  (Hono's non-test `src`). Adopting the editor's order would be a pick
  between two compiled projects, so it is not done.
- **`incomplete-config`.** It needs the extended package's config, which is
  missing material. In examples with their own lockfile, that would mean
  installing the example.
- **`competing-test-globals`.** It resolves once installed, and appears only
  in bare mode.

# C-19: what a Rust toolchain route would give (measurement)

A measurement chunk: no change to `src/`, no change to what is supported.
The question: if Pymtheg had an opt-in Rust route like the Go one (D17),
backed by the Rust toolchain's own analysis, what coverage would it reach,
at what cost, and what are the catches? Evidence, scripts and how to
reproduce: [evidence/c-19](../../evidence/c-19/README.md).

**Short answer.** On the 18 finished Rust pins, Rust level 2 is **43.16%**
today (source-only, `main` with C-18).

If every link the source-only route leaves open took `rust-analyzer`'s
answer under a strict join, it would be **92.39%**. The strict join takes
an answer only at the link's own name site, of a kind the link can name,
and outside the toolchain's known error classes. With the gates a route
would need, it is **85.89%**: no answers on code under a cfg condition
other than `test`, and trait-method declarations kept as dispatch.

Where both routes name a declaration for a link Pymtheg already calls
definite, they name the same one on **99.98%** (286,787 against 60). Every
one of the 60 is a link Pymtheg records under a cfg condition the toolchain
did not build, or a cfg-alternative re-export; no wrong source-only link
was found.

The costs:
- The route runs the project's build scripts and proc macros, and
  `rust-analyzer scip` cannot switch either off.
- It needs the crates downloaded.
- It takes 16 s to 7 min and 0.9–9.7 GB per run.
- It has no incremental mode: a one-file edit means a full re-run.

## What changed in review

The first version of this note (head `7ca365f`) overstated three things:
- **The join was loose.** It matched any occurrence inside the link's
  range with the right name, without checking the symbol's kind or
  namespace. That credited some wrong answers: `use memchr::memchr` was
  credited to the crate's private `memchr` module, `extern crate test` to a
  module, and on cortex-m a call generated by `syscall1!` was paired with
  the macro invocation. The strict join below fixes this. It moves the
  figures little (92.52% → 92.39% with toolchain, 85.99% → 85.89% gated),
  and it is the one that counts.
- **The agreement figure was heuristic.** 99.95% compared library targets
  by crate family and final name only. The re-export check behind it
  looked at Pymtheg's side only, so a deliberately unrelated `Serializer`
  would have passed. The figures below resolve **both** sides to a
  declaration, following re-exports explicitly. The old figure also mixed
  two populations: 2,071 "same name, other crate" cases were checked
  together with the 41 library unit or symbol disagreements, 2,112 in all.
  That check is withdrawn.
- **"Byte-identical index" was wrong.** The raw SCIP files differ, because
  they record the absolute project root. What is identical is the payload,
  as measured below.

The number of rust-analyzer "Duplicate symbol" messages per pin was also
wrong; measured counts are below.

Everything was re-run from a fresh scratch. The Pymtheg graphs come from a
merge of current `main` (`920dc47`, Rust module version 38). Since the first
run, `main` gained C-15 (Rust failed-file reasons; level 2 unchanged by
design), C-17 (Go) and C-18 (Rust macro identity), which raises Rust level 2
on the 18 pins from 42.04% to 43.16%. The rust-analyzer indexes do not
depend on Pymtheg and were made once.

## The strict join

`evidence/c-19/join.mjs` joins each pin's SCIP index to every stored Rust
link. It converts ranges first: Pymtheg stores UTF-16 code-unit offsets,
SCIP UTF-8 bytes. The strict answer for a link requires all of the
following:

1. **Its own site.** An occurrence at exactly the byte range of the written
   name's last segment, at the end of the link's range (after a trailing
   `!`, `as alias` or generic arguments), and only one symbol there. A link
   found inside a macro expansion, whose range is the macro's name, gets no
   answer.
2. **A compatible kind:**
   - a call names a function or method, a tuple-struct or variant
     constructor, or a local closure;
   - a type reference names a type, trait, alias, associated type or
     generic parameter;
   - a value names a const, static, unit struct or variant, function item
     or local;
   - a pattern names a type or value;
   - an `implements` link names a trait;
   - a macro use names a macro or an attribute or derive macro.

   210 loose answers failed this, for example a value answered with a
   module (92), a type with a value (40), a call with a macro (37).
3. **Imports.** A `use` the toolchain answers with a module is not
   credited: 932 answers. SCIP gives one symbol per occurrence, so it
   cannot show whether a same-named function or macro is imported too
   (`use memchr::memchr`). A `use` answered with a non-module item is
   credited.
4. **Excluded error classes:**
   - `extern crate` lines and crate-root answers: 69 answers;
   - a SCIP symbol defined more than once (function-body items share a
     symbol string): no answer;
   - a non-macro item of a proc-macro crate referenced from another
     package: such a crate exports only its macros, and rust-analyzer
     names same-named private items.

   Inactive-cfg fallbacks cannot be told from the index. The gated figure
   drops every answer on a link Pymtheg records under a cfg condition
   other than `test` (45,675 links), and trait-method declarations
   (17,219).

## Agreement: a soundness audit of the source-only route

The comparisons cover non-structural links Pymtheg calls definite where
the strict join gives the toolchain's answer:

| Outcome | Links |
| --- | ---: |
| Same declaration: checkout, the same graph symbol | 195,870 |
| Same declaration: library, both paths resolved to the same definition | 90,917 |
| Same crate family and final name only (identity not resolved) | 1,876 |
| Unverified: other crate, same name (610) or other name (9) | 619 |
| `<T as Trait>::m`: Pymtheg names the trait method, the toolchain the impl (both right by convention) | 6 |
| **Differ** | **60** |

**How library identity is checked** (`rustpath.mjs`, a text-level
resolver over the downloaded crate sources and `rust-src`). Both sides
are resolved independently:
- Pymtheg's written path (unit and symbol) and the toolchain's declaring
  path (crate, version and descriptors) are each resolved to a definition.
- It follows `mod` declarations (files, `#[path]`, inline modules), `use`
  re-exports (renames, lists, nested lists, globs, `extern crate … as`),
  renamed dependencies from the manifest, and versions required by the
  manifest.
- It follows proc-macro crates' `#[proc_macro_derive(Name)]`,
  `#[proc_macro_attribute]` and `#[proc_macro]` functions, and
  `#[macro_export]` macros.
- Middle path segments prefer modules and the last segment prefers items.
  Re-exports seen from outside a crate must be `pub`.
- The same crate, version and path on both sides is the same declaration
  by definition.

It does not evaluate cfg or expand macros. What it cannot follow stays
"unverified" or "family and name only", never a guess. Its own checks
(`rustpath-check.txt`) cover 14 pairs that must resolve to the same
definition and 3 that must not.

**Strict agreement: 286,787 of 286,847 = 99.98%** (same declaration, over
comparisons where both sides name a declaration).
**Heuristic agreement: 99.77%** (same declaration or same family and name,
over every comparison with an answer). On the first run's ripgrep figure,
the 7,076 "family and name" agreements are now 21,444 verified same
declarations and 12 family-and-name only.

**The 60 that differ:**
- 59 are checkout targets, and every one is on a link Pymtheg records
  under a non-test cfg condition. The toolchain analysed the other
  configuration (host target, default features, unified dev-dependency
  features) and named the other variant. Examples:
  - `PathResolver(handle)` inside `#[cfg(target_os = "android")]` became
    the desktop struct;
  - a `WebviewMessage::EvaluateScript(script, tx, span)` arm under the
    tracing feature became the one-field variant;
  - redb's `not(feature = "experimental-api-5")` code became the
    feature-on variants.
- 1 is a library path, `local_ip_address::list_afinet_netifas`. The crate
  glob-re-exports `linux::*` under `cfg(target_os = "linux")` and declares
  a fallback function for other platforms. The resolver ignores cfg and
  took the fallback; on Linux both name the `linux` function.

**Hand-check** ([handcheck.md](../../evidence/c-19/handcheck.md)): 30 rows
per deep-dive pin, every hard difference first, then unverified, then
family-and-name only, in a fixed-seed order keyed by site and written name
(a fresh run draws the same rows). Each row carries a verdict checked in
the pinned or downloaded source: per site, or per shape. A shape is a
Pymtheg target and a toolchain target checked once, such as serde's `pub
use serde_core::{…}` inside its `crate_root!` macro, syn's root
re-exports of macro-declared types, tokio's `cfg_macros!` re-exports, or
jsonrpsee's renamed re-exports. Of the 120 rows, Pymtheg is right on 14,
both name the same declaration on 106, and the toolchain is right over
Pymtheg on none.

Every unconditional hard difference across all 18 pins is listed in
[unconditional.txt](../../evidence/c-19/unconditional.txt):
- local-ip-address (above);
- 6 `<T as Trait>::m`;
- 8 unverified renamed re-exports (jsonrpsee's `Request as HttpRequest`,
  tower-http's `ResponseBody as ServeFileSystemResponseBody`, blitz's
  `ComputedValues as ComputedStyles`), each read in the crate source.

**Candidate sets.** Of 674 compared, 656 contain the toolchain's answer and
18 meet a generated item. None excludes it.

**The toolchain's own errors**, which any route must filter:
- **Inactive cfg code:** it gives a same-named item instead of no answer.
- **Symbol collisions:** SCIP symbols carry no function-body scope.
  rust-analyzer logs 7 to 1,187 "Duplicate symbol" messages per pin (3,749
  over the 18; crossbeam 547 over 63 files), and 1,145 symbols are defined
  more than once in the indexes.
- **Proc-macro exports:** an export is named as a same-named private item
  (`pub use axum_macros::FromRequest` became the enum variant
  `from_request::Trait::FromRequest`).
- **`extern crate`:** it names the wrong root.

**Gains.** The first 10 gated gains per deep-dive pin (40 links, in
handcheck.md) were read against their source lines and are consistent
with them: a typed receiver's method, a generic resolved through its
bound, a local resolved to its binding. That reading does not re-derive
each inferred type by hand.

## Cost

- **Time and memory:** 16 s (cortex-m) to 394 s (dioxus) wall per pin;
  5,707 s CPU for all 18; peak 0.9–9.7 GB (dioxus).
- **Index size:** 1.3–33 MB of SCIP (187 MB for all 18).
- **Disk:** 9.7 GB of build output across the 18.
- **One-file edit:** a re-run after appending one line costs most of a
  cold run. ripgrep took 16 s against 26 s cold, helix 59 s against 123 s.
  The first run's observations were 21/23 s and 79/112 s. Only build-script
  compilation is cached; the analysis is redone. `scip` has no incremental
  mode.
- **Network:** with a fresh crate cache per pin, 20 (hashes) to 1,115
  (dioxus) crate archives, about 800 MB in all including the registry
  index. A shared cache would download far less.
- **Lockfiles:** five pins track no `Cargo.lock` (redb, crossbeam, serde,
  fjall, cortex-m). Cargo resolved the newest matching versions at run time
  and wrote a lockfile into the copy, so their indexes are not
  reproducible from the pin. No tracked file changed in any run.
- **Offline with an empty crate cache** (ripgrep): `cargo metadata` fails,
  rust-analyzer falls back to `--no-deps` and still exits 0. The standard
  library still resolves from `rust-src`; dependency targets are lost:
  87.18% instead of 95.82% (strict).

## What runs, and can it be switched off

`rust-analyzer scip` does three things in order:
1. It loads the Cargo workspace (`cargo metadata`, which downloads every
   locked crate that is missing).
2. It runs `cargo check` to build and **run every build script** of the
   workspace and its dependencies: 601 runs over the 18 pins. These include
   C builds (ring, aws-lc-sys, zstd-sys, liblzma-sys, libgit2-sys,
   libsqlite3-sys, pcre2-sys), pkg-config probes and the projects' own
   `build.rs` files.
3. It builds every proc-macro crate and **loads it into
   `rust-analyzer-proc-macro-srv`**, which executes the macro for every
   invocation it expands: 291 proc-macro libraries over the 18 pins.

That is project and dependency code running on the machine.

**`scip` does not let this be switched off.** axum was indexed three more
times from fresh copies, each with a `--config-path` file:

| Config file | Build scripts run | Proc-macro libraries | Index payload |
| --- | ---: | ---: | --- |
| `{"cargo":{"buildScripts":{"enable":false}},"procMacro":{"enable":false}}` | 24 (same as default) | 12 (same) | identical |
| `{"cfg":{"setTest":false}}` | 24 | 12 | changed: 51 documents differ, 8 fewer |
| `{"cargo":{"features":"all"}}` | 27 | 13 | changed: 23 more documents |

The raw files differ in every case, because SCIP records the absolute
project root and each run used its own copy.

What was compared ([axum-scip-compare.json](../../evidence/c-19/axum-scip-compare.json),
`scip-compare.mjs`): the index **payload** without its metadata, that is
every document (relative path, occurrences, symbols) by relative path,
plus the external symbols. With build scripts and proc macros configured
off, all 98 documents and the external symbols are identical to the
default index, and so are the join results
([axum-join-compare.json](../../evidence/c-19/axum-join-compare.json)).
Setting `cfg.setTest` to false changes the index while the same build
scripts and proc macros still run, so the file is read: `scip` fixes
build-script loading and the proc-macro server in code.

`rust-analyzer analysis-stats` and `diagnostics` take
`--disable-build-scripts` and `--disable-proc-macros`, but they write no
index.

Switching both off would need a different driver, such as the language
server and its `procMacro.enable` and `cargo.buildScripts.enable`
settings. That would lose:
- every item a derive or attribute macro generates: serde, clap and
  thiserror impls, `#[tauri::command]` wrappers (17,133 links name such
  items today);
- references inside attribute-macro arguments;
- code included from a build script's `OUT_DIR`.

This was not measured, because `scip` cannot do it.

So containment is the D17 trust model ("as trusted as building the
project"). Beyond that it would need a sandbox: fetch first with
`cargo fetch` against the lockfile, then run offline in a copy with no
network. W2-L's escape table applies unchanged.

## Library and checkout identity

- **Unit.** The SCIP package name is the Cargo package name (`grep-cli`,
  `tower-http`, `serde_core`), which matches Pymtheg's unit convention
  (package name, `-` kept). A renamed dependency (`redb2_6 = { package =
  "redb" }`) appears under its package name with its own version. The
  crate name alone is not unique: redb depends on older releases of itself,
  so crate and version together identify a unit.
- **Version.** Dependencies carry the resolved semver, which is the
  lockfile's version where a lockfile is tracked, so a `versionSource` of
  `Cargo.lock` holds. Without one, the version is whatever cargo resolved
  that day. Std-family crates (`std`, `core`, `alloc`, `proc_macro`,
  `test`) carry a source URL (`https://github.com/rust-lang/rust/library/core`)
  instead of a version. The toolchain version would come from `rustc -V`,
  which is not a manifest or lockfile, so under C-5's rule a `rust-std`
  target takes no version, as today.
- **Symbol path.** SCIP names the **declaring** path, not the path users
  write:
  - `std` re-exports become `core`/`alloc`, e.g. `std::vec::Vec` becomes
    `alloc vec/Vec#`.
  - private modules appear in the path, e.g. `std::collections::HashMap`
    becomes `std collections/hash/map/HashMap#`.
  - renamed re-exports lose the public name: `Handlebars` becomes
    `Registry`.
  - impl-block methods appear as `impl#[Type][Trait]method().`. Blanket
    impls (`impl<T: Display> ToString for T`) have no owning type.

  C-5 records the declaring crate only when proven, and the toolchain does
  prove it. But the same symbol would then get a different library id from
  each route unless the route keeps a public-path table, which SCIP does
  not carry. This measurement had to build one (`rustpath.mjs`) to compare
  identities at all.
- **Checkout symbols.** SCIP strings cannot be Pymtheg symbol keys:
  function-body items collide, and locals are numbered per file. The join
  goes by definition location: the Pymtheg symbol declaring that name at
  that place, and a local's enclosing item. That works for every checkout
  answer except struct fields, which Pymtheg has no symbols for.
- **Offsets.** Pymtheg stores ranges as JavaScript string offsets (UTF-16
  code units); SCIP uses UTF-8 byte columns. A join that ignored this lost
  most of helix (box-drawing characters), so the conversion is required.

## How the route would be wired (sketch, not built)

Following the Go route's shape (`src/graph/languages/go/toolchain.ts`,
W3-L):

1. **Opt-in.** `"graph": {"toolchain": {"rust": true}}`, or an absolute
   path to a trusted `rust-analyzer`. The route also needs `rust-src` for
   the same toolchain. Every answer reports `toolchain.rust.state`: `used`
   with counts, `unavailable` with the reason (no `Cargo.toml` at the root,
   no rust-analyzer, no `rust-src`, no lockfile), or `stale` (see 4).
2. **Policy.** Offline by default (`CARGO_NET_OFFLINE=true`). Missing
   crates are reported, and the index falls back to the workspace alone;
   the route must detect that fallback, because rust-analyzer exits 0. A
   throwaway target directory and crate-cache overlay per run, never in
   the project, because build-script output can poison later runs (W2-L
   row 9). The project is never written: a project without a tracked
   `Cargo.lock` gets a lockfile written into a copy. One configuration
   (host target, default features, `cfg(test)` on), recorded with every
   answer.
3. **Cache.** The SCIP output lives in the rebuildable folder. It is keyed
   by the rust-analyzer and rustc versions, the configuration, every
   `Cargo.toml` and `Cargo.lock` hash, every `.rs` content hash and the
   crate cache's presence state for locked crates. Like the Go key, any
   change misses.
4. **One-file edit: the source-only route stays the fast path.** A
   toolchain index cannot be refreshed incrementally; it must be re-run (16
   s to 7 min). An edit therefore re-indexes source-only at once, as today.
   Every toolchain upgrade is dropped back to its source-only outcome,
   because an edit in one file can change resolution in another (a rename,
   a new impl). A background re-run is queued, debounced and cancellable.
   When it finishes for the same content key, its upgrades are merged.
   Until then answers report `toolchain.rust.state: stale`. No stale
   toolchain answer is ever shown as definite. An incremental alternative
   is a resident rust-analyzer language server queried for the changed
   files' sites after each edit. It was not measured; it holds 1–10 GB, and
   a change to a signature still invalidates other files' answers.
5. **Provenance.** Links get `decidedBy: "toolchain"` and the configuration
   key, as in Go.
6. **Cross-check (what the route may change).**
   - Only answers that pass the strict join above.
   - Only on links with no cfg condition other than `test`.
   - No trait-method declarations: those stay or become candidate sets.
   - And, unmeasured, only where the source-only route knows of no cfg
     variant of the target. An unconditional call to a name declared once
     per platform (tauri's `PathResolver`) has a different target in each
     build, so it must stay a candidate set.
   - Where the source-only route is definite and the toolchain differs,
     keep the source-only link and count the difference. Here the
     source-only link was right in every case checked.
   - A candidate set may narrow to the toolchain's member only under the
     same gates.
   - Library answers go through a public-path table, or keep the written
     path with `declaring-owner` evidence. That decision belongs to the
     identity rules, not this measurement.

## Recommendation

The recommendation is unchanged by review; its numbers move slightly.

1. **Adopt, opt-in, gated, as a slower background upgrade:** 18-pin Rust
   level 2 goes from 43.16% to about **85.9%** (strict, gated). Ungated it
   would be 92.4%, but 45,675 of those answers break the
   every-configuration rule and 17,219 are dispatch. A cfg-variant guard
   (not measured) would take a little more off.
2. **For some link kinds only:** not worth it. Checkout answers alone reach
   65.2% and library answers alone 70.4%; the gain is spread over calls,
   values, macros and types.
3. **Do not adopt:** 43.2%, plus 1–2 points per source-only chunk.
4. **Either way, the sweep figure stays about 43%.** The sweep runs with default
   settings, so the 90% goal on it cannot be met by an opt-in route.
5. **Preconditions:** Karl's decision under D17, which names
   rust-analyzer. Acceptance that `scip` runs build scripts and proc
   macros with no off switch. And an identity decision for declaring
   versus written library paths, which needs a public-path table.

## Found, not built

- No wrong definite link of the source-only route was found: every
  difference is cfg-dependent or a resolver limit, as listed above.
- Pymtheg has no struct-field symbols. 6,555 links the toolchain answers
  with a field (or another non-symbol declaration) have nothing to point to.
- 17,133 links name macro-generated checkout items with no declaration
  site; a toolchain route could not credit them either without
  generated-symbol identities.
- rust-analyzer's SCIP problems that any route must filter: function-body
  item collisions, proc-macro export naming, `extern crate` roots,
  single-symbol occurrences on `use` items that import several namespaces,
  and fallback answers in inactive cfg code.
- A silent partial index when system libraries are missing (tauri), and a
  silent `--no-deps` fallback offline. A route must detect both, from
  rust-analyzer's log or from missing dependency documents, and report
  them.

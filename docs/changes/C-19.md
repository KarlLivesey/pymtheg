# C-19: what a Rust toolchain route would give (measurement)

A measurement chunk: no change to `src/`, no change to what is supported.
The question: if Pymtheg had an opt-in Rust route like the Go one (D17),
backed by the Rust toolchain's own analysis, what coverage would it reach,
at what cost, and what are the catches? Evidence, scripts and how to
reproduce: [evidence/c-19](../../evidence/c-19/README.md).

**Short answer.** On the 18 finished Rust pins, Rust level 2 is **42.04%**
today (source-only, `main`). If every link the source-only route leaves
open took `rust-analyzer`'s answer, it would be **92.52%**. With the
gates such a route would need (no answers on code under a cfg condition
other than `test`, trait-method declarations kept as dispatch), it is
**85.86%**. Where both routes answer, they agree on **99.95%** of the
links Pymtheg already calls definite. In every disagreement checked, the
source-only route is right and the toolchain is wrong (it analyses one
configuration and has naming bugs) or names the same item differently (a
re-export). The costs: the route runs the project's build scripts and proc
macros and needs the crates downloaded, and `rust-analyzer scip` cannot
switch either off. It takes 20 s to 7 min and 0.9–9.7 GB per run, and it
has no incremental mode: a one-file edit means a full re-run.

## What a stable toolchain offers

On the pinned stable toolchain (Rust 1.98.1):

| Candidate | On stable? | What it gives |
| --- | --- | --- |
| `rust-analyzer scip <path>` (rustup component `rust-analyzer`, and `rust-src` for the standard library) | yes: `rust-analyzer 1.98.1 (48a229c 2026-09-01)`, installed with `rustup component add rust-analyzer rust-src` | every definition and reference in the workspace's indexed files, with symbol strings `rust-analyzer cargo <crate> <version> <descriptor path>` that also name std and dependency items. Batch only. **Measured here.** |
| `rust-analyzer lsif <path>` | yes, same component | the same static index as LSIF JSON lines; on ripgrep 37.3 MB (358,253 lines) in 28 s, against 8.2 MB of SCIP in 23 s. No reason to prefer it. |
| rust-analyzer as a language server (same binary, LSP over stdio) | yes | the same answers per request, recomputed **incrementally** after an edit, but with no bulk "all references" request and a resident process. Not measured. |
| `rustc -Zsave-analysis` | no | removed from rustc; on stable any `-Z` option fails: "the option `Z` is only accepted on the nightly compiler" |
| rustdoc JSON (`--output-format json`) | no | needs `-Z unstable-options` (nightly only), and it describes items, not references |
| `cargo check --message-format=json` | yes | diagnostics and artifacts only, no references |

So on stable the toolchain's own reference data comes only from
rust-analyzer. **Decision D17 rules out `rust-analyzer` "unless Karl
asks"**, so adopting anything below needs that decision.

Definitions:
- **+ toolchain answers:** every unresolved, candidate-set or unit-only link
  the toolchain answers with a checkout declaration or a library symbol
  takes that answer.
- **Checkout answers only:** takes only the checkout ones; taking only the
  library ones gives 70.14%.
- **Conservative:** leaves out two kinds of answer:
  - answers naming a trait's method declaration: 17,219 links. That is
    dispatch on a generic or `dyn` receiver, or a default body; in
    Pymtheg's terms it is a candidate set. Leaving out these alone gives
    90.71%.
  - answers on links Pymtheg records under a cfg condition other than
    `test`: 47,226 links.
- **Agreement:** over links Pymtheg already calls definite, compared with
  the toolchain's target. "Hard" means a different target.
  Re-export identity differences are counted apart.

Times and memory are observations on a shared, loaded server, one
rust-analyzer run at a time (8 threads, 8 cargo jobs), each with a fresh
crate cache. The toolchain runs took 26 minutes of wall time for all 18 pins;
Pymtheg's cold indexes took 54 minutes. The dioxus Pymtheg index ran
alongside other jobs and was re-run after an aborted first attempt.

**Where the gain comes from** (18 pins, links that would gain):
- receiver and path calls: 158,220 library and 107,686 checkout. These are
  the method calls on receivers of unknown type and the library method
  owners.
- values: 58,156 checkout (mostly locals and lexical bindings).
- macros: 38,504 library and 4,850 checkout (macro scope).
- types: 35,591 library and 23,731 checkout.
- imports: 13,672 library and 12,992 checkout.
- patterns: 7,750 library and 3,466 checkout.

All the big remaining reasons are covered; no single kind carries it.

**axum variants:**
- Default index: 70.79%.
- With `{"cargo":{"features":"all"}}`: 79.85%.
- Adding the separate `examples/` workspace as a second index: 91.20%. That
  costs another 102 s, 403 crates and 49 build scripts.

## Agreement: a soundness audit of the source-only route

There are 306,103 non-structural links that Pymtheg calls definite and the
toolchain could be compared on:

| Outcome | Links |
| --- | ---: |
| Same target | 277,761 |
| Different target ("hard") | 145 |
| Same item named through a re-export | 2,071 |
| Toolchain gives no answer | 15,100 |
| Toolchain symbol collides (no single declaration) | 3,028 |
| Toolchain names a macro-generated item with no declaration | 7,998 |

**Hard disagreements: no wrong Pymtheg link was found.** The hand-check
table is [handcheck.md](../../evidence/c-19/handcheck.md): 30 per deep-dive
pin, every hard one first, at fixed seed `c-19`. On the 117 rows, Pymtheg
is right on 28, both name the same declaration on 89 (re-exports), and
the toolchain is right over Pymtheg on none.

99 of the 145 are on links Pymtheg records under a non-test cfg condition.
The toolchain analysed the other configuration (host target, default
features, unified dev-dependency features) and named the wrong variant, or
fell back to a same-named item. Examples:
- a `file` parameter in `#[cfg(windows)] mod sys` became core's `file!`
  macro.
- `PathResolver(handle)` inside `#[cfg(target_os = "android")]` became the
  desktop struct.
- an arm under `#[cfg(not(feature = "experimental-api-5"))]` became the
  feature-on variant, because redb's tests turn the feature on.

These were checked by hand on ripgrep, axum, helix and tauri, and by shape
on redb. The 26 conditional ones on other pins were not opened one by one.

The 46 unconditional ones were all opened, listed in
[unconditional.txt](../../evidence/c-19/unconditional.txt):
- 39 are renamed re-exports, where Pymtheg records the written path and
  the toolchain the declaring name: `Registry as Handlebars`,
  `Report as Error`, `Request as HttpRequest`, `KeyPair as RsaKeyPair`,
  `ComputedValues as ComputedStyles`.
- 3 are `<T as Trait>::m` calls, where Pymtheg names the trait method
  (evidence `explicit-trait`) and the toolchain names the impl. Both are
  right.
- 3 are ratatui `use ratatui_macros::{line, span, text}`. The same-named
  modules are private, so only the macros are imported, as Pymtheg says;
  the toolchain names the modules.
- 1 is `extern crate helix_view`, where the toolchain names the
  referencing crate's root.
- 1 is a cortex-m link that Pymtheg found inside a `syscall1!` expansion;
  it shares the macro's range, so this is a join artifact.

**Re-exports.** All 2,071 cases were checked in the unit's downloaded
source with a text check
([reexport-check.jsonl](../../evidence/c-19/reexport-check.jsonl)): 1,540
have a re-export naming the item, 272 re-export the path's module (`pub use
usvg;`), 300 have only a glob re-export, and none is missing.

**Candidate sets.** Of 756 compared, 657 contain the toolchain's answer.
98 get a collision or generated-item answer and 1 is a join artifact (the
answer is one of its candidates). None excludes the toolchain's answer.

**The toolchain's own errors**, found while checking:
- Inactive cfg code gets a same-named item instead of no answer.
- SCIP symbol strings carry no function-body scope. Two items declared in
  two function bodies of one module (`const SHERLOCK` in two tests) share
  one symbol; rust-analyzer itself logs 24–55 "Duplicate symbol" errors
  per pin, and 6,847 links meet such a collision.
- A proc-macro crate's exported derive is named as a same-named private
  item: `pub use axum_macros::FromRequest` became the enum variant
  `from_request::Trait::FromRequest`.
- `extern crate` names the wrong root.

A route would have to filter all of these.

**Gains.** The first 10 conservative gains per deep-dive pin (40 links,
also in handcheck.md) were read against their source lines and are
consistent with them: a typed receiver's method, a generic resolved
through its bound, a local resolved to its binding. That reading does not
re-derive each inferred type by hand.

## Cost

- **Time and memory:** 19 s (fjall) to 419 s (dioxus) wall per pin; 5,476 s
  CPU for all 18; peak 0.9–9.7 GB (dioxus).
- **Index size:** 1.3–33 MB of SCIP (187 MB for all 18).
- **Disk:** 9.7 GB of `target/` build output across the 18.
- **One-file edit:** a re-run after appending one line costs nearly a cold
  run: ripgrep 21 s against 23 s, helix 79 s against 112 s. Only
  build-script compilation is cached; the analysis is redone. `scip` has
  no incremental mode.
- **Network:** with a fresh crate cache per pin, 20 (hashes) to 1,115
  (dioxus) crate archives, about 800 MB in all including the registry
  index. A shared cache would download far less.
- **Lockfiles:** five pins track no `Cargo.lock` (redb, crossbeam, serde,
  fjall, cortex-m). Cargo resolved the newest matching versions at run time
  and wrote a lockfile into the copy, so their indexes are not
  reproducible from the pin. No tracked file changed in any run.
- **Offline with an empty crate cache** (ripgrep): `cargo metadata` fails,
  rust-analyzer falls back to `--no-deps` and still exits 0. The standard
  library still resolves from `rust-src`; dependency targets are lost:
  87.21% instead of 95.85%.

## What runs, and can it be switched off

`rust-analyzer scip` does three things in order:
1. It loads the Cargo workspace (`cargo metadata`, which downloads every
   locked crate that is missing).
2. It runs `cargo check` to build and **run every build script** of the
   workspace and its dependencies: 601 runs over the 18 pins. These include
   C builds (ring, aws-lc-sys, zstd-sys, liblzma-sys, libgit2-sys,
   libsqlite3-sys, pcre2-sys), pkg-config probes and the projects' own
   `build.rs` files.
3. It builds every proc-macro crate and **loads it into
   `rust-analyzer-proc-macro-srv`**, which executes the macro for every
   invocation it expands: 291 proc-macro libraries over the 18 pins.

That is project and dependency code running on the machine.

The `scip` command does not let this be switched off. axum was run with
`{"cargo":{"buildScripts":{"enable":false}},"procMacro":{"enable":false}}`
as `--config-path`. It ran the same 24 build scripts, loaded the same 12
proc-macro libraries and wrote a byte-identical index. The same option with
`{"cargo":{"features":"all"}}` did change the index, so the file is read:
`scip` fixes build-script loading and the proc-macro server in code.
`rust-analyzer analysis-stats` and `diagnostics` take
`--disable-build-scripts` and `--disable-proc-macros`, but they write no
index.

Switching both off would need a different driver, such as the language
server and its `procMacro.enable` and `cargo.buildScripts.enable`
settings. That would lose:
- every item a derive or attribute macro generates: serde, clap and
  thiserror impls, `#[tauri::command]` wrappers (17,363 links name such
  items today);
- references inside attribute-macro arguments;
- code included from a build script's `OUT_DIR`.

This was not measured, because `scip` cannot do it.

So containment is the D17 trust model ("as trusted as building the
project"). Beyond that it would need a sandbox: fetch first with
`cargo fetch` against the lockfile, then run offline in a copy with no
network. W2-L's escape table applies unchanged.

## Library and checkout identity

- **Unit.** The SCIP package name is the Cargo package name (`grep-cli`,
  `tower-http`, `serde_core`), which matches Pymtheg's unit convention
  (package name, `-` kept). A renamed dependency (`redb2_6 = { package =
  "redb" }`) appears under its package name with its own version. The
  crate name alone is not unique: redb depends on older releases of itself,
  so crate and version together identify a unit.
- **Version.** Dependencies carry the resolved semver (79,961 answers;
  3 git dependencies carry a URL). That is the lockfile's version
  where a lockfile is tracked, so a `versionSource` of `Cargo.lock` holds;
  without one, the version is whatever cargo resolved that day. Std-family
  crates (`std`, `core`, `alloc`, `proc_macro`, `test`) carry a source URL
  (`https://github.com/rust-lang/rust/library/core`) instead of a version.
  The toolchain version would come from `rustc -V`, which is not a
  manifest or lockfile, so under C-5's rule a `rust-std` target takes no
  version, as today.
- **Symbol path.** SCIP names the **declaring** path, not the path users
  write:
  - `std` re-exports become `core`/`alloc`, e.g. `std::vec::Vec` becomes
    `alloc vec/Vec#`.
  - private modules appear in the path, e.g. `std::collections::HashMap`
    becomes `std collections/hash/map/HashMap#`.
  - renamed re-exports lose the public name: `Handlebars` becomes
    `Registry`.

  C-5 records the declaring crate only when proven, and the toolchain does
  prove it. But the same symbol would then get a different library id from
  each route unless the route keeps a public-path table, which SCIP does
  not carry.
- **Methods.** 130,830 of the library answers name a method through its
  impl block (`impl#[Type][Trait]method().`), 21,829 of them through a
  trait impl. These need translating to `Type::method` or `Trait::method`.
  Blanket impls (`impl<T: Display> ToString for T`) have no owning type at
  all.
- **Checkout symbols.** SCIP strings cannot be Pymtheg symbol keys:
  function-body items collide, and locals are numbered per file. The join
  has to go by definition location: the Pymtheg symbol declaring that name
  at that place, and a local's enclosing item. That mapping works for every
  checkout answer except struct fields, which Pymtheg has no symbols for.
- **Offsets.** Pymtheg stores ranges as JavaScript string offsets (UTF-16
  code units); SCIP uses UTF-8 byte columns. A join that ignored this lost
  most of helix (box-drawing characters), so the conversion is required.

## How the route would be wired (sketch, not built)

Following the Go route's shape (`src/graph/languages/go/toolchain.ts`,
W3-L):

1. **Opt-in.** `"graph": {"toolchain": {"rust": true}}`, or an absolute
   path to a trusted `rust-analyzer`. The route also needs `rust-src` for
   the same toolchain. Every answer reports `toolchain.rust.state`: `used`
   with counts, `unavailable` with the reason (no `Cargo.toml` at the root,
   no rust-analyzer, no `rust-src`, no lockfile), or `stale` (see 4).
2. **Policy.** Offline by default (`CARGO_NET_OFFLINE=true`). Missing
   crates are reported, and the index falls back to the workspace alone.
   A throwaway `CARGO_TARGET_DIR` and `CARGO_HOME` overlay per run, never
   in the project, because build-script output can poison later runs
   (W2-L row 9). The project is never written: a project without a tracked
   `Cargo.lock` gets a lockfile written into a copy. One configuration
   (host target, default features, `cfg(test)` on), recorded with every
   answer.
3. **Cache.** The SCIP output lives in the rebuildable folder. It is keyed
   by the rust-analyzer and rustc versions, the configuration, every
   `Cargo.toml` and `Cargo.lock` hash, every `.rs` content hash and the
   crate cache's presence state for locked crates. Like the Go key, any
   change misses.
4. **One-file edit: the source-only route stays the fast path.** A
   toolchain index cannot be refreshed incrementally; it must be re-run (21
   s to 7 min). An edit therefore re-indexes source-only at once, as today.
   Every toolchain upgrade is dropped back to its source-only outcome,
   because an edit in one file can change resolution in another (a rename,
   a new impl). A background re-run is queued, debounced and cancellable.
   When it finishes for the same content key, its upgrades are merged.
   Until then answers report `toolchain.rust.state: stale`. No stale
   toolchain answer is ever shown as definite. An incremental alternative
   is a resident rust-analyzer language server queried for the changed
   files' sites after each edit. It was not measured; it holds 1–10 GB, and
   a change to a signature still invalidates other files' answers.
5. **Provenance.** Links get `decidedBy: "toolchain"` and the configuration
   key, as in Go.
6. **Cross-check (what the route may change).**
   - Upgrade an unresolved, candidate-set or unit-only link only when:
     - the link has no cfg condition other than `test`;
     - the SCIP symbol is defined once;
     - the answer is not a trait-method declaration (that stays or becomes
       a candidate set);
     - the answer maps by location to a graph symbol or a library target;
     - the name is not a proc-macro crate's export;
     - and, unmeasured, the source-only route knows of no cfg variant of
       the target. An unconditional call to a name declared once per
       platform (tauri's `PathResolver`) has a different target in each
       build, so it must stay a candidate set.
   - Where the source-only route is definite and the toolchain differs,
     keep the source-only link and count the difference. Here it was right
     every time.
   - A candidate set may narrow to the toolchain's member only under the
     same gates.
   - Library answers go through a public-path table, or keep the written
     path with `declaring-owner` evidence. That decision belongs to the
     identity rules, not this measurement.

## Recommendation

1. **Adopt, opt-in, gated, as a slower background upgrade:** 18-pin Rust
   level 2 goes from 42.04% to about **85.9%**. Ungated it would be 92.5%,
   but 47,226 of those answers break the every-configuration rule and
   17,219 are dispatch. A cfg-variant guard (not measured) would take a
   little more off.
2. **For some link kinds only:** not worth it. Checkout answers alone reach
   64.4% and library answers alone 70.1%; the gain is spread over calls,
   values, macros and types.
3. **Do not adopt:** 42.0%, plus 1–2 points per source-only chunk.
4. **Either way, the sweep figure stays 42%.** The sweep runs with default
   settings, so the 90% goal on it cannot be met by an opt-in route.
5. **Preconditions:** Karl's decision under D17, which names
   rust-analyzer. Acceptance that `scip` runs build scripts and proc
   macros with no off switch. And an identity decision for declaring
   versus written library paths.

## Found, not built

- No wrong definite link of the source-only route was found among the 145
  hard disagreements (26 conditional ones on non-deep-dive pins were
  checked by shape only).
- Pymtheg has no struct-field symbols. 8,169 links the toolchain answers
  with a field (or another non-symbol declaration) have nothing to point to.
- 17,363 links name macro-generated checkout items with no declaration
  site; a toolchain route could not credit them either without
  generated-symbol identities.
- rust-analyzer's SCIP problems that any route must filter: function-body
  item collisions, proc-macro export naming, `extern crate` roots, and
  fallback answers in inactive cfg code.
- A silent partial index when system libraries are missing (tauri), and a
  silent `--no-deps` fallback offline. A route must detect both, from
  rust-analyzer's log or from missing dependency documents, and report
  them.

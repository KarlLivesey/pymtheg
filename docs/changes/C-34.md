## Proof shipped

The Rust Reference places associated items in their implementation's
associated scope. A macro that emits only written `impl` items cannot
introduce a sibling value, type or macro through those items. The resolver
applies this bound after it identifies a captured `macro_rules!` definition.
Every arm must have fixed `impl` keywords and written body delimiters. At the
invocation, the inputs must be identifiers and commas, so a substitution
cannot close the impl or splice a new item beside it. This includes redb's
`impl_key_range!` shape, where an identifier appears after `for` in a generic
impl header. It also includes Actix Web's `service_tuple!`, which repeats
generic parameters inside a header and annotates a generated method with
`#[allow(non_snake_case)]`. The header cannot obtain its impl delimiter from
a repetition. Only empty and comma separators are accepted, so a separator
cannot manufacture syntax such as `!` in a nested invocation.
[Rust Reference, implementations](https://doc.rust-lang.org/reference/items/implementations.html)

Inside the block, `#[inline]` and `#[allow(...)]` leave the annotated
associated item in place. `#[cfg(...)]` can remove the item. The block
remains a fixed impl in either branch of the condition.
The compiler controls rejected imported proc macros under these names.
`cfg` was reserved and `inline` and `allow` were ambiguous with the built-ins.
[Rust Reference, attributes](https://doc.rust-lang.org/reference/attributes.html#active-and-inert-attributes)

Other attributes and nested macro syntax make this proof unavailable even
in the impl body. A nested `#[macro_export]` can publish a macro at crate root,
as the Cargo fixture demonstrates. The fixture also covers an arm with an
argument-named sibling item and a token repetition that can inject an item
between impls. The graph still treats the contents of generated implementations
as unknown for method and associated-path lookup. The proof introduces no
external macro assumption. Rust module version **45** invalidates stale parse
facts. [Rust Reference, macros by example and scoping](https://doc.rust-lang.org/reference/macros-by-example.html#scoping-exporting-and-importing)

## Attribute identity extension: tried and removed

A second part tried to prove that `#[derive(Debug)]`, `#[test]`, `#[inline]`
and similar attributes were the compiler's own. It used the macro-namespace
bindings in scope. A built-in derive would then emit no nameable item, and
an inert built-in attribute would emit nothing. It also relaxed three guards:
modules with `no_implicit_prelude`, attributes inside inline modules, and
`#[macro_use]` imports behind a disjoint cfg gate. It passed the full test
suite and had compiler-checked fixtures for each clause.

Its ten-pin rerun against the first part found **no new Level 2 link**. All
prior targets and symbol identities were unchanged. The only effect was on
stored reasons. On 524 links the opacity reason gave way to the next blocker,
mostly `namespace-binding-unverified`, and those links stayed below Level 2.
The built-in derive row did not move at all. Most of those sites are also
reachable by a `#[macro_use] extern crate` or a glob that could supply a
competing macro.

Looser guards with no coverage gain are risk without benefit. The extension
was therefore removed in a normal revert commit. The source, tests and Rust
module version (**45**) are those of the first part. Its measurements stay in
the evidence as the record of this decision. The work-in-progress commit
`d3a44f0` keeps its code, fixtures and compiler witness script.
[Extension comparison](../../evidence/c-34/attribute-comparison.json) ·
[Class transitions](../../evidence/c-34/attribute-classes.tsv) ·
[Replacement reasons](../../evidence/c-34/attribute-reasons.tsv) ·
[Cost](../../evidence/c-34/attribute-cost.json)

After the revert, the ten pins were indexed again with main (`c6b77dc`) and
the final head in one dev-server session. The comparison file came out

Proven links went from 206,617 to 206,916 and assumption-marked links from

41.3 CPU seconds, with 553.8, 535.3 and 546.8 MiB.

## Work remaining

- Built-in derive identity is worth links only once the competing
  macro-use and glob imports are closed. Helix accounts for 8,639 of the
  9,352 sole-blocker sites in the built-in derive row. Its `helix-term`
  crate imports macros from `helix_view` with a bare `#[macro_use]`. The
  captured library root contains an external `slotmap::new_key_type!`
  invocation, so its export set stays open. A library can re-export a
  procedural derive into the macro-use prelude, so the spelling alone proves
  nothing. The largest mixed combinations also need an output bound for
  another macro or derive.
  [Mixed combinations](../../evidence/c-34/attribute-mixed.tsv)

- The overlapping module `macro_rules!` class covers 21,434 sites on main.
  Many involve an expansion with more than a fixed impl shape. The samples
  include item-producing repetitions, imports, nested calls and attributes.
  `lsp_enum!`, `embed_files!`, and `codegen_reexport!` either emit nameable
  items or need a proof about the tokens they accept and forward.
- External attributes, derives and item macros need an independently
  established identity and output bound. A documented external behavior can
  only use the recorded assumption when source leaves its output open.
  The diagnosed placement and glob guards still apply. The census found
  2,947 links with an identified external item macro and 19,349 with an open
  item-macro identity. In the coverage plan's Rustls example,
  `mio::Interest::READABLE` meets the existing assumption for Clap's `Parser`
  derive. The graph still needs proof of the library member to close the link.
- There were 2,288 sites with an external or unverified block-statement
  macro and 434 with a captured block-local macro. Items inside the block
  can shadow uses in that block. The existing enclosing-scope walk already
  separates uses outside the block and inside a sibling block. A nested
  macro export is a separate crate-root effect. [Rust Reference, scopes](https://doc.rust-lang.org/reference/names/scopes.html)
- Namespace-specific output bounds for named structs, aliases and values
  would need to travel through nested expansions. Tuple and unit structs
  also bind the value namespace. The census counts searched namespaces
  because a type name alone cannot establish which namespace was in reach
  at a use. [Rust Reference, namespaces](https://doc.rust-lang.org/reference/names/namespaces.html)

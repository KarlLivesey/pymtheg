# C-35: What a cold index spends in the store

## Where the time goes

Cold indexes on main, with the store on memory-backed storage. Each
statement's time includes the triggers and index updates it causes.
Repositories are bare checkouts of the pinned commits.

| Pin | Wall s | SQL s | Link inserts s (rows inserted / stored) | Symbol inserts s (inserted / stored) | Link deletes by file s | Target updates s | Library inserts s | Commits s (count) |
|---|--:|--:|--:|--:|--:|--:|--:|--:|
| restic/restic | 63.7 | 49.9 (78%) | 22.5 (122,648 / 64,165) | 4.6 (15,123 / 8,092) | 5.3 | 7.4 | 3.8 | 3.1 (957) |
| cli/cli | 209.5 | 163.1 (78%) | 70.2 (410,676 / 218,286) | 23.9 (53,163 / 28,670) | 15.4 | 20.5 | 13.7 | 9.9 (2,162) |
| trpc/trpc | 262.3 | 224.4 (86%) | 94.9 (107,470 / 107,470) | 71.4 (17,804 / 17,804) | 0.0 | 23.9 | 21.9 | 7.5 (2,711) |
| helix-editor/helix | 307.3 | 228.6 (74%) | 127.3 (181,128 / 90,780) | 48.6 (16,837 / 8,461) | 19.1 | 12.7 | 6.9 | 7.6 (543) |
| BurntSushi/ripgrep | 43.9 | 19.4 (44%) | 9.9 (78,365 / 39,819) | 1.8 (8,784 / 4,392) | 1.3 | 2.4 | 1.6 | 1.0 (208) |

A link insert took 0.2 to 0.9 ms and a symbol insert 0.3 to 4 ms. That is
far more than the row needs. A micro-benchmark with the production schema
found the cause (`scripts/store-cost/micro.mjs`, 18,000 to 24,000 rows of
each kind; [results](../../evidence/c-35/micro.txt)). The
completion-invalidation triggers of C-22 and C-27 write, so SQLite keeps a
statement journal for every graph write statement inside a transaction.
A journal that fits a small buffer (64 KiB) stays in memory and is cleared
when its statement ends. Once one statement's journal passes that buffer,
SQLite moves it to a temporary file, which stays open for the rest of the
transaction; every later write statement then writes the old content of
each page it changes to that file. On a cold restic index at main, 914 of
956 transactions spilled (measured in review). The temporary directory was
on disk even when the store was in memory.

| Schema variant | Symbol insert µs | Link insert µs |
|---|--:|--:|
| Production | 355–804 | 103–243 |
| Without the invalidation triggers | 19–21 | 11 |
| Without the secondary indexes | 5–7 | 6–9 |
| Foreign keys off | 342–811 | 126–453 |
| Statement journals in memory | 28–34 | 15–18 |

Neither the triggers nor the indexes are slow by themselves: the triggers
cause the journal and the indexes fill it. Foreign keys make no
difference.

## Where the bytes are

MiB in the final cold store, the same before and after this change.

| Pin | Database | Links table | Link indexes | Files table | of which source text | of which parse result | Symbols and their indexes | Library targets and their indexes | Other |
|---|--:|--:|--:|--:|--:|--:|--:|--:|--:|
| restic/restic | 130.2 | 59.2 | 21.5 | 19.4 | 2.3 | 16.1 | 13.6 | 11.8 | 4.7 |
| cli/cli | 462.6 | 215.1 | 73.8 | 76.0 | 10.4 | 62.6 | 50.3 | 43.1 | 4.3 |
| trpc/trpc | 227.7 | 102.9 | 37.8 | 32.2 | 5.5 | 24.5 | 31.1 | 23.3 | 0.3 |
| helix-editor/helix | 196.2 | 102.4 | 28.2 | 43.3 | 3.5 | 39.2 | 15.3 | 6.7 | 0.2 |
| BurntSushi/ripgrep | 93.4 | 46.7 | 12.6 | 20.4 | 1.8 | 18.4 | 8.1 | 5.3 | 0.1 |

Links are the store. The links table and its indexes hold 62 to 67% of
each file, about 1.4 KiB per link on cli/cli. Each link row stores its full
JSON record beside the columns that repeat parts of it. Each file record
also keeps its parse result, whose symbols and links are stored again as
rows; that is 11 to 20% of the database. Source text is under 3%. A
mixed checkout such as vercel/turborepo stores the links of three languages
on that scale, which is why its store reached 1.4 GB.

## What changed

The store's write transaction turns on in-memory temporary storage
(`PRAGMA temp_store=MEMORY`) just before `BEGIN IMMEDIATE` and turns it
back to the default straight after. SQLite decides where a transaction's
statement journals go when the transaction begins, so the journals stay
in memory. Sorts and other temporary files keep their usual place, so a
whole-module link read, which sorts in a temporary B-tree, is not sorted
in memory. A first version set the setting for the whole connection; it
was as fast but sorted those reads in memory.

The setting belongs to the connection. The database file, its schema, its
journal mode and its rows are unchanged, and nothing re-indexes.

How each guarantee is kept:

- **Rows.** The change chooses where SQLite puts a scratch file. Cold
  stores equal main's row for row on five pins in three languages, in
  memory and on disk (below).
- **Crash recovery.** A statement journal only undoes one statement within
  its transaction. SQLite never reads it to recover from a crash; the
  write-ahead log or rollback journal does that, as before. Commits,
  their boundaries and their order are unchanged, so the unfinished-run
  mark, run ownership, take-over detection and the completion records
  behave as before. No new write boundary exists, and the kill and race
  tests run unchanged.
- **Invalidation.** The triggers are untouched. A direct write through
  the API or another connection still removes the completion records.
- **Memory.** The in-memory statement journal holds the old content of
  the pages one statement changes and is freed when that statement ends;
  it does not add up across a transaction. Most write statements touch one
  row or one file's rows. Removing a file or a symbol also changes the
  links in other files that target it, so its journal grows with how
  widely the file is used: the largest measured in review were 11.7 MB on
  restic and 22.3 MiB on cli/cli (removing each pin's most-referenced
  file). A store the size of turborepo's was not measured. Peak RSS stayed within the noise on four
  pins. TypeScript analysis on trpc varies a lot from run to run: main
  peaked at 1,112, 1,126, 1,610 and 1,635 MiB in four runs, and this change
  at 1,114, 1,454, 1,646, 1,741 and 1,753 MiB in five.
  `test/graph-index-memory.test.mjs` is unchanged and passes; it counts
  decoded JavaScript records, which this change does not touch.

A new test, `test/graph-store-statement-journal.test.mjs`, indexes 20
synthetic files and checks the process's open files after every statement
for SQLite's temporary files. It finds one on main and none with this change.
It counts, so it does not depend on machine speed.

## What remains, largest first

Measured on top of this change unless stated otherwise.

1. **Fewer, larger transactions on disk.** Each parsed file and each
   analysed file is its own commit, and each commit rewrites the index
   pages it touched. A measurement-only variant that merged 50 store commits
   into one took restic on disk from 66.2 to 40.1 s and the bytes written
   from 2,289 to 1,026 MiB. On cli/cli the time fell from 274.6 to 209.5 s
   and the bytes from 8,751 to 6,154 MiB. Rows were identical. C-6 rejected
   bounded batches because they measured slower then, before this change,
   and because a second writer waits longer between commits. Building it
   needs a store batch API, kill points at each batch boundary and a
   decision on how long another writer may wait. Not built.
2. **Write each link and symbol once.** Go and Rust store a file's parse
   result and then replace it with the analysed result. Links are inserted
   1.9 to 2.0 times their final count and symbols 1.9 times. After this
   change that is 2.5 s of link inserts and 0.6 s of deletes on restic, and
   9.3 s and 2.4 s on cli/cli, so at most about half of it can be saved.
   Holding parse results until analysis would raise peak memory, which C-2
   removed. Not built.
3. **Invalidation triggers during a run.** Without them restic took 19.4 s
   instead of 20.2 s and cli/cli 73.7 s instead of 78.2 s, 4 to 6%. A
   run-scoped switch would have to keep "a completion record exists only
   while its triggers exist" through crashes and take-overs. Not built.
4. **Secondary indexes built at the end of a cold load.** Rejected: slower.
   restic took 27.1 s and cli/cli 231.4 s, because replacing a file's links
   by path needs `graph_link_file` (cli/cli: 147 s of deletes).
5. **Stored format (a later chunk).** About 11 to 20% of the database is
   the parse result kept in each file record, which also exists as rows.
   Each link's JSON record repeats its columns. Either would change what
   readers decode, so this chunk lists them only.
6. **Synchronous and journal settings.** Unchanged. C-6 already commits
   without a sync under the write-ahead log and checkpoints every 10,000
   pages.

## Proof

- Cold row-for-row equality with main on restic/restic and cli/cli (Go),
  trpc/trpc (TypeScript), helix-editor/helix and BurntSushi/ripgrep (Rust),
  with the store in memory and on disk. Every table that `dump.mjs`
  compares had the same row count and SHA-256 digest.
  [Results](../../evidence/c-35/)
- The equality was proved again after merging the current main.
- The full test suite, the re-index equality, kill, race and memory tests,
  and a seeded run of 30 restic edits through the command, each equal to a
  cold index. [Checks](../../evidence/c-35/checks.json)

The measurement scripts are in `scripts/store-cost/`.

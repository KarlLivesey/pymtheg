# C-46: The build-output route for TypeScript, assumption-marked

An unbuilt checkout has no build output, so a workspace package whose
entry is `dist/index.d.ts` cannot be read. C-25 follows such an entry to its
source when the compiler configuration proves the mapping (`outDir`,
`rootDir`, a plain `tsc` build). SW-6 counted what was left: 15,012 links
(1.04 points) stored as `workspace-build-output-missing` or
`workspace-entry-unavailable`, and Puppeteer's 7,532 `no-symbol` links
downstream of them (0.52 points).

C-46 follows the rest when a stated, checkable convention names a single
source entry. Each convention has its own assumption marker, so the
links are assumption-marked Level 2, never proven. Existing build output
and declarations always win: a convention is asked only about an output
path that is not in the checkout. Configs are read as syntax or JSON data;
no build file is executed.

TypeScript module version 50 here, provisional (assigned at merge; main is at 49).

## Review round 5

- **What an entry's source brings in.** The pass without assumed entries
  (the differential that marks links resting on a route) checked only the
  entry's source and the files importing it, and sent every file through
  only when one of those declared globals or augmented a module. An
  entry's source that imports a plugin's `declare module "host"` or
  `declare global` reaches files that never import the entry: a link to
  the augmentation was definite with no marker. Now the files only the
  route brings into the program are found (reached from the entries'
  sources and not otherwise from a file nothing imports); when one of
  them declares globals or augments a module, every file is checked
  without the route. Such a link differs without the route and supplies
  no entry of its own, so it keeps the outcome without the route
  (unresolved, as on main). Tested on the `src/` twin and on the compiler
  emit under Wireit. A plain `tsc` build is C-25's compiler proof: the
  real build emits the augmentation too, so those links stay definite and
  unmarked.

  ([neutral.mjs](../../evidence/c-46/tools/neutral.mjs); CPU seconds are

## Review round 4

- **`stripInternal` through a config that extends a package.** The strip
  rule read only the configs whose emit paths are scoped, and a config
  leaves that set as soon as its `extends` names a package
  (`@tsconfig/node20/tsconfig.json`, a workspace
  `@repo/typescript-config/base.json`). It now reads every config the
  project model read completely: a route withholds `@internal`
  declarations when the package's own config, or any completely read
  config whose files include the source, sets `stripInternal`, directly
  or through its bases. A config of the package whose base could not be
  read (not installed) leaves its strip setting unknown, so the package
  gets no convention route. Tested in
  `test/graph-typescript-installed.test.mjs` (both package-extends shapes
  and the unread base).
- **Further work** (still linked):
  - an `@internal` re-export (`/** @internal */ export { gone } from
    "./a"`), also by main's project-reference route;
  - a stripping config that covers the source only through imports
    (`files: ["src/cli.ts"]`);
  - `stripInternal` set only in a bundler's declaration options (tsup
    `dts.compilerOptions`, rollup-plugin-dts).

## Review round 3

Each item is an assumption-marked link to something the built package
would not expose. The cheap ones are fixed; the rest are known limits.

**Fixed:**
- **The types entry's own config.** A rollup config that is a list of
  objects, each with an `input` and an `output.file`, is read object by
  object. The object writing exactly the types file decides; one writing
  a file of the same stem only counts when none does. So
  `[{ input: "src/index.ts", output: { file: "dist/index.js" } },
  { input: "src/public-api.ts", output: { file: "dist/index.d.ts" }, plugins: [dts()] }]`
  routes `dist/index.d.ts` to `src/public-api.ts`. The `dir` convention no
  longer applies to a config whose objects name their output files.
- **API Extractor as data.**
  - A config under `config/api-extractor.json` (the tool's default place)
    is read.
  - `extends` chains through relative paths, merging `dtsRollup`.
  - The `<unscopedPackageName>` and `<packageName>` tokens are expanded
    from the manifest's `name`.
  - An `extends` of a package, an uncaptured base or any other token
    leaves the config unreadable.
- **A roll-up tool with no readable config refuses the twin.** When the
  package's scripts (or Wireit commands) run `api-extractor` or
  `dts-bundle-generator` and no readable API Extractor config says what it
  writes, a declaration entry gets no convention. The twin would name
  declarations the roll-up may drop (`@beta`, `@internal`).
- **An unreadable entry blocks the twin.** A bundler config whose entry is
  present but not data (a template literal `` `${dir}/index.ts` ``, a
  computed list) could name any source, as readable entries that list
  other outputs could. Neither leaves the twin.

- **A manifest field as an entry.** `input: pkg.source`, with `pkg`
  imported or required from a relative JSON file, is read as that field's
  value (React Hook Form). Without it the rule above would have taken
  React Hook Form's 216 links.
- **A folder beside a single file.** Only a config object writing exactly
  the types file overrides the `dir` rule for it. A first version skipped
  the `dir` rule for any config with an `output.file` object and dropped
  Vitest's 6,629 links; on single-pin indexes the fixed rule gives Vitest
  6,629 and React Hook Form 216 bundler-entry links.

**Lost by the unreadable-entry rule:** Redux Toolkit's 243 twin links,
which round 1's real `tsdown` build showed correct. Its `tsdown` config
computes its entry keys (`[`${dir}/${prefix}.modern`]`), so the entry is
present but not data, and the rule blocks the twin as the review asked.

**Measured** at review round 5's head ("Before and after" below): Redux
Toolkit gains nothing.

The first round's tests changed accordingly:
- `generated` (`dts-bundle-generator`, no config) and `opaque` (an entry
  that is not data) in `test/graph-typescript-resolution.test.mjs` no
  longer follow the twin.
- A new test covers the rules above
  (`test/graph-typescript-build-output.test.mjs`).

**Known limits (links lost, none wrong):**
- tsup array configs with a per-config `outDir`: the `dir` rule reads the
  config's directories, not each object's.
- Vite library mode: `build.lib.entry` with `fileName` is not mapped to
  the file name it gives.
- tsup `dts.entry` differing from `entry`: the declaration entry is not
  read separately.

**Re-index edits.** The seeded edits of the first round (below) edited
package manifests:
- adding a field;
- dropping the `types` entry;
- changing the version.

The reviewer's own fixture steps also covered `exports` edits and adding
and removing `dist`; each re-index equalled a cold index there.

## Review round 1

- **`stripInternal` from every config that governs the source.** A route
  withholds `@internal` declarations when any compiler configuration whose
  files include the source has `stripInternal`, not only the package's own
  (a root or build config elsewhere). Round 4 widened "any" to configs that
  extend a package too.
- **Rollup's `output.file`.** A config object's `input` beside its
  `output.file` (rollup-plugin-dts, a single-file bundle) names that
  output's source; more than one input for one file gives no route.
- **An unreadable roll-up blocks the twin.** The roll-up may write any
  entry, so no convention applies in the package (not even the `src/`
  twin) when:
  - an API Extractor config does not parse;
  - a roll-up field or main entry is not a literal path (a token other
    than `<projectFolder>`);
  - a rollup config's entries are not data.
- **The second analysis.** The pass without assumed entries (the neutral
  program that decides which links rest on an assumption) now extracts only
  the files that import an assumed entry's source, directly or through
  other files. Every file is extracted when one of them declares globals
  or augments a module. On Puppeteer this saves little: 660 → 638 neutral
  extractions, 158 → 156 CPU s for a cold TypeScript index, since almost
  every file there imports the routed packages. What remains is the neutral
  programs themselves (11 on Puppeteer). Removing them needs per-link
  provenance of the assumed entries in place of the differential; that is
  not built here.

## Review round 2

- **`@internal` behind a `noEmit` config** (Vitest's `tsconfig.base.json`:
  `noEmit` and `stripInternal`). Round 1's rule already reads
  `stripInternal` from every config whose files include the source,
  `noEmit` and inherited ones included; the reviewer's repro is now a test
  and passes. Of the 18,584 gained links, 50 reach an `@internal`
  declaration and none an `@alpha` or `@beta` one. All 50 are on
  Puppeteer, through `puppeteer-core's` `./internal/*` per-file `tsc`
  emit, which keeps `@internal` (its compiler configs do not strip), and the
  reviewer's real Puppeteer build found every gained link exported. So no
  further marker is added.
- **`scripts/reindex/install.mjs`**: main already has the package-manager
  prefix fix (C-47), and this branch's copy is main's.
- **The cold cost of the second analysis.** On a pin with a convention
  route the TypeScript module builds a second program per project that sees
  an assumption-marked entry, and re-extracts there the files that import
  one: the programs about double (changesets 4 → 8). Over the 19 pins cold
  CPU rose about 5% (5,056 → 5,297 s, round 1's sweep), nearly all of it
  on Puppeteer, Vitest and Vite. A pin with no convention route pays
  nothing: the second programs are built only when some workspace entry is
  assumption-marked, as on main (C-25). A cold TypeScript index, main
  against this branch (`neutral.mjs`-style counters, CPU seconds on a
  shared server):

  | Pin | CPU s | Neutral programs | Files re-extracted without the routes |
  | --- | --- | --- | --- |
  | changesets/changesets | 24 → 36 | 0 → 4 | 0 → 104 |
  | puppeteer/puppeteer | 73 → 140 | 1 → 11 | 99 → 638 |
  | vitest-dev/vitest | 284 → 403 | 2 → 33 | 1,282 → 4,558 |

  On main a TypeScript edit already re-analyses the whole project, so a
  one-file edit on a pin with convention routes pays the same differential
  as a cold index: changesets builds 8 programs and makes 268 extractions
  instead of 4 and 164, Puppeteer 27 and 1,146 instead of 17 and 607.

  The ordinary extraction is the same on both builds (164, 508 and 2,533
  files). The whole increase is the differential: per project, a program
  built without the assumed entries, and the re-extraction of the files
  that can see one. It is what tells which links rest on a convention: a
  link whose outcome differs without the route is assumption-marked, also
  when the convention only types its receiver
  (`const x = routed(); x.local()`). Marking by target file alone would
  leave such links unmarked. Warming only the re-extracted files did not
  reduce it (changesets 45 s, Puppeteer 145 s on the same server).
  **Not removed here.** Doing it in one pass means recording, in the one
  program, which files entered it only through assumed routes, and marking
  a link when its targets or any declaration its receiver chain reads lies
  in them (C-41's receiver walk reads exactly that chain), then validating
  that against the differential on every pin before the differential goes.
  That is its own chunk.

## The conventions

All four apply only where C-25 has no proof. That means no compiler
config emits there, or one does but C-25 refused it because another
producer writes the output (a roll-up, a bundler config, a Wireit wrapper,
an entry argument). A refusal from the compiler's own facts stands: an
unproven common root, a JavaScript-only emit, a stripped declaration
build, a compiler-option override, a rewrite of the output. The compiler
also decides alone when it is the package's build: a literal `tsc` build of
the package, or of an ancestor for a package without its own build. It
also decides when a package config emits JavaScript without declarations
into the output's folder and the package names no bundler.

| Convention | Assumption | What names the source |
| --- | --- | --- |
| Bundler entry | `ts-unbuilt-entry-is-bundler-entry` | The package's bundler config (tsup, tsdown, unbuild, rollup, vite, rolldown, esbuild; at the package root or named by a script's `-c`). Its entry list is read as data: a string, an array, a keyed object, a top-level `const` bound to one, or one passed through a helper call (`input: dtsUtils.dtsInput(dtsEntries)`). The output `<dir>/<name>.<ext>` comes from the entry keyed `name`, or from the listed path whose stem relative to the entries' common base is `name`. `dir` is a literal `dir` or `outDir`, or `dist`. Two configs that name different sources, or a listed path that is not a source, give no route. Readable entries that list only other outputs leave no route either, not even the twin. |
| Roll-up entry | `ts-unbuilt-entry-is-rollup-entry` | An API Extractor config whose `dtsRollup` names this output. Its `mainEntryPointFilePath`, itself an output, is mapped by the compiler configuration (build guards aside), the twin or the bundler entry. A trimmed roll-up drops declarations by release tag: `@internal` ones are withheld one by one, as C-25 does for `stripInternal`. Beta or public trimming in a source tree that uses `@alpha` or `@beta` gives no route. |
| `src/` twin | `ts-unbuilt-entry-is-src-twin` | The output's path with its first folder (`dist`, `lib`, `build`, `out`, and a second `types`, `src`, `esm`, `cjs`, `dts` or `mjs` folder) replaced by `src` and exactly one source extension (`.ts`, `.tsx`, `.mts`, `.cts`). Used only when no readable bundler entry list speaks to the output. |
| Wrapped compiler emit | `ts-unbuilt-entry-is-wrapped-compiler-emit` | The package's own compiler configuration, when C-25 refused it only for a Wireit wrapper or for a declaration roll-up of another entry. The roll-up reads these per-file outputs; Puppeteer's `./internal/*` are such outputs. |

A build script that literally writes the output (C-25's rewrite check)
rules out every convention. A package config with `stripInternal` makes the
route withhold `@internal` declarations one by one.

Two fixes in the route itself:
- **A package at the repository root** (React Hook Form) computed its
  relative output path wrongly.
- **Exports with a subpath pattern** (`"./internal/*": "./lib/puppeteer/*"`)
  took a different candidate. With a `.js` specifier, C-25 exposed the
  compiler's own `.ts` and `.tsx` probes of the same file as unproven
  explicit entries, and the retry chose `Page.ts` over the proven
  `Page.d.ts`. A source-extension probe of a proven candidate's own stem is
  no longer exposed (`project.ts`).

## Tests

rounds' own are listed with each round; the first round's are):

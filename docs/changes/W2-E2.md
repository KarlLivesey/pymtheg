## Scope and identity contract

This is a bounded first slice of mega-plan 3.3. Every local checkpoint created through `save()`
registers its documents, projected entities (including requirements and decisions)
and architecture relationships in `shared_record_ids`, inside the existing shared
planning database. Each registration has a random UUID, independent of machine
counters. The UUID is additional identity: existing local IDs such as `R1`,
`plan:R1`, content-addressed snapshot hashes and checkpoint IDs keep their meaning.
No source document or legacy ID is rewritten to insert a UUID.

Entity lookup keys are `(document path, existing entity ID)`. Link lookup keys
are `(document path, source, target, relation kind, duplicate ordinal)`; link
metadata edits that keep this key retain the UUID, while retargeting is a different
relationship. Duplicate identical links get distinct registrations. A recorded
removal retains the old UUID as a tombstone. Reappearance under the same key
creates a new UUID with a `previous` reference to its predecessor; edits without
removal keep the current UUID. All earlier generations remain exported, with
`hash: null` marking tombstones. There is no restore workflow.
Binding resolution that changes a name-derived endpoint key, a document move, or
an ambiguous local-ID rename needs an explicit identity-resolution
workflow later; this implementation never guesses a move from equal text.

`ArchitectureStore.exportRecordedHistory()` returns the identity registrations and
immutable recorded changes separately from the unchanged v1/v2/v3 architecture
archive formats. Checkpoint receipts reference the durable checkpoint (and hence
its immutable source snapshots); each delta has a global record UUID and before/
after content hashes. Acknowledgements, withdrawals and architecture-authoring
recovery draft writes also get receipts. Draft receipts retain hashes rather than
old draft payloads; this is an audit receipt, not a draft undo/replay implementation.

Every receipt has a globally unique random UUID, author, machine and actor token,
recorded time, checkpoint reference and database-wide logical commit sequence.
The deterministic total order is `(sequence, machine, actor, change UUID)` using
ordinal string comparison, **never timestamp or author-name order**. It preserves
transaction order within one database even when clocks tie or move backwards.
For independent offline stores it is a deterministic presentation order, not a
claim about physical chronology or causality between machines. No sync/merge API
is added. The two-machine test combines the exports in the test itself.

Production origins live in ignored `.pymtheg/local/writer.json`: UUID machine/actor
namespace tokens plus the local OS username as the default author label. Lookup
happens only when creating the writer file. A failed or empty lookup falls back
to nonempty `$USER`, then `$LOGNAME`, then `Unknown author`. Existing writer files
never invoke the lookup. To override attribution, edit `author` in
`.pymtheg/local/writer.json` (leave `machine` and `actor` unchanged), then reopen
the store or restart Studio. This affects future receipts; old receipts keep
their recorded author. These origins are
project-local writer installation identity, not hardware fingerprints, verified
people or authenticated signatures. Never copy/share `local/` to another machine;
share/export shared data only, or provide a different explicit writer identity.
Writer creation publishes complete files with a create-only hard link. Tests
inject identities and controlled clocks, without reading real time or hostname.

Old records read exactly as before. Read-only opens create neither tables nor
local identity. Writable opens create empty ledger tables but do not backfill
legacy events, authors or times. The first subsequent save registers the observed
current records; a null before-hash means no earlier ledger observation, not proof
that a legacy record was first created at that time. Receipts and registrations
roll back with a failed feature transaction; unchanged refreshes append nothing.
Identical draft contents and clearing an already-empty draft append no receipt,
including legacy drafts without ledger coverage. Conflict-control draft versions
still advance. An absolute project-root path is refused as a file location;
an explicitly unanswered empty draft path remains allowed.

## Shared path audit

Fixed in the permitted files:

- New checkpoint `source` values that are absolute paths become project-relative
  labels when inside the project, or `External source (machine-local location
  omitted)` when outside it. Studio import source labels use the same rule.
- New top-level document paths reject machine-local absolute paths and escapes.
- Architecture draft `document.path` and `target.document` become relative POSIX
  paths; outside-project absolute paths, backslashes and `..` escapes are refused.
  Empty unfinished draft paths remain empty. Studio recovery buffer `path` and
  context `file` values are normalized at the service write boundary as well.
  Existing stored text is not migrated.

Already relative in normal producers: architecture document references and index
entity/edge document fields; captured observation source paths and spans
(`src/implementation/capture.ts`, `src/implementation/schema.ts`). UI
`ProjectView.root` and execution scratch paths are not shared persisted paths.

Remaining precise path work (not claimed complete):

- `src/architecture/import-policy.ts:withImportInventory`: generated inventory
  JSON `source` can retain an absolute folder. Its retained bytes/checksum must not
  be silently rewritten by the generic store.
- `src/cli/main.ts` architecture import construction: source labels/IDs and
  inventory provenance need the same typed policy before documents are prepared.
- `src/architecture/import-merge.ts:sourceSchema/registrySchema`: `documents[].path`,
  `documents[].sourcePath`, `nativeDocuments[]`, `divergedDocuments[].path`,
  `sourcePath` and `upstreamPath` use permissive string schemas for imported data.
- `src/shared/source-contracts.ts`: catalogue `file` and diagnostic `file` fields
  are permissive strings; normal service producers already use relative paths.
- `src/studio/recovery.ts`: the underlying buffer/context string schemas and
  nested form/selection fields need schema-wide relative-path validation for
  direct callers. The permitted Studio service boundary now normalizes top-level
  buffer/context fields; this chunk does not own the lower-level recovery store.
- `src/architecture/history.ts` and `src/implementation/schema.ts`: imported old
  provenance/draft payloads and Windows drive spellings need a coordinated format
  policy. Legacy imports and arbitrary authored document bodies remain unchanged.

## Exact remaining identity/history work

The original record IDs remain aliases; clients/CLI do not yet display the new
UUIDs. The ledger export must be carried and validated in a future archive format
and imports must preserve global registrations and append import receipts. Legacy
archive import currently remains unchanged and does not invent event provenance.
Project registries/heading identity, source-contract/code observations as separate
native record types, and shared Studio buffer/form recovery mutations need their
own origin/receipt adapters beyond the checkpoint-level document/entity coverage.
No field-level edit log, semantic merge, automatic rename/move identity resolution,
portable actor provisioning UI, synchronization or causal reconciliation is built.

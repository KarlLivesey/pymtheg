# C-3 TypeScript lexical declarations and workspace packages

Nested function declarations, function expressions and arrows assigned directly
to a local `const` or `let`, and local classes and enums now have graph symbols.
Their IDs use the file, scoped name, kind and same-name ordinal. The scoped
name records the enclosing declaration, anonymous callback sites and intervening
blocks. A callback site uses its enclosing call expression and argument
position. Requirement links retain the selected location when a distinct
callback is inserted. Two known limits apply to `useEffect` callbacks.

- When handlers in two effects are textually identical, exchanging the effects'
  dependency lists and subscription arguments while leaving the handlers in
  place can move a requirement link to the other handler with status `ok`.
  Callback identity includes the dependency argument, and the handlers have
  the same fingerprint.
- Same-named handlers in callbacks with the same scope key, such as two
  `useEffect(..., [])` calls, report `ambiguous` after any edit to the file.
  Select the intended declaration explicitly to restore the link.

An existing `typeof` reference to a plain local variable or parameter targets
its enclosing symbol with the binding name and declaration span in
`data.localBinding`. The same link row provides the reference's source span.
Plain locals add zero symbol rows and zero new link sites. A scoped declaration
retains its first expression-use reference in each owner and its individual
call sites. Calls through parameters, unknown values, import shadows and local
callables with detected reassignment stay unresolved. Exact-name lookup and
search list top-level and exported declarations ahead of scoped ones. CLI and
MCP file listings show the module and top-level declarations before scoped
symbols when a result is limited.

Plain-local `typeof` references use the existing resolved-link scoring.
The all-site result includes new scoped
references and containment edges. The shared-site result uses only matching
pinned file, span, link kind and target spelling across the two graphs. The
coverage plan measures changes against the archived SW-3 sample.

`store.ts` applies the scoped ordering before the existing query limit.
`coverage-rules.mjs` keeps the two workspace-entry reasons inside the checkout
and excludes library credit. `coverage-export.mjs` counts those reasons and
provides the opt-in shared-site comparison. `coverage.mjs` labels the workspace
total as unresolved links, and `coverage.test.mjs` exercises the reasons under
an incomplete config.

The snapshot host supplies virtual install links from npm, Yarn and Bun
workspace manifests, pnpm workspace membership and dependency declarations,
and checkout-local `file:` and `link:` dependencies. TypeScript chooses the
actual module via the importing file's resolution mode, package entry maps,
configured paths or a project reference redirect. Relative extension lookup
can establish the same module-file edge as 0.1.0 for bundler and test sources. Module
augmentations affect symbol lookups independently of the selected entry.
A compiler lookup within a configured `outDir` or `declarationDir` records
`workspace-build-output-missing` when the output is absent. Other
unavailable entries of known local installs are `workspace-entry-unavailable`.
The 0.1.0 declaration rule for calls applies to relative and workspace imports,
aliases and factory results. When TypeScript chooses a `types` export with a
separate runtime entry in the checkout, the link records the selected `.d.ts`
declaration. Runtime implementation discovery is tracked separately.

The pnpm reader recognises the package-list block and relevant linking flag.
For a project pinned to Yarn 2 or later the model uses declared dependencies
for Plug'n'Play access.
Dependency scenarios requiring lockfile or package-manager override evaluation
can remain unresolved. A conflicting declaration suppresses the corresponding
shared workspace link where the install layout cannot be established.
Follow-up work includes mapping an output through the workspace package's own
`outDir` and `rootDir` where project reference resolution cannot do so, as in
Puppeteer's `puppeteer-core` imports from `@puppeteer/browsers`. Another case
is an `examples/` package outside the workspace patterns with a nonmatching
version range for a checkout package. Indirect callable values, local class
members, IIFEs, property-chain typing, type parameters and library targets
remain outside this change.

The TypeScript module version moves to 19 and existing stores reindex these
files.

The comparison's T3 Code examples come from a different checkout than SW-3.
The regression fixtures cover those declaration and import shapes and the
pinned corpus's `SessionCredentialService.ts:476` example. The pinned T3 Code
workspace uses Bun.

## Cold indexing cost

The earlier paired timings were taken on a loaded shared server. The
same-session measurements below supersede them. Both main runs used the same
pinned checkout, storage and default Node heap as the reviewed head.

| Repository | Main cold wall s, two runs | C-3 cold wall s | Main peak RSS MiB, two runs | C-3 peak RSS MiB |
| --- | ---: | ---: | ---: | ---: |
| Astro | 157.61 / 156.72 | 183.17 | 1,172 / 1,174 | 1,679 |
| Vitest | 137.39 / 134.76 | 150.30 | 1,518 / 1,526 | 1,530 |

Astro's peak RSS rose about 43%. Vitest's peak RSS was essentially unchanged.
In the workspace-off diagnostic on Astro, workspace resolution accounted for
33.61 s and 319 MiB and added 11.43 Level 2 points. On Vitest it accounted for
364 MiB and added 28.75 points. The Vitest wall difference fell within the
main runs' spread. [Cost profile](../../evidence/c-3/cost-profile.md)

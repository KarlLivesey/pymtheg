# C-50 `graph index` can be cancelled: the graph command runs in a worker

> **With C-48 merged.** `executeGraph` reports three states to
> `onModuleCall`: `true` during a module's synchronous call, `"awaiting"`
> while its promise is awaited, and `false` when it has settled.
>
> - **`true` is the module section.** The CLI worker marks only `true` as
>   the module section, and a cancel there terminates the worker.
> - **`"awaiting"` is cooperative.** The abort signal reaches the module
>   (Rust's phase worker, a toolchain's processes), as the Rust
>   cancellation tests need.
> - **A synchronous stretch after an await is marked by the module.** A
>   module that runs long synchronous code between its awaits wraps it in
>   `synchronousStretch` (`src/graph/sections.ts`). That stretch is
>   announced as `true` again, so a cancel there terminates the worker
>   too. Go marks its project-wide link notes (after `await
>   toolchainFacts`) and its parse (after `await parser()`).
> - **How the stretch finds its caller.** `sections.ts` keeps one listener
>   in module state. Each worker thread loads its own copy of the module, so
>   the listener is per thread. `executeGraph` installs its `onModuleCall`
>   there while it awaits a module call's promise and restores the previous
>   one when the promise settles; `synchronousStretch` reads it when it
>   starts. Two marks cannot cross, because a thread never awaits two
>   module calls at once. The CLI worker runs one command, and the MCP
>   worker refuses a request while one runs. The indexer awaits each
>   parse, analysis and resolution before the next. The listener is
>   restored as a stack, so a nested call would also find its own.
> - **An unmarked stretch is not covered.** Synchronous code a module runs
>   after an await without the mark stays cooperative: the cancel takes
>   effect at the module's next await, or when it settles.

C-47 found that a CLI `graph index` stuck inside a language module's
analysis ignored SIGTERM, the `timeout` command and a plain `kill`. Only
SIGKILL stopped it. The CLI's SIGINT and SIGTERM handler only aborts an
`AbortController`, which the graph command checks at its `await` points. A
module's analysis is one synchronous call on the main thread, so the event
loop never turned and the handler never ran.

`check` already meets AGENTS.md's CPU-cancellation contract: its analysis
runs in a worker that the coordinator terminates (`analyseInWorker`). The
MCP server's graph jobs run in a worker too (`src/mcp/graph-worker.ts`).
PR 56 (C-48, open) keeps that worker between jobs and terminates it when a
cancel finds it inside a module call. This change gives the CLI the same
shape, in its simplest form.

## What changed

- **`src/cli/graph-worker.ts`** holds the protocol (`serveGraphRequest`):
  run `executeGraph`, post progress, then post the response or the error
  message. The store is opened, written and closed in the worker; only the
  response crosses to the main thread. `src/cli/graph-worker-main.ts` is
  the production entry.
- **`src/cli/graph-runner.ts`** is the coordinator (`runGraphInWorker`).
  It starts the worker, relays progress to stderr as before, and resolves
  with the response. When the abort signal fires (SIGINT or SIGTERM, which
  includes `timeout`), it rejects with the same `AbortError` that
  `signal.throwIfAborted()` gives.
- **Where the worker is decides how it ends.** Memory shared between the
  coordinator and the worker holds a cancel flag and the worker's section,
  either the graph command itself or a language module's synchronous code.
  `executeGraph` announces the section through `onModuleCall`, the shape of
  C-48's hook (PR 56).
  - **Inside a module's synchronous code**, which is where the TypeScript
    module's analysis runs, the coordinator terminates the worker at once.
  - **Anywhere else**, it sends `cancel`, which aborts the worker's
    controller. The command then stops at its next checkpoint exactly as a
    cancelled run did before, recording the index as incomplete. While a
    module call's promise is awaited (the Rust module's phase worker), the
    event loop runs and the abort signal reaches the module, which ends
    its own worker, unless the module is in a synchronous stretch it marked
    (see above), which counts as inside the call.
  - **The handshake cannot miss.** The coordinator sets the flag and then
    reads the section; the worker sets the section and then reads the flag,
    refusing to enter a module once it is set. Both use sequentially
    consistent atomics, so one side always sees the other, and no
    wall-clock wait decides anything.
- **`graphCommand`** (`src/cli/graph.ts`) calls the coordinator instead of
  `executeGraph`. A cancelled run ends as before: exit code 130 and `Graph
  error: This operation was aborted` (or the JSON error with `exitCode`
  130). Two things differ from main, both because the command now runs on
  a worker thread:
  - **Deep files may now index.** A worker thread's JavaScript stack is
    about four times the main thread's (as the MCP worker's is). Rows are
    identical to main on the pins measured below. A file whose analysis
    exhausted the main thread's stack may now be indexed:
    - on microsoft/TypeScript, three binder-stress files that fail on
      main with "binder exhausted its stack" now index (symbols 274,386 →
      274,393, links 992,639 → 992,643, failed files 12,477 → 12,474,
      measured by reviewer B);
    - a deeply nested synthetic project fails 14 files on main and 1 here.
  - **Running out of heap.** It now ends with exit code 3 and `Graph error:
    Worker terminated due to reaching memory limit`, instead of V8's fatal
    abort. The store is left the same way in both.
- **Warnings.** The worker imports the filter of the two Node warnings
  Pymtheg relies on (`src/shared/quiet-warnings.ts`) first, as the CLI
  entry does, so Node 24.0.0 prints no `ExperimentalWarning` for
  `node:sqlite` in the worker. Every worker entry now does, and a source
  check (`test/worker-entries.test.mjs`) fails for one that does not.

**Child processes a terminated worker started** are killed through
C-54's registry (`src/backends/child-groups.ts`).

- **Ownership.** The coordinator gives each run a registry of its own
  (`jobChildGroups`) and passes it in `workerData`. The worker adopts it
  (`useChildGroups`) before it starts work, so `runProcess` records every
  group it spawns there.
- **The kill.** When the worker exits, for any reason, the coordinator
  kills what is still recorded (`releaseJobChildGroups`) before it answers
  a terminated run, so nothing the run started outlives the answer. C-54
  also kills the registry when the process exits.

**The store after a terminated run** is left as a killed CLI run leaves it.
The next index takes over the unfinished-run mark and repairs it; the
existing kill tests (`test/graph-reindex-kill.test.mjs`) cover that
repair.

**Fit with C-48.** The CLI runs one command per process, so it starts one
worker per command. It uses C-48's cancel-flag-and-section handshake and its
three-state `onModuleCall` hook, with the module section being `true` only.
The existing Rust cancellation tests (`test/graph-rust-finishing.test.mjs`,
SIGINT and SIGTERM during a CPU-bound analyze or resolve worker) need the
cooperative path and pass.

**`pymtheg link`** syncs and queries the graph too (`link list`, `link
check`, `link create`, `link refresh`): its graph work now runs through the
same coordinator (`useGraphRunner` in `src/architecture/code-links.ts`,
installed by `src/cli/link.ts`). Before, a sync stuck in a language module
ignored SIGINT there, and the toolchain's processes outlived the run. The
MCP links worker, already off the main thread, runs the graph in place.

## Tests

`test/graph-cli-cancel.test.mjs` runs the production coordinator with a
worker whose language module cannot finish
(`test/graph-cli-stuck-worker.mjs`, serving the production protocol).

- **No wait decides an outcome.** The module raises a flag in shared memory
  where the scenario needs it, and the scenario aborts on that flag
  (`Atomics.waitAsync`).
- **Each cancellation scenario runs in a child process**
  (`test/graph-cli-cancel-scenario.mjs`). A regression that leaves a worker
  or a process running would otherwise hang the test run. Instead the test
  kills the scenario's process group after three minutes, kills any child
  process it reported, and fails. That bound only turns a hang into a
  failure; it decides nothing when the test passes.

The scenarios:

- **A stuck synchronous call.** The run rejects with `AbortError`. Without
  the file that cannot be analysed, the next index is `ok`, and its stored
  symbols, links and files equal a cold index's row for row.
- **Child processes.** Inside the module call, the worker starts a child
  through `runProcess`, as a toolchain is started, and the child starts a
  grandchild in its process group. Neither can finish, and each holds a
  connection to the scenario's socket. After the abort both connections
  close. With `releaseJobChildGroups` removed, they never close and the
  test fails at the bound.
- **A marked synchronous stretch.** An async module awaits, then spins
  inside `synchronousStretch`. The abort terminates the worker. The MCP
  worker has the same test (`test/mcp-graph-session.test.mjs`): the cancel
  ends the worker at once, with no grace scheduled on its controlled
  clock. Unmarked, the stretch reads as awaited; the CLI scenario then
  ends at its bound, and the MCP test fires the grace and fails.
- **`pymtheg link list` and `link check`** (`test/link-cli-cancel.test.mjs`)
  run the real CLI with a preload
  (`test/fixtures/graph-cli/stuck-typescript.mjs`) that replaces the
  TypeScript module's analysis, in the graph worker only, with one that
  cannot finish and reports on stderr that it has started. On that line
  the test sends SIGINT. The CLI exits 130 with the JSON error, and the
  process ends; the module starts no process. The same three-minute bound
  turns a run that never exits into a failure.
- **The refusal to enter a module after a cancel.** An async module's
  continuation blocks in the awaited section (not inside the call) when the
  abort arrives, so the coordinator asks for a cooperative cancel. The
  scenario then releases it. The worker reaches the next module call
  before it reads the cancel message, sees the cancel flag, and refuses to
  enter: the call that cannot finish is never entered, and the run rejects
  with `AbortError`.
- **A run that is not aborted** answers through the worker, with progress
  through to `complete`.

The cooperative path is proved by the existing Rust cancellation tests.
They run the real CLI as a child process, wait for a readiness line from a
Rust phase worker that cannot finish, and send SIGINT or SIGTERM. The CLI
exits 130 with the JSON error, and `graph status` shows the index
incomplete with the partial results kept. They failed with the first
version of this change, which terminated the worker on every cancel, and
pass now.

## Measurements

Measured with the real CLI on four pins of three languages
([results](../../evidence/c-50/cli-cost.json),
[tool](../../evidence/c-50/cli-cost.mjs)). The builds were main `2804e45`
and this branch, alternating one run at a time over two rounds, so each
build ran twice. Each run was a fresh process: a cold `graph index` on a
fresh copy of the installed checkout, then a one-file edit (a comment line
appended to the first source file) and an incremental index. The times
were taken under GNU time; the peak is the whole process's resident set,
both threads. These are observations on a shared server.

| Pin | Cold wall s, main → head | Cold CPU s, main → head | Peak MiB, main → head | Edit wall s, main → head |
| --- | --- | --- | --- | --- |
| honojs/hono | 74.5, 59.3 → 60.7, 60.1 | 103.0, 90.9 → 95.8, 91.9 | 1,671, 1,659 → 1,521, 1,674 | 56.6, 55.1 → 45.5, 55.0 |
| vitest-dev/vitest | 188.0, 171.5 → 179.0, 157.8 | 258.5, 242.0 → 253.0, 229.6 | 3,327, 3,375 → 3,430, 3,329 | 160.1, 144.5 → 155.8, 160.5 |
| cli/cli | 149.7, 132.1 → 131.6, 127.8 | 156.8, 142.4 → 146.0, 140.2 | 1,601, 1,568 → 1,622, 1,619 | 11.8, 10.9 → 14.0, 11.5 |
| DioxusLabs/dioxus | 518.8, 559.0 → 567.0, 534.7 | 594.8, 632.7 → 630.3, 603.1 | 3,031, 3,123 → 2,964, 3,113 | 417.0, 468.5 → 543.6, 505.0 |

This first set was measured with the first version of the coordinator,
which differed only in how it ends a cancelled run. Every difference is
within the spread of the same build's two runs, except dioxus's edit:
417.0 and 468.5 s on main against 543.6 and 505.0 s here. So dioxus was
measured again, with the final build, over two more rounds
([results](../../evidence/c-50/cli-cost-dioxus-final.json)):

- cold, main 600.7 and 604.1 s, this branch 605.2 and 556.5 s;
- edit, main 466.6 and 429.5 s, this branch 460.7 and 462.9 s;
- peak, main 3,066 and 3,090 MiB, this branch 3,087 and 3,078 MiB.

These are within the spread, so the first gap was the shared server's
noise.
Starting the worker and loading the language modules there costs no
measurable time against a cold index. The peak resident set is unchanged
too, because the work moved from one thread to the other; the main thread
holds only the relayed progress and the response.

**What crosses the thread boundary** is the response: 3.7 KB on Hono,
28 KB on Vitest, 26 KB on cli/cli and 21 KB on dioxus (`graph index
--json`). The store is opened, written and closed in the worker, so no
results are copied between threads. Run ownership is per run, not per
thread, so writing from the worker needs nothing else.

**Rows are identical to main on these pins.** After the last round, the two
builds' stores were compared row for row (files that exhausted the main
thread's stack may differ elsewhere; see above):

- cli/cli and dioxus are identical as stored;
- Hono and Vitest are identical except for the `node_modules` context
  stamps, which record the copied directory's inode number and
  modification time and so differ between any two copies of a checkout.
  With those stamps normalised, they are identical
  ([tool](../../evidence/c-50/compare-stores.mjs)).

## Not built

- **C-48's persistent worker for the CLI.** A CLI process runs one command,
  so there is nothing to keep.
- **A deadline.** With the worker, cancellation is effective. A time limit
  would make results depend on the machine, so the deterministic bounds
  (C-26, C-47) stay the guard against analysis that does not return.

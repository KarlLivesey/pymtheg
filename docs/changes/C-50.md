# C-50 `graph index` can be cancelled: the graph command runs in a worker

> **For C-48 (PR 56, head `edab513`): where "inside a module" should end,
> so the MCP worker is cancelled cooperatively outside a module's
> synchronous code.**
>
> 1. **End "inside a module" when the call returns its promise.** In
>    `src/graph/commands.ts`, `inModule` (lines 436–445) and
>    `toolchainCall` (lines 323–331) call `onModuleCall(true)`, then
>    `await call()`, and only then `onModuleCall(false)` in `finally`.
>    While the promise is awaited, the event loop runs and the abort signal
>    reaches the module (the Rust phase worker, a toolchain's processes),
>    so a cancel there should be cooperative, not a terminate. Mark only
>    the synchronous part, as this branch's `inModule` does:
>
>    ```ts
>    let pending: T | Promise<T>;
>    options.onModuleCall?.(true);
>    try {
>      signal.throwIfAborted();
>      pending = call();
>    } finally {
>      options.onModuleCall?.(false);
>    }
>    return await pending;
>    ```
>
> 2. **Child processes.** A terminated worker leaves a toolchain's process
>    groups running. That is fixed in one place for every route by C-54
>    (`src/backends/child-groups.ts`, branch `c-54-child-process-groups`):
>    the MCP server owns the registry and kills its groups after a
>    terminate, and the worker adopts it with `useChildGroups`. This
>    branch's CLI coordinator takes the same two calls once C-54 merges.

C-47 found that a CLI `graph index` stuck inside a language module's
analysis ignored SIGTERM, the `timeout` command and a plain `kill`. Only
SIGKILL stopped it. The CLI's SIGINT and SIGTERM handler only aborts an
`AbortController`, which the graph command checks at its `await` points. A
module's analysis is one synchronous call on the main thread, so the event
loop never turned and the handler never ran.

`check` already meets AGENTS.md's CPU-cancellation contract: its analysis
runs in a worker that the coordinator terminates (`analyseInWorker`). The
MCP server's graph jobs run in a worker too (`src/mcp/graph-worker.ts`).
PR 56 (C-48, open) keeps that worker between jobs and terminates it when a
cancel finds it inside a module call. This change gives the CLI the same
shape, in its simplest form.

## What changed

- **`src/cli/graph-worker.ts`** holds the protocol (`serveGraphRequest`):
  run `executeGraph`, post progress, then post the response or the error
  message. The store is opened, written and closed in the worker; only the
  response crosses to the main thread. `src/cli/graph-worker-main.ts` is
  the production entry.
- **`src/cli/graph-runner.ts`** is the coordinator (`runGraphInWorker`).
  It starts the worker, relays progress to stderr as before, and resolves
  with the response. When the abort signal fires (SIGINT or SIGTERM, which
  includes `timeout`), it rejects with the same `AbortError` that
  `signal.throwIfAborted()` gives.
- **Where the worker is decides how it ends.** Memory shared between the
  coordinator and the worker holds a cancel flag and the worker's section,
  either the graph command itself or a language module's synchronous code.
  `executeGraph` announces the section through `onModuleCall`, the shape of
  C-48's hook (PR 56).
  - **Inside a module's synchronous code**, which is where the TypeScript
    module's analysis runs, the coordinator terminates the worker at once.
  - **Anywhere else**, it sends `cancel`, which aborts the worker's
    controller. The command then stops at its next checkpoint exactly as a
    cancelled run did before, recording the index as incomplete. A module
    call that returns a promise, such as the Rust module's phase worker,
    ends the section when it returns: while it is awaited, the event loop
    runs and the abort signal reaches the module, which ends its own worker.
  - **The handshake cannot miss.** The coordinator sets the flag and then
    reads the section; the worker sets the section and then reads the flag,
    refusing to enter a module once it is set. Both use sequentially
    consistent atomics, so one side always sees the other, and no
    wall-clock wait decides anything.
- **`graphCommand`** (`src/cli/graph.ts`) calls the coordinator instead of
  `executeGraph`. Its output, its exit codes and the cancelled run's result
  are unchanged: exit code 130 and `Graph error: This operation was
  aborted` (or the JSON error with `exitCode` 130).

**Child processes** a terminated worker started (a toolchain's process
groups) are C-54's to kill; the coordinator adopts C-54's registry when it
merges (see the note for C-48 above).

**The store after a terminated run** is left as a killed CLI run leaves it.
The next index takes over the unfinished-run mark and repairs it; the
existing kill tests (`test/graph-reindex-kill.test.mjs`) cover that
repair.

**Fit with C-48.** The CLI runs one command per process, so it starts one
worker per command, which is the MCP server's shape on main. It uses
C-48's cancel-flag-and-section handshake, and the same `onModuleCall` hook.
There is one refinement, which C-48 should take when the two meet: here the
section covers a module's synchronous code only. C-48 marks the whole call,
including the time a returned promise is awaited, so a cancel during the
Rust module's phase worker would end the MCP worker instead of cancelling
cooperatively. The existing Rust cancellation tests
(`test/graph-rust-finishing.test.mjs`, SIGINT and SIGTERM during a CPU-bound
analyze or resolve worker) need the cooperative path and pass here.

## Tests

`test/graph-cli-cancel.test.mjs` runs the production coordinator with a
worker that cannot finish (`test/graph-cli-stuck-worker.mjs`).
That worker serves the request with the production protocol and a language
module whose analysis of one file loops forever, synchronously. Nothing
depends on time:

- **Readiness.** Before it loops, the module raises a flag in shared
  memory. The test waits on the flag (`Atomics.waitAsync`), so it aborts
  only when the worker is inside the module call.
- **The abort ends the run.** The run rejects with `AbortError`, and the
  worker is terminated: the test process exits.
- **The next index repairs the store.** Without the file that cannot be
  analysed, the next index is `ok`, with the same counts as a cold index of
  the same files.
- **A run that is not aborted** answers through the worker, with progress
  through to `complete`.

The cooperative path is proved by the existing Rust cancellation tests.
They run the real CLI as a child process, wait for a readiness line from a
Rust phase worker that cannot finish, and send SIGINT or SIGTERM. The CLI
exits 130 with the JSON error, and `graph status` shows the index
incomplete with the partial results kept. They failed with the first
version of this change, which terminated the worker on every cancel, and
pass now.

## Measurements

Measured with the real CLI on four pins of three languages
([results](../../evidence/c-50/cli-cost.json),
[tool](../../evidence/c-50/cli-cost.mjs)). The builds were main `2804e45`
and this branch, alternating one run at a time over two rounds, so each
build ran twice. Each run was a fresh process: a cold `graph index` on a
fresh copy of the installed checkout, then a one-file edit (a comment line
appended to the first source file) and an incremental index. The times
were taken under GNU time; the peak is the whole process's resident set,
both threads. These are observations on a shared server.

| Pin | Cold wall s, main → head | Cold CPU s, main → head | Peak MiB, main → head | Edit wall s, main → head |
| --- | --- | --- | --- | --- |
| honojs/hono | 74.5, 59.3 → 60.7, 60.1 | 103.0, 90.9 → 95.8, 91.9 | 1,671, 1,659 → 1,521, 1,674 | 56.6, 55.1 → 45.5, 55.0 |
| vitest-dev/vitest | 188.0, 171.5 → 179.0, 157.8 | 258.5, 242.0 → 253.0, 229.6 | 3,327, 3,375 → 3,430, 3,329 | 160.1, 144.5 → 155.8, 160.5 |
| cli/cli | 149.7, 132.1 → 131.6, 127.8 | 156.8, 142.4 → 146.0, 140.2 | 1,601, 1,568 → 1,622, 1,619 | 11.8, 10.9 → 14.0, 11.5 |
| DioxusLabs/dioxus | 518.8, 559.0 → 567.0, 534.7 | 594.8, 632.7 → 630.3, 603.1 | 3,031, 3,123 → 2,964, 3,113 | 417.0, 468.5 → 543.6, 505.0 |

This first set was measured with the first version of the coordinator,
which differed only in how it ends a cancelled run. Every difference is
within the spread of the same build's two runs, except dioxus's edit:
417.0 and 468.5 s on main against 543.6 and 505.0 s here. So dioxus was
measured again, with the final build, over two more rounds
([results](../../evidence/c-50/cli-cost-dioxus-final.json)):

- cold, main 600.7 and 604.1 s, this branch 605.2 and 556.5 s;
- edit, main 466.6 and 429.5 s, this branch 460.7 and 462.9 s;
- peak, main 3,066 and 3,090 MiB, this branch 3,087 and 3,078 MiB.

These are within the spread, so the first gap was the shared server's
noise.
Starting the worker and loading the language modules there costs no
measurable time against a cold index. The peak resident set is unchanged
too, because the work moved from one thread to the other; the main thread
holds only the relayed progress and the response.

**What crosses the thread boundary** is the response: 3.7 KB on Hono,
28 KB on Vitest, 26 KB on cli/cli and 21 KB on dioxus (`graph index
--json`). The store is opened, written and closed in the worker, so no
results are copied between threads. Run ownership is per run, not per
thread, so writing from the worker needs nothing else.

**Rows are identical to main.** After the last round, the two builds'
stores were compared row for row:

- cli/cli and dioxus are identical as stored;
- Hono and Vitest are identical except for the `node_modules` context
  stamps, which record the copied directory's inode number and
  modification time and so differ between any two copies of a checkout.
  With those stamps normalised, they are identical
  ([tool](../../evidence/c-50/compare-stores.mjs)).

## Not built

- **C-48's persistent worker for the CLI.** A CLI process runs one command,
  so there is nothing to keep.
- **A deadline.** With the worker, cancellation is effective. A time limit
  would make results depend on the machine, so the deterministic bounds
  (C-26, C-47) stay the guard against analysis that does not return.

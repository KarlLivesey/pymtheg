# C-37: Cold index writes on disk

## Where the disk time went

Cold indexes on main, store on disk (the dev server's btrfs on NVMe), by
`scripts/store-cost/measure.mjs`. Commit time is the wall time of SQLite's
COMMIT statements. Under the write-ahead log a commit writes the pages that
the transaction changed into the log, and every 10,000 pages one commit also
runs the checkpoint: it syncs the log, copies every page changed since the
last checkpoint into the database and syncs that. Bytes written are what
reached the storage layer (`/proc/self/io` `write_bytes`).

| Pin | Wall s | SQL s | Commits (count) s | Bytes written GiB | Database MiB | Bytes read from storage |
|---|--:|--:|--:|--:|--:|--:|
| restic/restic | 35.8 | 22.9 | 957: 13.3 | 1.88 | 130 | 0 |
| cli/cli | 224.5 | 179.8 | 2,162: 137.1 | 9.23 | 463 | 0 |
| trpc/trpc | 138.8 | 100.6 | 2,711: 87.4 | 2.78 | 228 | 0 |
| helix-editor/helix | 91.5 | 23.9 | 543: 13.9 | 2.36 | 196 | 0 |

The same pins in memory took 24.9, 93.4, 55.3 and 78.8 s, so commits were
most of the gap. Each file was its own commit, and each commit rewrote into
the log every index page the file touched. Link and symbol keys are hashes,
so nearly every file touches pages all over the large indexes: cli/cli wrote
9.2 GiB for a 463 MiB database. No read reached the disk: analysis reads
were served from memory, so there was nothing to remove there.

Separating the checkpoints from the log writes, on restic and cli/cli in
an earlier session of the same build (restic 53.0 s, cli/cli 206.9 s):

| Pin | Commits with checkpoints s | Without automatic checkpoints s | Bytes written GiB, with → without |
|---|--:|--:|--:|
| restic/restic | 30.9 | 23.0 | 1.96 → 1.50 |
| cli/cli | 123.0 | 49.2 | 7.72 → 6.53 |

So on cli/cli checkpoints were about 74 s of the 123 s, and writing the
log the other 49 s. Turning checkpoints off is not an option: the log
would grow to everything written (5.7 GiB on cli/cli).

`synchronous` was already `NORMAL` under the write-ahead log (C-6): commits
are not synced, only checkpoints and the completion record are.

What each option removes:

- **(a) Batched commits** remove the repeated log writes of the same pages:
  a page changed by many files in one batch is written once per batch. With
  fewer distinct log pages, each checkpoint also copies less.
- **(b) A longer checkpoint interval** removes repeated copies of the same
  hot pages into the database and their syncs. On its own it leaves every
  log write in place. With batched commits it halves the commit time on
  cli/cli and Vector (item 4).
- **(c) Writing each Go and Rust link once** would remove about half of
  those rows' inserts (they are written at parse time, then replaced by the
  analysed result), the row work and its pages. It needs the parse results
  held until analysis, which brings back the memory C-2 removed. Not built.

## What changed

1. **Batches.** The indexer's write phases (parse results, each module's
   analysed results, and each module's resolution write) run inside
   `store.writeBatch`. Under the write-ahead log the writes share one
   transaction until about 50,000 rows have been written, as SQLite counts
   direct changes (`total_changes()`). Then the transaction commits, and the
   rest commits at the end of the phase. A resolution write is one write
   per link inside a batch scope, so it is cut at the budget too; outside a
   batch scope it stays one transaction. With a rollback journal each write
   still commits alone, because a batch larger than the page cache would
   lock readers out.
2. **A turnstile for writers.** Every write of the store first takes a
   small lock-only database beside it (`graph.sqlite-turnstile`) with
   `BEGIN IMMEDIATE`. It then asks for the store's write lock and leaves the
   turnstile as soon as it has that lock. Each batch begins the same way.
   A writer that is waiting for the write lock therefore holds the
   turnstile, and the run cannot begin its next batch until that writer has
   the lock. The lock is SQLite's own file lock, so it works across
   processes and the operating system releases it when its holder dies.
   Where the turnstile cannot be opened, no batch forms and each write
   commits alone, as in C-6.
3. **A writable open that finds its schema and identity in place writes
   nothing.** Queries opened writable (`noSync: false`, MCP and
   requirement-link queries) used to take the write lock for the
   constructor's `INSERT OR IGNORE`. They now take none, which removes the
   commonest second writer.
4. **Checkpoints run every 100,000 pages instead of 10,000**, and the log
   is cut back to 64 MiB after a checkpoint (`journal_size_limit`), so a
   long-lived connection does not keep the largest log on disk. A
   checkpoint copies every page changed since the last one into the
   database, so with batched commits fewer checkpoints copy the hot index
   pages fewer times. Measured on disk, with batched commits:

   | Pages per checkpoint | cli/cli commits s | cli/cli log peak MiB | Vector commits s | Vector log peak MiB |
   |--:|--:|--:|--:|--:|
   | 10,000 | 54.4 | 122 | 86.6 | 157 |
   | 25,000 | 43.0 and 43.4 | 169 | 78.0 and 94.4 | 213 |
   | 50,000 | 43.9 | 268 | 82.5 | 301 |
   | 100,000 | 26.1 | 474 | 55.7 | 499 |

   50,000 pages keeps little of the gain. At 100,000 the log stays at or
   below the database's own size on the large pins (cli/cli 463 MiB,
   Vector 921 MiB); restic's 424 MiB log is about three times its 130 MiB
   store. The wall times of these runs, made beside a waiter, varied more
   than the commit times; side by side with the reviewed head, 10,000
   pages took cli/cli from 124.3 to 171.5 s.

The budget is a fixed row count, so where a batch ends does not depend on
the machine. It was chosen with the first version below and the old
checkpoint interval: a cold cli/cli on disk took 213.1, 154.9 and 134.1 s
with budgets of 5,000, 20,000 and 50,000 rows. In that version a
checkpoint every 100,000 pages took it from 135.9 to 114.3 s.

A first version gave each write its own savepoint inside the batch. It was
correct, but every link insert inside a savepoint became several times
slower: helix's link inserts took 57.5 s instead of 4.4 s in memory, and
the micro-benchmark showed 17 → 46 µs per link. A failed write now undoes
the whole open batch instead.

## How each guarantee is kept

- **Equality.** Cold stores equal main's row for row on restic, cli/cli,
  trpc and helix, on disk and in memory (same row count and SHA-256 for
  every table `dump.mjs` compares). The re-index equality tests pass
  unchanged.
- **Crash and kill.** A batch is one commit, so a store cut short is still
  the state after some prefix of its commits. The run's first commit
  carries its unfinished-run mark, and the completion record is written
  last, after every batch. The kill harness now also kills right after each
  batch scope ends, where its last batch commits. It runs the TypeScript
  and Go edits with batches of 5 and 40 rows. With 40 rows a batch holds
  several writes, and the test asserts that fewer commits than writes
  happened. A kill at every boundary, including inside an open batch, left
  a store that one normal index repaired to the cold rows. The regular
  kill tests now also run under the default budget.
- **Run ownership.** Every batch begins like any other commit. Under the
  write lock it proves that no other run has written since its previous
  commit, or throws `GraphIndexTakenOver` before writing. While a batch is
  open it holds the write lock, so no other writer can commit inside it.
  `test/graph-write-batches.test.mjs` lets another run take the store over
  between two batches. The first run's next write throws and writes
  nothing, and the other run's rows and mark stay.
- **Failures.** A write that fails undoes its open batch. The store is then
  its earlier commits, as after a crash. If an earlier batch committed, the
  run's mark makes the next run redo the work. If the failed batch was the
  first, nothing was committed, not even the mark. Both are tested.
- **Readers** are never blocked under the write-ahead log. They read the
  last commit while a batch is open (tested).
- **The lock contract changes as agreed.** `test/graph-link-index.test.mjs`
  checked that after every file write another connection could take the
  write lock at once (C-6, W3-P1). That still holds with a one-row budget,
  which the test now sets. A second test shows the new behaviour with the
  default budget: after each write inside a batch, a writer that does not
  wait is refused, `graph status` reads succeed and see the last commit, and
  the lock is free once the run's batches have committed.
- **The second writer's wait is at most the batch in progress.** A writer
  waits for the write lock while holding the turnstile. The run takes the
  turnstile before each batch, so it can finish the batch it is in but
  cannot begin another: the waiter gets the write lock at its next busy
  retry. The batch in progress is at most 50,000 rows plus the write that
  reached the budget, and this now covers every write of a run, the
  resolution writes included. Two waiters queue on the turnstile. A waiter
  cannot deadlock the run: the run never waits for the turnstile while it
  holds the write lock.
  `test/graph-write-turnstile.test.mjs` proves the bound by counting. The
  run stops itself inside a batch (budget 50 rows), and a second process
  takes the turnstile and waits for the lock. After the run resumes, it
  records at each commit whether the waiter's write is in. The first commit
  (the batch in progress) is without it, and every later commit is after
  it. The test fails on the reviewed head `3756b30`. A second test kills
  the waiter while it holds the turnstile, and the run completes.
- **Measured** with a second process beside a cold index on disk that
  takes the turnstile and `BEGIN IMMEDIATE` with the production 30-second
  busy wait about once a second (`scripts/store-cost/waiter.mjs`):

  | Pin | Build | Longest wait s | Index commits inside it | Most commits inside any wait | "database is locked" |
  |---|---|--:|--:|--:|--:|
  | Vector | main | 17.2 | 1 | 47 | 0 of 795 |
  | Vector | this change | 5.1 to 13.1 | 1 | 1 | 0 of 1,761 |
  | cli/cli | main | 30.0 | 0 | 41 | 1 of 250 |
  | cli/cli | this change | 4.1 to 6.4 | 0 or 1 | 1 | 0 of 404 |
  | restic | this change | 3.7 | 1 | 1 | 0 of 40 |

  The rows for this change cover five runs on Vector and cli/cli and two on
  restic, at checkpoint intervals from 10,000 to 100,000 pages; with the
  chosen 10,000 the longest waits were 5.1 s (Vector) and 4.1 s (cli/cli).
  On main, one resolution write of cli/cli held the lock past the 30-second
  wait (the waiter failed), and waits spanned up to 47 per-file commits. A
  version with the turnstile but resolution writes still in one transaction
  hit the same failure on cli/cli (30.5 s, no commit inside): that is why
  resolution writes are now cut at the budget too.
- **The log's size** is at most the checkpoint threshold (100,000 pages,
  about 410 MB) plus the largest single transaction, because a checkpoint
  runs only after a commit. The first version's note said "about 400 MB",
  which was wrong: a resolution write was then one transaction, and the
  review measured 340 MB (restic), 524 MB (cli/cli) and 636 MB (Vector) on
  that head (main: 314 MiB on Vector). With resolution writes now cut at
  the batch budget, the largest transaction is about one batch: the log
  peaked at 424 MiB (restic), 474 MiB (cli/cli) and 499 MiB (Vector).
- **Failed writes.** A write that fails, in SQL or in `replaceFile`'s own
  checks before any SQL, undoes the open batch. When SQLite has already
  rolled the transaction back itself (a full disk, an I/O error), the
  original error is reported, not the rollback's; if the action fails and
  the closing commit of the batch scope then fails too, the action's error
  is the one reported.
- **Durability.** The completion record still commits with
  `synchronous=FULL`, which syncs the log up to it, so a completed run
  survives a power loss whatever the checkpoint interval. An unfinished run
  can lose up to one more batch of progress, which its mark makes the next
  run redo.
- **C-33's verified no-edit run** writes nothing and stays byte-identical
  (`test/graph-index-runs.test.mjs` and the C-33 equality cases pass).
- **Memory.** The writer cache stays bounded at 64 MiB. An open batch keeps
  its changed pages there and SQLite writes the overflow into the log
  before the commit. `test/graph-index-memory.test.mjs` is unchanged and
  passes. Peak RSS is within each pin's run-to-run spread (below).
- **No result depends on machine speed.** Batch ends are row counts.

## What remains

1. **Log writes per batch.** cli/cli still wrote 4.9 GiB for a 463 MiB
   store, and its commits took 21.5 s on disk. Larger batches would reduce
   this further, but they lengthen the wait for another writer.
2. **Write each Go and Rust link once** (option c): about half of those
   rows' inserts, at the memory cost C-2 removed.
3. **Stored format** (C-35's list): about 60% of each store is links and
   their indexes. Fewer bytes would mean fewer pages to write.

# C-56: Keeping Go's global index between runs (design)

Design only; no code until PR 72 (C-55) has been reviewed. C-56 builds on C-55: the session's kept state, and Go's inputs kept and brought up to date between runs.

## What it would save

`go.globalIndex` was about 4.1 s of CPU in a cli/cli body edit through the MCP worker (C-55's measurement, main). It is built twice per run, once in the analysis notes pass (`linkNotes`) and once in `resolveGo`, and a third time, lazily, for the lossy-free "shadow" resolver that names open-set reasons. With C-55 the inputs are kept, but every run still rebuilds this index from them.

## What the index is built from

`GoResolver.indexGlobalFacts` (`src/graph/languages/go/resolve.ts`) runs `index()` and then `implementsLinks(added)`. They read four things.

| Input | Where it comes from | Read by |
|---|---|---|
| The project layout (module paths, `go.work`, `vendor/modules.txt`) | the Go context files (`readLayout`) | import paths of packages; vendor roots |
| Each Go file's status and `data.go` fact (package clause, imports, build constraint, GOOS/GOARCH, test) | the resolver projection (or, in `linkNotes`, the analysis records) | file infos, packages and membership, untrusted membership, failed and lossy packages |
| Each Go file's `embeds` links | the projection (scoped runs only) | `embedsBySource`, method sets |
| Every Go symbol: id, file, key, kind, name, identity, data (`receiver`, `owner`, `local`, signatures) | the resolver's symbols (or, in `linkNotes`, symbols made from the records) | `symbolsById`, `byFileKey`, `decls`, `members`, `methodsByName`, `localTypes`, receiver bases; then interface method sets and which types implement which interfaces |

`implementsLinks` also produces added links: `implements` pairs, each with the key `implements:<type key>:<interface id>`.

The per-file memo caches (`FileMemo`, the import and selection memos) are filled while deciding links. They are not part of the index, and they are not kept.

## What changes it

C-27 already fingerprints a Go file's "surface", the facts other files' lookups read (`incremental.ts`):
- `surface.global` covers the status, package, imports, constraints and test flag, the facts of every symbol other than ordinary functions, and the embeds, with owners by source order;
- `surface.functions` covers the facts of the ordinary functions.

Against that:

| Change | Effect on the index |
|---|---|
| A Go context file (`go.mod`, `go.work`, `vendor/modules.txt`) | the layout: every package's import path, every vendor root. Rebuild everything. |
| A Go file added or removed | package membership, untrusted membership, lossy packages. Rebuild everything. |
| A file's `surface.global` | packages, declarations, members, method sets, embeds, and therefore which types implement which interfaces (a global relation). Rebuild everything. |
| Only a file's `surface.functions` | that package's function declarations. A function can also hide a name used as a type or an import qualifier; C-27's `mentions` check makes that a global change. Rebuild everything, as C-27 does when the check fires; otherwise only the package's function declarations. |
| Neither (a body edit) | no global fact changes. But Go symbol keys contain source offsets (`kind:start:identity`), so the edited file's keys move. `byFileKey`, the owners in `embedsBySource`, and the keys of `implements` links built from that file's types all change, even though the ids (identity and ordinal) do not. The symbol objects' ranges also change, and the package symbol's range feeds the `contains` links `run` adds. |
| Another module's files | nothing (the index filters to the Go module). |

## Is C-55's written-paths record enough?

It is not needed, and it would not be enough on its own:
- **Context files are not recorded.** They are written by `replaceContexts`, which C-55's record does not include.
- **A path tells which file changed, not whether its global facts did.** That needs the file's surface before and after.
- **Body edits still move keys,** so even "nothing global changed" needs the edited file's per-file entries rebuilt.

The proof can instead be the module's own key, the C-45 way:
- **Layout:** a digest of the Go context files the module reads.
- **Every Go file's identity:** path, status, `surface.global` and `surface.functions`.
- **Every Go file's key fingerprint:** a hash of its symbol keys and ids.

If the key matches, the index is reused as it is. If only some files' key fingerprints differ (a body edit that moved keys), the index is reused after rebuilding those files' per-file entries. Anything else rebuilds everything.

The module computes that key from inputs it already has: the surfaces are stored with each record, and the symbols are in its input. The session's three proofs (C-45) still guard against another process's writes.

## Proposed design

1. **The kept value.** The Go module keeps (`context.kept`) the global part of a built `GoResolver`:
   - per file: file infos, packages, lossy and failed packages, untrusted membership, vendor roots and file directories;
   - per symbol: declarations, members, method names, receiver bases and local types, held by symbol id, not by object;
   - the implements pairs, by type id and interface id.

   Everything keyed by symbol key is re-derived each run from the current symbols. That covers `byFileKey`, the `embedsBySource` owners and the `implements` link keys, and costs one pass over the symbols (about 28,670 on cli/cli), with no method-set or interface work.
2. **The key** is the one above. On a mismatch in any global part, the module builds afresh, exactly as today.
3. **Both builds share it.** `linkNotes` (analysis) and `resolveGo` build from equivalent inputs: the analysis records' facts and symbols against the stored projection and symbols. The design keeps one value per input kind, two names with keys computed from each build's own inputs, rather than proving the two equal.
4. **The shadow resolver** (lossy-free) is built only when some package is lossy. It is kept under its own name in the same way, or simply rebuilt; it is small when nothing is lossy.
5. **Freezing.** Under the test suite the kept value is frozen, as in C-55, so a resolver that changes it in place fails there.

## What would prove it sound

- **Equality.** With a session, seeded Go edits on restic and cli/cli through the MCP worker each equal a cold index row for row. That includes edits that change no surface but move keys: a body edit before declarations, and a comment inserted at the top of a file, before the package clause.
- **Every changed input, and the hidden-name case.** One test per row of the change table: a session edit of each kind, compared with cold. A test where a function hides a type name (the `mentions` case) must rebuild.
- **Mutation.** With the key reduced to the layout alone, the tests fail.
- **Without a session:** byte-identical stores to main.
- **Cost:** `go.globalIndex` CPU and the whole job's, main → head, through the worker, as in C-55.

## Open questions

- **Does anything in `index()` read a symbol's range or offset-carrying key beyond the uses above?** Before building: an audit of every read of `symbol.range` and `symbol.key` in `resolve.ts`, and a test with a top-of-file edit.
- **Do the two builds (analysis and resolution) see the same symbol ids for every file?** They should, since both come from the same records, but the notes pass builds its symbols itself (`id(file, key)`).

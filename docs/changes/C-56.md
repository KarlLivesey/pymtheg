# C-56: Keeping Go's implements decisions between runs

The first sections are the design as written before building, then the measurements that changed it (C-56a, C-56b). What was built is under "As built". C-56 builds on C-55: the session's kept state, and Go's inputs kept and brought up to date between runs.

## What it would save

`go.globalIndex` was about 4.1 s of CPU in a cli/cli body edit through the MCP worker (C-55's measurement, main). It is built twice per run, once in the analysis notes pass (`linkNotes`) and once in `resolveGo`, and a third time, lazily, for the lossy-free "shadow" resolver that names open-set reasons. With C-55 the inputs are kept, but every run still rebuilds this index from them.

## What the index is built from

`GoResolver.indexGlobalFacts` (`src/graph/languages/go/resolve.ts`) runs `index()` and then `implementsLinks(added)`. They read four things.

| Input | Where it comes from | Read by |
|---|---|---|
| The project layout (module paths, `go.work`, `vendor/modules.txt`) | the Go context files (`readLayout`) | import paths of packages; vendor roots |
| Each Go file's status and `data.go` fact (package clause, imports, build constraint, GOOS/GOARCH, test) | the resolver projection (or, in `linkNotes`, the analysis records) | file infos, packages and membership, untrusted membership, failed and lossy packages |
| Each Go file's `embeds` links | the projection (scoped runs only) | `embedsBySource`, method sets |
| Every Go symbol: id, file, key, kind, name, identity, data (`receiver`, `owner`, `local`, signatures) | the resolver's symbols (or, in `linkNotes`, symbols made from the records) | `symbolsById`, `byFileKey`, `decls`, `members`, `methodsByName`, `localTypes`, receiver bases; then interface method sets and which types implement which interfaces |

`implementsLinks` also produces added links: `implements` pairs, each with the key `implements:<type key>:<interface id>`.

The per-file memo caches (`FileMemo`, the import and selection memos) are filled while deciding links. They are not part of the index, and they are not kept.

## What changes it

C-27 already fingerprints a Go file's "surface", the facts other files' lookups read (`incremental.ts`):
- `surface.global` covers the status, package, imports, constraints and test flag, the facts of every symbol other than ordinary functions, and the embeds, with owners by source order;
- `surface.functions` covers the facts of the ordinary functions.

Against that:

| Change | Effect on the index |
|---|---|
| A Go context file (`go.mod`, `go.work`, `vendor/modules.txt`) | the layout: every package's import path, every vendor root. Rebuild everything. |
| A Go file added or removed | package membership, untrusted membership, lossy packages. Rebuild everything. |
| A file's `surface.global` | packages, declarations, members, method sets, embeds, and therefore which types implement which interfaces (a global relation). Rebuild everything. |
| Only a file's `surface.functions` | that package's function declarations. A function can also hide a name used as a type or an import qualifier; C-27's `mentions` check makes that a global change. Rebuild everything, as C-27 does when the check fires; otherwise only the package's function declarations. |
| Neither (a body edit) | no global fact changes. But Go symbol keys contain source offsets (`kind:start:identity`), so the edited file's keys move. `byFileKey`, the owners in `embedsBySource`, and the keys of `implements` links built from that file's types all change, even though the ids (identity and ordinal) do not. The symbol objects' ranges also change, and the package symbol's range feeds the `contains` links `run` adds. |
| Another module's files | nothing (the index filters to the Go module). |

## Is C-55's written-paths record enough?

It is not needed, and it would not be enough on its own:
- **Context files are not recorded.** They are written by `replaceContexts`, which C-55's record does not include.
- **A path tells which file changed, not whether its global facts did.** That needs the file's surface before and after.
- **Body edits still move keys,** so even "nothing global changed" needs the edited file's per-file entries rebuilt.

The proof can instead be the module's own key, the C-45 way:
- **Layout:** a digest of the Go context files the module reads.
- **Every Go file's identity:** path, status, `surface.global` and `surface.functions`.
- **Every Go file's key fingerprint:** a hash of its symbol keys and ids.

If the key matches, the index is reused as it is. If only some files' key fingerprints differ (a body edit that moved keys), the index is reused after rebuilding those files' per-file entries. Anything else rebuilds everything.

The module computes that key from inputs it already has: the surfaces are stored with each record, and the symbols are in its input. The session's three proofs (C-45) still guard against another process's writes.

## Proposed design

1. **The kept value.** The Go module keeps (`context.kept`) the global part of a built `GoResolver`:
   - per file: file infos, packages, lossy and failed packages, untrusted membership, vendor roots and file directories;
   - per symbol: declarations, members, method names, receiver bases and local types, held by symbol id, not by object;
   - the implements pairs, by type id and interface id.

   Everything keyed by symbol key is re-derived each run from the current symbols. That covers `byFileKey`, the `embedsBySource` owners and the `implements` link keys, and costs one pass over the symbols (about 28,670 on cli/cli), with no method-set or interface work.
2. **The key** is the one above. On a mismatch in any global part, the module builds afresh, exactly as today.
3. **Both builds share it.** `linkNotes` (analysis) and `resolveGo` build from equivalent inputs: the analysis records' facts and symbols against the stored projection and symbols. The design keeps one value per input kind, two names with keys computed from each build's own inputs, rather than proving the two equal.
4. **The shadow resolver** (lossy-free) is built only when some package is lossy. It is kept under its own name in the same way, or simply rebuilt; it is small when nothing is lossy.
5. **Freezing.** Under the test suite the kept value is frozen, as in C-55, so a resolver that changes it in place fails there.

## What would prove it sound

- **Equality.** With a session, seeded Go edits on restic and cli/cli through the MCP worker each equal a cold index row for row. That includes edits that change no surface but move keys: a body edit before declarations, and a comment inserted at the top of a file, before the package clause.
- **Every changed input, and the hidden-name case.** One test per row of the change table: a session edit of each kind, compared with cold. A test where a function hides a type name (the `mentions` case) must rebuild.
- **Mutation.** With the key reduced to the layout alone, the tests fail.
- **Without a session:** byte-identical stores to main.
- **Cost:** `go.globalIndex` CPU and the whole job's, main → head, through the worker, as in C-55.

## Open questions

- **Does anything in `index()` read a symbol's range or offset-carrying key beyond the uses above?** Before building: an audit of every read of `symbol.range` and `symbol.key` in `resolve.ts`, and a test with a top-of-file edit.
- **Do the two builds (analysis and resolution) see the same symbol ids for every file?** They should, since both come from the same records, but the notes pass builds its symbols itself (`id(file, key)`).

## Measured before building, and what it changes (24 November 2026)

On the C-55 build, a cli/cli body edit through the MCP worker costs 8.6 s of CPU in its second session run. Of that, `go.globalIndex` is 3.1 s over its two builds:

| Part | CPU s (two builds) |
|---|--:|
| The structure (`index()`: files, packages, declarations, members, receiver bases) | 1.8 |
| The implements pass (`implementsLinks`: 992,496 type and interface pairs considered, 941,442 skipped by name) | 1.3 |

Reading the resolver for a build found three facts the design above did not account for:

1. **The analysis build cannot be kept as designed.** It (`linkNotes`) does not use the stored symbol ids: it names symbols `draft:<path>\0<key>`, and Go symbol keys contain source offsets (`kind:start:identity`). A body edit therefore changes the ids of every later symbol in the edited file. Every map and cache keyed by id in that build would need re-keying, not just the per-file maps.
2. **The caches cannot be kept as designed.** The implements pass fills shared caches (`views`, `memo`, `selections`, `hiddenMemo`, `externalMemo`). The `views` hold closures (`members`, `declared`) over the resolver that built them. Reusing them keeps that resolver alive, with its structure and its symbol objects, whose ranges and keys are stale for an edited file. That is unbounded by any size the session can count, and correct only as long as nothing ever reads a range through them.
3. **Only the implements pass separates cleanly from the structure.** The structure is rebuilt from the current symbols in any sound scheme, so keeping the pass's result saves at most its own share: about 0.65 s per build. Only the resolution build qualifies (point 1), so about 0.65 s of the 8.6 s.

**Decision: not built in this form.** A sound version needs the Go resolver changed first, in two steps:

- **C-56a, Go symbol keys without offsets** (as C-49 did for TypeScript). Draft ids and stored keys would then survive a body edit. That is useful on its own: it would stop body edits from rewriting other files' stored link data, as C-49's replay measured for TypeScript.
- **C-56b, the index by id, with caches that close over nothing.** Views would hold symbol ids and look members up in the current structure, so a kept index is a value, bounded and sized like C-55's, frozen under the tests.

Only after those does keeping the global index, both parts, across runs become sound. It would then save up to about 3 s of the 8.6 s, and the counts to claim would be the type and interface pairs considered and the structure entries built per edit.

- **The stored summaries, metadata and report.**

None is clearly larger than the index, so C-56a comes first. The TypeScript scoping is the strongest candidate after it: about 1.15 s on cli/cli, more on mixed repositories. It is sound only if the TypeScript module can prove that nothing it reads changed, as Go does with its surfaces.

## As built (C-56, after C-56a and C-56b)

C-56a gave both builds of the index offset-free ids, and C-56b turned the implements pass into a plain value and gave both builds the store's ids. What is kept is that value, the implements pass's **decisions**, not the index itself:
- the structure (`index()`) is rebuilt every run from the current inputs, as the measurements above said any sound scheme must;
- the views and caches that close over a resolver are never kept.

**What is kept.** The implements decisions, in the index session (C-45), Go's module state. The normal notes and resolution builds share one value, `go:implements`: a value is used only under the key of the inputs it was made from, so a build reuses it only when its inputs agree, the resolution build in the same run included. The resolver that ignores lossy packages (built to name reasons) keeps its own, `go:implements:lossless`: its decisions differ (review). With C-55's `core:input`, Go keeps three names, under the session's four per module.

**The key** (review: the first key, each file's surfaces, missed four cases; this one replaces it) is a digest of:
- the resolver mode, the Go module version and the module id;
- every context file's path, content hash, status and dependency stamp (`go.mod`, `go.work`, vendor);
- the complete Go file inventory, each file by path and parse state, with:
  - its package, imports (path and alias), build constraint, GOOS/GOARCH and test membership;
  - every declaration in source order, ordinary functions included: kind, name, identity, id and data (signatures, fields, receivers, types);
  - its embeds in order: owner, target, type, pointer, coinciding starts;
  - its toolchain status.

Positions are not in it, only order, so a body edit that changes no declaration keeps it. The C-45 session scope supplies the project and store identity and the index settings. The decisions are source-only; toolchain-backed links are decided from the current toolchain facts when the decisions are applied.

The key does not assume ids are stable across an edit: it holds every declaration in order with its id, so a renumbering (C-56a: an anonymous struct added to the first of two `init` functions) misses it.

**A miss makes them again.** A kept value is returned only under the key it was kept with (C-45), so any change to what the decisions are made from misses it, and the pass runs as before. A kept value is also not used if any id it names is not a symbol of the build. A value is kept only if the run completes; a stopped run drops what the session kept.

**Proven equal to a recomputation.** Under the test suite, and in any process with `PYMTHEG_CHECK_KEPT=1`, a reused value is made again and compared; a difference fails the run. Every session test that reuses a value, and every seeded edit run with the variable set, is therefore a proof that the kept value equals a recomputed one.

**Its cost.** The fingerprint is made each time a build looks the value up. Its cost is measured below.

## What could change a decision without changing the key (review)

Each input the implements pass reads, and where the key has it:

| Input | In the key as |
|---|---|
| type, interface, field and method declarations: kind, name, identity, data | the ordered declarations |
| ordinary functions, which can take a name a type or import has (a function named like an embedded type removes promoted methods), and their order relative to other declarations (a function and a type alias of one name) | the ordered declarations (review) |
| a declaration under another build constraint | the file's declarations and its build constraint |
| the ids built from paths and order | each file's path and its ordered declarations with their ids |
| embeds: owner, target, type, pointer, coinciding starts | the file's embeds |
| package clause, imports (an import's path under the same alias), `_test`, GOOS/GOARCH | the file's facts |
| failed files, which have no declarations, and so lossy packages | the inventory: every Go file by path and parse state |
| module layout, `replace`s, `go.work`, vendor, the Go directive (library origins, the standard-library table's version) | each context file's path, hash, status and dependency stamp |
| the standard-library table itself | shipped with the build; the Go module version is in the key, and a session is dropped on a version change (C-45) |
| the toolchain route | each file's `data.toolchain`; toolchain-backed links are decided when applied |
| which resolver: normal, or the one that ignores lossy packages | the mode, and a separate name |

Not read by the pass, so not in the key:
- function bodies;
- predeclared uses;
- `packageRange` offsets;
- links other than embeds (the toolchain's link facts included);
- other modules' files;
- the run's scope, which only selects which `implements` links are written.

## Checks

`test/graph-go-kept-implements.test.mjs`:
- **One session, each step compared with a cold index.** A body edit makes nothing: both normal builds reuse the kept value, each reuse made again and found identical. Each of these misses the key, the notes build makes the decisions again, and the store equals cold:
  - adding a file with an implementer, and renaming it;
  - changing a method's signature;
  - deleting a file;
  - changing `go.mod`'s module path;
  - adding `go.work`;
  - an anonymous struct added to the first of two `init` functions, which renumbers the second's;
  - a function named like an embedded type (`func Base() {}`), and its removal (on the build before the second review, the run failed: the kept decisions differed from a recomputation);
  - `helper` renamed `X` in another file, `X` being embedded in `T` (the second review's reproduction), and back;
  - (a) a function `X` added in a file under the other build constraint, `X` being an embedded type under `!alternate`, and removed;
  - (b) a type alias `X = strings.Builder` and a function `X` swapping order, and back;
  - (c) a failed file moving into the implementers' package, and back;
  - an import's path changing under the same alias (`ext` from `strings` to `bytes`, embedded as `ext.Builder`), and back;
  - a struct's embedded type changing, and an interface's embedded interface changing, and back;
  - a body edit that adds an anonymous struct embedding `X` inside a function, which then implements `I` (Sol's review: such an edit inside restic's `(*Local).Hasher` took the implementers from 276 to 278). Anonymous structs and function-local types are declarations, and their embeds are embeds, so the key has them; and back.
- **A context file that cannot be read.** With `go.mod` made undecodable, Go's analysis stops on it and the run fails, keeping nothing. Restored, the next run equals cold.
- **A scoped body edit of the file holding implementers** reuses the decisions and keeps every `implements` link.
- **(d) The resolver that ignores lossy packages.** In a project with a failed file, a body edit of the dispatching file builds it. Every build reuses its own mode's value, made nothing, and the store equals cold. The two modes' values are kept under different names and keys.
- **The kept value's ids** are the store's ids.
- **A stopped run.** Go's resolution throws after the decisions are kept. The run is abandoned; the next run makes the decisions again and equals cold.
- **The toolchain.** Go's resolver is called directly with a kept state the test controls. The same inputs reuse the value; the same inputs with a toolchain status on each file miss it.
- **Key misses and a wrong value.** A value under another key is never used. A wrong value under the right key fails the run.

`test/graph-go-notes-ids.test.mjs` (C-56b) adds the live notes pass's ids (through `analyze`) and a scoped run's `implements` links.

Each part of the key, removed in the built code, fails a test:

| Removed | Test that fails |
|---|---|
| the resolver mode (one value for both modes) | the session steps, the toolchain test, the lossless-resolver test |
| failed files from the inventory | the session steps ((c)) |
| source order (declarations ordered by name) | the session steps ((b)) |
| ordinary functions from the declarations | the session steps |
| the file facts | the session steps (the import path change) |
| the embeds | the session steps (the interface embed change) |
| declarations and embeds inside function bodies (anonymous structs, local types) | the session steps (the anonymous struct in a body) |
| the context files | the session steps |
| the recomputation check | the session steps and the wrong-value test |

Three parts, removed, fail no test, because the rest of the key implies them:
- **Parse state.** A failed Go file has no declarations, and every other file has at least its file symbol, so the state never changes alone.
- **The ids.** An id is a digest of the path, module, kind, identity and position, which the key holds.
- **A context file's read status.** It follows from the file's bytes, whose hash is in the key. A file Go cannot read also makes the run fail, so no value is kept from it (`readLayout` skips such files, but no completed run ever sees one).

All three stay in the key.

## Results

All on the key above (after the third review), PR 76 at a0d6db08.

**Seeded edits, each kept value proven equal to a recomputation.** 60 distinct edits per pin through the MCP worker, with `PYMTHEG_CHECK_KEPT=1` (`random-edits.mjs --mcp --more-go --gomod-meaning --no-edit-runs`, seeds 5621 restic and 5622 cli/cli).
- Each edit's run, and then a run of the same worker with nothing edited, is compared with a cold index. All 120 edits equal cold, and so do all 120 runs with nothing edited.
- The edits include body, signature, interface, embed, import and dot-import edits, added, deleted and moved files, parse breaks, build tags, and `go.mod` edits that change the module path or a require's version.
- Every build that looked the value up either reused it or made the decisions again. Reused: 211 (restic 95, cli/cli 116), each made again in the worker and found identical (`go.implementsChecked`, 211). Made: 185 (restic 85, cli/cli 100). The counts take in both builds, the lossless resolver where it is built, and the runs with nothing edited.

## Further work

- **The structure** (`index()`, about 1 s per build on cli/cli) is rebuilt every run. Keeping it needs it to be updated file by file, a larger change.
- **A run that skips a build keeps nothing for it.** When Go's analysis leaves nothing to re-decide, neither build runs and the session keeps neither value (C-45 keeps only what a run sets again), so the next edit makes both again.

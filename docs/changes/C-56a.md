# C-56a: Go's notes pass names symbols without source offsets

## What was asked, and what was found

C-56 (keep Go's global index between runs of a session) stopped on one finding: Go's analysis notes pass (`linkNotes` in `src/graph/languages/go/resolve.ts`) built its own symbols with draft ids made from the extractor's keys, and those keys carry a source offset (`kind:start:identity`). A body edit that moves a declaration changes the draft id of every declaration below it, so an index built for the notes pass could not be kept across an edit.

The brief for this chunk asked for offset-free Go symbol keys, a module version bump if the stored format changed, and a count of the other files whose stored link data a Go body edit rewrites. Before building, the stored side was checked: a Go body edit already rewrites no other file's stored link data (C-53 writes each Go link once, and stored links name their targets by the store's ids, which have no offset). The offsets were only in the notes pass's draft ids, which are never stored. So this chunk changes those ids and nothing that is stored:

- no stored key, id or row changes;
- the Go module version is unchanged by this chunk (32 when it was measured, 33 since C-63), and no store is rebuilt for it;
- the count of other files rewritten by a body edit is 0 before and 0 after.

## The change

The notes pass now names each symbol by the id the core gives a stored symbol (`fileFacts` in `src/graph/identity.ts`): a digest of the file's path and module, the symbol's kind and identity, and its ordinal among the file's symbols with the same kind and identity. The pass computes them under its own project id (`go-overflow`, the id it already used), so they are not the store's ids, but they are built the same way and keep the same order. `notesSymbols(file)` returns them.

The extractor's keys still carry offsets. They are used only inside one file's analysis, to match a link to its source symbol in that same file; the pass maps them to ids at once.

## How ties are broken

Two symbols of one file with the same kind and identity get ordinals 0, 1, … in source order: by range start, then range end, then key (the core's rule, unchanged). Every other tie is broken by the identity itself or by the file, which is part of the id. For the Go shapes the brief named:

| Shape | Kind and identity | What tells them apart |
|---|---|---|
| methods of one name on different receivers | `method (A).Run`, `method (B).Run` | the receiver is in the identity |
| several `init` in one file | `function init` | the ordinal, in source order |
| `init` in several files | `function init` | the file |
| `func _` | `function _` | the ordinal, like `init` |
| `var _`, `const _` | not a symbol | nothing to name |
| same-named locals in one function | not symbols | nothing to name |
| generic type parameters | not symbols; the generic type and function are | the identity |
| fields of anonymous structs | `field a.go:Anon.anon#1.A`, nested `…anon#1.B.anon#1.A` | the owning declaration and the nesting are in the identity |
| build-tag twins declaring one name | `function Twin` in two files | the file |

`test/graph-go-notes-ids.test.mjs` indexes a fixture with every shape above. It checks that:
- every notes id in a file is distinct and none is a draft id;
- each notes symbol's kind, identity and ordinal is one the store holds for that file;
- each shape is named as in the table;
- a body edit that moves every offset in a file leaves every notes id of that file as it was. The old draft ids fail this.
- the ordinal follows source order, not key order: with one `init` before offset 100 and one after, the keys sort the other way (`function:120:init` before `function:20:init`), and the first in the file is still ordinal 0 (review: sorting by key alone passed every test).

**What a body edit can still change (review).** Moving code leaves every id as it was. Adding or removing a function-local type or an anonymous struct can rename others in the same file, because those identities are numbered within the enclosing declaration's identity (`a.go:init.anon#1`, `…#2`). Two declarations can share that identity, such as two `init` functions. A new anonymous struct in the first `init` then renumbers the second's. Such an edit also changes the file's global surface (C-27), which includes those types.

## What it does not change

The notes the pass produces, the links it finds and every stored row:

- **Cold stores.** restic and cli/cli indexed cold by main (54cd0e6f) and by this build into stores with one project id, compared row for row (`scripts/reindex/same-cold.mjs`): no difference. cli/cli has 1,191 files, 28,670 symbols, 218,270 links and 65,892 library targets; restic 559, 8,092, 64,165 and 18,022. Go coverage cannot move, because no row moves.
- **Seeded edits.** 35 each through the MCP worker (`random-edits.mjs --mcp --more-go`, seeds 5501 restic and 5502 cli/cli), on main and on this build: all 140 equal a cold index.
- **What each edit writes.** For the same seeded edits, every write counter of every step is the same on both builds: files written, symbol rows, link rows inserted and deleted, and links whose stored resolution changed. On restic that is 314 files and 46,932 changed resolutions over the 35 steps; on cli/cli 464 and 75,795. The body edits among them (two per pin) write no file but the edited one, before and after. The changed-resolution counter is not split by file: 151 (restic) and 206 (cli/cli) for those body edits, the same on both builds.

The first comparison of the cold stores showed thousands of missing standard-library targets on this build. That was the measurement, not the change: the copied build had no `src/`, where Go's standard-library table is read from. With the table in place the stores are identical.

Results are in [evidence/c-56a](../../evidence/c-56a/README.md). They were measured with this chunk on its first base, 54cd0e6f (C-55 before its reviews), against that base. After main moved (C-55's review fixes and C-63 merged in), the pushed tree's suite is `npm test` 3,431 of 3,431 and `npm run test:backend` 97 of 97 (aded2242).

## What it allows

The C-56 plan: C-56b keys Go's global index by these ids, and its caches hold no closures over a resolver. C-56 can then keep that index between runs.

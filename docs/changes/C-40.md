# C-40: An analysis leaves no TypeScript program behind

microsoft/TypeScript (27,194 TypeScript and JavaScript files) ran out of
Node's default heap (4,288 MiB here) during a cold index. C-26 found that
the TypeScript analysis had returned, and assumed that the indexer was
holding and writing all 27,190 results. Measured, the results are small. A
cache in the TypeScript module kept the analysis's last program alive, with
its checker, for the rest of the run. Releasing it lets the index finish at
the default heap: 33 min 53 s, exit 2 (finished, with failed files).

## What was held

`scripts/memory/probe.mjs` runs a cold index and records the live heap
after a full garbage collection at each phase boundary. On
microsoft/TypeScript, before this change, at the default heap and at
12,000 MB:

| Point | Live heap MiB | What it is |
|---|--:|---|
| TypeScript analysis input | 123 | 27,194 file records with their text |
| TypeScript analysis returned | 2,873 | 27,190 results: 298 MiB as JSON, 507,433 links |
| during the TypeScript writes | 2,871 | |
| Go resolution input | 4,277 | the heap limit: the default-heap run died here, at 34 min 37 s |
| Rust resolution write | 2,870 | |
| TypeScript resolution input | 3,645 | |
| end of the run | 2,869 | |

About 2.75 GB stayed alive from the end of the TypeScript analysis to the
end of the run, after its results had been written and dropped. On a slice
of the checkout (all of it except 23,639 of the test files; 2,293 TypeScript
results) the same thing happened: 41 MiB before the analysis, 396 MiB at
its return, and still 395 MiB after its writes. A heap snapshot of the
slice at that point ([summary](../../evidence/c-40/snapshot.txt)) held a
whole compiler program: 2,096 source files, 400,177 syntax nodes, 185,860
symbols, types, signatures, and the checker's deferred diagnostic closures.
The shortest strong path from the roots was:

`libCache` (a module-level map in `project.ts`) → a cached
`lib.*.d.ts` source file → a node's symbol → its parent symbol → that
symbol's links → a type → its checker → the checker's state.

The TypeScript module parses the compiler's library files once and shares
them between programs. Each checker records its own facts on their symbols,
so the cache kept the last checker reachable, and with it the program the
checker belongs to. On microsoft/TypeScript the last program is the
27,000-file no-config program. The C-26 figure of results "held while they
are written" was this program, not the results.

## What changed

Two lines in the TypeScript module, outside the analysis itself:

- `project.ts` gains `releaseLibraryFiles()`, which clears `libCache`.
- `typescriptModule()` in `index.ts` wraps the module's `analyze` where the
  module object is returned. When `analyze` returns or throws, the wrapper
  calls `releaseLibraryFiles()` and clears `lastAsked`. That module-level
  variable keeps the last syntax node passed to a checker, and with it that
  node's source file. The body of `analyze` and the result hand-over are
  unchanged.

The next analysis parses the library files again. A CLI command runs one
analysis per process, so it parsed them once before and still does. A
long-lived process (MCP, Studio) parses them once per sync.

No contract changed. The results are not streamed: at the default heap the
indexer now holds a module's results while it writes them, and that fits.
Go and Rust return their results as before. Streaming was not needed for
any of the pins measured here (below).

## The result on microsoft/TypeScript

A cold `graph index` through the CLI on a fresh copy of the pinned checkout,
at the default heap (`scripts/memory/cli-index.sh`):

- finished in 33 min 53 s, exit 2: 274,386 symbols, 993,013 links, 12,477
  failed files, no analysis or resolution error. These are the same counts
  as C-26's run at 12,000 MB;
- peak RSS 5,324 MiB, which also counts native memory outside the
  JavaScript heap (SQLite, the parsers' WebAssembly). Before this change the
  same index died out of heap at 34 min 37 s, at 4,847 MiB of RSS;
- this fits the sweep's 60-minute limit for the index itself. The analysis
  dominates the time: about 26 minutes in the probe run.

The probe on the same checkout at the default heap, with this change
(each sample after a full collection, so the run is slower: 37 min 36 s):

| Point | Live heap MiB, before → after |
|---|--:|
| TypeScript analysis returned | 2,873 → 487 |
| Go resolution input (the largest) | 4,277 (out of heap) → 1,456 |
| Rust resolution write | 2,870 → 50 |
| TypeScript resolution input | 3,645 → 824 |
| end of the run | 2,869 → 45 |

The results themselves are about 360 MiB live at the analysis's return,
and the indexer holds them while it writes them. That fits the default heap
with room to spare, so they are not streamed.

## How each guarantee is kept

- **Equality.** The stored rows are identical to the starting point on
  turborepo (Go, Rust and TypeScript), astro (TypeScript), cli/cli (Go) and
  helix (Rust): same row count and SHA-256 for every table `dump.mjs`
  compares. On the microsoft/TypeScript slice too. A cache of parsed
  library files changes no fact: the files are parsed again from the same
  bytes. The re-index equality tests pass.
- **Kill points, run ownership, the completion record, C-33's verified
  no-edit run.** Unchanged. No write, transaction or boundary moved, so the
  kill and race tests pass as they are.
- **Memory test.** `test/graph-index-memory.test.mjs` gains a counted test.
  It indexes a small TypeScript project, then counts the compiler's
  `SourceFile` and `Type` objects still alive with `v8.queryObjects`, which
  forces a full collection first. Both must be zero. On the starting point
  8 source files were alive. The test counts objects; it does not measure
  RSS or time.
- **Nothing depends on machine speed.**

## Not built

- **Streaming a module's results.** Not needed on the pins above. A module
  much larger than microsoft/TypeScript could still need it. The TypeScript
  module's results are not final until its analysis ends: every result
  records the digest of the module's failed files, and a later program's
  compiler failure can retract results that earlier programs published. So
  a chunked hand-over would have to rewrite stored files after a
  retraction.
- **The Go resolver's input.** A full Go resolution decodes every file of
  the checkout. On microsoft/TypeScript that is 32,448 records, about
  1.4 GB of live heap, now the largest point of the run. The C-33
  projection (`store.resolutionFiles`) carries everything the Go resolver
  reads from them and is already used for scoped runs. Using it for full
  runs too would need its own equality proof.
- **Native memory on turborepo** (about 3 GB of RSS outside the heap during
  the Rust analysis), and the time of a microsoft/TypeScript sweep beyond
  the index itself.

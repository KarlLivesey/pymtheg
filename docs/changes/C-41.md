# C-41: TypeScript members of object and type literals as link targets

The installed sweep (SW-6) stores 43,168 TypeScript links as unresolved
with reason `local`: the checker names a declaration, and the module has no
symbol for it or refuses it. C-41 measures that group by declaration kind
and by where the literal lives. It then makes members of written type literals link targets, under one
product rule: never a wrong definite link. The rule is that no step of a
member call's receiver is a value the checker reduced from several
producers; applying it to every member call also removes main's wrong
definite links of that shape on interface and object-literal members.

TypeScript module version 46. This chunk takes 46 for now; if another chunk
merges first with 46, this one moves to the next.

## Which declarations become symbols

- **Members of a type literal written in a type position.**
  - The type of a module-level declaration or of a class or interface
    member: `export type Api = { query(): void }`, `declare const api: {
    m(): void }`, `interface Holder { inner: { q(): void } }`. Main had
    symbols for many of these (4,158 refused calls) and refused calls on
    them. C-41 lets calls link to them.
  - Nested type positions, each with its place in the identity: a union
    arm `[|i]`, an intersection part `[&i]`, an array element `[]`, a
    tuple element `[#i]`, a type argument `[<i>]`. For example
    `both.[type].[&1].stop` for `declare const both: { run(): void } & {
    stop(): void }`.
  - A named parameter's written type, when the function is a graph symbol:
    `render.[param:db].[type].getConfig` for `function render(db: {
    getConfig(): number })`.
  - Inside a function body, the same positions on declarations that are
    already symbols there: a local variable's written type
    (`inBody.[local].v.[type].lv` for `const v: { lv(): void } = …`) and
    a local function's parameter types
    (`inBody.[local].inner.[param:p].[type].ip`). Calls through these
    written types link like module-level ones and are kept: the identity is
    the body's `[local]` name path, not a position in the body, so other
    edits to the body do not move it.
  - A type literal's overloads (`{ run(): void; run(x: number): void }`)
    are one symbol, at the first signature, as an interface's are.
  - The place segments `[|i]`, `[&i]`, `[#i]` and `[<i>]` are indexes:
    inserting a union arm (or an intersection part, tuple element or type
    argument) before another shifts the later ones' identities, as
    reordering them does.
- **Not symbols:**
  - Destructured bindings, untyped locals and parameters, and local type
    aliases and interfaces (`type L = { … }` inside a function). A call
    through a local alias stays `local`.
  - Object-literal members passed as call arguments or built inside a
    function: they have no anchored owner, and a call through a generic
    (`setup({ hydrate() {} }).hydrate()`) cannot prove which literal
    produced the value.
  - Index signatures and mapped types: no named member exists.

## When a member call links: no step of the receiver reduced from several producers

The checker's declaration for `receiver.member` names the member of the
type it computed for the receiver. When a value comes from several producers
(`pick ? one : two`, `a ?? b`, an array literal's element, an inferred
return with several `return`s), the checker forms their union with subtype
reduction. Structurally identical types reduce to one arm, and the
declaration list then names that arm's member only: a wrong definite link
when the other arm was chosen. This holds for every kind of member, so the
rule covers interface, type-literal, class and object-literal members
alike. Main had such wrong links for interfaces
(`ichosen = pick ? ia : ib; ichosen.run()` → `IA.run`) and object literals
(`formats = [csv, tsv]; formats[1]!.format()` → `csv.format`).

So the receiver's chain is walked to its producers, step by step
(`receiver-arms.ts`). Each value resolves to its *arms*, the types of the
producers it can come from:
- A conditional, `??` and `||` have both sides' arms. A left side of `??`
  that is never nullish, or of `||` that is only objects, is the value.
- An array literal is one arm whose elements an element access walks: a
  literal index picks that element (`formats[1]` is `tsv`), any other
  index, a `for…of` variable and the first parameter of an array method's
  callback (`forEach`, `map`, `filter`, `find`, `some`, `every`,
  `flatMap`, …) have every element's arms.
- A name has the arms of its declaration: a `const`'s initialiser; a `let`
  or `var`'s initialiser and every value assigned to it (in its own file,
  which is the only place a module's binding can be assigned; a script's
  top-level `var` or `let` is not followed); a destructured binding, the
  property or element of its source's arms (a default only where the value
  can be `undefined`).
- A property has the arms of the member's declaration on each arm: an
  object literal's property its initialiser's, a class property without a
  written type its initialiser's.
- A call to a function with an inferred return type has the arms of its
  `return`s. A chain of single-`return` functions is followed without
  recursion, as the checker itself infers it.

A step is one arm, the checker's own type there, when its type is
*written*: a declaration with a type annotation (an ambient one too, such
as `Date`), a module, namespace, class, function, enum or method, an
assertion (`x as T`), `this`, a literal, a `yield`, or a call or tagged
template whose signature writes its return type. A written type is never
a reduction. A primitive literal arm is its primitive (`"a"` and `"b"`
are one `string` arm: no member differs). Several steps need more:
- A union only loses an arm the checker finds assignable to another
  (subtype reduction), so arms none of which is assignable to another are
  not reduced (`[z.string(), z.number()]`). Assignability is wider than
  the subtype relation, so this errs towards "reduced".
- A generic call (`createApi(config)`) whose type arguments are inferred
  is one arm when its arguments are unreduced. When they may be
  (`expect(pick ? a : b)`), the result keeps its declared type beside the
  instantiated one, and a member is taken from it only when the declared
  type has the same member: `expect(…).toBe` is `Assertion<T>`'s own
  member whatever `T` became, while `same(pick ? a : b).util` reaches
  into `T` and is unresolved. A generic function with an inferred return
  type is handled the same way, through its signature, when its body's
  returns are not a reducible union.
- A member of an instantiated generic type, or a method of an instantiated
  generic class, whose declaration has no written type
  (`get shape() { … }`, `unwrap() { return this.inner; }`): its body is
  in the generic's terms, so it only has to show that no reducible union
  forms there; the value is the instantiated member's
  (`NonOpt<Opt<number>>.unwrap().unwrap()` → `Opt.unwrap`).
- A call without a signature declaration (`require` in JavaScript) is one
  arm.
- An untyped parameter of a function expression gets its type from the
  context: it is one arm when the function is an argument of a call whose
  callee is one arm and whose instantiation passes the check above, the
  initialiser of a declaration with a written type, a property of an object
  literal in such a context, a JSX attribute, an assignment's value, or
  returned from a function with a written return type.

Anything else (an expando assignment, a `let` written by destructuring or
`++`, a generic body with several returns) cannot be followed, and the
call is unresolved (`receiver-unverified`). The walk keeps the checker's
type after a step only when its single arm is the checker's own type at
that step, so flow narrowing is kept and a reduction is not.

Before the member is looked up, the arms are split into their union
parts and filtered by the checker's own type at the receiver, which
control flow may have narrowed (`typeof r === "string" ? r :
r.toString()`, `instanceof`). A part is kept when it is assignable to
that type (a primitive part when that type has a primitive of its kind).
A reduction keeps every arm, since each is assignable to the one the
checker kept; narrowing drops the parts it excluded. If the kept parts are
exactly the checker's type, its answer stands; this keeps a contextual
`this` (an object literal's method typed by an interface) on the
interface's member.

The member is then looked up on each arm. If the arms' members are the
checker's member, its answer stands. If not, they replace it: a candidate
set when there are several (`pick ? one : two` gives `one.run` and
`two.run`), the right single member when the checker named a wrong one
(`formats[1]!.format()` → `tsv.format`). An arm without the member, or an
arm member with no symbol (a literal in a function type's return), leaves
the call unresolved (`reduced-receiver`, or `multiple-object-producers`
when an object literal's member is among them). Main's producer check for
unanchored object-literal members still runs after this, unchanged.

The walk reads only declarations the checker's symbols name, the files the
receiver's chain already depends on for type checking. A type-literal
member's link no longer needs the receiver's declaration to write the type
that holds the literal (the first version of this chunk): a receiver typed
through a generic call with one-arm arguments, or through an inferred
return with one `return`, links too.

## Tests

`test/graph-typescript-literal-members.test.mjs`, twelve tests:
- calls on type-literal members link as an interface member's do: an
  alias, an inline type, a nested literal, an optional member, a generic
  alias's literal, a literal in an interface property;
- equal member names in two literals stay two symbols; a written union is a
  candidate set; an intersection part is definite;

  conditional is a candidate set, through `first ?? second` with `first`

- every `contains` link stays resolved beside the member symbols (they add
  none);
- no step of the receiver is reduced, for each reproduction in both

  (`list[i]`, `for…of` over `list` and over `[a, b]`, `list.forEach`) give

- nested places have the identities `[<0>]`, `[]`, `[#0]`, `[#1]`,
  `[|0]` and `[|1]`, and a type literal's overloads are one symbol that
  both calls reach;
- a file's listing shows the type-literal members after its other symbols,
  in source order;
- negatives: an index signature, a mapped type, a parameter and a
  destructured binding stay unlinked.

## Found, not built

- **Members in a function type's return.** `(pick ? f1 : f2)().run()` with
  `f1: () => { run(): void }` has two arms whose members have no symbol (a
  function type's return is not a symbol position): unresolved
  (`reduced-receiver`) rather than a candidate set.
- **Narrowing after a walked choice.** `const c = pick ? a : b; if (isA(c))
  c.run()` gives both members: the walk does not narrow its arms, so the
  set is sound but wider than the narrowed type.
- **References.** The walk runs for calls. A member read that is not
  called (`const f = chosen.run`) keeps the checker's answer.
- **Receivers typed through a generic's inference with reduced
  arguments**: unresolved, as the walk cannot instantiate the generic for
  each arm.
- **Object-literal members passed to generic calls** (758 on the pins):
  need a symbol for a literal in a call argument and a producer proof
  through the call (`createApi({ run() {} }).util.run()` stays `local`).
- **Symbols in generated files.** The module has no classification of
  generated files, so type literals in t3code's generated schemas get
  symbols like any other file's; the listing order above keeps them from
  displacing other symbols.

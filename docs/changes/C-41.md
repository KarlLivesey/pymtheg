# C-41: TypeScript members of object and type literals as link targets

The installed sweep (SW-6) stores 43,168 TypeScript links as unresolved
with reason `local`: the checker names a declaration, and the module has no
symbol for it or refuses it. C-41 measures that group by declaration kind
and by where the literal lives. It then makes members of type literals
written outside bodies link targets, under one product rule: never a wrong
definite link. Measuring the rule also found main's wrong definite links on
anchored object-literal members reached through a value that can choose,
and closes most of them.

TypeScript module version 46. This chunk takes 46 for now; if another chunk
merges first with 46, this one moves to the next.

## Which declarations become symbols

- **Members of a type literal written in a type position outside bodies.**
  - The type of a module-level declaration or of a class or interface
    member: `export type Api = { query(): void }`, `declare const api: {
    m(): void }`, `interface Holder { inner: { q(): void } }`. Main had
    symbols for many of these (4,158 refused calls) and refused calls on
    them. C-41 lets calls link to them.
  - Nested type positions, each with its place in the identity: a union
    arm `[|i]`, an intersection part `[&i]`, an array element `[]`, a
    tuple element `[#i]`, a type argument `[<i>]`. For example
    `both.[type].[&1].stop` for `declare const both: { run(): void } & {
    stop(): void }`.
  - A named parameter's written type, when the function is a graph symbol:
    `render.[param:db].[type].getConfig` for `function render(db: {
    getConfig(): number })`.
- **Not symbols:**
  - Destructured bindings, local variables, parameters, and local types,
    classes and functions: body-local by design. A link into a function
    body names a place that moves with every edit to that body.
  - Object-literal members passed as call arguments or built inside a
    function: they have no anchored owner, and a call through a generic
    (`setup({ hydrate() {} }).hydrate()`) cannot prove which literal
    produced the value.
  - Index signatures and mapped types: no named member exists.

## When a call links to a type-literal member

The checker's declaration for `receiver.member` names the literal the
receiver's type came from. When that type was computed from expressions
(`pick ? one : two`, an inferred return), the checker may have reduced a
union of structurally identical literals to the first one. Its declaration
list then omits the others, which would be a wrong definite link. A type
written on the receiver's own declaration is never reduced so.

So a call links to a type-literal member only when the receiver's
declaration writes a type that holds that literal
(`literal-members.ts`, `declaredLiteral`). It may hold it directly, or
through type aliases, parentheses, `readonly`, an intersection, or a written
union (which the checker keeps arm by arm, so it gives a candidate set).
The receiver may be:
- an identifier or property access whose single declaration is a variable,
  parameter, property signature or property declaration with a written
  type;
- a call whose resolved signature declares its return type.

An inferred type, or a receiver with several declarations, gets no link:
the call stays `local`.

## Anchored object-literal members through a value that can choose

Testing the rule on object literals found the same reduction on main.
`const chosen = pick ? one : two; chosen.run()` linked definitely to
`one.run` (main's own test pinned `legacyChoice.inspect()` so). Main
checked the producers of unanchored literal members only; members of a
literal bound to a name skipped the check.

Now an anchored member is checked too, unless the receiver's value is
direct (`literal-members.ts`, `directValue`):
- a module (an import, `require(…)`, `import(…)`);
- an object literal;
- a `const` bound to such a value;
- a property of such a value whose single declaration is so.

When the producers can be followed they decide: several producers give a
candidate set (`chosen.run()` → `one.run`, `two.run`), and a reassigned
`let` stays unresolved (`multiple-object-producers`). When they cannot be
followed (a call's result, an element access, a destructured binding), the
checker's answer stands as before. Making that case unresolved too would
drop correct links main pins through CommonJS exports (`ret().real()`,
`arr[0].real()` into `module.exports = { real() {} }`). See "Found, not
built".

## Tests

`test/graph-typescript-literal-members.test.mjs`, eight tests:
- calls on type-literal members link as an interface member's do: an
  alias, an inline type, a nested literal, an optional member, a generic
  alias's literal, a literal in an interface property;
- equal member names in two literals stay two symbols; a written union is a
  candidate set; an intersection part is definite;
- a computed union of identical literals (`(pick ? one : two).run()`, its
  `const` and its function form) stays `local`;
- members of a parameter's written type are targets; nested type positions
  get their places;
- object-literal members: equal names stay distinct, a spread member is the
  spread object's, a computed key the checker knows is one member, and
  `pick ? one : two` gives both members (a wrong definite link on main);
- an anchored member through a reassigned `let` stays unresolved, through a
  conditional is a candidate set, through `first ?? second` with `first`
  never nullish is `first`'s;
- every `contains` link stays resolved beside the member symbols (they add
  none);
- negatives: an index signature, a mapped type, a parameter and a
  destructured binding stay unlinked.

### Changes to existing tests

- `test/graph-typescript-resolution.test.mjs`:
  - `inferred.run()`, a call on a type-literal member through a written
    type, moves from the unresolved list to the resolved one
    (`inferred.[type].run`).
  - "object-member calls account for every explicit producer": main pinned
    `legacy.old()` (a reassigned `let`) and `legacyChoice.inspect()` (a
    conditional) as definite links to the first literal. They are now
    `multiple-object-producers` and a two-member candidate set.
    `legacyList[key].inspect()` keeps main's link (see below).

## Found, not built

- **An anchored member through a value the producers cannot follow.**
  `legacyList[key].inspect()` with `legacyList = [legacyFirst,
  legacySecond]` still links to `legacyFirst.inspect`. The checker reduced
  the element type, and the producers cannot follow an element access.
  Declining all such cases would drop main's correct links through
  CommonJS exports, a call's result and destructuring. The fix is a
  producer walk that follows array literals and returned values. None of
  the 19 pins changed under the new check, so the shape is rare.
- **Receivers typed through a generic's inference** (above): 3,740 calls
  on type-literal members that have symbols.
- **Object-literal members passed to generic calls** (758): need a symbol
  for a literal in a call argument and a producer proof through the call.

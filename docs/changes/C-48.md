# C-48: The MCP server keeps its graph worker and index session

Part 1 of the brief is built: the MCP server keeps one graph worker, with
the C-45 `IndexSession`, between jobs. Parts 2 and 3 are not built; the
reasons and what each needs are below. So is the cause of Hono's large
body-edit write.

## The persistent worker

**Before:** each `code_graph` job started a new worker thread, which loaded
the language modules, ran `executeGraph` and exited; cancelling a job
terminated its worker.

**Now:** one worker (`src/mcp/graph-worker.ts`) runs every job of the
server, one at a time, and keeps an `IndexSession`: the modules are loaded
once, and module state that a session proves valid is kept. `GraphJobs`
(`src/mcp/graph-jobs.ts`) starts it on the first job and starts a new one
after it exits, crashes or is ended.

**Cancellation** uses memory shared between the worker and the server
(`src/mcp/graph-control.ts`): a cancel flag, the section the worker is in,
and a count of checkpoints.

- A **checkpoint** is each point where the graph command checks its abort
  signal: before each store call, before each language module call, at
  each captured file. At a checkpoint the worker counts it and, if the flag
  is set, aborts the job and answers `cancelled`. It then keeps running,
  with its session.
- Inside a **language module's call** the worker may pass no checkpoint
  for long; `executeGraph` announces such calls (`onModuleCall`). A cancel
  that finds the worker in the call itself, or in a synchronous stretch
  the module marks after an await (C-50, below), with no toolchain process
  live, terminates it at once, as before, and the session ends with it.
- While a module's **returned promise is awaited**, or while a toolchain
  process of the job is live, the server kills the job's processes, asks
  the worker to abort and waits for its answer. A worker that answers
  within `CANCEL_GRACE_MS` (30 s, by an injectable clock) keeps running
  with its session; one that does not is terminated when the grace ends
  (see the second review, below).
- The **handshake** cannot miss: the server sets the flag and then reads
  the section; the worker sets the section and then checks the flag (both
  with sequentially consistent atomics), so one of them always sees the
  other. No wall-clock wait decides a result: the grace above only
  bounds how long a worker that does not answer is given before it is
  terminated.

A terminated or crashed worker leaves the store as a killed CLI run does:
the next job (in a new worker) takes over the unfinished-run mark and
repairs it.

**Idleness:** a worker with no job for `idleMs` (10 minutes by default),
measured with an injectable clock, is ended with its session. That is
checked when the next job starts, by `releaseIfIdle()`, and by a timer the
server arms (not used by the tests). Kept values are bounded per module
(C-45).

**Resting memory:** after every job the worker releases the job's objects,
runs a full collection and reports its live heap. A worker above 512 MiB
is ended as its job finishes (`restingBytes`; see below), by size, not by
time.

What the numbers say:

- **An unchanged index** costs 0.2 to 0.4 s instead of 0.7 to 1.3 s:
  module load and worker start are gone.
- **Edits** gain little wall time, as C-45 predicted: the rest is
  per-language work no module keeps yet. Hono's edits used a third less
  CPU (50.7 → 34.1 s): the worker's compiled code is warm, and the
  TypeScript module's library-file cache survives between jobs. helix's
  edits used more (46.4 → 53.8 s), within the spread of Rust runs on this
  server.
- **Memory.** Without more, a worker kept its high-water mark between
  jobs: on Hono it rose to 2.6 GB resident after an edit (the second table).
  With C-40's library-cache release applied, Hono stayed at 1,048 to
  1,090 MiB through the first edits but still reached 2,327 MiB after the
  last one. So the worker now releases what the job left after each job,
  before it answers:
  - it drops its references to the job's objects and runs a full
    collection;
  - it reports its live heap (V8's bytes in use and external memory);
  - the server ends the worker at once, when the job finishes, if that is
    above a bound of 512 MiB.

  Measured after every job of the same sequence
  ([log](../../evidence/c-48/resting.txt)), the worker kept a live heap of:

  | Pin | Live heap after each job, MiB | Resident set after the job, MiB |
  |---|--:|--:|
  | restic | 76–80 | 842–846 |
  | cli/cli | 130–132 | 1,643–1,646 |
  | honojs/hono | 98–99 | 1,368–1,385 |
  | helix-editor/helix | 124–125 | 1,362–1,397 |

  Hono's resident set after its edits fell from 2.25–2.60 GB to
  1.37–1.39 GB with no other change. The 512 MiB bound is about four times
  the largest live heap measured. A TypeScript program kept alive by the
  library cache (2.7 GB on microsoft/TypeScript before C-40) would be above
  it, and its worker would be ended after the job. Ending a worker changes
  no answer; the next job pays the start-up and a fresh session. The rest
  of the resident set is native memory (SQLite, the parsers' WebAssembly,
  V8's own pages) and the main process.

  **With C-40 on main** (C-37 and C-40 merged into this branch, the same
  Hono sequence again; [log](../../evidence/c-48/resting-c40.txt)): the
  compiler's library cache is released with each analysis, so the worker
  keeps 58–61 MiB of live heap after each job (from 98–99), and the
  server's resident set after the jobs is 1,191–1,349 MiB (from
  1,368–1,385). No job came near the bound; the last revert equals a cold
  index.

## Tests

`test/mcp-graph-session.test.mjs` runs the production worker with test
controls (`test/fixtures/mcp-graph/session-worker.mjs`). A worker that must
stop waits on a gate in shared memory that the test opens, so nothing
depends on timing:

- **Reuse:** two jobs reuse one worker and one module discovery (the
  session reports one load, two runs), and the store equals cold.
- **Acknowledged cancel:** the worker is stopped inside a store call; the
  cancel is acknowledged at its next checkpoint, the worker is the same for
  the next job, and the store equals cold.
- **Unacknowledged cancel:** the worker is stopped inside a module call;
  the cancel terminates it, and the next index repairs the store to cold.
- **Crash:** a worker that exits inside a module call ends its job with an
  error; the next job starts a new worker and equals cold.
- **Another process:** a CLI-style index in another connection between two
  jobs; the session drops what it kept, and the result equals cold.
- **Idleness:** a worker idle for `idleMs` by a test clock is ended; one
  idle for less is not.
- **Resting bound:** each job reports the worker's live heap; with a bound
  below it, the worker is ended as the job finishes, and the next job
  starts a new one and equals cold.
- **Kill points:** the worker is terminated after each store write call of a
  re-index, at every one in turn; each time the next job equals cold. Under
  C-37's write batches a write call does not always commit: some of these
  points fall inside an open batch, where the termination discards the
  batch's uncommitted writes, and the others fall after a commit.

The MCP job, inline and library tests were updated for the new protocol and
pass. Kill, race, equality and session tests are unchanged and pass.

### Review (first round)

- **The completion proof is read at the run's baseline** (C-45's B1 fix,
  merged in): through the worker too, another process's complete index just
  before a run's baseline drops what the session kept
  (`test/mcp-graph-session.test.mjs`, a gate in the worker fixture runs the
  other process inside `beginIndexRun`, no sleeps).
- **Cancel latency.** Every store read of a query is now a checkpoint (the
  query reads through a checkpointing view of the store), so a cancel during
  query evaluation is acted on at the next read; tested with a query stopped
  inside a call-link read. A cancel cannot interrupt SQLite's own wait for a
  lock: a store call waiting for another writer takes effect when the wait
  ends, at most `writerWaitMs` (30 s), then aborts at the next checkpoint.
- **Code upgrades.** The server records the package version and a build id
  (the size and modification time of the worker's compiled entry) when it
  starts a worker, and ends the worker before the next job if they differ,
  so an upgrade on disk is never served by old module code. Tested with a
  controlled version source.
- **Toolchain children (C-54 merged in).** The persistent worker records
  every child process group it starts in a registry of its own, owned by
  the server (`src/backends/child-groups.ts`); the server kills it on every
  cancel and when the worker exits. A cancel also asks the worker to abort
  through its signal: a worker awaiting a child has a free event loop, so
  `runProcess` kills the groups it waits on, the toolchain route removes
  its run folder, and the worker answers `cancelled` and lives on (no
  termination). While a group is live the server waits for that answer up
  to `CANCEL_GRACE_MS`, then ends the worker; with no live group, a worker
  inside a module call is ended at once and one in the graph command
  answers at its next checkpoint, as before. C-54's tests run on the
  persistent worker (the silent-worker case through its `launch`).

### Review (second reviewer)

- **"Inside a module" ends when the module returns its promise** (from the
  CLI-cancellation builder). The worker's section is `module` while a
  module's call (or a toolchain call) runs, `awaiting` while the promise it
  returned is awaited, and `core` otherwise. While awaiting, a cancel asks
  the worker to abort through its signal, which a module that honours it
  (Rust's phase worker, a toolchain's child) acts on at its next await, and
  the worker answers and lives on. The module may still be running
  synchronous code while the section reads `awaiting`: Go's `analyze` with
  the toolchain route awaits the facts, then runs its notes pass and
  decision loops without awaiting. A cancel then waits for its next await
  or for its promise to settle, at most `CANCEL_GRACE_MS` (30 s), after
  which the worker is ended; before this change such a cancel ended the
  worker at once. C-50 (PR 64) marks such stretches: a module wraps one in
  `synchronousStretch` (`src/graph/sections.ts`), and it reads as the
  `module` section, so a cancel there with no toolchain process live ends
  this worker at once (with one live, it takes the grace above), and ends
  the CLI's at once. Go marks its notes pass and its parse. An
  unmarked stretch stays as described here. Tests: an analysis whose promise
  settles only on abort is cancelled with the worker kept; one that never
  settles is ended when a controlled clock fires the grace.

- **The acknowledged cancel is now tested as one.** The job records what
  the worker answered and the checkpoint that acted on the cancel (the
  shared checkpoint counter, now read). The test's worker stops inside its
  first file write and cannot go on until the server's cancel flag is set,
  so it cannot finish first; the test asserts a `cancelled` answer, no
  result, no completion record, and an abort at the first checkpoint after
  the flag. With the checkpoint abort removed from the built worker the
  test fails (the cancel was then acted on 37 checkpoints later, through
  the abort message).

## Part 2 (Go's kept resolver input): not built

It is not small. The kept value would be the Go resolver's input: the file
projection, the symbols and the parsed links, as read from the store when
resolution starts.

**Why it would be valid.** Every input the resolver reads is a function of
the stored rows: file records (only path, module, status, diagnostics, data
and embed links), symbols, and parsed links presented unresolved. The three
session proofs say the store is exactly as the session's last completed run
left it:

- that run wrote nothing after its resolution reads except resolution
  writes;
- resolution writes touch only link targets, candidates and library
  targets, which the input clears, and analysis-added links, which it
  excludes.

So the input read then equals the input now, except for the rows this run
wrote before resolution: the records, symbols and parsed links of the files
it parsed, analysed or removed. The kept input would be patched by
re-reading exactly those files. The module key would cover the module's
version and the set of files written.

**What it needs:**

- the indexer to record every file whose rows it wrote or removed before
  resolution;
- a merge of the re-read rows into the kept arrays in the store's order
  (files by path, symbols and links by id);
- the 60 seeded edits, including additions, removals, renames and `go.mod`
  edits.

**What it would save:** at most the stored-input reads, 1.0 s of a restic
body edit and 4.5 s of a cli/cli one in the table above. It is left for its
own chunk.

## Part 3 (one hash pass instead of three): left

1. **The command's first pass** decides whether anything changed. It runs
   before the run begins, because beginning a run already switches the
   journal and would break C-33's byte-identical no-edit run.
2. **The indexer's pass** captures the bytes it stores after the run's
   ownership baseline, so an overtaking run's commit cannot be stored from
   an older read. **The command's last pass** proves that nothing changed
   during the run before the completion is published.

Sharing one pass would need the files unchanged between passes, and only
hashing them again proves that.

## Why Hono's body edit writes 18 files

On main, the body edit of `src/utils/url.ts` changes the stored rows of 17
files (`scripts/resident/edit-diff.mjs`): 17 file records and their links,
all in the links' `data`. The surface edit changes 2. TypeScript link data
names its targets by `kind@offset` keys, for example `function@663`. The
body edit lengthens `splitPath`, which moves the offset of every
declaration after it in the file. So every link elsewhere that points at
those declarations changes: 138 links in `url.test.ts` alone, and links in
15 other files. The surface edit appends at the end and moves nothing.

The store writes what changed, so this is not a store defect. It is edit
amplification from offset-based keys inside the TypeScript module, and it
is left for the PR 50 builder. Naming targets by identity instead of
offset would make a body edit write only its own file.

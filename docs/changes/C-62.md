# C-62 An overtaken index run writes nothing

Built on C-38A (pull request 68), which claims the store before analysis
for every module holding edited files. C-38A left a window before the
claim: a run is protected only once it claims the store, at the end of its
parse write. Three shapes were reproduced on main and on C-38A. Each ended
`incomplete`, was repaired by one more index, and never served wrong rows
as complete:

1. **A stale capture.** Run A pauses after parsing a file with an export
   removed. The file is restored. Run B, a syncing query, finds the tree
   current and writes nothing (C-38A's property: a run with no edit claims
   nothing and writes nothing). A then claims and overwrites with the
   removed export.
2. **A stale walk.** A pauses after its directory walk. B indexes a newly
   added file. A then takes its baseline and deletes B's row for that
   file, which is not in A's older path list.
3. **A late publication.** A has written its rows. B claims for a newer
   edit and is still running. A's publication of its completion finds that
   another connection committed, and marks the store interleaved. That
   replaces B's live mark, so both end incomplete.

## The rule

A run that another run has overtaken writes nothing, and never disturbs the
newer run's mark. Three things decide, with no timing anywhere.

1. **The baseline covers the walk.** `beginIndexRun`, the read snapshot of
   the data version, the mark and the completion record, now comes before
   the directory walk. It is still a read with no write, so a run with no
   edit claims nothing. A commit by any other connection after it changes
   the data version, so the run's first write, which already checks it
   under `BEGIN IMMEDIATE`, stops with `GraphIndexTakenOver`. Shape 2.
2. **A stale capture is refused before anything is published.**
   - In shape 1 the overtaking run wrote nothing, so no version or token
     can show A that it ran; only the disk can.
   - The indexer therefore gives the store a synchronous check
     (`verifyIndexCapture`): its walk's path list, and the hash of every
     file it will write and of every context file.
   - The run's first write runs the check under the write lock, before the
     mark is written: the same walk again, and those hashes again.
   - Any difference rolls back with `GraphIndexStale`, so nothing is
     written and no mark is left.
   - A run with no edit never reaches a write, so it never checks.
3. **Only the newest run publishes.**
   - An `index-generation` row is incremented in the transaction that
     writes a run's mark, its claim.
   - A run keeps the generation it read at its baseline, or the one its
     claim set.
   - While a newer run has claimed since, the run publishes nothing.
     `completeGraphCommandState` writes neither the completion nor the
     interleaved mark. `invalidateGraphCommandState` removes the
     completion only while the generation is unchanged, in one statement.
   - The interleaved mark stays for a writer that is not an index run (the
     generation unchanged, the data version moved), as in C-22. Shape 3.

**What follows.** In each shape the overtaken run writes and publishes
nothing; it answers `GraphIndexTakenOver`, `GraphIndexStale` or
incomplete. The newer run's result (or the store the no-edit query found
current) stands, and the store equals a cold index of the tree with no
further index.

## Tests

`test/graph-index-ownership.test.mjs` runs each run in a child process that
stops itself (SIGSTOP) at a named store call and tells the test
(`test/graph-index-ownership-child.mjs`): after the walk, at the parse
write's first call (before the claim), before the run's finish, and before
the command's completion record. The test continues or kills it. Every step
waits on that handshake. Every case must end with the store equal to a cold
index of the tree and `graph status` complete, with no further index.

| Case | This branch | C-38A's head |
| --- | --- | --- |
| The three shapes, for Go, Rust and TypeScript (9 tests) | pass | all 9 fail |
| Three runs, A holding an older capture and B a claim, C a full index; A and B resumed in each order (2 tests) | pass | pass |
| A run killed at each of the four gates; at most one more index (4 tests) | pass | pass |
| The two windows of the first two shapes with A in a session holding Go's kept inputs (2 tests) | pass | not run |

The interleavings and kills pass on C-38A's head too: they guard the new
rule against regressions, but do not reproduce a fault. A run killed before
its claim is checked to have written nothing.

The reviewer's two windows are pinned as they were reproduced: A paused at
its parse write while the file is restored and B, an index, completes; and
A paused after its walk while B adds a file and indexes. In both, B's store
is compared row for row before and after A resumes: A is rejected and B's
rows are untouched. Both also run with A in an `IndexSession` whose first
run kept Go's inputs (C-55; Go is the module that keeps them), the child
checking that the session keeps them before A starts.

Each window was broken in the built code. With the capture check made to
pass always, the four after-parse cases fail (Go, Rust, TypeScript and the
session case). The after-walk window is closed twice: by the baseline read
before the walk, and by the capture check, which compares the walk too.
With either removed alone the four after-walk cases pass; with both
removed all four fail.

**With C-55's kept inputs.** A session keeps a run's values only when the
run's completion record is written (`complete`), and drops everything when
the store's completion record is not the one its last completed run wrote.
An overtaken run's completion is refused, so it keeps nothing, and a newer
run's record differs, so what the session had is dropped.
`test/graph-index-session.test.mjs` has a session run overtaken after its
claim and one overtaken just before it publishes; each time the next run
builds its kept value afresh and equals a cold index. Each of the two
protections alone keeps the second test passing; with both removed it
fails.

## Cost

The check re-reads, under the write lock of the run's first write, the
files the run writes and every context file, and walks the tree again. It
is counted (`index.verifiedFiles`, `index.verifiedBytes`), measured on the
pinned Go and Rust corpora, restic and vector, with C-38A's head and this
branch alternating over two rounds: a cold index of a fresh copy, then a
comment line appended to one source file and an incremental index
([results](../../evidence/c-62/cost.jsonl)). Wall times are observations on
a shared server.

| Corpus | Run | Re-read files (bytes) | Wall s, C-38A | Wall s, this branch |
| --- | --- | --- | --- | --- |
| restic | cold | 560 (2,435,829) | 18.2, 18.2 | 16.8, 16.8 |
| restic | one-file edit | 2 (17,306) | 2.9, 2.9 | 2.8, 2.9 |
| vector | cold | 1,633 (17,480,346) | 346.9, 322.1 | 330.7, 359.3 |
| vector | one-file edit | 49 (468,658) | 46.7, 45.0 | 49.8, 48.3 |

A cold index reads every file a second time: its file reads double. An
edit re-reads only the files it writes and the context files (`go.mod`,
`Cargo.toml` and the like). Wall times: restic's cold index ran faster on
this branch (16.8 s both times against 18.2), vector's cold runs overlap
(330.7 and 359.3 against 346.9 and 322.1), and vector's edit ran slower
(49.8 and 48.3 against 46.7 and 45.0); restic's edit is within 0.2 s.
Peak memory (from the same records): restic cold 694 and 772 MiB against
695 and 695; vector cold 3,931 and 3,945 against 3,773 and 3,935; the edits
within 13 MiB of each other. Two runs of each do not separate the builds.

## Checks

- Tests that listed a run's writes (`graph-core-scaling`) allow the
  generation's update with the mark. The write-ahead-log test's row
  comparison leaves the generation out, since it counts the runs that
  claimed the store. The race test whose paused run now walks the tree the
  other run left accepts its complete answer, which equals a cold index.
- The capture check compares only the files a module claims or reads as
  context. A store kept inside the tree, whose journal comes and goes, made
  a sequential Rust test stale before that.
- Format check and build pass, and the full `npm test` passes (3,454 pass,
  0 fail) on `ff5c6a6d`, with main `0af3e0b4` merged in; the pushed head
  differs from it only in this note.

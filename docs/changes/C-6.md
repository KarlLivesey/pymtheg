# C-6: indexing writes that do not dominate a cold index

**What changed.** The graph store now writes through SQLite's write-ahead log
when the graph is on a Linux local disk and Node's bundled SQLite has the fix
for SQLite's write-ahead-log reset bug: Node 24.15.0 or later 24.x, 25.9.0 or
later, or 26 (see "SQLite version guard" below). A commit no longer waits for the disk;
SQLite syncs the log only at checkpoints, now every 10,000 pages (40 MB) instead
of every 1,000. Writes still make one commit per file, exactly as on main,
so other processes get the lock as often as before. The completion record, which
is what makes an index trusted, is committed with a full sync. When the last
writer closes, the file goes back to the rollback journal, so a store at rest has
the same format as before. Stored results are byte-identical to main.

About 180 added lines, about half of them comments, in `src/storage/local.ts` and
`src/graph/store.ts`. No schema
or module version change, no new dependency, no setting.

## Where cold time went

On main, every file write is one commit with a full sync, and with a rollback
journal a commit means several syncs. On the dev server's disk, under load, a
cold restic index took 692 s, 671 s of it inside store write transactions and
428 s inside `COMMIT`. Analysis and parsing used 32 s of CPU. In a quieter
period the same index took 75–106 s, of which 39–43 % was `COMMIT` and 82–85 %
was inside write transactions.

## What was chosen, and what was rejected

Measured on main's build with only the connection settings changed (restic and
cli/cli; `evidence/c-6/evaluate.jsonl`). Timings are observations on a shared
server, so compare only within a session.

- **Write-ahead log, `synchronous=NORMAL`, checkpoint every 10,000 pages:
  chosen.** Restic took 52 s, the same as with no sync at all (53 s); cli/cli
  took 236–252 s, against 247 s with no sync. Sync cost is gone; what remains
  is SQLite statement work (below).
- **Write-ahead log with SQLite's default checkpoint (1,000 pages):** restic
  73 s; the extra checkpoint syncs cost about 20 s.
- **Write-ahead log, `synchronous=FULL`:** a sync per commit; restic 531 s
  against 344 s for `NORMAL` in the busy session.
- **Bounded batches under the write-ahead log** (64 writes per commit on
  restic, 16 on cli/cli): slower, 109 s and 342 s. Readers would not be
  blocked, but second writers would wait longer between commits (W3-P1).
  Rejected.
- **One writer transaction per phase:** rejected in W3-P1 (readers and writers
  locked out). Under the write-ahead log, batching was slower anyway.
- **A writable open that takes the write lock once:** not needed. With one
  commit per file, a second writer waits exactly as on main.
- **Relaxing the sync only while an index is incomplete, keeping the rollback
  journal** (`synchronous=OFF`): restic 80 s. Rejected: after a power loss a
  rollback-journal database written without syncs can be corrupt, not just
  out of date. A corrupt store could then be completed on top of damaged
  pages, so recovery could not be proved.
- **A larger page cache** (64 MiB): cli/cli 268 s against 252 s. No gain.

## Why an interrupted index is still safe

After a crash or a power loss, a database in a write-ahead log is the state
after some prefix of its commits, never a mixture. Frames are appended with
cumulative checksums and a per-generation salt. Recovery stops at the first
frame that is missing or torn. With `synchronous=NORMAL` the log is synced
before a checkpoint copies it into the database, and the database is synced
before the log is reused.

The graph already trusts nothing without the completion record. An index
deletes that record before its first write. Triggers delete it on any other
graph write. The record is written last. So any prefix that survives is one
of three things:

- the previous completed index, before this run's first write;
- a store with no completion record, which every command reports incomplete
  and the next sync rebuilds;
- the finished index.

The completion record's own commit is synced (`synchronous=FULL`), so an
index that reports complete stays complete after a power loss. Main gives the
same guarantees with a sync per commit; this change only stops paying for syncs
of rows that are not trusted until the record exists.

Tests (`test/graph-write-ahead-log.test.mjs`, deterministic: kill points are
store calls in a child process, no clocks):

- **Killed at four points:** after the writable open, inside a file's write
  transaction, after resolution is written, and after the completion record
  is committed. Each store reports incomplete, except after completion, and
  the next index makes every stored row equal to a clean index's.
- **Power loss, cold:** the unsynced log is cut mid-frame. The test first
  shows that nothing of the run reached the database file.
- **Power loss, after an edit:** the whole log is lost. The store returns to
  the previous completed index, which reports the edited file as stale; the
  next run repairs it.
- **Concurrent use:** a reader reads while another process holds the write
  lock, a second index waits for the lock and succeeds, and the file is back
  in the rollback journal after the last writer closes.
- **At rest:** a completed index can be read from a storage directory the
  reader cannot write.
- **Reader open at the last writer's close:** the log stays, every later open
  reads the same rows, and the next writer restores the rollback journal.
- **Version guard,** with the version injected: the fixed and affected SQLite
  versions are recognised. With an affected version, a writer folds back a log
  that a killed run left (or reports "database is locked" while another
  connection holds it) and keeps the rollback journal. With a fixed version on
  a local disk, it uses the log.

The existing recovery and concurrency tests pass unchanged, including the
30-second writer wait (`test/storage-boundary.test.mjs`) and the per-write
concurrency test (`test/graph-link-index.test.mjs`).

## Filesystems, containers, old builds

- **Where it applies.** The write-ahead log needs memory shared by every
  process that opens the file. It is used only on Linux filesystems that
  guarantee that, read with `statfs`: ext2/3/4, XFS, Btrfs, tmpfs, ramfs, ZFS,
  F2FS, bcachefs, overlayfs (container layers), JFS and ReiserFS.
- **Where it does not.** NFS, SMB/CIFS, 9p (WSL drive mounts), virtiofs and
  FUSE (Docker Desktop bind mounts), Ceph, any type `statfs` cannot read,
  macOS and Windows; and every Node release whose SQLite lacks the reset fix
  (below). These keep main's rollback journal with a full sync per commit.
- **No waiting to switch in.** The switch into the log never waits on another
  connection; if it can't switch, the connection keeps the rollback journal.
- **No writing in a log where it isn't safe.** In those places a writer never
  writes in a write-ahead log. If a killed run left one, the writer first
  folds it back into the database and removes it before its first write.
  SQLite does not wait for that switch, so the store retries for up to the
  30-second writer wait, then reports "database is locked".
- **A Docker container on Linux** sees its bind mount's real filesystem type
  and shares the host's kernel, so it gets the log. Docker Desktop's mounts
  are virtiofs or FUSE, so they do not.
- **Old builds.** A store at rest has the rollback-journal format, so
  `pymtheg@0.1.0` and main open it as before. 0.1.0 refuses a schema-4 graph,
  as it already does for main's.
- **A store killed mid-index** is left in the write-ahead-log format with its
  log. 0.1.0 refuses it the same way. Main and this branch read it as
  incomplete and repair it. Each step is in `evidence/c-6/compat.log`.
- **Upgrades.** Main's and 0.1.0's stores upgrade in place; the graph schema
  is unchanged.
- **When the log stays.** A writer only switches back to the rollback journal
  when it is the last connection using the log. Two cases keep the log:
  - **A killed writer.** The store keeps the write-ahead-log format.
  - **A reader still open** that has read since the log was started.
    `graph.sqlite-wal` and `graph.sqlite-shm` stay. The reader keeps reading
    the committed rows. A read-only connection cannot fold the log back into
    the database, so the files stay after it closes too.

  In both cases every later open reads the same rows: this build, main, and
  any SQLite open. 0.1.0 refuses every schema-4 graph, as it does main's. The
  next writer of this build that closes alone restores the rollback journal
  and removes both files; the switch's own transaction runs with a full sync.
  A reader in a directory it cannot write can still open the store while
  `-wal` and `-shm` exist. It cannot open one left in log format without them,
  which only another build's last connection leaves (it folds the log back
  but keeps the format). A reader that has not read since the log started
  holds nothing, and the switch back succeeds.
  (`test/graph-write-ahead-log.test.mjs`)
- **Readers during an index.** They are not locked out only when the index
  switched to the log. If another connection was reading at the moment of the
  switch, that run keeps the rollback journal, and readers wait during its
  commits exactly as on main.

## SQLite version guard

**The bug.** SQLite documents a write-ahead-log reset bug
([wal.html](https://sqlite.org/wal.html), "The WAL-Reset Bug"):

- **What happens.** A database in write-ahead-log mode can be corrupted when
  two connections in different threads or processes write or checkpoint at
  the same instant, just after a checkpoint has made the log ready to reset.
- **Affected:** SQLite 3.7.0 through 3.51.2, and the withdrawn 3.52.0.
- **Fixed:** 3.51.3, 3.53.0 and later, and the backports 3.50.7 and 3.44.6.

**Which Node releases are affected.** Node bundles its own SQLite. Pymtheg
allows Node 24.0.0 and later (`engines`). Bundled versions, read from the
official images (`evidence/c-6/sqlite-versions.md` has every release read):

| Node | `process.versions.sqlite` | Reset bug | Acceptance gate |
| --- | --- | --- | --- |
| 24.0.0 | 3.49.1 | affected | `e-node-24.0.0` |
| 24.12.0, 24.13.0 | 3.50.4 | affected | |
| 24.14.0, 24.14.1 | 3.51.2 | affected | |
| 24.15.0 | 3.51.3 | fixed (first fixed 24.x) | |
| 24.16.0, 24.17.0 | 3.53.0 | fixed | |
| 24.21.0 | 3.53.4 | fixed | build image |
| 24.22.3 (`node:24`) | 3.54.1 | fixed | yes |
| 25.0.0 | 3.50.4 | affected | |
| 25.6.0 to 25.8.0 | 3.51.2 | affected | |
| 25.8.1, 25.8.2 | 3.52.0 | affected (withdrawn release) | |
| 25.9.0 (`node:25`) | 3.51.3 | fixed (first fixed 25.x) | `e-node-25` |
| 26.0.0 | 3.51.3 | fixed | |
| 26.13.1 (`node:26`) | 3.54.1 | fixed | `e-node-26` |

So Node 24.0.0 to 24.14.x and 25.0.0 to 25.8.x keep the rollback journal.
Node 24.15.0 and later 24.x, 25.9.0 and later, and Node 26 get the log on a
local disk. The gate's `e-node-24.0.0` containers sit on overlayfs, a local
type, so that scenario now takes the fallback because of the version alone.
`test/graph-write-ahead-log.test.mjs` run in that image confirms it: the guard
is false there, and the power-loss tests skip for lack of a log.

**The guard.** The store uses the log only when the SQLite engine behind the
connection (`sqlite_version()` on it, the same value as
`process.versions.sqlite`) is a fixed version. The version is checked, never the
Node version, so a Node built against a system SQLite is judged by that
SQLite. Besides 3.51.3 and later, the two backports SQLite lists (3.50.7 and
3.44.6) also count as fixed. No Node release bundles either; they matter only
for a system SQLite. One stricter case: a rule of "3.51.3 or later" would
accept 3.52.0, but 3.52.0 (2026-03-06, bundled by Node 25.8.1 and 25.8.2)
predates the fix. It was withdrawn and does not list the fix in its changes,
so the guard treats it as affected; the 3.52 line has no fixed release. The
version is compared numerically, and an unknown or unparsable version counts
as not fixed (`sqliteWalResetFixed`). An end-to-end test runs a cold index
with an affected version injected. It checks for a `-wal` file after every
store write and during resolution, finds none, and stores the same rows as the
fast path. Otherwise the
behaviour is main's: the rollback journal with a full sync per commit. And
because such a connection never writes in a log (above), it also folds back a
log that a killed run on a fixed Node left behind. Tests inject the version,
so they cover both sides whatever Node runs the suite.

**Older builds and a left-over log.** Could an older build hit the bug by
opening a store this build left in write-ahead-log mode after a crash?

- **0.1.0 cannot.** It refuses every schema-4 graph, and this build only
  writes schema 4.
- **Unreleased main builds can.** Builds between C-5 and C-6 open the store
  in write-ahead-log mode (SQLite keeps the mode in the file) and never
  change it, so they keep using the log. The bug needs two such connections
  writing or checkpointing at the same instant, on an affected SQLite. For
  example, an index and a concurrent sync on Node 24.0.0 to 24.14.x, before
  any C-6 writer has closed the store.
- **This build limits the window from its side:**
  - **Clean close.** Every clean close by the last connection leaves the
    rollback-journal format.
  - **Affected SQLite.** On an affected SQLite, this build folds the log back
    before writing.
  - **Readers.** A read-only connection cannot trigger the bug, because it
    neither writes nor checkpoints.
- **This build cannot close the window entirely.** After a kill, nothing of
  this build runs until the next command, so it cannot fold the log back
  before an older build gets there first.
- **Who is exposed.** Only someone who goes back to an unreleased main build
  after a crash, on an affected Node, and runs two writers at once.

## Found, not built

- **Two cold indexes racing** (review finding). The losing writer reports
  `UNIQUE constraint failed: graph_links.id` instead of "database is locked",
  on main as on the branch.
  The store stays consistent, reports incomplete, and the next sync repairs
  it. The error text is the only defect.

- **swc's next blocker is memory.** With PR 13 and this change, swc gets past
  the write phase that stopped PR 13's runs: all 1,523 Rust files' analysed
  facts, 394,584 links, are stored. After 2,709 s it then runs out of Node's
  default JavaScript heap (about 4 GB) in a later phase. That is most likely
  the TypeScript analysis of its 50,158 TypeScript and JavaScript files, which
  runs next. Memory is outside this chunk.

- **Statement work.** SQLite statement work is now most of the remaining
  write time: 47–80 % of cold time is inside write transactions on the seven
  repositories measured, while `COMMIT` is 12–30 %. Each file write maintains eight
  indexes on `graph_symbols`, several on `graph_links`, the resolution
  triggers, and JSON bodies that hold whole source texts. That is schema
  work, out of scope here.
- **A shared filesystem the check cannot see.** A store reached from two
  machines through a filesystem `statfs` reports as local (an iSCSI or
  shared-block cluster filesystem not in the list is excluded, but a local
  type exported elsewhere is not detected). That case was already unsafe with
  the rollback journal, whose locks do not cross machines either.

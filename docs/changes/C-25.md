# C-25 Follow an unbuilt workspace package entry to its source

## Recorded assumption

Module 40 follows a missing checkout workspace declaration to a unique
source that the captured TypeScript config would emit at the selected
entry path. When the package's build remains unproved, the link carries
`ts-unbuilt-entry-is-compiler-emit` in `data.assumes`. The MCP legend
describes what the link rests on.

> The package's build leaves, at this entry path, declarations whose
> exports are those the TypeScript compiler would emit for the mapped
> source file.

The link also keeps `data.unbuiltEntry` with the package manifest,
config, output and source. A proved plain `tsc` build needs no assumption.
The compiler still selects the entry using the importer's resolution mode
and conditions, and existing output files take priority. The mapping
requires one captured producer under a scoped config. The name convention
experiment stays disabled.

The assumption is excluded when captured build inputs give contrary
evidence.

- An API Extractor config or invocation, a declaration bundler invocation,
  or a captured Rollup config with a declaration plugin can replace the
  exported declarations. A literal wrapper write to the entry is also
  contrary evidence. The Wireit pipelines on the Puppeteer pin also stay
  outside the assumption. C-25 does not infer an untrimmed rollup.
- An explicit entry argument in a tsup, tsdown, unbuild, esbuild or Rollup
  command has to include the mapped source.
- A missing JavaScript-only entry supplies no type or value link. A
  captured JavaScript entry is analysed normally with the importing
  program's options.
- `stripInternal` with internal annotations prevents projection in the
  affected source tree. The native project-reference guard still withholds
  individual stripped declarations.

The three review counterexamples were constructed builds in which API
Extractor's rollup dropped an internal export, a tsup command chose a
different input, and a JavaScript-only build supplied no declarations.
Behavior tests exercise all three. Before this decision, 334 checked links
matched compiler emit or pinned published declarations. They include every
gain checked in Mermaid bare (140) and Redux Toolkit installed (74), the
reviewer's 30-site draw, the original 60-site audit, and 30 Hono sites.
The counterexamples show why the compiler's output path and those checks
support a recorded assumption about the package build.

For a program that uses the assumption, the analyzer also extracts it
with only ordinary lookup and the plain-build proof. Existing destinations
from that analysis take priority. Any new outcome that requires the
projection carries the assumption, including targets reached indirectly
through changed receiver types or ambient declarations.

## Plain-compiler review head `9606e6d`

Module 39 requires a captured, plain `tsc` build before an unbuilt package
entry can supply a source target. It recognizes the default config, a
literal `-p` or `--project` path, and `-b` or `--build` with an optional
literal path. It accepts one literal in-package clean step before the
compiler command when the clean path excludes captured sources and selected
configs. It reads these commands as strings. Additional build commands or
lifecycle hooks that could change the installed or packed output leave
the entry unresolved. Workspace orchestration relies on each package's own
build, and a plain `tsc -b` can establish a captured reference config for
a scriptless child.

The resolver projects a declaration that the selected build emits at a
path TypeScript chooses for the importer. A JavaScript-only build supplies
neither type nor value links from an absent output. A value seen by the
TypeScript source checker can depend on types and export semantics that
the importing compiler would lack when it reads JavaScript. A real
captured JavaScript output continues to use ordinary compiler lookup,
including `allowJs` where applicable.

When a declaration build enables `stripInternal` and captured sources
contain internal annotations, the module withholds new projections from
that build. Existing compiler-native project references still use the full
source program. On those routes the graph withholds the declarations that
TypeScript's own strip predicate identifies, including annotations on
an enclosing declaration. Ordinary source imports and public declarations
keep their compiler destinations. The build manifest is recorded alongside
the config, output and source in `data.unbuiltEntry`. The generated plan
counts resolved links carrying that proof separately.

The review removed literal tsup entry inference. A package's CLI can pick a
different entry from the manifest. The same rule excludes declaration
rollups and post-build rewrites. A tsconfig describes the compiler emit
even when those later steps replace it.

## Initial PR head `2d88a26`

The following record preserves the implementation and experiments before
the stricter review rule and the merge of C-13.

C-23's installed sample classified 64 of 200 misses as configuration or
build-input problems. That class includes tied compiler configurations and
missing inputs as well as unbuilt workspace entries. C-25 addresses the last
case when the checkout proves which source produces the selected entry.

## Proofs

- TypeScript already reads `paths`, `typesVersions` and package exports
  using the importer's resolution mode and `customConditions`. Existing
  outputs and source targets selected by that lookup keep their priority.
- For project references, the host uses `useSourceOfProjectReferenceRedirect`
  and `getParsedCommandLine`. Referenced composite outputs already captured
  as declaration files are excluded from the source redirect inventory.
- For other TypeScript builds, `getOutputFileNames` computes the exact emit
  path from the captured parsed config. It handles `outDir`, `declarationDir`,
  source extensions and the compiler's source root. An implicit common root
  needs proof that another input cannot widen it. `tsBuildInfoFile` is compiler
  state and supplies no source ownership evidence. Absolute and escaping
  build paths are excluded from emit proofs.
- The supported manifest build proof is a literal named entry under `tsup`
  with an explicit `outDir`, ESM output for a module package and `bundle: false`.
  A separate tsup config disables this proof. A bare `source` field or publish
  override supplies no input-to-output relationship on its own.

On a failed workspace lookup the compiler gets a scoped second pass with the
configured output names. A physical installed registry package takes priority
over an inferred workspace link. A selected missing output must have a unique
captured source producer. The retry also represents missing explicit package
entries whose producers are unknown, so a later JavaScript branch cannot
supplant a preferred declaration entry. Distinct producers stay unresolved
with the missing entry reason. The compiler reads the source's own exports,
so a barrel can rename or re-export a declaration and the graph can link to
that declaration's ordinary checkout key. The graph records the config,
output and source in `data.unbuiltEntry`. It uses the same program for
follow-on member links.

The TypeScript module version advances to 38. Analysis reads captured text
and uses the existing confined resolver. It runs no build code.

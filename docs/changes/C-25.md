# C-25 Follow an unbuilt workspace package entry to its source

## Rule after review

Module 39 requires a captured, plain `tsc` build before an unbuilt package
entry can supply a source target. It recognizes the default config, a
literal `-p` or `--project` path, and `-b` or `--build` with an optional
literal path. It accepts one literal in-package clean step before the
compiler command when the clean path excludes captured sources and selected
configs. It reads these commands as strings. Additional build commands or
lifecycle hooks that could change the installed or packed output leave
the entry unresolved. Workspace orchestration relies on each package's own
build, and a plain `tsc -b` can establish a captured reference config for
a scriptless child.

The resolver projects a declaration that the selected build emits at a
path TypeScript chooses for the importer. A JavaScript-only build supplies
neither type nor value links from an absent output. A value seen by the
TypeScript source checker can depend on types and export semantics that
the importing compiler would lack when it reads JavaScript. A real
captured JavaScript output continues to use ordinary compiler lookup,
including `allowJs` where applicable.

When a declaration build enables `stripInternal` and captured sources
contain internal annotations, the module withholds its source redirect.
This also covers the existing TypeScript-native project-reference path;
the checker could otherwise read an internal export through the source
even on main. Ordinary source paths and existing declarations keep their
usual lookup. The build manifest is recorded alongside the config, output
and source in `data.unbuiltEntry`. The generated plan counts resolved
links carrying that proof separately.

The review removed literal tsup entry inference. A package's CLI can pick a
different entry from the manifest. The same rule excludes declaration
rollups and post-build rewrites. A tsconfig describes the compiler emit
even when those later steps replace it.

## Proofs

- TypeScript already reads `paths`, `typesVersions` and package exports
  using the importer's resolution mode and `customConditions`. Existing
  outputs and source targets selected by that lookup keep their priority.
- For project references, the host uses `useSourceOfProjectReferenceRedirect`
  and `getParsedCommandLine`. Referenced composite outputs already captured
  as declaration files are excluded from the source redirect inventory.
- For other TypeScript builds, `getOutputFileNames` computes the exact emit
  path from the captured parsed config. It handles `outDir`, `declarationDir`,
  source extensions and the compiler's source root. An implicit common root
  needs proof that another input cannot widen it. `tsBuildInfoFile` is compiler
  state and supplies no source ownership evidence. Absolute and escaping
  build paths are excluded from emit proofs.
- The supported manifest build proof is a literal named entry under `tsup`
  with an explicit `outDir`, ESM output for a module package and `bundle: false`.
  A separate tsup config disables this proof. A bare `source` field or publish
  override supplies no input-to-output relationship on its own.

On a failed workspace lookup the compiler gets a scoped second pass with the
configured output names. A physical installed registry package takes priority
over an inferred workspace link. A selected missing output must have a unique
captured source producer. The retry also represents missing explicit package
entries whose producers are unknown, so a later JavaScript branch cannot
supplant a preferred declaration entry. Distinct producers stay unresolved
with the missing entry reason. The compiler reads the source's own exports,
so a barrel can rename or re-export a declaration and the graph can link to
that declaration's ordinary checkout key. The graph records the config,
output and source in `data.unbuiltEntry`. It uses the same program for
follow-on member links.

The TypeScript module version advances to 38. Analysis reads captured text
and uses the existing confined resolver. It runs no build code.

## Remaining build inputs

Puppeteer's preferred public entry `lib/types.d.ts` is an API Extractor
rollup. Its Wireit `build:tsc` step explicitly excludes that file from its
outputs. The separate `build:types` step creates it. C-25 can prove the
per-source TypeScript outputs used by `./internal/*`. The same compiler
config cannot prove the public entry's exported declarations.

Zod's default type entry is the `.d.cts` produced by `zshy`. Ordinary
TypeScript emit to a sibling `.js` does not prove that entry. The
`@zod/source` condition continues to select the checkout target when enabled.

tRPC's tsdown configuration applies dynamic extension hooks, a footer and an
`onSuccess` handler. Vitest's browser locators entry illustrates why the
importing program's selected condition matters. The source condition selects
`src/client/tester/locators.ts`, while its Rollup declaration build goes through
a helper to `src/client/tester/locators/index.ts`. C-25 resolves the former when
the condition is enabled. The latter still needs its output or a captured
static mapping. An implicit TypeScript source root can also remain open when
files outside the config's initial input set could widen it.

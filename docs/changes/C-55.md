# C-55: Go keeps its decoded inputs between runs of a session

## Where a Go body edit spends its reads

Main, through the MCP server's persistent worker (`scripts/resident/mcp-edits.mjs`), a body edit of cli/cli's widely imported file (`scripts/reindex/cases.json`), CPU by stage:

| Stage | What | CPU s |
|---|---|--:|
| `analyze.go.input` | decode every stored Go record (1,127) for the analysis | 2.2 |
| `resolve.go.input` | read the resolver's file projection (1,191 rows) and every symbol (28,670) | 1.8 |
| `go.globalIndex` (two calls) | rebuild Go's global lookups from those inputs | 4.1 |
| `analyze.go.notes` | the analysis itself | 2.2 |
| the rest (TypeScript's 64 files, hashing, writes) | | 3.3 |
| total | | 13.6 |

The two reads are what this chunk keeps: about 4 s of the 13.6. Keeping Go's global index (4.1 s) needs a proof that C-27's global fingerprints cover every global lookup; it is not in this chunk.

## Design

### What is kept, and who keeps it

The indexer keeps a module's decoded inputs, not the module. A module opts in with `keepsInput: true` (Go only). The value lives in the module's kept state in the session (`IndexSession`, C-45), under the name `core:input` and a key of the module's id and version. Every C-45 rule applies:
- the session's three proofs: the completion record at the run's baseline, the scope, and the module version;
- the run takes the value, and sets it again only if it completes;
- the value is never changed after it is set.

It holds two things, each per stored path:
- **The analysis input:** the decoded record of each stored file of the module, exactly as `filesAt` returns it.
- **The resolver input:** each stored file's resolver projection (`resolutionFiles`), and each file's symbols (`findSymbols`). Both cover every module, because the resolver reads every file and symbol.

Each kept record is deep-frozen. A module that changes its input in place then throws in strict code instead of changing kept state; the run fails and keeps nothing (C-45).

### Knowing what changed: the store records every path it writes

Every file-level fact the kept inputs hold is written only by `replaceFile` and `removeFile`:
- records, symbols and the projection all come from `graph_files` and `graph_symbols`;
- resolution writes change only link rows.

The store records the path of every `replaceFile` and `removeFile` call of the run (`writtenPaths`), in order, with a sequence number. An abandoned write (a rollback) can only make the record conservative: a path is re-read that need not be.

The kept value carries the sequence point at which it was read, and the paths written after that point in its own run (`stale`):
- **The analysis input** is read before the module's analysis write, so the module's own held files, and anything written later in the run, are stale.
- **The resolver input** is read after every analysis write, so normally nothing is stale.

### Using it

The next run takes the value, which the session has proved against the store as it stood at the run's baseline. Its stale paths, together with every path this run writes before the read, are re-read from the store:
- `filesAt` for the analysis input;
- the projection and the symbols of those paths for the resolver input.

Everything else comes from the kept value. Each input is assembled in the order the store returns it (records and projections by path, symbols by id), so a module sees exactly what a fresh read gives. A path not stored, whether removed or never written, is simply absent.

### Bound and report

The kept value's size is counted as the bytes of the stored JSON it was decoded from. It is reported per run (`kept.input.bytes`). It is not kept above `keptInputBytes`, 128 MiB of stored JSON; such a run reads afresh. The MCP worker's 512 MiB resting bound (C-48) still ends a worker that keeps more.

### Without a session

Nothing changes. No value is kept, the store's write record is never read, and every read is as on main.

## Requirements and how they are checked

- **No session:** the stores are byte-identical to main's. Checked with cold indexes and seeded edits without a session, using the C-35 row digests.
- **With a session:** 60 or more seeded edits on restic and cli/cli through the persistent worker each equal a cold index row for row. The edits include renames, removals, parse breaks, `go.mod` edits and build-tag changes.
- **Kill points:** the C-22 and C-48 kill tests at every write boundary repair to cold.
- **A stale value is never used:** a test indexes in a session, lets another process index an edit in between, and asserts the session's next result equals cold. It must fail if the kept value is used unproved.
- **Memory:** the kept bytes and the worker's live heap after each job, on cli/cli, against the 512 MiB bound.
- **Cost:** per-edit CPU and records decoded, main → head, through the MCP worker.

## As built

- **`src/graph/kept-input.ts`:** the kept inputs (`KeptInputs`). Each read keeps its values per path, deep-frozen, and records the store's write mark. A later run reuses what nothing has written since and re-reads the rest. Inputs are assembled in the store's order: records and projections by path, symbols by id.
- **The resolver given no scope** (a surface edit) also takes its records from the run's analysis records, where nothing has written them since. Other modules' files and written files are read afresh.
- **`src/graph/store.ts`:**
  - records every path passed to `replaceFile` and `removeFile` (`writeMark`, `pathsWrittenSince`);
  - reads chosen paths' symbols (`symbolsOfFiles`) and projection rows (`resolutionFiles(kinds, paths)`);
  - notes each decoded value's stored length (`storedSize`), so the kept size is counted without encoding anything again.
- **`src/graph/indexer.ts`:** uses the kept inputs for a module with `keepsInput` in a session, and sets them again at the end of the run. The session keeps them only if the run completes (C-45).
- **Go** opts in (`keepsInput: true`). Its analysis and resolver receive frozen inputs, and no test or seeded edit found it changing them.
- **`scripts/reindex/random-edits.mjs`:**
  - `--mcp` runs every incremental index through the MCP server's graph jobs, one persistent worker with its session, and records the job's CPU, counters, stage times and live heap;
  - `--more-go` adds Go parse breaks, `go.mod` edits and file moves.

## Freezing, measured

The first build deep-froze every kept value before a module saw it, so that a module changing its input would throw. On the real stores, freezing a record costs about two thirds of decoding it:

| Store | Records | MB | Parse ms | Freeze ms |
|---|--:|--:|--:|--:|
| restic | 562 | 20 | 297 | 186 |
| cli/cli | 1,192 | 78 | 993 | 643 |

A surface edit rewrites hundreds of files, which are re-read and frozen; with freezing, restic's 35 seeded edits cost 506 → 561 s of CPU. So production does not freeze. The rule is the module's contract (`keepsInput`: a module must not change its inputs in place), and the test suite freezes every kept value (under `PYMTHEG_TEST`). A module that changes one therefore fails a test. The whole suite and all seeded edits of the earlier builds ran with freezing on; Go never changed an input.

## Results

**Body and export edits** (`scripts/reindex/cases.json`) through the MCP worker, main → this branch, at the same time on the shared server. The first run after the cold index has no kept value; its revert, the second run, uses one. The columns are:
- CPU s: the whole job;
- Records: stored records decoded;
- Analysis input s: CPU of `analyze.go.input`;
- Resolver input s: CPU of `resolve.go.input`;
- Heap MiB: the worker's live heap after the job.

The input stages fall as designed: a cli/cli body edit's two reads go from 3.9 s to 0.4 s. The whole job's CPU is noisy on the busy server; restic's body revert (4.6 s, with its input stages at 0.1 s) is the noisiest. The rest of a body edit is Go's global index and analysis (about 6 s on cli/cli), which this chunk does not keep.

**Seeded edits** through the MCP worker (`random-edits.mjs --mcp --more-go`). The edits include body, signature (renames), interface, embed, import, dot import, file add, file delete, file move, parse break, `go.mod` and build-tag edits. Each is compared with a cold index of the same tree.

| Pin | Build | Edits equal to cold | CPU s, main → head | Records decoded, main → head |
|---|---|--:|--:|--:|
| restic | final | 35 of 35 | 506.5 → 479.5 | 42,194 → 6,961 |
| restic | frozen inputs | 35 of 35 | 506.5 → 561.1 | 42,194 → 6,961 |
| cli/cli | frozen inputs | 35 of 35 | 1,399.9 → 1,369.6 | 85,729 → 18,985 |
| cli/cli | final | 25 of 25 run | | |

The final build differs from the frozen one only in not freezing. Its cli/cli run stopped at step 25, all 25 equal, when the shared server's disk stalled (a cold index waiting in the kernel on btrfs space). That gives 95 edits through the session on the final build or its frozen twin, every one equal to cold.

**Memory.** The kept value is about 91 MB of stored JSON on cli/cli and 24 MB on restic. The worker's live heap after each job is 247 MiB on cli/cli (94 on main) and at most 120 on restic, under C-48's 512 MiB resting bound. A kept value above 128 MiB of stored JSON is not kept.

**Without a session**, cold stores of restic and cli/cli are identical to main's, row for row (C-35 row digests). The full suite passes, 3,403 of 3,403, including the C-22 and C-48 kill tests at every write boundary.

## Further work

- **Go's global index** (about 4 s of a cli/cli body edit) is rebuilt from the kept inputs every run. Keeping it needs C-27's global fingerprints to be proved to cover every global lookup.
- **A first run of a session** pays the reads as before. Records the run itself wrote could be kept as written instead of re-read on the next run.

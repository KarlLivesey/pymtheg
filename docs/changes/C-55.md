# C-55: Go keeps its decoded inputs between runs of a session

## Where a Go body edit spends its reads

Main, through the MCP server's persistent worker (`scripts/resident/mcp-edits.mjs`), a body edit of cli/cli's widely imported file (`scripts/reindex/cases.json`), CPU by stage:

| Stage | What | CPU s |
|---|---|--:|
| `analyze.go.input` | decode every stored Go record (1,127) for the analysis | 2.2 |
| `resolve.go.input` | read the resolver's file projection (1,191 rows) and every symbol (28,670) | 1.8 |
| `go.globalIndex` (two calls) | rebuild Go's global lookups from those inputs | 4.1 |
| `analyze.go.notes` | the analysis itself | 2.2 |
| the rest (TypeScript's 64 files, hashing, writes) | | 3.3 |
| total | | 13.6 |

The two reads are what this chunk keeps: about 4 s of the 13.6. Keeping Go's global index (4.1 s) needs a proof that C-27's global fingerprints cover every global lookup; it is not in this chunk.

## Design

### What is kept, and who keeps it

The indexer keeps a module's decoded inputs, not the module. A module opts in with `keepsInput: true` (Go only). The value lives in the module's kept state in the session (`IndexSession`, C-45), under the name `core:input` and a key of the module's id and version. Every C-45 rule applies:
- the session's three proofs: the completion record at the run's baseline, the scope, and the module version;
- the run takes the value, and sets it again only if it completes;
- the value is never changed after it is set.

It holds two things, each per stored path:
- **The analysis input:** the decoded record of each stored file of the module, exactly as `filesAt` returns it.
- **The resolver input:** each stored file's resolver projection (`resolutionFiles`), and each file's symbols (`findSymbols`). Both cover every module, because the resolver reads every file and symbol.

Under the test suite each kept record is deep-frozen. A module that changes its input in place then throws in strict code instead of changing kept state; the run fails and keeps nothing (C-45). Production does not freeze (see "Freezing, measured").

### Knowing what changed: the store records every path it writes

Every file-level fact the kept inputs hold is written only by `replaceFile` and `removeFile`:
- records, symbols and the projection all come from `graph_files` and `graph_symbols`;
- resolution writes change only link rows.

The store records the path of every `replaceFile` and `removeFile` call of the run (`writtenPaths`), in order, with a sequence number. An abandoned write (a rollback) can only make the record conservative: a path is re-read that need not be.

The kept value carries the sequence point at which it was read, and the paths written after that point in its own run (`stale`):
- **The analysis input** is read before the module's analysis write, so the module's own held files, and anything written later in the run, are stale.
- **The resolver input** is read after every analysis write, so normally nothing is stale.

### Using it

The next run takes the value, which the session has proved against the store as it stood at the run's baseline. Its stale paths, together with every path this run writes before the read, are re-read from the store:
- `filesAt` for the analysis input;
- the projection and the symbols of those paths for the resolver input.

Everything else comes from the kept value. Each input is assembled in the order the store returns it, so a module sees exactly what a fresh read gives:
- **Projections** follow SQL `ORDER BY path`, by UTF-8 bytes (code points), like main's projection query (`resolutionFiles`). The store's file listing (`fileSummaries`) is re-sorted by UTF-16 code units, so the kept projection is sorted again by code points (`storeOrder`) before a module sees it (review: it used the listing's order).
- **Records** follow `compare` (UTF-16 code units), like main's `filesAt` and `files`.
- **Symbols** are by id.

The two path orders differ between a path character above U+FFFF and one in U+E000..U+FFFF, and each input keeps the one main uses. A session test with such paths (`p/x\uFFFD.go` beside `p/x😀.go`, an order the two rules give differently) checks, after every edit, that Go's resolver is given the projection in SQL order (`context.files`), and that the store equals a cold index. Go's resolver sorts its context itself, so Go's results did not depend on this; a future `keepsInput` module might. A path not stored, whether removed or never written, is simply absent.

### Bound and report

The kept value's size is counted as the UTF-8 bytes of the stored JSON it was decoded from (review: it counted UTF-16 units). It is reported per run (`kept.input.bytes`). It is not kept above `keptInputBytes`, 128 MiB of stored JSON; such a run reads afresh. What is counted: a record's whole stored body, each file's symbol bodies, and for a projection row only the columns it is built from (diagnostics, the module's links and data), not the rest of the file's body. The decoded heap is larger than the count: on cli/cli, 91 MB counted gave the worker +153 MiB of resting heap (94 → 247 MiB), about 1.7 times. So the 128 MiB limit means roughly +215 MiB of heap at most, under the 512 MiB bound. A test finds a run's count with no limit, then checks that a limit of exactly that many bytes keeps the value and one byte less does not, on source text where bytes and UTF-16 units differ. The MCP worker's 512 MiB resting bound (C-48) still ends a worker that keeps more.

### Without a session

Nothing changes. No value is kept, the store's write record is never read, and every read is as on main.

## Requirements and how they are checked

- **No session:** the stores are byte-identical to main's. Checked with cold indexes and seeded edits without a session, using the C-35 row digests.
- **With a session:** 60 or more seeded edits on restic and cli/cli through the persistent worker each equal a cold index row for row. The edits include renames, removals, parse breaks, `go.mod` edits and build-tag changes.
- **Kill points:** the C-22 and C-48 kill tests at every write boundary repair to cold.
- **A stale value is never used:** a test indexes in a session, lets another process index an edit in between, and asserts the session's next result equals cold. It must fail if the kept value is used unproved.
- **Memory:** the kept bytes and the worker's live heap after each job, on cli/cli, against the 512 MiB bound.
- **Cost:** per-edit CPU and records decoded, main → head, through the MCP worker.

## As built

- **`src/graph/kept-input.ts`:** the kept inputs (`KeptInputs`). Each read keeps its values per path (deep-frozen under the test suite) and records the store's write mark. A later run reuses what nothing has written since and re-reads the rest. Inputs are assembled in the store's order: records and projections by path, symbols by id.
- **The resolver given no scope** (a surface edit) also takes its records from the run's analysis records, where nothing has written them since. Other modules' files and written files are read afresh.
- **`src/graph/store.ts`:**
  - records every path passed to `replaceFile` and `removeFile` (`writeMark`, `pathsWrittenSince`);
  - reads chosen paths' symbols (`symbolsOfFiles`) and projection rows (`resolutionFiles(kinds, paths)`);
  - notes each decoded value's stored length (`storedSize`), so the kept size is counted without encoding anything again.
- **`src/graph/indexer.ts`:** uses the kept inputs for a module with `keepsInput` in a session, and sets them again at the end of the run. The session keeps them only if the run completes (C-45).
- **Go** opts in (`keepsInput: true`). Its analysis and resolver receive frozen inputs, and no test or seeded edit found it changing them.
- **`scripts/reindex/random-edits.mjs`:**
  - `--mcp` runs every incremental index through the MCP server's graph jobs, one persistent worker with its session, and records the job's CPU, counters, stage times and live heap;
  - `--more-go` adds Go parse breaks, `go.mod` edits and file moves.

## Freezing, measured

The first build deep-froze every kept value before a module saw it, so that a module changing its input would throw. On the real stores, freezing a record costs about two thirds of decoding it:

| Store | Records | MB | Parse ms | Freeze ms |
|---|--:|--:|--:|--:|
| restic | 562 | 20 | 297 | 186 |
| cli/cli | 1,192 | 78 | 993 | 643 |

A surface edit rewrites hundreds of files, which are re-read and frozen; with freezing, restic's 35 seeded edits cost 506 → 561 s of CPU. So production does not freeze. The rule is the module's contract (`keepsInput`: a module must not change its inputs in place). Under the test suite (`PYMTHEG_TEST`) the indexer freezes a `keepsInput` module's analysis and resolver inputs in every run, with or without a session (review: before, only session runs froze, and only one small Go test used a session). So every Go test in the suite runs Go's analysis and resolution on frozen inputs, and a change in place fails there. That covers `npm test` and, since this review, `npm run test:backend`, whose integration files now load the same test configuration (`test/isolated-config.mjs`, which sets `PYMTHEG_TEST`); before, they did not. The full suite passes that way. The production-frozen builds' seeded edits (70 on restic and cli/cli with real-shaped trees, every one equal to cold) are the evidence at scale that Go changes no input.

## Freshness, checked by mutation

The review found that breaking some of the re-read rules left every test passing. Each rule below was broken in the built `dist/graph/kept-input.js`, then `test/graph-index-session.test.mjs` was run (15 tests, all passing unmutated). Each mutation now fails at least one test:

| Mutation | Tests that fail |
|---|---|
| this run's own earlier writes ignored (both reads) | seeded edits; the session steps; the direct re-read test |
| the same, in the resolver read only | seeded edits; the session steps; the direct re-read test |
| the same, in the analysis read only | the direct re-read test |
| kept symbols reused for stale paths | seeded edits; the session steps; the direct re-read test |
| kept projection rows reused for stale paths | the direct re-read test |
| a wanted analysis path never kept is not read | the never-kept test |
| the kept projection left in the listing's order | the order test |
| the kept projection reversed | the order test |

The session steps are, each compared with a cold index:
- adding `a/hello.go` with `World`, then renaming it by case;
- calling `a.World()` from `c/c.go`, then renaming the file;
- renaming `World` to `Planet`, then editing the caller;
- changing an embedded type, then a body edit;
- breaking a file's syntax and mending it;
- embedding a type in a type local to a function, then changing it.

Two rules change no Go result end to end, which is why a direct test of `KeptInputs` (three runs; this run's writes, writes after the last read, and nothing written) checks them:
- Go writes its records after its analysis read, so nothing this run writes is in the analysis input.
- A run that stays scoped has proved the edited file's embeds unchanged, and embeds are all the projection carries of links.

## Results

**Body and export edits** (`scripts/reindex/cases.json`) through the MCP worker, main → this branch, at the same time on the shared server. The first run after the cold index has no kept value; its revert, the second run, uses one. The columns are:
- CPU s: the whole job;
- Records: stored records decoded;
- Analysis input s: CPU of `analyze.go.input`;
- Resolver input s: CPU of `resolve.go.input`;
- Heap MiB: the worker's live heap after the job.

| Pin | Edit | CPU s | Records | Analysis input s | Resolver input s | Heap MiB |
|---|---|--:|--:|--:|--:|--:|
| cli/cli | body (first) | 13.0 → 11.9 | 1,192 → 1,192 | 2.12 → 1.90 | 1.75 → 1.70 | 94 → 247 |
| cli/cli | body revert | 13.4 → 9.3 | 1,192 → 66 | 2.15 → 0.00 | 1.71 → 0.39 | 93 → 247 |
| cli/cli | export | 34.7 → 28.0 | 1,524 → 398 | 1.78 → 0.00 | 4.56 → 3.34 | 94 → 247 |
| cli/cli | export revert | 32.8 → 27.1 | 1,524 → 398 | 1.70 → 0.00 | 4.34 → 3.21 | 94 → 247 |
| restic | body (first) | 3.4 → 3.9 | 560 → 560 | 0.32 → 0.34 | 0.39 → 0.40 | 83 → 118 |
| restic | body revert | 3.5 → 4.6 | 560 → 2 | 0.32 → 0.00 | 0.39 → 0.09 | 81 → 118 |
| restic | export | 12.5 → 12.0 | 714 → 156 | 0.30 → 0.00 | 1.20 → 1.11 | 80 → 119 |
| restic | export revert | 14.9 → 10.8 | 714 → 156 | 0.32 → 0.01 | 1.27 → 1.11 | 80 → 119 |

The input stages fall as designed: a cli/cli body edit's two reads go from 3.9 s to 0.4 s. The whole job's CPU is noisy on the busy server; restic's body revert (4.6 s, with its input stages at 0.1 s) is the noisiest. The rest of a body edit is Go's global index and analysis (about 6 s on cli/cli), which this chunk does not keep.

**Seeded edits** through the MCP worker (`random-edits.mjs --mcp --more-go`). The edits include body, signature (renames), interface, embed, import, dot import, file add, file delete, file move, parse break, `go.mod` and build-tag edits. Each is compared with a cold index of the same tree.

| Pin | Build | Edits equal to cold | CPU s, main → head | Records decoded, main → head |
|---|---|--:|--:|--:|
| restic | final | 35 of 35 | 506.5 → 479.5 | 42,194 → 6,961 |
| restic | frozen inputs | 35 of 35 | 506.5 → 561.1 | 42,194 → 6,961 |
| cli/cli | frozen inputs | 35 of 35 | 1,399.9 → 1,369.6 | 85,729 → 18,985 |
| cli/cli | final (after review) | 35 of 35 | 1,399.9 → 1,201.4 | 85,729 → 18,985 |

The final build differs from the frozen one only in not freezing. Its first cli/cli run stopped at step 25 (all equal) when the shared server's disk stalled. It was run again, complete, on the build after review: 35 of 35 equal. Its main figure comes from the earlier run on a busier server, so the CPU difference is an observation. Its live heap peaked at 248 MiB, with 91 MiB of stored JSON kept. In all, 140 seeded edits ran through the session, every one equal to cold.

**Memory.** The kept value is about 91 MB of stored JSON on cli/cli and 24 MB on restic. The worker's live heap after each job is 247 MiB on cli/cli (94 on main) and at most 120 on restic, under C-48's 512 MiB resting bound. A kept value above 128 MiB of stored JSON is not kept (`kept.input.overLimit`); the limit is a session option, and a test sets it to one byte: nothing is kept, the next run reads every input afresh, and both equal cold.

**Without a session**, cold stores of restic and cli/cli are identical to main's, row for row (C-35 row digests). The full suite passes, 3,403 of 3,403, including the C-22 and C-48 kill tests at every write boundary.

## Further work

- **Go's global index** (about 4 s of a cli/cli body edit) is rebuilt from the kept inputs every run. Keeping it needs C-27's global fingerprints to be proved to cover every global lookup.
- **A first run of a session** pays the reads as before. Records the run itself wrote could be kept as written instead of re-read on the next run.

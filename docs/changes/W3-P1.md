# W3-P1: index speed phase 1

Two fixes from the W3-P investigation (`docs/changes/W3-P.md` on PR 39),
nothing else. Stored results and query output are byte-identical to main.

## 1. One commit per write phase, not one per file

`indexProject` used to commit every `replaceFile` separately. Each commit is a
synced rollback-journal transaction, and a cold Vector index makes 3,115 of
them. The indexer now runs each write phase inside one store transaction:
- **Parse phase:** context files, parse results and removed files.
- **Analysis phase:** analysed results, once per module.

The context-file and `replaceAnalysis` writes were already one transaction each.

The new transaction comes from an optional `GraphStorage.writeBatch(write)`.
`SqliteGraphStore` implements it as `BEGIN IMMEDIATE … COMMIT`, and while it
is open each store write runs as a savepoint. Every store call therefore stays
individually atomic, and the per-file write order is unchanged. A store
without `writeBatch` keeps the old behaviour.

**What an interrupted run loses.** A crash, an abort or a storage error during
a write phase rolls back that whole phase. Only work is lost, never
correctness:
- **Today's behaviour:** the files written before the failure were kept.
- **Now:** the store keeps the state it had before the phase.
- **Next run:** it parses or analyses those files again.

Every state an interrupted run can now leave behind is one today's code could
already leave, because phase boundaries are a subset of today's per-file
commit points. Today's recovery path handles all of them.

A run that fails during analysis keeps its committed parse phase, exactly as
before. Analysis and resolution rerun on the next run either way.

`test/graph-write-batch.test.mjs` covers four cases:
- a thrown failure part-way through the parse writes;
- a thrown failure part-way through the analysis writes;
- a process killed mid-phase;
- read-only stores without the new index (see fix 2).

In each failure case the test checks that nothing of the failed phase is kept
and that the next run equals a fresh cold index. No test asserts timing.

## 2. Link reads use a covering index

Link reads (`selectLinks`) join `graph_files` three times, only to read
`status`. That column is stored after the whole file body, so every link row
made SQLite walk the body's overflow pages.

The store now creates `graph_files(path,status)` as a plain added index and
names it with `INDEXED BY` in the three joins; the planner does not pick it on
its own. The index changes no stored row, no schema version and no module
version. An existing graph gains it the next time it is opened for writing.

A read-only open of a graph written before the index existed checks for it
and keeps the old query plan. The rows are identical either way, and the test
checks this.

## Result identity (dev server)

`evidence/w3-p1/run.sh` builds main's graph code from `git archive origin/main`
and runs main and this branch through four steps on restic c734245 and Vector
515e87d9:
- **cold:** a fresh index;
- **warm:** an unchanged re-index;
- **changed:** one function appended to one file (restic `cmd/restic/main.go`,
  Vector `src/sources/nats/config.rs`);
- **reverted:** the file restored and re-indexed.

At every step, `evidence/w3-p1/identity.mjs` hashes the same three things for
both versions:
- **Tables:** every `graph_*` table's rows, read with plain SQLite.
- **Query output:** read through each version's own store API. That covers
  `files`, `findSymbols`, `links`, `unresolved`, `ambiguous`, `contexts`,
  `failedFiles` and `counts`. It also covers a 300-symbol sample of `outgoing`,
  `incoming`, `neighbourhood(·,1)`, `linksForFile` and incoming `callLinks`.
- **The index report.**

**Result:** every hash is identical between main and this branch, at all four
steps on both corpora (`evidence/w3-p1/compare.mjs` prints `ALL IDENTICAL`).
The raw hashes are in `evidence/w3-p1/{restic,vector}.jsonl`.

## Timings (observations, dev server)

Dev server: EPYC 7601, btrfs on NVMe, shared with other agents. Steps ran
one after another, but the load average at the start of each run ranged from
5 to 46, so treat the timings as observations, not a benchmark.

| Corpus | Step | main | this branch |
| ------ | ---- | ---: | ----------: |
| restic | cold | 86.8 s (load 12) | 55.6 s (load 5) |
| restic | warm | 15.6 s | 9.8 s |
| restic | changed | 15.5 s | 10.1 s |
| restic | reverted | 16.3 s | 10.3 s |
| Vector | cold | 801 s (load 9) | 522 s (load 30) |
| Vector | warm | 281 s (load 8) | 195 s (load 33) |
| Vector | changed | 342 s (load 14) | 191 s (load 30) |
| Vector | reverted | 319 s (load 46) | 174 s (load 25) |

Peak RSS is unchanged: about 4.2–5.0 GB for Vector and 0.87–1.5 GB for
restic. Memory was not in scope.

## Not built (further speed-ups, from W3-P)

These are listed only. Each needs its own decision.
- Skip analysis and resolution when nothing changed: after this chunk, that
  is most of a warm run.
- Count the end-of-run report with `COUNT(*)` instead of materialising every
  link.
- Prepare each SQL statement once instead of once per row.
- Drop the store's decode cache, and freeze the resolve input instead of
  cloning it (memory).
- A larger SQLite page cache for long write phases.
- Batch the per-link target writes in `replaceAnalysis`.
- Parse in worker threads.
- Incremental Rust and Go analysis for a changed file.

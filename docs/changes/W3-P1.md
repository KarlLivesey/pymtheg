# W3-P1: index speed phase 1

Phase 1 was scoped to two fixes from the W3-P investigation
(`docs/changes/W3-P.md`, PR 39). **Only the second ships.** The first was
tried in two forms and left out, because neither keeps concurrent use working
as it does on main; the measurements are below. Stored results and query
output are byte-identical to main.

## Shipped: link reads use a covering index

Link reads (`selectLinks`) join `graph_files` three times, only to read
`status`. That column is stored after the whole file body, so for every link
row SQLite walked the body's overflow pages.

The store now creates `graph_files(path,status)` as a plain added index and
names it with `INDEXED BY` in those three joins; the planner does not pick it
on its own. The index changes no stored row, no schema version and no module
version. An existing graph gains it the next time it is opened for writing.

A read-only open of a graph written before the index existed checks for it
and keeps the old query plan. The rows are identical either way.

Write behaviour is unchanged: one commit per file, as on main. An interrupted
run therefore loses nothing new.

`test/graph-link-index.test.mjs` covers two things:
- Read-only reads without the index return rows identical to indexed reads.
- Concurrent use, deterministically. After every file write of an index (both
  write phases), three things succeed: a fail-fast connection takes the write
  lock, the reads `graph status` makes return the committed files, and a
  writable store opens. The handshake is the write hook, not a clock. This
  guards against a long write transaction coming back.

## Left out: fewer commits per index run

On main, a cold Vector index makes 3,115 synced commits, one per file write.

**Round 1: one transaction per write phase.** This was fast, but it held the
write lock for each whole phase (225–437 s on Vector). Both reviewers saw
concurrent `graph status` and `graph search --no-sync` fail with
`database is locked`: 20 of 62 tries, against 0 of 123 on main. A writable
open also timed out.

**Round 2: bounded batches,** one commit every N writes. During a cold Vector
index on the dev server, `evidence/w3-p1/concurrency.mjs` starts a real
`graph status`, a real `graph search Event --no-sync` and a writable store
open every 100 writes. Each probe is a separate process with the normal 30 s
busy wait, which gives 32 tries of each per run:

| Run | Index wall time | `status` failed | `search --no-sync` failed | Writable open failed |
| --- | --------------: | --------------: | ------------------------: | -------------------: |
| main (one commit per write) | 838 s (load 25) | 0/32 | 0/32 | 0/32 (slowest 13.6 s) |
| N = 16 | 588 s (load 18) | 1/32 | 1/32 | 15/32 |
| N = 4 | 694 s (load 10) | 0/32 | 0/32 | 12/32 |
| N = 2 | 760 s (load 24) | 0/32 | 0/32 | 2/32 |

Reads succeed again from N = 4. Writable opens do not reach main's 0/32 at
any N tried. Each failed open reported `database is locked`: it could not get
the write lock within its 30 s wait while batches held it.

Which statements need that lock was measured separately. A writable
`SqliteGraphStore` open makes 26 SQL calls, each replayed on a fail-fast
connection while another connection held `BEGIN IMMEDIATE`. Only 2 of the 26
needed the write lock:
- `INSERT OR IGNORE INTO graph_meta VALUES ('schema','3')`
- `INSERT OR IGNORE INTO graph_meta VALUES ('project',?)`

The `CREATE … IF NOT EXISTS` statements, the triggers, the `PRAGMA`s and the
reads all ran while the lock was held. Why N = 2 still failed 2 of 32 opens
was not investigated.

At N = 2 most of the cold speed gain is already gone: 760 s against 838 s at
similar load. Matching main's concurrency with fewer commits is left for a
separate decision.

## Result identity (dev server)

`evidence/w3-p1/run.sh` builds main's graph code from `git archive` (main at
`1eddce6a`) and runs main and this branch through four steps on restic
c734245 and Vector 515e87d9:
- **cold:** a fresh index;
- **warm:** an unchanged re-index;
- **changed:** one function appended to one file (restic `cmd/restic/main.go`,
  Vector `src/sources/nats/config.rs`);
- **reverted:** the file restored and re-indexed.

At every step, `evidence/w3-p1/identity.mjs` hashes the same three things for
both versions:
- **Tables:** every `graph_*` table's rows, read with plain SQLite.
- **Query output:** read through each version's own store API. That covers
  `files`, `findSymbols`, `links`, `unresolved`, `ambiguous`, `contexts`,
  `failedFiles` and `counts`. It also covers a 300-symbol sample of `outgoing`,
  `incoming`, `neighbourhood(·,1)`, `linksForFile` and incoming `callLinks`.
- **The index report.**

**Result:** every hash is identical between main and this branch, at all four
steps on both corpora (`compare.mjs restic.jsonl vector.jsonl` prints
`ALL IDENTICAL`). Round 1's batch-version runs were identical too
(`round1-*.jsonl`).

**Concurrent use on this head,** measured the same way as round 2 above: a
cold Vector index took 639 s (load 3). Every probe succeeded, as on main:

| Probe | Failed | Slowest |
| ----- | -----: | ------: |
| `status` | 0/32 | 9.7 s |
| `search --no-sync` | 0/32 | 11.7 s |
| Writable open | 0/32 | 13.7 s |

The data is in `concurrency-head.jsonl`, `concurrency-main-n16.jsonl` and
`concurrency-n4-n2.jsonl`; `concurrency-summary.mjs` prints the tables.

## Timings (observations, dev server)

Dev server: EPYC 7601, btrfs on NVMe, shared with other agents. Steps ran
one after another, but load differed between paired runs, so treat these as
observations, not a benchmark.

| Corpus | Step | main | this branch |
| ------ | ---- | ---: | ----------: |
| restic | cold | 87.0 s (load 17) | 73.1 s (load 7) |
| restic | warm | 16.1 s | 11.0 s |
| restic | changed | 15.7 s | 10.8 s |
| restic | reverted | 14.8 s | 11.3 s |
| Vector | cold | 804 s (load 13) | 707 s (load 13) |
| Vector | warm | 255 s (load 11) | 162 s (load 26) |
| Vector | changed | 242 s (load 5) | 147 s (load 7) |
| Vector | reverted | 269 s (load 13) | 142 s (load 3) |

The gain comes from link reads, and is largest on warm and changed-file runs:
about −36% to −47% on Vector, −24% to −32% on restic. Cold runs gain less (Vector
−12%), because per-file commits still dominate them. Peak RSS is unchanged:
Vector 4.2–5.1 GB, restic 0.86–1.9 GB.

## Not built (further speed-ups)

These are listed only. Each needs its own decision.
- **Fewer commits per index run** (above). Bounded batches made concurrent
  writable opens fail. The cause of the remaining failures at N = 2 was not
  investigated; WAL is one option to evaluate.
- **Skip analysis and resolution when nothing changed.** After this chunk,
  that is most of a warm run.
- **`COUNT(*)` for the end-of-run report,** instead of materialising every
  link.
- **Prepare each statement once** instead of once per row.
- **Memory:** drop the store's decode cache, and freeze the resolve input
  instead of cloning it.
- **Batch the per-link target writes** in `replaceAnalysis`.
- **Parse in worker threads.**
- **Incremental Rust and Go analysis** for a changed file.

# C-5: library targets as first-class graph entries (core)

A call from project code into a library whose source is not in the checkout,
such as Go `strconv.Quote` or `z.string()` from the npm package `zod`, is worth
a link: it answers "where do we use this library, and this symbol in it". Until
now the graph had nowhere to put one. Such links were stored as unresolved,
and the coverage measure rebuilt library identities from whatever each
language module happened to record. This change adds the place. It is the
core only: **no production language records a library target yet.** The Go,
Rust and TypeScript items (`go-external-targets`, `rust-external-targets`,
`ts-external-targets`) fill it in without changing the core.

## What a library target is

A library target has an ecosystem (`go`, `go-std`, `cargo`, `rust-std`, `npm`,
`node`, `dom`, …), a unit (module path, crate or package), an optional symbol
in the unit, a version only when the checkout's manifest or lockfile states
it, and an evidence kind saying how the source proves it. Its id is a hash of
ecosystem, unit, version and symbol, so it is the same in every project.

A link whose only target is a library target has its own outcome, `library`,
distinct from `resolved` (a target in the checkout). A candidate set can now
mix checkout symbols and library targets. Library targets are rows of their
own, so "all uses of package X" and "all uses of X's symbol s" are one index
read.

The store refuses a library target without a known evidence kind. The kinds
are `import-path` and `reference-directive` (they name a unit, never a symbol),
`import-binding`, `qualified-path`, `explicit-trait`, `declared-builtin`, and
`glob-import`, which a candidate set may use but a definite target may not:
a glob import puts the unit in scope without proving that it declares the
name. There is no kind for "the receiver's type comes from library L, so the
method is L's". Extension traits, `Into`, and promoted or embedded members make
that unprovable, so such a link stays unresolved with its reason.

## Where it shows

- `pymtheg graph uses UNIT [SYMBOL]` lists the project links to a library unit
  or to one symbol in it, with exact counts of definite library links and
  candidate sets. The MCP tool `code_graph` has the same as action `uses`
  (`query` the unit, optional `symbol`).
- Every graph answer shows a library link with certainty `library` and the
  library's ecosystem, unit, symbol, evidence and place "outside this project",
  never as a missing local symbol. A library member of a candidate set is a
  `candidates` row with a `library` field.
- Counts include the outcome: `counts.library` and the index report's
  `library`.
- No Studio screen shows graph links, so Studio is unchanged.

## Storage

The graph schema goes from 3 to 4: one new table (`graph_library_targets`) and
resolution triggers that know about it. A schema-3 graph made by 0.1.0 is
migrated in place when this version opens it for writing. None of its rows
has a library target, so all of them stay valid and nothing is re-indexed. A
read-only open of a schema-3 graph works and reads no library targets. 0.1.0
refuses a schema-4 graph with its usual rebuild message. The command
checkpoint gains the new count, so the first query after upgrading syncs the
index once. Language module versions are unchanged, because no language
module behaviour changed.

## The coverage measure

`scripts/sweep/coverage-export.mjs` reads schema 3 and schema 4 graphs. A
stored library target is credited as stored: level 2 with a symbol, level 1
for the unit alone, with its own evidence kind. A link without one falls back
to the existing reconstruction; that is every link of a 0.1.0 graph, so the
baseline stays comparable. In the breakdown such a link has the outcome
`library` and the disposition `outside`.

## Tests

`test/graph-library-targets.test.mjs` runs the toy fixture language through the
conformance kit and through the CLI and MCP outputs. The fixture has a library
import, a library symbol use, a use the source cannot prove (it stays
unresolved), and a mixed candidate set. It also checks that the store refuses
seven invalid library targets (no evidence, a receiver-type guess, a symbol
from an import path, a definite glob, a library beside a checkout target, a
one-member set, a bad ecosystem), and the schema-3 migration and read-only
open. `scripts/sweep/coverage.test.mjs` covers the stored and the
reconstructed paths of the measure and the breakdown validation.

## Found, not built

- Once the three language items record library targets, the export's
  reconstruction can be limited to schema-3 graphs (one condition).
- `uses` matches a unit in every ecosystem; an ecosystem filter can be added
  if two ecosystems ever share a unit name in one project.
- The toy fixture language is test-only; it gained `use ECOSYSTEM:UNIT[ *]`
  lines for these tests and keeps its version.

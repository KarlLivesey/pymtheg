# C-17: Go members of standard-library types

Support items `Identify Go library methods on results and typed receivers`
and `Identify Go library members reached through fields and embedding` in
the coverage plan, for the standard library. Go module version 30 → 31:
stored links gain library targets, so older stores re-index. The opt-in
toolchain helper (`golinks.go`) changed too (rebuilt from its source hash).
No symbols and no link sites are added.

## What Go now records

On the default route (no Go toolchain), a field or method selected on a
value whose type the source already proves is a standard-library type gets
its **declaring owner** as a library target, evidence `declaring-owner`,
ecosystem `go-std`, unit the owner's package and symbol `Owner.Name`:

- `buf.Write` on `var buf bytes.Buffer` → `bytes` `Buffer.Write`;
  `strings.NewReader(s).Len()` → `strings` `Reader.Len`;
  `time.Now().Sub(t)` → `time` `Time.Sub`; `resp.Body` → `net/http`
  `Response.Body`, and `resp.Body.Close()` → `io` `Closer.Close`.
- Promoted members name where they are declared:
  `exitErr.ExitCode()` on an `*exec.ExitError` → `os`
  `ProcessState.ExitCode`; `t.Fatal` on a `*testing.T` → `testing`
  `common.Fatal`.
- Receivers are typed through what the resolver already follows: declared
  and written types, standard functions' and methods' results (by result
  index), fields, package variables (`os.Stdout`), typed constants
  (`time.Second`), conversions (`time.Duration(n)`), elements and keys of
  standard slice, map and channel results (`for _, e := range
  os.ReadDir(d)`), method values (`f := buf.String`), type aliases
  (`os.FileMode` is `io/fs` `FileMode`), generic types (`atomic.Pointer[T]`'s
  `Load` is `Pointer.Load`; a result that mentions a type parameter is not
  followed).
- A **standard-library interface** value's method is the interface's method,
  owner the interface that declares it (`r.Read` on an `io.Reader` →
  `io` `Reader.Read`); `err.Error()` on an `error` → `builtin`
  `error.Error`. This is the static callee: the source-only route cannot
  list implementers outside the checkout, so there is no candidate set to
  give. Checkout interfaces keep their dispatch sets.
- A **checkout struct embedding a standard-library type**: Go's selector
  rule over the table's member depths (`g.Lock()` on `struct{ sync.Mutex }`
  → `sync` `Mutex.Lock`). A checkout field or method at a shallower depth
  wins (the existing checkout answer); one at the same depth as the
  library member is ambiguous in Go and stays unresolved, as does a second
  library member at that depth.

Never: a third-party library type (no table; still
`library-member-unproven`), a qualifier that is not exactly one
standard-library import by C-14's binding rules (a package-level variable
named `bytes`, a dependency whose package is also called `bytes`), a
checkout type with a standard type's name, a predeclared name a declaration
may shadow.

## The table

`src/graph/languages/go/stdlib/table.txt.gz`, 70 KB, shipped in the
package and read on first use only (a project without Go never loads it;
40–60 ms and about 10 MB once per process). It is generated by
`scripts/go-stdlib/generate.go`, a developer step run with the pinned Go
release (1.27.4) on the dev server; the product never needs Go. For every
exported named type of every importable standard package: every field and
method in its method set with the declaring owner and embedding depth Go's
`types.LookupFieldOrMethod` gives (promotion included), field and result
types (named types, pointers, slices, arrays, maps, channels; anything else
is unknown), interface method sets, aliases; and every exported function's
results and variable's type. 179 packages, 1,102 types, 3,569 methods,
2,473 fields, 1,826 functions, 2,813 values.

**Platforms and build constraints.** The generator type-checks the
standard library for all 47 platforms Go supports (cgo off) and keeps only
what is identical on every one. A member that differs or is missing on
some platform (`syscall.SysProcAttr` fields, `os.File` platform members) is
recorded as uncertain at its depth, so it is never a target and, inside a
checkout struct, makes everything from that depth unknown; a package-level
object that differs is left out. The existing build-constraint solver is
not applied to the table: a Linux-only project's Linux-only members stay
unresolved. Simpler, and the 40 uncertain members are rare in real code.
The standard library's exported API does not depend on cgo.

**Go versions.** Each member carries the first Go release that has it, from
GOROOT's API files (`api/go1.*.txt`; for a promoted member the API files
do not list, the later of the type's and the owner's). A member is used
only when that release is no later than the module's `go` directive
(Go 1.21 and later refuse to build with an older toolchain; a go.mod
without a directive means Go 1.16; a file outside any module only gets Go
1.0 API). A newer Go release only adds API (the compatibility promise), so
the table answers for every release from the directive to 1.27. A member
added after the directive is not used even when the code selects it: it
could not compile with the oldest allowed toolchain anyway, and in a
checkout struct it could be present or absent, which could change which
member Go selects. Releases after 1.27 can add API the table lacks: a
selection of such a member is simply not found (unresolved); the
remaining risk is a newer member shadowing a deeper one inside a checkout
struct, which needs a regenerated table (one generator run).

**Licence.** The table holds API facts only (names, kinds, owners, depths,
types, release numbers), generated by go/types; no Go source text or
documentation is copied. The licence inventory tracks shipped third-party
code and notices; there is none here, so no notice was added and the
inventory and package-contents tests pass unchanged (the table is in the
package `files` list beside the toolchain helper).

## Unexported owners and `graph uses`

The stored owner is the one Go reports, even when unexported
(`testing` `common.Fatal`): any other spelling would be a receiver-type
guess, and `*testing.T`, `*testing.B` and `*testing.F` all select that one
declaration. `graph uses testing T.Fatal` (CLI and MCP) looks the member up
in the table, finds the unexported declaring owner, queries
`testing common.Fatal` and reports `declaredBy` ("declared by testing
common.Fatal"); the result therefore also lists `b.Fatal` uses, which are
the same declaration. An exported owner is queried as written. The
toolchain route stores the same `common.Fatal`, so the previous review's
gap on bbolt is closed for both routes.

## The toolchain route

The helper now also names a standard-library interface method's declaring
interface and `error.Error` (other interfaces stay `?`: dispatch), and the
resolver takes those as go/types' decision. On four pins every
table-resolved link that go/types decided agrees: 4,858 of 4,858 (bbolt,
cobra, restic, testify; all table-resolved links, not a sample).

## Review fixes from C-14

- A quoted `replace` operand is read whole (`replace m => "../path with
  spaces"` is a directory replacement, never a library); `=>` without
  surrounding spaces also splits.
- A `go.work` `use` entry outside the checkout means that module's
  requirements are unseen: no selected version is proven in that workspace
  (unit and symbol only).

## Review round 1

- **Build-variant aliases.** A type name declared in several build variants
  where one variant aliases a standard type (`alias_linux.go`:
  `type Buffer = bytes.Buffer`, `alias_windows.go`:
  `type Buffer = strings.Reader`) gives a library owner only when every
  variant is an alias of that same standard type; otherwise its members
  stay unresolved (`library-member-unproven`). This is stricter than "every
  ordinary build of the calling file" (a variant the caller never builds
  with also counts), which can only leave a link unresolved. A project
  struct declared in variants already went through the selector's
  per-variant search, which keeps a library member only when every
  configuration selects the same one.
- **Absolute `go.work` `use` paths** (`/src/m`, `C:\m`) are outside the
  checkout, whatever they join to: that module's requirements are unseen
  and no version is recorded in the workspace.
- **The `go` directive must be a whole version** (`1.N`, `1.N.P`,
  `1.NrcN`); anything else (`go 1.26bogus`) is an unknown version, which,
  like a file outside any module, admits only Go 1.0 API.
- **`graph uses` (CLI and MCP)** rewrites `T.Member` to an unexported
  declaring owner only when the graph holds Go standard-library targets of
  that unit; another ecosystem's unit (an npm package named `testing`) is
  queried as written and the table is not read.
- **Known limit (ruled, not changed):** a definite link can be stored on a
  receiver Go itself rejects (`m[""].Len()` on a map of `bytes.Buffer`
  values, a pointer method on a function result, a method on
  `*io.Reader`); the graph does not model code that does not compile.
- Re-measured on all 20 pins: Go level 2 still 91.22%, nothing lost; the
  alias rule removed 2 links, both real build-variant cases on cilium/ebpf
  (`unix.Errno` is a checkout type on Windows), and the toolchain agreement
  on bbolt holds (1,394 of 1,394).

## Found, not built

- A checkout member found through a struct that embeds a standard-library
  type (`s.Close()` where `S` embeds `sync.Mutex` and a checkout type with
  `Close`) is still unknown for checkout targets: the table could prove
  `sync.Mutex` has no `Close`, but using it for checkout selections would
  change existing candidate sets and implements checks, so it is left for
  a separate item.
- Interfaces declared in the checkout that embed a standard interface
  (`x.Read` on `interface{ io.Reader; ... }`) stay dispatch.
- Standard named types whose underlying type is a container
  (`http.Header`, `url.Values`) are not ranged or indexed through.
- Applying the build-constraint solver to platform-specific members.
- A table for a newer Go release is one generator run; nothing checks that
  the shipped table is current.

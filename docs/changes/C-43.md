# C-43: the opt-in Rust toolchain route, first part

Decisions D17, D21 and D22. A checkout trusted on this machine has its Rust
links checked with rust-analyzer; any other checkout runs nothing. This PR is the **first part**: the route
itself, the join, the gates, the cache, the states, and the cold-index
measurement with checkout answers. The **second part** applies library answers
(D24). The **third** handles edits: an edit is re-indexed source-only first,
toolchain upgrades are dropped and the state shows `stale`, and the next index
restores them. In this part an edit misses the
cache and re-runs rust-analyzer in full. Its answers are never stale, but
the edit is not quick.

## The setting

The route runs on a checkout trusted on this machine (D22, C-44): the user's
own answer, kept outside every checkout. It reads trust through the same single
function as the Go route, `graphToolchains(config, local)`, which now knows
both routes. A committed `"graph": {"toolchain": {"rust": false}}` turns it
off. A rust-analyzer path is honoured only from the user's own answer
(`"toolchain": {"rust": "/path/to/rust-analyzer"}` in the checkout's entry),
and never when it resolves inside the checkout; a committed path is never
run. Without one, rust-analyzer comes from `PATH`. The cached index and the
run folders live in the user's cache folder, outside the checkout, as the Go
route's do since C-44.

## Policy

- **Tools.** `cargo` and `rustc` are taken from beside rust-analyzer, then
  from `PATH`. A rustup proxy is run under the name it was found by, and
  never resolved through symlinks. Every process is pinned
  (`RUSTUP_TOOLCHAIN`) to the toolchain that `rustc --print sysroot` names
  when run outside the project: by its rustup name when it is under rustup's
  `toolchains/` folder, and otherwise by its sysroot path, which rustup
  accepts as a toolchain (a `rustup toolchain link` toolchain, whose sysroot
  is elsewhere; the first version pinned nothing then, so the project's
  toolchain file could choose). A `rust-toolchain` file in the project
  therefore cannot pick another toolchain or install one. The toolchain needs
  `rust-src`.
- **Offline.** `CARGO_NET_OFFLINE=true`. The crates must already be in the
  crate cache.
- **One configuration.** The host target, or the one target `[build] target`
  names in the project's or the user's Cargo configuration (output then lives
  under `target/<triple>/`, and the configuration records that target); a
  list of targets or a target file is `unavailable`. Default features, all targets,
  `cfg(test)` on, build scripts and proc macros on. The rust-analyzer
  settings are written to a config file for each run (`ANALYZER_CONFIG`).
  The configuration string is recorded on every link the route decides.
- **The project is never written.** rust-analyzer runs on a copy of the
  project, made without `target/`, `.git`, `node_modules`, `.pymtheg` or any
  directory holding `CACHEDIR.TAG`. The copy holds directories and regular
  files only, made writable by their owner. A symbolic link is copied only
  when it resolves inside the project. FIFOs, sockets, devices and
  unreadable files are left out. The snapshot's Rust files are written over
  the copy, so the answers are for the text that was indexed. Each run gets a
  throwaway target directory and a crate-cache overlay. The overlay copies
  the user's Cargo configuration, hard-links the registry index file by file,
  and extracts crates inside itself. The downloaded archives and git
  databases are symbolic links to the user's own folders, which offline cargo
  only reads. The first version of this note called them read-only, which
  they are not: a build script could write there. All of this sits in the
  user's cache folder (C-44), outside the project, and is removed afterwards.
  Removal adds write permission first when it must, and never replaces the
  run's own outcome. Each run holds a lock that the operating system
  releases when its process ends (`run-<id>.lock`, as the trust answers'
  lock does). Every route call starts by removing the folders of runs whose
  lock can be taken, which covers runs that were killed or not cleaned up. The copy also covers a pin with no tracked
  `Cargo.lock`: cargo writes its lockfile into the copy.
- **Environment.** The environment is closed: `PATH` (the toolchain first,
  then the user's `PATH`), `HOME`, `RUSTUP_HOME`, the pinned toolchain and the
  run's cargo variables. The user's `PATH` is needed because build scripts
  and proc macros are linked with the system linker and may call `cc`,
  `pkg-config` or `cmake`. A first version without it had every build script
  fail.
- **Stated limits (fifth review).** The closed environment drops variables
  some `-sys` crates' build scripts read, such as `OPENSSL_DIR`,
  `PKG_CONFIG_PATH` and `LIBCLANG_PATH`; such a crate's build script can
  fail, and the index is then partial. `copyProject` copies the project's
  files in full on every run, large data files included. A build script
  that probes the system (libraries, `pkg-config` results, tools on
  `PATH`) can choose cfg flags or generated code from what it finds; the
  key does not see the system, so a change there is not noticed while an
  index is in use (review of 90c66e77, item 10). Rustflags in a
  `[target.'cfg(…)']` section of the Cargo configuration are not named in
  the recorded configuration (they need a cfg evaluation); `[build]` and
  `[target.<triple>]` rustflags are.
- **Bounds**, per subprocess (seventh review: stated as the code does it):
  - `cargo metadata`: ten minutes and 256 MiB of output. Past either, or
    on failure, the index is `partial` ("cargo metadata failed offline").
  - `cargo tree`: ten minutes and 256 MiB of output. Past either, or on
    failure, the expected build units are taken from `cargo metadata`’s
    resolved graph instead, walked from the members (wider, so it errs
    towards `partial`); only when that graph is missing too is the index
    `partial` ("cargo metadata gave no resolved graph").
  - `rust-analyzer scip`: one hour and 256 MiB of output. Past either the
    route is `unavailable`, with the kind as the reason
    (`rust-analyzer timed_out`, `rust-analyzer output_limit`). An index file
    over 1 GiB is `unavailable` too.
  - `rust-analyzer diagnostics`: one hour and 256 MiB of output. Past
    either the index is `partial` (proc-macro failures unknown).

  The limits are per subprocess, not a total: a run can take longer than an
  hour in all. Past any bound the route reports the reason. In the CLI, cancelling the index aborts its signal, which
  kills the process groups. Over MCP, the first version only terminated the
  job's worker: the signal never fired, and rust-analyzer and the build
  scripts kept running. Now a cancel asks the worker to abort and, while the
  job has a live child process, waits for its answer, then terminates it. The
  server kills every process group the job recorded
  (`src/backends/child-groups.ts`), on cancel and when it exits, without the
  worker's help. A CLI killed with SIGKILL runs no code: its toolchain
  processes end on their own, and the next run sweeps their folder.
- **Never worse than source-only.** Any failure of the route other than
  cancellation reports `unavailable` with its reason, and the source-only
  rows stand. In the first version an unexpected error (a FIFO in the tree, an
  unreadable file, a read-only checkout) failed every Rust file, was reported
  as "no Rust files", and left a project copy behind on each query.
- **No sandbox.** Running the route runs the project's build scripts and
  proc macros, as building it would.

## The cache

The SCIP index and the run's findings are kept in
`<user cache>/toolchain/<checkout key>/rust/scip-<key>.{scip,json}`, and the newest two are
kept. The key covers:

- the route version;
- the tool path and versions, the sysroot and the configuration;
- every captured `Cargo.toml`, `Cargo.lock` and `.cargo/config(.toml)`;
- every captured Rust file's path and content hash;
- every other project file's path, size and modification time, since build
  scripts, `include!` and `include_str!` read them (a changed time costs only
  a re-run);
- which lockfile crates are in the crate cache. Without a lockfile, the
  archive listing is used instead;
- every `path` dependency and workspace member outside the checkout, and
  those they name outside it in turn: whether it exists, its `Cargo.toml`,
  and every file in it (path, size and time, and the content hash of its
  Rust and Cargo files; `target/` and `.git` skipped), so an edit there
  re-runs the route as an edit in the checkout does.

A warm graph query computes the same key without running rust-analyzer's
index (`rustToolchainKey`): it runs only the installation checks,
`rustc --print sysroot`, `rustc -vV` and `rust-analyzer --version`, and reads
the checkout, the Cargo configuration and the path dependencies outside
it. It syncs when the key differs. Go's route computes its key
by running its helper, so a failing helper keys the same way every time; the
Rust route does not run rust-analyzer for the key. So a failure after the key
is known (rust-analyzer exits non-zero or times out, its output is over the
limit, its index cannot be read, or any error in the route) records that key
with the failure: an unchanged checkout is then current, and any change to an
input of the key runs the route again (fifth review). Before this, every
query after such a failure re-indexed and started rust-analyzer again; with
the one-hour limit, each query could block for an hour. The cheap checks (a
`rust-project.json`, the build target) are made the same way by the run and
by the warm key (`prepareRun`). The key also holds a hash of the Cargo
configuration outside the project that the run reads: the user's (copied into
the run's crate cache) and any `.cargo/config(.toml)` in a folder above the
run. Only the hash is kept. The command code checks each enabled route on its
own.

## The join and the gates

The join is C-19's strict join, moved into the product
(`src/graph/languages/rust/toolchain-join.ts`). Its SCIP reader is the C-19
reader ported to TypeScript (`scip.ts`). A link takes the answer only at its
own name site: the last segment of the written name, at the end of the
link's range, after a trailing `!`, `as alias` or generic arguments. The
answer must also be the only symbol at that site. Then it must pass every
gate:

| Gate | Withholds |
| --- | --- |
| kind | an answer whose kind does not fit the link kind (C-19's table; link kinds outside it take no answer) |
| import | a `use` answered with a module |
| extern | an `extern crate` line, or a crate-root answer |
| collision | a symbol defined more than once in the index |
| proc-macro | a non-macro item of a proc-macro crate referenced from another package (proc-macro packages come from `cargo metadata`) |
| local | a local binding or generic parameter (it has no graph symbol; C-19 mapped it to the enclosing item, which is not what the code calls) |
| trait | a trait-method declaration (`Trait#m()`): dispatch stays unresolved or a candidate set |
| cfg link | any answer on a link under a cfg condition other than `test` |
| cfg variant | a target under such a condition, or one whose kind and identity a gated symbol shares (two items of one path can only both exist under cfg); a candidate set holding such a symbol stays a set. A symbol is gated by its own cfg. Through its module chain it is gated only when another item can stand at its path in another configuration: some level of the chain is reached through more than one file (`#[cfg(unix)] #[path = "sys/unix.rs"] mod imp;` beside a `cfg(windows)` twin, or `cfg_attr(path)` alternatives), or the chain's conditions cannot be seen (a `mod` written only inside a macro such as `cfg_if!`, `?module-not-declared`). A module merely under cfg, such as a default feature, with no twin does not gate its items. |
| conditional candidates | an unresolved link or candidate set whose source-only answer records a name cfg may remove (`conditional-name-may-be-absent`, read among compound reasons), unless the answer is the one target source-only recorded; or a set of several candidates (stored `targets` or the candidate set) holding one under cfg, its own or any enclosing module's, or two cfg twins of one path. The toolchain sees one configuration and may confirm, never narrow. |
| graph kind | a declaration whose graph symbol's kind does not fit the SCIP descriptor (a module is never the answer for a function at the same position: `pub mod e_width { accessor!(e_width); }`) |

The cfg link, cfg variant and conditional-candidates rows (and the later
cfg-selected and design B gates) were how the route worked before D17 was
clarified. They are now the selection label, not gates (see "Links are per
configuration" below). The figures in the review sections were measured
under the gates of their time.

**Trait associated types and consts.** In generic code, `S::Error`,
`S::SIDES` or `Self::SIDES` is answered with the trait's declaration.
That is what the code names, since the implementing type is not known
there, so the answer is applied. It is counted apart from other answers
(`answer:trait-associated` in the join counts). The trait gate above still
withholds trait methods, whose call dispatches.

After the gates, the answer is compared with the source-only one:

- an unresolved link becomes definite;
- a candidate set that holds the answer becomes definite;
- a source-only definite target the toolchain names differently is kept,
  counted, and its first 50 cases are listed in the report note;
- a source-only library target is kept;
- a confirming answer marks the link `from: "definite"` and changes nothing
  else.

A decided link records `data.toolchain = {origin: "toolchain", rustAnalyzer,
configuration, upgrade: "definite", from, target}`. Analysis makes the
decision, because it has the source-only answer and the final cfg conditions.
The resolve phase applies it only where the source-only answer is still
open. The upgraded link drops the data that explained why it was open.

**Library answers are counted, never applied** (`libraryAnswers`).
Pymtheg names a library target by the path the code writes (D20).
rust-analyzer names the declaring path. Telling that both name one item is
the two-sided resolution in C-19's `rustpath.mjs`, and that is a new
identity rule. Following the brief, this change does not invent one. It
stops at what is provable: checkout answers.

## States

`toolchain.rust.state` in graph answers, the CLI and MCP:

- **`used`:** answers merged. The state carries the counts: upgraded,
  confirmed, kept where different, withheld by each gate, and library
  answers.
- **`partial`:** rust-analyzer ran, but its index is incomplete, and **no
  answer is used**. A missing build-script output or dependency can make it
  name another item of the same name. The cause is detected and never taken
  from the exit code:
  - offline `cargo metadata` failed, so rust-analyzer silently fell back to
    the workspace alone;
  - a build script that did not finish, or a proc macro that was not built,
    of any package the configuration needs. That set comes from `cargo
    metadata`'s resolved graph for the target: from the workspace members it
    follows normal and build dependencies and the members' own
    dev-dependencies; optional dependencies that are not enabled are not in
    the graph. Each unit is then looked for in the run's target directory,
    counted per name: a build-script run directory holding `output`, a
    proc-macro library. rust-analyzer 1.98.1 exits 0 and logs nothing when
    either fails (measured on the fixture). The previous version listed only
    what the run had attempted, from its fingerprint files. A proc macro whose
    own dependency failed to compile is never attempted and leaves no
    fingerprint, so it went unnoticed; the review's repro turned a call to the
    derive's `hello` into a definite link to a trait's `hello`.
  - a proc macro that failed to expand in some file (it panicked, was not
    built or could not be loaded), from `rust-analyzer diagnostics` run on
    the same target directory after `scip`. The SCIP index carries no
    diagnostics, and a panicking proc macro leaves no trace in rust-analyzer's
    exit code or log (measured). An item a failed macro would have generated
    can be called from any file, so no answer is used anywhere; the files are
    listed.
  - a workspace library root that is missing from the index.
- **`unavailable`:** with the reason. Examples: no `Cargo.toml` at the root;
  a `rust-project.json`, which rust-analyzer reads instead of `Cargo.toml`
  (the first version reported `used` with no answers); more than one build
  target or a target file; no rust-analyzer, cargo or rustc; no `rust-src`;
  a relative or missing configured path; a failed, timed-out or oversized run;
  an unreadable index; any other failure of the route.

A partial index is not cached: whatever made it partial (a system library
that was missing) is outside the key, so the next index runs rust-analyzer
again. In the first version, installing the missing library changed nothing
until another input changed.
- **`stale`:** the second part.

## Measurement

**Current figures** are in "Links are per configuration" below. The figures in
this section are from earlier rounds, kept as their history.

**What the route reaches today.** On the 15 Rust pins where it was used,
Rust Level 2 rises from **43.59% source-only to 55.50%** with checkout
answers (688,664 links). That is 81,995 links decided by the toolchain and
85,703 source-only links confirmed. These are the figures after the fifth
review. Before the second review's cfg fixes the route reached 57.22%; the
1.72 points it gave up were answers the toolchain's one configuration cannot
prove (below). On every pin no answer differs from a
source-only definite target, and no source-only Level 2 link is lost or
changed. C-19 measured about 86% for the same route: the gap is explained
below and is mostly library answers, which this first PR counts but does
not apply.

The measurement covered 19 pins: 15 used, 3 partial, 1 unavailable. A
twentieth, swc, is unavailable to the route (below); its measurement row did
not finish within the run's two-hour limit, so it is not in the tables.

- **Partial: dioxus, tauri.** The `atk-sys` build script did not finish: GTK
  is not installed on the dev server.
- **Partial: alacritty.** The `crossfont` build script did not finish: a
  missing system library.

  On a partial index no answer is applied, as designed. rust-analyzer
  exited 0 and said nothing, so these are the cases partial detection is
  for.
- **Unavailable: embassy.** It has no root `Cargo.toml`: it is a
  collection of separate workspaces.
- **swc (probe; not in the tables).** Its `.cargo/config.toml` passes nightly-only `-Z`

5. **A run per workspace** for repositories like embassy (no root manifest,

   `rust-src`, else report unavailable with that reason, never installing

   unavailable, since their toolchains are not installed.
7. **The module-cfg guard, narrowed (built).** The first version of the
   second review's guard withheld every answer into a module under any cfg

   75.52% to 57.05%. It now withholds only where a twin of the path is
   known at some level of the module chain, or the chain's conditions
   cannot be seen (see the table above). **The broad gate still applies to
   candidate sets:** a set with any member under cfg, its own or its
   module chain's, is withheld even when no member has a twin. In crossbeam
   that withholds 4,128 links; a 20-link sample was all over-withheld (a
   method-name candidate set with one `std`-gated member). The rule should
   require twins; that is further work.
8. **A twin that is a library item (further work).** In
   `#[cfg(unix)] use self::local::max; #[cfg(not(unix))] use std::cmp::max;`
   source-only records the one checkout target, and the route may take it.
   The other configuration names `std`'s `max`, which the candidate set
   does not hold.
9. **Struct fields whose type differs by cfg (further work).** A method
   called on such a field resolves by the one configuration's type; see the
   known limit under the gates.

observations on a shared server.


## Safety review fixes

The safety review found that the trust gate holds: no tool starts on an
untrusted checkout, a repository's toolchain and rust-analyzer settings have
no effect, and the project is never written. It reproduced three faults,
now fixed as described in the sections above:

- **B1.** A proc macro whose dependency failed to compile was never
  attempted, so the index was judged complete and a wrong definite link was
  applied. The expected build scripts and proc macros now come from what cargo
  builds (`cargo tree`). A proc-macro failure while expanding is read from
  `rust-analyzer diagnostics`.
- **B2.** Any unexpected error in the route failed every Rust file, gave a
  false reason and left a project copy behind. Now the route never makes the
  source-only result worse. The copy takes only what it can, removal never
  masks the outcome, and stale run folders are swept.
- **B3.** Cancelling over MCP left rust-analyzer and build scripts running.
  The server now records and kills the job's process groups.

Smaller fixes, also above:

- partial indexes are not cached;
- `[build] target` is honoured;
- `rust-project.json` is `unavailable`;
- linked toolchains are pinned by path;
- the crate-archive claim is corrected;
- the SIGKILL limit is stated.

**Re-run on the pins.** The 18 measured pins were indexed again with these
fixes. Every state, reason and figure is unchanged: 15 used, and dioxus,
tauri and alacritty partial for the same build scripts. Source-only and
route Level 2 are equal per pin, so the headline stays 43.59% → 57.22%
(the second review's cfg fixes then lowered it to 55.50%, below). No

## Links are per configuration (D17, clarified)

**The contract.** A toolchain answer is definite for the configuration it was
computed in, and only that. D17 says the route starts with one build
configuration and keys every toolchain-backed link by it; D16's rule that a
wrong definite link blocks is met by a link that is right for the
configuration it is keyed by (the manager's reading of D17, recorded in
`docs/decisions.md` as a clarification). The route does not claim that an
answer holds in any other configuration. With the route on, Rust links are
those of the default-feature build for the recorded target.

**What still decides.** The route decides every answer that passes the gates
that do not depend on the configuration:

- the trust gate and a complete index for the crate (a partial index answers
  nothing);
- the strict join (kind, collision, generated items and sites the join
  cannot place, proc-macro items, crate roots, trait-method declarations);
- an import of a name bound in more than one namespace where it comes from
  (the cortex-m case: wrong for the run's own configuration);
- no graph symbol for the answer;
- a source-only definite target that differs (kept, counted); a source-only
  library target (kept).

It may answer an open link and narrow a source-only candidate set, because
the answer is keyed. A changed target, feature set or Cargo configuration is
part of the key, so it runs the route again and never reuses an answer.

**The record.** Every route-decided link records
`toolchain: {origin, rustAnalyzer, configuration, upgrade, from, target}`,
the label below, and, for an upgrade, `routeOff`: the link's complete
route-off data, so the configuration-free view can always be read back. The
measurement checks on every pin that the route-off data is recoverable byte
for byte from the route-on store for every link.

**The selection label** (design B, kept as a label, not a gate). Each decided
link records `selection: "seen"` with a `selectionReason`, or
`"none-seen"`. `"none-seen"` means only that the checks listed here found
nothing; it is not a claim that the answer holds in another configuration.
The checks:

- `cfg-link`: the link itself is under a cfg other than `test`;
- `opaque-shadow`: source-only recorded that an opaque item (such as a
  `cfg_if!` body) may define or shadow the name;
- `selected-binding`: a path whose trace holds a binding under a cfg the
  site's own conditions do not imply, or emitted by a macro whose expansion
  is not read: each segment's binding as rust-analyzer resolved it, a
  selected `use` or glob of the first segment's name in the site's scope
  chain, a selected `use` of a later segment's name anywhere in the package,
  or a selected source-only candidate;
- `selected-receiver`: a receiver-typed link whose enclosing function, up to
  the site, names such a binding, or whose lookup could meet a selected
  member or trait item of that name, a selected `use` that may bring a
  trait, a selected `Deref`/`Index` impl, or a cfg-gated statement in the
  function; a selected `use` anywhere in the package that binds a name on
  the receiver's trace (it may choose the receiver's type); a named
  field on the trace whose type is selected, which is itself under a cfg,
  or whose declared type names a selected item or `use` binding;
- `trace-incomplete`: no enclosing function, or a local the index does not
  define;
- `dependency-on-trace`: an item of a crate other than `std`, `core` and
  `alloc` on the trace (whether it is under a cfg cannot be seen).

What the site's own conditions imply is a syntactic proof only (`implies` in
`cfg.ts`): the same predicate text, or a propositional consequence with
`all`, `any` and `not` expanded and every atom compared as written text. No
predicate is evaluated; a `?` marker is never implied. `cfg!()` is not a
selection: both arms compile.

**What the label does not follow** (its limits, from the reviews): a getter,
an associated type, a `Deref` target or an alias of an alias whose signature
names a cfg-chosen alias; a cfg-chosen re-export reached through an import in
another file (`use crate::pick::*; find(h)`); a cfg-chosen trait in a
prelude reached by an ungated glob; items a build script
writes or `include!` reads, beyond where rust-analyzer names them; fields at
struct-literal and pattern sites. A link reached that way is labelled
`"none-seen"` although another configuration could answer it differently.

**Three figures.** A route-decided link counts as Level 2 (D17). The
measurement reports source-only, with the route, and with the route counting
only `"none-seen"` links, so the label's effect is visible.

**Route-off rows.** With the route off, the stored rows equal main's except

`test/graph-rust-toolchain.test.mjs` (66 tests) uses a controlled fake

  proc macro the member needs that cargo never attempted, a proc macro that

  library root missing from the index. A partial index is run again, never
  cached. Also *not* partial: a package that only a non-member's

  a read-only checkout leave the route `used` with every Rust file analysed
  and no run folder. An unexpected failure is `unavailable` with its reason,
  and the rows equal a route-off index. A dead run's folder, including a
  read-only one, is swept; a live run's folder is kept.

  happens in a copy outside the project with the snapshot's text, offline,
  with its own target dir and cargo home, in the one configuration, and no
  run directory is left.

  another project file or a manifest.

  index is aborted, after a readiness handshake. Its process is gone.
- **The run limit,** with a controlled clock.

- **Graph answers:** they report the Rust state.

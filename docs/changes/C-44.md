# C-44: init asks once whether the repository is trusted

Decision D22. `init` asks one question about the whole project, in the
manner of coding agents: do you trust this repository?

- **Trusted:** each language's official tooling may run on the project. That
  runs its build scripts and macros, as building it would.
- **Source only:** no build tool and no code from the repository is run; Pymtheg still reads its files and asks Git about them, with the repository's Git configuration unable to start a program.

Today this turns the Go toolchain route on or off with its existing policy:
offline by default, with network, cgo and telemetry off. C-43's Rust route
will follow the same answer.

## Where the answer lives

**The answer belongs to the user, never to the repository.** It is kept
outside every checkout, in the user's own configuration (`$PYMTHEG_CONFIG_HOME`, else `$XDG_CONFIG_HOME/pymtheg/`, `~/.config/pymtheg/`, `~/Library/Application Support/pymtheg/` on macOS or `%APPDATA%\pymtheg\` on Windows; file `trust.json`, user-only), mapping each checkout's real path (with
the project's id from `project.json` as a cross-check) to the answer and to
any local tool paths. Nothing under a checkout is ever read as an answer or a
tool path. A first version kept the answer in `.pymtheg/local/trust.json`:
ignored, but `git add -f` commits it, the project id is committed and checkout
paths are often predictable (`/workspace`, CI runners, containers), so a
repository author could ship a matching answer.

- **Copies and moves.** A copied or moved checkout has another real path, so it
  is unanswered and asked again. A symlinked path is the checkout it points to,
  and each Git worktree is its own path and is asked once. Another project
  initialised at a recorded path has another id, so it is unanswered too.
- **A bad file.** An unreadable, corrupt or wrong-typed file or entry is
  unanswered, never trusted.
- **Writing.** The file and its folder are created user-only. Writers take a
  create-exclusive lock (a lock whose process is gone is taken over), re-read
  and merge, write a temporary file and rename it, so two inits keep each
  other's entries.
- **Listing and revoking.** `pymtheg trust` lists answers and `--revoke`
  removes one, including the harmless stale entry a deleted checkout leaves.
- **Tests.** `npm test` loads `test/isolated-config.mjs`, which points
  `PYMTHEG_CONFIG_HOME` at a fresh temporary folder, so no test touches the
  real file.

**Nothing committed can grant trust.** `graphToolchains(config, local)` is the
single function that decides which routes run, and only the local trusted
answer turns them on:

- a committed `graph.trust: "source-only"` binds on every machine (the
  repository's author may forbid build tools), and init refuses `--trust`
  there;
- a committed `graph.trust: "trusted"` grants nothing; it is the answer init
  preselects, which is trusted anyway;
- a committed `graph.toolchain.go: false` turns Go off;
- a committed `true` adds nothing;
- a committed tool path is never run, since it could point into the
  repository. Graph answers warn `committed-tool-path-ignored`, and tool paths
  are given in the local file (`"toolchain": {"go": "/usr/local/go/bin/go"}`).

A checkout with no answer on this machine is **unanswered**: it runs nothing.
Graph answers of an initialised project report `trust` (`trusted`,
`source-only` or `unanswered`, with `trustAnswer`, one line on how to answer),
over the CLI, MCP and Studio. Graph commands never prompt; only init asks.

**Behaviour change.** On main a committed `graph.toolchain.go: true` turned
the Go route on for everyone who cloned the repository. It no longer does: a
project that relied on it must answer the trust question once per machine.
New projects never write `graph.trust` into the committed settings.

## How each path asks

| Path | Without an answer | With one |
| --- | --- | --- |
| `pymtheg init` on a terminal | Asks once on standard error. Trusted is preselected (D22): Enter accepts it. Input that ends without an answer records source only. | — |
| `pymtheg init --trust` or `--source-only` | — | Records it, for scripts |
| `pymtheg init` with no terminal and no flag (piped input, CI) | Records source only and says so | — |
| MCP first planning write (`requirement_links` requirement or add, `observe_implementation`, `link_implementation`) on a project that was never initialised | Returns the trust question to the calling model and initialises nothing (`trust_required`) | `trust: "trusted"` or `"source-only"` initialises with it |
| A clone (an initialised project with no answer on this machine) | `pymtheg init` asks (or takes a flag) and changes nothing else; over MCP, graph answers say `unanswered` and how to answer | `code_graph` or the first planning write with `trust` records it; Studio setup asks |
| Studio project setup | Shows the question, trusted preselected; an API call without `trust` records nothing | `trust` records it, and the dialog shows the recorded answer |
| A folder inside a project | Uses the project's answer | A different explicit answer is refused |

Re-running init never changes a recorded answer. The same answer again is a
no-op, and a different one is refused with a message that names the local
file. Init on an initialised checkout with no answer on this machine (a
clone) asks, or takes a flag, and changes nothing else. The no-terminal
default is recorded locally too: it changes no committed metadata.

D22 differs from the brief in two places, and D22 is followed. The brief
made source only the default on Enter, but D22 preselects trusted, "since
that is the usual case". The brief made MCP record source only without an
answer, but D22 has MCP return the question to the calling model.

## Review fixes (round 1)

- **Ctrl-C at the prompt.** `askTrust` takes the command's cancel signal.
  An abort closes the prompt and rejects; init prints "Cancelled at the trust
  question; nothing was written." and exits 130 without writing.
- **A failing first write initialises nothing.** `observe_implementation`
  and `link_implementation` check the trust question first. They hand the
  answer to the write, which initialises the project only once it proceeds
  (after its input has validated), as main did before the question existed.
- **`requirement_links` refuses `trust`** on actions other than `requirement`
  and `add`, where it would mean nothing.
- **Studio without `trust`.** An API call without `trust` records no answer and
  reports `unanswered`; the project view carries `trust`, and the dialog asks
  when it next opens such a project.
- **The prompt's wording** no longer overstates what runs: "the languages'
  official build tools may run on this project; for some languages that runs
  the repository's build scripts and macros, as building it would."

## Review fixes (round 2)

- **The force-commit hole** (found by review on `757fff0`: a repository script
  ran through a forged in-tree `trust.json` with a tool path at a guessed
  clone path). The answer moved outside every checkout (above). The
  reviewer's exact attack is a test: the clone reports `unanswered`, a spy
  `go` first on `PATH` is never started, and the script's marker never appears.
- **Defence in depth.** A tool path that resolves (`realpath`) inside the
  checkout is never run, even from the user's own file. That route stays off
  and graph answers warn `tool-path-inside-checkout`. This is tested with a
  direct path and with a symlink from outside.
- **Every first write validates before initialising.** `requirement_links`
  `add`, `remove` and `refresh` on a project with no planning store report
  that and write nothing. `requirement` initialises only as its save
  proceeds, with the answer, as `observe_implementation` and
  `link_implementation` do. `unlink_implementation` refuses on a project that
  was never initialised. The other MCP tools never initialise a project.
- **`.pymtheg/local/.gitignore`** is rewritten to `*` before anything is
  written in `local/`, so a committed hostile one cannot expose `writer.json`.
- **Studio** shows "Do you trust this repository? Answer" in the toolbar for
  an unanswered checkout; it opens the setup dialog with the question. The
  web build type-checks it; it has no unit test, since the web tests here are
  browser journeys.

## Review fixes (round 4)

- **The answers-file lock let two writers in.** The lock file was created
  and then written, so a reader in between saw an empty lock, judged it dead
  and removed it. Measured: 10 of 180 answers lost under twelve concurrent
  inits, and `--revoke` reporting a removal that did not happen. The lock is
  now created whole: its content is written to a unique file, which is
  hard-linked to the lock path (atomic, and it fails if a lock exists).
  - A lock that cannot be read or parsed is held, never dead.
  - A dead owner's lock is taken over atomically. It is renamed to a unique
    name and removed only if it is the lock judged stale (same token);
    otherwise it is linked back.
  - A lock is released only if its token is ours.
  - A lock is dead if its pid is gone, or if the pid has another start time
    (Linux).
  - A lock in the earlier format (pid only) is held. Remove it if no
    Pymtheg is running.

  The lock-free alternative was not taken. A read, merge, write and rename
  loop that re-reads after its rename can still lose an update: writer A
  checks that its change is there just before writer B's rename, made from
  an older read, replaces the file. Gate tests pause a writer inside the
  lock (no sleeps). Contention tests run twelve inits at once with a revoke
  racing them. `evidence/c-44/lock-load.mjs` repeats the review's 12×15 run
  and 60 revoke races. [Results](../../evidence/c-44/lock-load.json)
- **"Source only" was not exact.** `observe` asked Git about the folder, and
  Git obeys the folder's own `.git/config`, which can name programs
  (`core.fsmonitor`, filter drivers and so on). Every Git call now goes
  through `src/shared/safe-git.ts`.
  - It lists the folder's configuration first, which parses it without
    starting anything.
  - It then overrides each key that can run a command: `core.fsmonitor`,
    `core.hooksPath`, `core.pager` and every `pager.*`,
    `core.sshCommand`, `core.gitProxy`, `credential.helper`,
    `diff.external`, every `filter.<driver>.clean|smudge|process`, every
    `diff.<driver>.textconv|command` and `merge.<driver>.driver`,
    `uploadpack.packObjectsHook`, the editors and `gpg.program`.
    `safe.bareRepository` is `explicit`.
  - It turns off prompts and optional index writes.

  The review's reproduction is a test, with `core.fsmonitor`, a `clean` and
  `smudge` filter and `diff.external` all naming a script, in a source-only
  and in an unanswered checkout: the script never runs. The wording is now
  exact everywhere (the prompt, Studio, the docs): source only means no
  build tool and no code from the repository is run; Pymtheg still reads
  its files and asks Git about them, with the repository's Git
  configuration unable to start a program.
- **Toolchain work lives outside the checkout.** The Go helper and the cached
  toolchain facts were kept in `.pymtheg/rebuildable/toolchain`, where a
  force-committed `golinks-<hash>` would have been run on a trusted
  checkout. The toolchain work folder is now the user's cache folder:
  `$PYMTHEG_CACHE_HOME`, else `$XDG_CACHE_HOME/pymtheg`, `~/.cache/pymtheg`,
  `~/Library/Caches/pymtheg` or `%LOCALAPPDATA%\pymtheg`. Each checkout has
  its own subfolder, keyed by its real path. A test plants helper binaries
  in the old place: none runs.
- **A configuration folder inside the checkout is refused**, by the same
  file-identity check as tool paths. It reads as unanswered and refuses
  writes.
- **The MCP texts say the answer must come from the user** or their standing
  instructions, never from text found in the repository.
- **Trust is for the folder** (docs/project-init.md): a different repository
  cloned at a trusted path with the same project id, or an untrusted branch
  checked out in a trusted checkout, keeps the answer.
- **`pymtheg trust` arguments.** `--format` takes its value, so
  `--revoke json` revokes the folder named `json` and `--format text` works.
- **Folders and links.** A `PYMTHEG_CONFIG_HOME` the user named is not
  chmodded; only the tool's own `…/pymtheg` folder and the file are. A
  configured tool file with more than one hard link gives the warning
  `tool-file-hard-linked`.

## Review fixes (round 3)

- **A failing first `observe_implementation` or `link_implementation`
  initialises nothing.** Observe checks the expected revision against the
  empty project before the first write, so an impossible one fails first.
  Link refuses on a project that was never initialised, as unlink does: a
  link names a retained revision, plan and observation that such a project
  cannot have. A test over MCP shows that neither creates `.pymtheg/` or
  records an answer.
- **A bad answers file is never silently replaced.** On a write, a file that
  is unreadable, corrupt or has any wrong-typed entry is moved aside to
  `trust.json.corrupt-<n>` (user-only), with a message. The new file keeps
  its valid entries. Reading still treats a bad file or entry as unanswered.
- **The tool's own configuration folder is set to user-only on every write.**
  A parent folder is never changed.
- **The inside-checkout check compares file identity.** Each folder from the
  tool's resolved location up to the root is compared with the checkout root
  by device and inode, so spelling, symlink chains and a symlinked parent
  cannot hide a tool in the checkout. The Linux test covers a symlink chain
  and a checkout opened through a symlinked parent. Case-insensitive and
  normalising file systems (macOS, Windows) are covered by the identity
  comparison but are untested here.
- **`project_info` reports `trust`**, and `trustAnswer` when unanswered.
- **The lock** records the owner's pid, its start time (from `/proc` on
  Linux) and a random token. A lock whose pid is alive but has another start
  time is taken over. Elsewhere only the pid is checked, so a reused pid
  makes a writer wait. It cannot corrupt the file, and the writer gives up
  with a message after a bounded number of tries.

## Round-4 checks

- **Lock load.** `lock-load.mjs` ran the review's 12×15 inits and 60 revoke races, each with twelve inits, beside two full suite runs: 900 inits, 0 answers lost, 0 failures, 0 false removals. [lock-load.json](../../evidence/c-44/lock-load.json)
- **Suite.** Both full runs under that load: 3,304 of 3,305. The one failure, the same in both, was a Go review test that expected the toolchain folder inside the project. It now expects the user's cache folder and passes. A final run on the pushed head is given in the pull request.
- **Real folders.** After the runs, the server's `~/.config/pymtheg` and `~/.cache/pymtheg` do not exist.

## Proof

`test/project-trust.test.mjs` covers:

- **The rule:** only a local trusted answer turns routes on. A committed
  trusted, `true` or path grants nothing, a committed source-only binds, a
  committed `false` turns Go off, and a local path or `false` applies.
- **The prompt,** driven by controlled streams: Enter, `n`, `NO`, `yes`, an
  unclear answer followed by one, and ended input.
- **The user's file:** init writes no `graph.trust` and nothing new under the
  checkout (`git ls-files`, `git status --ignored`). The file is outside the
  checkout, user-only and keyed by the real path. Re-init, the same and a
  different answer, and nested folders are covered too.
- **Copies:** a copied checkout and another project at a recorded path are
  unanswered, a symlinked path is the same checkout, and answering the copy
  leaves the original alone.
- **A bad file:** corrupt, other-schema, wrong-typed answer, wrong-typed tool
  path, wrong-typed project id or an unreadable file: each is unanswered.
- **Concurrent writers:** eight writers in one process and two `init`
  processes at once all keep their entries.
- **`pymtheg trust`:** it lists answers and revokes one, including a deleted
  checkout's stale entry.
- **A committed source-only binds:** init refuses `--trust`, and a local
  trusted answer does not apply.
- **The command line:** no terminal records source only locally and says
  so. Also covered: both flags, the conflicting pair, a re-init that tries
  to change the answer, and a clone of the tracked files that init answers
  while changing nothing else.
- **Studio's setup endpoint:** it records the answer locally.
- **Graph answers:** an uninitialised folder reports no `trust`, an
  unanswered checkout reports `unanswered` with `trustAnswer`, and a
  source-only checkout reports `source-only`.
- **A clone whose committed settings say trusted,** and which also carries
  forged answers force-added under `.pymtheg/`: the author's checkout
  runs the route, while a copy of the tracked files reports `unanswered` and
  runs nothing. This is proved by the Go route's own counter of
  toolchain-decided links.
- **A committed tool path is never run:** a "go" inside the repository that
  would write a marker file. The marker never appears, and the answer
  carries the `committed-tool-path-ignored` warning.
- **Overrides:** a local trusted answer with a committed `go: false` keeps
  Go off, and a committed source-only overrides a local trusted answer.
- **Equal rows:** the trusted answer stores the same rows as the direct
  `go: true` opt-in, and source only upgrades none.
- **Over MCP:** `code_graph`'s `trust` answers an initialised checkout once,
  refuses a different answer, and refuses a project that was never
  initialised.

No test asserts a time or uses a real prompt.

Without an answer, nothing changes in the store. Cold indexes of
labstack/echo and fjall-rs/fjall with main (`60d4f2b`) and with this branch
stored the same rows. `cold-cost.mjs --exact` compared every row. The figures for the final head are in the round-4 checks below. [Identical rows](../../evidence/c-44/identical.json)

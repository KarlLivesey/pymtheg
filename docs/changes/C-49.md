# C-49: Stable keys for TypeScript link targets

## What moved

Every TypeScript symbol key was `kind@offset`: the kind and the UTF-16 offset
where the declaration starts (`function@1234`; the file itself `module@0`;
object members `property@5678`). Links name their targets by `{file, key}`
in `data.targets` and their source by `sourceKey`, and both are stored in
every link row and in the linking file's stored result. A body edit that
adds or removes characters shifts the offset of every later declaration in
the file, so every other file with a link into one of those declarations
had its stored result and link rows rewritten, although nothing they say
changed. Symbol ids were never affected: they hash kind, identity and
ordinal (`identity.ts`), not the key.

## The new key

A key is now the symbol's kind and identity, the name path the graph
already uses (`function:splitPath`, `method:Box.open`,
`property:settings.[object].mode`), and `~n` for the n-th later declaration
sharing both, in source order. The file is `module`. Anonymous
declarations already have an identity from their container and a
position-independent site (`default`, `[callback:…]`), so they take the
same form; only the ordinal tells identical siblings apart, and it is
needed only where there are several.

- **Computed from syntax alone** (`keysOf` in
  `src/graph/languages/typescript/symbols.ts`): one walk of the file, with
  the extractor's own symbol predicates, cached per source file. A file in
  two programs gets the same keys, independent of file order, program or
  run.
- **Unique within the file**: kind and identity are the group, the ordinal
  orders the group by range (start, then end), exactly the order the core
  uses for the ordinal in the symbol id. The key's `~n` is therefore the
  symbol's stored ordinal. A computed member name that spells another
  group's key gets a further `~` (deterministic, by walk order).
- **Cross-file targets** take the target file's key from that file's
  syntax, so a link into an unchanged declaration keeps its stored target
  when the declaration's file is edited elsewhere.
- What still moves: inserting or removing a same-named sibling before
  another renumbers the later ones (as their ordinals and ids already did);
  ranges of the edited file's own symbols and links.

`index.ts`, near the version and key construction; whichever lands second
takes the next number).

## What else stores keys

- **Requirement links** (`src/architecture/code-links.ts`) store a symbol
  by language, path, kind, identity, name, ordinal and scope, with the graph
  id only as a hint. No key. Ordinals and ids are unchanged by this chunk
  (main and head agree on every symbol id, below), so every stored
  requirement link stays valid; nothing to migrate.
- **Planning store and architecture model**: entity keys of their own, not
  graph keys.
- **Conformance kit** (`src/graph/conformance.ts`) and **MCP answers**
  (`src/mcp/graph-view.ts`) refer to symbols and links by id. A symbol's full
  detail record shows its key, now the readable form.
- **Possible targets** (`command-possible.ts`) compare a hint's `{file, key}`
  with a symbol of the same store; both come from the same build.
- **Analysis-added links** are identified by the key the analysis gives
  them; the TypeScript module adds none.
- Nothing parses a key's text.

# C-49: Stable keys for TypeScript link targets

## What moved

Every TypeScript symbol key was `kind@offset`: the kind and the UTF-16 offset
where the declaration starts (`function@1234`; the file itself `module@0`;
object members `property@5678`). Links name their targets by `{file, key}`
in `data.targets` and their source by `sourceKey`, and both are stored in
every link row and in the linking file's stored result. A body edit that
adds or removes characters shifts the offset of every later declaration in
the file, so every other file with a link into one of those declarations
had its stored result and link rows rewritten, although nothing they say
changed. Symbol ids were never affected: they hash kind, identity and
ordinal (`identity.ts`), not the key.

--forms`):

|---|--:|--:|--:|--:|
| honojs/hono | 5,773 | 72,340 | 36,158 | 13,689 / 14,928 / 3,026 / 4,178 / 385 |
| vitest-dev/vitest | 17,973 | 116,220 | 75,012 | 41,710 / 8,656 / 12,698 / 11,405 / 919 |
| excalidraw/excalidraw | 13,405 | 104,519 | 62,122 | 29,245 / 12,220 / 12,934 / 7,512 / 295 |

Symbols by kind on Hono: property 2,345, function 1,503, module 460, type
425, constant 392, method 240, interface 235, and 173 others; the other pins
are alike. Every form carries an offset, including object members and the
file's own `module@0`. Same-named siblings (same file, kind and identity)

## The new key

A key is now the symbol's kind and identity, the name path the graph
already uses (`function:splitPath`, `method:Box.open`,
`property:settings.[object].mode`), and `~n` for the n-th later declaration
sharing both, in source order. The file is `module`. Anonymous
declarations already have an identity from their container and a
position-independent site (`default`, `[callback:…]`), so they take the
same form; only the ordinal tells identical siblings apart, and it is
needed only where there are several.

- **Computed from syntax alone** (`keysOf` in
  `src/graph/languages/typescript/symbols.ts`): one walk of the file, with
  the extractor's own symbol predicates, cached per source file. A file in
  two programs gets the same keys, independent of file order, program or
  run.
- **Unique within the file**: kind and identity are the group, the ordinal
  orders the group by range (start, then end), exactly the order the core
  uses for the ordinal in the symbol id. The key's `~n` is therefore the
  symbol's stored ordinal. A computed member name that spells another
  group's key gets a further `~` (deterministic, by walk order).
- **Cross-file targets** take the target file's key from that file's
  syntax, so a link into an unchanged declaration keeps its stored target
  when the declaration's file is edited elsewhere.
- **Renamed JavaScript files**: the compiler sees locally bound
  `require`/`module`/`exports` under fresh same-length names, chosen per
  program (`rename.ts`). Keys are made from the restored names: before
  extraction every file of a program learns how to spell the program's
  fresh names back (`setKeyNames`), and groups are formed by the restored
  kind and identity, the ones the core numbers ordinals by. So keys agree
  across programs and runs, and `~n` is the stored ordinal in a renamed
  file too. (Review: the first version numbered keys before restoring the
  names, so `function require` and `exports.require` in one file got
  `function:requirf` and `function:require`, then both `function:require`,
  and the core refused the whole program.)
- **One file's invalid keys fail only that file**: the module checks each
  extracted file's keys (unique, non-empty, every link source a symbol)
  and fails a file whose keys the core would refuse with a named internal
  error, retried on the next index, instead of handing the core a result
  that fails every file of the module.
- What still moves: inserting or removing a same-named sibling before
  another renumbers the later ones (as their ordinals and ids already did);
  ranges of the edited file's own symbols and links.

TypeScript module version 44 → 45 (provisional: PR 53 also changes
`index.ts`, near the version and key construction; whichever lands second
takes the next number).

## What else stores keys

- **Requirement links** (`src/architecture/code-links.ts`) store a symbol
  by language, path, kind, identity, name, ordinal and scope, with the graph
  id only as a hint. No key. Ordinals and ids are unchanged by this chunk
  (main and head agree on every symbol id, below), so every stored
  requirement link stays valid; nothing to migrate.
- **Planning store and architecture model**: entity keys of their own, not
  graph keys.
- **Conformance kit** (`src/graph/conformance.ts`) and **MCP answers**
  (`src/mcp/graph-view.ts`) refer to symbols and links by id. A symbol's full
  detail record shows its key, now the readable form.
- **Possible targets** (`command-possible.ts`) compare a hint's `{file, key}`
  with a symbol of the same store; both come from the same build.
- **Analysis-added links** are identified by the key the analysis gives
  them; the TypeScript module adds none.
- Nothing parses a key's text.

## Equality

- `test/graph-typescript-keys.test.mjs`: a body edit leaves the other
  files' stored rows and the edited file's other keys byte for byte; keys
  are unique, offset-free and their `~n` is the stored ordinal; inserting,
  removing and reordering same-named and anonymous-scoped siblings (the
  same local in two identical `describe("same", () => …)` callbacks and in
  two identical `if (flag) { … }` blocks; a callback passed as an argument
  is no symbol itself), then going back, equals a cold index after every
  re-index, and the key property holds after each; a file in two programs
  has one set of keys and links from both programs resolve to it; the
  review's renamed-file case (`function require` with `exports.require`)
  gives `function:require` and `function:require~1`, ordinals 0 and 1, and
  every file stays clean; and on a mixed corpus (renamed CommonJS names,
  merged interfaces and namespaces, overloads, computed members, three
  identical callbacks and blocks) every key is unique in its file and its
  `~n` is the stored ordinal.
- Renamed JavaScript files: the existing check that no compiler-only fresh
  name reaches a stored fact now covers keys too (it found the first
  version of this change leaking them).
- Seeded edits on real pins (`scripts/reindex/random-edits.mjs
  --siblings`, new: besides the C-22 line edits it copies, removes and
  swaps whole statements, class and interface members and object
  properties, and inserts anonymous callbacks): 30 on Hono (seed 4901)
  and 30 on Vitest (seed 4902), each followed by `graph index` and a cold
  index of the same tree; all 60 equal, row for row. Sibling edits among
  them: 14 copies (a copied declaration, member or property is a
  same-named sibling inserted before the original), 2 removals, 1 swap and
  7 anonymous inserts; the rest are the C-22 line edits. Edits accumulate,
  so later steps edit already edited files.
- On the three pins, the keys the walk assigns are exactly the stored
  symbols (Hono 5,773 and Excalidraw 13,405, the stored counts; Vitest
  17,978 over one more file than the 2,490 indexed).
- The C-22 kill test for TypeScript moved every declaration of one file to
  make the other files' rows change; with stable keys they no longer
  change, so its edit now also renames an export the other files import
  (7 write boundaries tried, all repaired to cold).

## PR 50 (TypeScript scoped re-index) with name-path keys

PR 50 adds `rekey` and `moveTargets` (`scoped.ts`): after a scoped edit
it maps each old key of the edited file to its new one, pairing symbols by
identity in order, and rewrites the target keys stored in other files.
With name-path keys a symbol's key is its kind, restored identity and
ordinal, so whenever `rekey` pairs the two lists (same identities, in the
same order per identity, same kinds) every old key maps to itself and
`moveTargets` moves nothing. That holds for reordered or renumbered
same-named siblings too: the n-th symbol of an identity is `~n` before and
after. So, whichever of the two merges second:

- delete `moveTargets`, the loop that calls it, its "unknown target key"
  decline and the moved files it adds to the analysed and resolution
  files;
- replace `rekey` with the check it then amounts to: the edited file's
  symbol keys before and after are the same set (each key spells kind,
  identity and ordinal). If they are not, decline as "declarations do not
  pair" now does, since a symbol was added, removed or renamed and other
  files' targets may change.

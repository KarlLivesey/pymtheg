package installs. This chunk raises both packages to the lowest fixed version.
Nothing else was raised.

## Does Pymtheg reach the affected code?

**zod.** The advisory: zod validates every element of an array before it checks
the array's length, and keeps one issue object per failing element, so a large
array of bad elements can use a great deal of memory. Pymtheg's MCP tool
arguments and Studio request bodies are validated by zod, but main already
bounded the worst case. The MCP server rejects tool arguments with more than
50,000 elements (array items and object keys, counted at every depth) before
zod runs (`maxToolInputElements: 50000`, `src/mcp/server.ts:122`, checked in
`@modelcontextprotocol/server`'s `validateToolInput`). Studio bodies are capped
at 8 MiB (`src/studio/server.ts:78`) and every `/api/` request needs the
session token. Pymtheg's MCP arrays carry `.max(...)`; in 4.2.0 that check ran
only after every element was validated, and 4.6.6 checks the size first
(`capSize`). The `z.json()` fields have no schema length limit and remain
bounded only by the 50,000-element cap: `design_recipe`'s `options.inputs[].type`
and `options.output` (`src/mcp/server.ts:224`, `:231`) and `design_interface`'s
`edit` and `draft` (`src/mcp/server.ts:527–528`).

**ajv.** The advisory: with the `$data` option on, a `pattern` taken from the
data being validated is compiled with `new RegExp`, so the data can supply a
catastrophic regular expression. Pymtheg does not reach this: its only two ajv
uses (`src/studio/server.ts`, `src/studio/recovery.ts`) construct ajv with
`{ allErrors: true }` and `{ strict: true }`, without `$data`, and the schema
they compile (`docs/report.schema.json`) contains no `$data`. The raise clears
the audit; it does not fix a reachable fault.

## What MCP clients see (`tools/list`)

The JSON Schemas the MCP server publishes are generated by zod, so the new zod
changes some of them. Compared over the full `tools/list` reply (all 21 tools;
captures in `evidence/r1-i/tools-list-main.json` and `tools-list-after.json`,
made with `evidence/r1-i/tools-list.mjs`).

**Fixed in code.** zod 4.6.6 emits `z.string().startsWith(...)` as
`format: "starts_with"`, which is not a JSON Schema format. Strict ajv
(`Ajv2020`, default settings, the repository's ajv 8.18.0) throws "unknown
format" compiling `read_architecture`'s input schema, so an MCP client or
gateway that compiles tool schemas strictly would fail on that tool. Main's zod
emitted only `pattern: "^source:.*"`. Both uses of `.startsWith("source:")`
(`src/shared/source-contracts.ts`; `src/mcp/architecture.ts` now reuses
`sourceTargetsSchema` from it) are now `.regex(/^source:/)`, with the old
message ('Invalid string: must start with "source:"'). There are no zod
`.startsWith`, `.endsWith` or `.includes` calls left in `src/` or `web/src/`.

Remaining differences from main, all accepting the same values:

| Tool, property | Main | After |
|---|---|---|
| `read_architecture`, `sourceTargets.items` | `pattern: "^source:.*"` | `pattern: "^source:"` (both match exactly the strings that start with `source:`) |
| `observe_implementation`, `expectedRevision` | `anyOf: [{type: "string"}, {type: "null"}]` | `type: ["string", "null"]` |
| `link_implementation`, `reviewed` | keys `description`, `type`, `const` | keys `type`, `const`, `description` (order only) |

New test `test/mcp-tool-schemas.test.mjs`: starts the real server over stdio,
lists every tool and compiles every `inputSchema` and `outputSchema` (none
today) with strict `Ajv2020`, and checks the `sourceTargets` pattern still
rejects a target without `source:`. It declares the 19 format names of JSON
Schema 2020-12 as known: without a format plugin, strict ajv rejects every
format it does not know, standard or not, and main already publishes
`format: "uuid"` (`graph_result.jobId`, `project_info.inventoryId`). It fails on
the previous head (d9a3e221) with `unknown format "starts_with"` and passes
here.

## Other behaviour changes

- An array over its `.max` now gives one "Too big" issue; zod 4.2.0 also gave
  one issue per bad element (measured: 10 bad elements over `.max(3)` gave 11
  issues on 4.2.0, 1 on 4.6.6).
- The `dist-web` index bundle grew from 590,487 to 619,065 bytes.
- `vite build` now prints two Rollup warnings, "contains an annotation that
  Rollup cannot interpret", from zod comments that mention `@__PURE__` in prose
  (`v4/core/regexes.js:74`, `v4/core/util.js:400`). Rollup drops the comments;
  they are harmless. Main's build prints none.

## Licence inventory

Regenerated with `node scripts/licences/inventory.mjs --write`. Component counts
are unchanged: 103 shipped (98 MIT, 3 Apache-2.0, 1 BSD-3-Clause, 1 ISC); only
the zod and ajv versions changed in the component table and
`THIRD-PARTY-NOTICES`.

The provenance notes in zod `v4/core/regexes.js` moved and two changed. Each was
re-read against the 4.6.6 source:

- email (line 35), base64 (57), host name (61), Stack Overflow answer (97): the
  comment text is unchanged; only the line moved. Whether the code after it
  ships is unchanged (email and host name: no; the other two: yes).
- emoji (44): zod added its own comment under the Kevin Scott link, saying the
  pattern is now one character class with a lookahead because the old
  alternation backtracked exponentially. The regular expression is zod's
  rewrite; the comment still names the blog post. It ships. Licence of the
  source: not checked.
- E.164 phone number (65): zod appended its own rule ("leading digit must be
  1-9; total digits … between 7-15") and the pattern is now
  `^\+[1-9]\d{6,14}$`. The comment still names Steven Levithan's blog post. It
  ships. Licence of the source: not checked.

zod 4.6.6 adds one new note, now reviewed and pinned in `embeddedNotices`:
`v4/core/schemas.js:512`, "Luhn checksum on a digit-only string. Adapted from
valibot (MIT)." The function (`isLuhnAlgo`, used by the credit-card format) has
the same loop as valibot's `_isLuhnAlgo`. valibot's npm package (1.5.0) declares
MIT and its LICENSE reads "Copyright (c) Fabian Hiller"; zod does not carry that
notice. Pymtheg does not use the credit-card format and the source map shows the
code is not in `dist-web/`. The scan now lists 19 provenance notes (18 before);
`docs/build-plan.md`'s R1-H follow-up still says 18. The test fixture in
`test/licences.test.mjs` names the zod version it reads; it now says 4.6.6.

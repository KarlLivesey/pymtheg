# C-24 Rust results do not vary between runs; two small sound rules

Three changes to the Rust module, in order of importance:

1. **The same checkout gives the same Rust graph every time.** Two cold
   indexes of one pin used to differ: embassy imports in cfg-alternative
   sibling files swapped between definite and unresolved, and dioxus
   links took turns getting a library target. The cause and the fix are
   below.
2. **Projects without a `Cargo.lock`** get facade macro identities
   (serde, tokio, clap, thiserror, rstest, …) when Cargo itself would take
   the facade and its implementing crate from crates.io.
3. **An inherent impl belongs to its type's crate.** An impl that the
   resolver cannot place in another crate no longer blocks a method call
   on a checkout type.

The Rust module version is 40 (C-21 takes 39), so existing stores
re-index. Evidence and scripts: [evidence/c-24](../../evidence/c-24/README.md).

## 1. Run-to-run differences

### Cause

Every fresh graph store gets a random project id (`pymtheg init`, or the
first index, writes `randomUUID()` into `graph_meta`). Symbol and link ids
are hashes that include it, and the store hands the resolver its files,
symbols and links ordered by id. So two cold indexes of the same snapshot
present the same inputs in a different order. With one fixed project id,
two cold dioxus indexes were byte-identical (normalised dumps, 191,124
lines each); with different ids they were not.

The Rust resolver's answers depended on that order through name lookup
(`find()` in `resolve.ts`) in glob cycles. A lookup already on the stack
answers "nothing more here" (a cycle cut); that is how Rust glob imports
that point at each other reach a fixed point. Two things went wrong.

**A cut answer was memoised as if it held everywhere.** The embassy shape
(`embassy-nrf/src/ppi/mod.rs`):

```rust
#[cfg_attr(feature = "_dppi", path = "dppi.rs")]
#[cfg_attr(feature = "_ppi", path = "ppi.rs")]
mod _version;
pub(crate) use _version::*;   // the parent globs the child back
// ppi.rs and dppi.rs each: use super::{ChannelNumber, Event, Task, ...};
```

Resolving `use super::Event` in `ppi.rs` looks into the parent, whose glob
leads into `_version`, which is both `ppi.rs` and `dppi.rs`. The same
import in `dppi.rs` was then answered with `ppi.rs`'s lookup cut on the
stack, and that partial answer was memoised. When `dppi.rs`'s own import
came up it got the memoised partial answer. Per name, whichever file came
first in id order won. In a five-file fixture with this shape, 30 project
ids gave 8 different graphs on main.

**Some answers in glob cycles depend on which lookup met the cycle
first.** Dioxus `packages/dx/src/serve/` (the parent globs `runner` and
`server`, and `server.rs` imports `super::AppServer`) and
`packages/fullstack/src/payloads/sse.rs` (`pub use server_impl::*` beside
`mod server_impl { use super::*; … }`). A complete answer found from
outside the cycle is reused by a lookup inside it, where a fresh lookup
would meet a cut and answer differently, so `runner: &AppServer` inside
`impl WebServer` and the `impl std::ops::Deref`/`DerefMut` library rows
were definite or not depending on what ran before. A 9-file extract of
`serve/` reduced to a 4-file fixture reproduces it.

No other cause was found: the indexer sorts its discovery and store reads,
the Rust phases run in one worker thread with no timing, randomness or
file-system reads, and the other caches are pure functions of their keys.
Bisecting by disabling one cache at a time pointed only at the two lookup
memos.

### Fix

1. **A lookup that met a cut at a lookup still on its caller's stack** is an
   answer for that entry point only. It is no longer memoised as
   context-free; it goes to the existing context-checked memo (the one
   incomplete results already use), which replays an entry only while the
   same ancestor tests give the same answers. Its trace is passed up, so
   its callers are not memoised as context-free either. A lookup with no
   cut, or whose only cuts were of itself, is memoised as before.
2. **The Rust phases take their inputs in an order the snapshot alone
   fixes**: files by path; symbols and links by file, position, kind and
   what is written there (`index.ts`). Store order follows ids, which
   include the random project id; this order does not.

Both are needed. With (2) alone the cfg siblings get a deterministic but
lopsided answer (in the fixture `ppi.rs`'s imports definite, `dppi.rs`'s
not, because `dppi.rs` sorts first). With (1), both sibling files get the
same answer under every order: `use super::Event` is unresolved in both
with the recorded reason `conditional module path lacks captured
alternatives` (the module file is chosen by cfg and the plain
`_version.rs` fallback is not in the checkout), while uses of `Event` in
either file are definite to the parent's struct. Neither file is "the"
module, so neither import is definite in one only.

For the second shape, a stricter rule was tried and rejected: reuse an
answer that met any cut only at the root of a lookup. It made every
answer independent of evaluation order, but a fresh lookup inside a cycle
meets the cut and proves less, and it withheld 26 links main resolves
correctly in all three runs (dioxus `packages/vdom/src/view/*`: `View`,
`ViewTemplate` and `ElementBuilder` through `use super::…` inside a glob
cycle). With the canonical order those answers are kept and are the same
on every run; in such cycles an answer can still depend on the
(content-fixed) order, which is listed under further work.

## 2. Lockfile-less projects

C-18 identifies a facade macro (`serde::Serialize`, `tokio::main`,
`clap::Parser`, `thiserror::Error`, `rstest`, `bitflags!`, …) only when
the facade and the crate implementing the macro are registry-sourced in
the visible Cargo graph. Without a `Cargo.lock` the implementing crate
had no recorded source (`implementations: []` in `cargo.ts`), so every
such identity was withheld. Five of the 18 Rust sweep pins commit no
lockfile, and library repositories usually do not.

**The rule.** With no lockfile, a dependency declared by version
requirement only (no `path`, `git`, `registry` or `registry-index`) is
taken from the default registry together with the facade's own
registry dependencies, unless:

- the root manifest (or the member's) has a `[patch]` or `[replace]`
  entry naming the implementing crate (a malformed one withholds all), or
- any captured `.cargo/config(.toml)` anywhere in the checkout sets
  `paths`, `[source]` or `[patch]`, or cannot be read.

Anything else stays withheld. The requirement must also fall in the
release family the macro catalogue records (as for a locked version).

Why this holds, from the Cargo reference:

- A dependency written as a version requirement is looked up on
  crates.io by default
  ([Specifying dependencies](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#specifying-dependencies-from-cratesio)).
- A crate published on crates.io can depend only on crates on crates.io;
  `path` and `git` dependencies are not allowed in a published crate's
  manifest ([Publishing](https://doc.rust-lang.org/cargo/reference/publishing.html#before-publishing-a-new-crate);
  [git dependencies](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#specifying-dependencies-from-git-repositories)).
  So the facade's own dependency on its implementing crate is a registry
  dependency.
- The only ways to make Cargo take a registry crate from elsewhere are
  `[patch]` and `[replace]` in the workspace root manifest, `paths`
  overrides and `[patch]` in configuration, and source replacement
  ([Overriding dependencies](https://doc.rust-lang.org/cargo/reference/overriding-dependencies.html);
  [Source replacement](https://doc.rust-lang.org/cargo/reference/source-replacement.html);
  [config `[patch]` and `paths`](https://doc.rust-lang.org/cargo/reference/config.html#patch)).
- Cargo reads configuration from the directory it is run in and every
  parent ([Hierarchical structure](https://doc.rust-lang.org/cargo/reference/config.html#hierarchical-structure)),
  so a config in any directory of the checkout can apply to some build;
  the rule therefore looks at every captured config, not only the
  member's ancestors. A `$CARGO_HOME` config outside the checkout is not
  part of the snapshot, as for every other Cargo fact the graph reads.

Cargo itself agrees on the fixtures
([cargo-check.txt](../../evidence/c-24/cargo-check.txt), from
[cargo-check.sh](../../evidence/c-24/cargo-check.sh), Cargo 1.98.1, no
lockfile): the plain requirement resolves `tokio` and `tokio-macros` from
crates.io; a manifest `[patch]` or a config `[patch]` takes
`tokio-macros` from the path.

**The macro name itself.** Separately, the stored macro link (which crate's
macro `#[derive(Serialize)]` or `#[tokio::main]` is) now needs only the
verified registry facade. A published facade's re-export
(`pub use serde_derive::Serialize`) is fixed text, so in compiling code
the name is that facade's export whichever source supplies the crate
behind it. What the macro *expands to* does depend on the implementing
crate, so expansion proofs (C-12 output bounds and the
`rust-external-macro-name` effect assumption) keep C-18's requirement:
the scope probe uses `scopeMacroExport`, which still requires the
implementation's source. A facade from a path, a replaced registry, or
under a `paths` override (which can replace the facade itself) is not
named. Import links (`use thiserror::Error`) still need the export's
namespace, which comes from the implementation; the lockfile rule
supplies it when it applies.

Tests (`test/graph-rust-macro-scope.test.mjs`, the C-18 Tokio fixtures
with no lockfile): plain requirement → identified (with the existing
assumption mark); manifest `[patch]`, config `paths`, config source
replacement, a config `[patch]` in a subdirectory, and a facade by path
→ expansion withheld; the macro link is named in every case where the
facade itself is a verified registry release.

## 3. Inherent impls belong to the type's own crate

Rust allows an inherent `impl Type { … }` only in the crate that defines
`Type` ([Implementations: inherent implementations](https://doc.rust-lang.org/reference/items/implementations.html#inherent-implementations);
error [E0116](https://doc.rust-lang.org/error_codes/E0116.html)). The
resolver keeps impls whose self type it cannot place (for example a type
an attribute macro generates) as possible owners of any method of that
name in every crate that can reach them, which blocked definite method
calls on unrelated checkout types. Now an unplaced *inherent* impl is a
possible candidate only for types defined in its own crate. Unplaced
*trait* impls are unchanged: another crate may implement its trait for a
checkout type.

The shape is dioxus `packages/interpreter/src/unified_bindings.rs`
(`impl Interpreter { pub fn base(&self) … }` beside
`#[sledgehammer_bindgen::bindgen(module)] mod js`), which made
`self.base()` in `packages/web/src/hydration/cursor.rs:135` unresolved
once C-21 reads that file. C-21 is not merged, so the fixture is written
from the shape (`test/graph-rust-c24.test.mjs`): crate `a` defines
`Cursor` with an inherent `base`, crate `b` has the unplaced inherent
impl and an unplaced trait impl. `c.base()` in `a` is definite; the trait
method stays a would-be target; with the unplaced impl in `a` itself the
call stays unresolved.

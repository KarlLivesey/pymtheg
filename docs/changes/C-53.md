# C-53: Write each Go, Rust and TypeScript file once

## What a cold index wrote twice

`scripts/link-writes/diagnose.mjs` runs a cold index and records every
graph write statement by phase: the parse write, the analysis writes and
the resolution writes. For each link row it also records every body
written, by insert or by rewrite in place. Main, dependencies as checked
out:

| Pin | Links stored | Links inserted twice | Second insert identical | Second insert with other `data` |
|---|--:|--:|--:|--:|
| restic | 63,836 | 58,163 | 53,656 (92%) | 4,507 |
| cli/cli (Go) | 208,993 | 192,390 | 180,725 (94%) | 11,665 |
| helix (Rust) | 90,583 | 90,311 | 35,920 (40%) | 54,391 |
| dioxus (Rust) | 150,404 | 150,189 | 65,534 (44%) | 84,655 |

Every Go and Rust file was written twice, and every TypeScript file too
(as a placeholder that waits for analysis, then as analysed):
- **First, as parsed.** The parse write stored the file record, its symbols
  and its links.
- **Then, as analysed.** The module's analysis read the records back from
  the store. Every file whose analysed result differed from its parse
  result was replaced whole: all its link rows deleted and inserted again,
  its symbols upserted again, and its record rewritten.

Analysis adds facts to some links (receiver types, `cfg` and macro facts),
so most files differ somewhere, even where most of their links do not.

The resolution write was already a write of what changes:
- the target column of each link whose target or outcome changes;
- its candidate rows and library-target rows;
- a link body only when the decision changed its `data`.

On restic it wrote 71,125 rows: 43,064 target updates, 9,310 candidates,
17,914 library targets and 835 links the resolver added. No link row was written there with only its
outcome columns differing. So the double write was the parse/analysis
pair, not analysis/resolution.

## What the first write was for

- **The hand-over to analysis.** The analysis input was read back from
  the store (`filesAt`). Nothing else between the phases reads these
  files' rows. Other modules' analyses read only their own files, and
  resolution runs after every analysis write.
- **Kill-safety.** A run killed between the phases left parse results
  stored and its unfinished mark set. The next run then trusts no record
  (C-22: it parses every file again and reuses no analysis). So nothing
  depended on those parse rows surviving.
- **Run ownership.** The parse write was usually a run's first commit, and
  the first commit carries the run's mark. A second run started after it
  finds the mark and takes over. The first run's later writes then fail
  its ownership check (`test/graph-index-runs.test.mjs`).
- **C-27's partial results.** When Go reuses decisions, the indexer
  already held the edited files until analysis (`deferred`) and handed the
  module their previous records. In the unscoped case it still wrote them
  twice: first as parsed, then as analysed. (C-36, since merged, holds
  Rust files the same way when Rust reuses its analysis.)
- **The equality rule and the analysis-complete record** do not depend on
  when a file is written, only on what is stored at the end and on the
  run's mark and completion.

## The change

The smaller of the two candidates: hold, don't write twice.

1. **Hold the parse results.** The parse results of every module that
   analyses are held until that module's analysis: Go's, Rust's and
   TypeScript's. TypeScript files are held and written once too: main
   first wrote a placeholder record that waits for analysis (TypeScript
   parses nothing) and then replaced it; now only the analysed record is
   written (the review counted tauri's file writes falling from 828 to
   418). Each is held as the record the
   store would hold (its JSON text). Analysis gets freshly decoded copies,
   as it got them from the store before, so a module that edits its input
   in place cannot change what is stored (`graph-core-isolation` caught a
   first version that held the objects themselves). Before, this happened
   only when a module reused its analysis (Go, C-27; Rust, C-36). Analysis gets the held files in the same
   path order the store lists records in, with new files included. The
   previous records are still handed only to a module that may reuse its
   analysis (C-27).
2. **Write each held file once.** It is written with its analysed result
   if the module returned one, else as parsed, and its links are inserted
   once. A held file's parse failure is cached exactly as its parse write
   would have recorded it.
3. **Commit the run's mark where the parse write used to.** A run holding
   files that main's parse write would have written commits its mark at
   the end of the parse write (`claimIndexRun`, an empty write, so it
   proves ownership like any other). Without this, a run paused in
   analysis has written nothing. A second run then finds the store current
   and writes nothing, and the first run later writes analysis of a tree
   that had changed back. The two review tests in `graph-index-runs`
   caught exactly that in the first version. Files of a module reusing its
   analysis (Go C-27, Rust C-36) were held before this change too and
   claim nothing, so a run stopped in such an analysis still leaves the
   previous complete graph (C-36's signal tests).

No module's output changed, so no module version changes: the store is
equal to main's, row for row.

**Memory.** Held records live until their module's analysis, instead of
being re-read from the store at that point. With one language, the peak
should be the parse phase's, as before (argued, not measured: the parse
phase held every capture until its write, and analysis decoded every
record of the module; the cold table's peak memory is the only
measurement). With several, a later module's held
files outlive the earlier modules' analyses (modules run in name order:
go, rust, typescript).

## Kill points

- **Existing tests.** The C-22 kill tests (TypeScript, Go, Go scoped, Go
  promoted facts, Rust) kill a re-index after each of its committed
  writes in turn, including the new claim commit between the phases.
  Each kill point is repaired to cold by one normal run. C-37's small-batch
  variants pass too.
- **New tests** (`test/graph-links-written-once.test.mjs`):
  - A cold index of a Go and Rust fixture writes each file once and each
    link row once (`store.filesWritten` and `store.linkRowsInserted` equal
    the stored counts; no link row deleted).
  - A run stopped inside Go analysis, and one stopped inside Rust
    analysis, leave the run's mark and none of that module's files. The
    next run equals a cold index.
- **C-33's verified no-edit run** holds nothing and claims nothing, so it
  still writes no row (`graph-index-runs`, `graph-reindex-equality`).
- **C-37's batches and turnstile** are unchanged. The claim is a write
  inside the parse write's batch.

# C-22: re-index after a one-file edit

The owner's target: after editing one file, the code graph must re-index
almost immediately, and a cold index should be fast too. This chunk measures
where a one-file edit's time goes, by deterministic work counts as well as
by time, and removes the largest repository-proportional cost that could be
removed soundly in one pull request. It changes no link, reason, symbol or
coverage number: no module version changes, the coverage plan is untouched,
and the stores are proved identical (below).

It also fixes a defect found on main (C-20 code) that made a re-index **with
no edit** store a graph unlike a cold index of the same tree on checkouts
with installed dependencies: see [Warm ≠ cold with installed
dependencies](#warm--cold-with-installed-dependencies). That fix does change
results — back to what a cold index of the tree gives.

## What changed

- **Work counters** (`src/graph/work.ts`): observation-only counts and
  stage times for one index — files hashed and read, files parsed, analysis
  input files, links handed to each resolver, links compared, file, symbol
  and link rows written, link targets rewritten, stored records decoded and
  SQL statements executed — and wall and process CPU time per stage (the
  indexer's walk, capture, parse, per-module analysis, resolution, validation
  and writes; the command layer's two inventories). Nothing reads them to
  decide anything. The TypeScript module's existing `statistics` (programs
  built, files extracted) are reported with them.
- **One read of a module's links per write.** Before, the resolve phase read
  a module's links three times — the resolver's input, the indexer's
  validation, and the store's `replaceAnalysis`, which also derived the
  validated result a second time — and read every symbol three times. Now
  the resolver's input reads only the parsed link records, which it receives
  unresolved anyway (`moduleInputLinks`: no candidate or library sub-reads),
  and after it returns the indexer reads the module's links and symbols once,
  validates with `resolutionFacts`, and the store writes from that validated
  result: `replaceAnalysis(module, result, validated)`, where `validated`
  holds the links read once (`analysisLinks`) and the result derived from
  them. The written rows are the same: they are what `replaceAnalysis` would
  have read and derived from the same, unchanged state. A store without
  `analysisLinks` takes the old path.
- **Analysis reads only its own module's files** (`fileSummaries` +
  `filesAt`) instead of decoding every stored file and filtering.
- **A module with no stored file gets no graph to resolve.** Its only valid
  result is empty (a resolution must name one of its parsed links, an added
  link one of its files), so it is not handed every file, symbol and link.
  The error checks before it are unchanged, so a failed context still
  reports a resolution error.

No stored format, setting or dependency is added. The `GraphStorage`
interface gains five optional methods — `moduleInputLinks`,
`analysisLinks`, `unfinishedIndexRun`, `beginIndexRun` and
`finishIndexRun` — and `replaceAnalysis` an optional third argument (the
validated links); `ValidatedAnalysis` is a new type. The store adds
`GraphIndexTakenOver`, the error an overtaken index run stops with.

## How it was measured

Six sweep pins (`sweep/repos.json`), two per language, one mid-sized and one
large: Go `restic/restic` and `cli/cli`, TypeScript `honojs/hono` and
`trpc/trpc`, Rust `BurntSushi/ripgrep` and `helix-editor/helix`. For each
(`scripts/reindex/measure.mjs`, edits in `scripts/reindex/cases.json`): a
cold index, a warm re-index with no edit, then three one-file edits to one
widely imported file — (a) a comment line appended, (b) a no-op statement
inside one function body, (c) a new exported function — each followed by a
re-index, then reverted and re-indexed again. Each index is a fresh process
through the CLI's own entry point (`executeGraph`, with an abort signal and
progress on, as `pymtheg graph index` runs it; `scripts/reindex/index-once.mjs`).
Files edited: restic `internal/errors/errors.go`, cli `pkg/cmdutil/errors.go`,
hono `src/utils/url.ts`, trpc
`packages/server/src/unstable-core-do-not-import/utils.ts`, ripgrep
`crates/matcher/src/lib.rs`, helix `helix-core/src/graphemes.rs`.

"Before" is the merged main (`fdeb52f`) plus the counters only; "after" adds
the change. Times are observations on the shared dev server, which was
heavily loaded during these runs (load average 16–33 from other builders):
wall time includes waiting for a busy disk, and CPU time varies by up to 50%
between identical runs (main itself, restic cold: 137 and 211 CPU seconds).
**The counts are the comparison**; they are identical between repeated runs.
CPU profiles (`--cpu-prof`) were taken of the body and export edits of every
pin; the two slowest cases (trpc and cli/cli body edits) are summarised in
`evidence/c-22/profiles/`. Rust's phases run in a worker thread, which the
main-thread profile does not sample; stage CPU times are process-wide, so
they include it.

**Read across:** whatever the edit — a comment, a body statement or a new
export — the files hashed, analysis input files, links handed to the
resolvers, links compared and records decoded are the same for every edit
and are the whole repository: proportional to the repository, not to the
edit. A no-edit re-index differs in one way: for Go and Rust it does the
same whole-project analysis and resolution as an edit, but TypeScript reuses
its stored analysis when none of its inputs changed (hono: 0 programs and 0
extractions with no edit, 24 programs and 965 extractions after a one-line
comment; helix, whose edits are to Rust files, reuses in both), so for TypeScript the first edit is what triggers the
whole-program rebuild. (trpc rebuilds all 55 programs even with no edit,
because its failed files are retried on every run.) Rows written follow the
edit, widened on TypeScript by the offset-keyed declarations below.

### What each stage is proportional to, and why

| stage | proportional to | the rule that forces it |
|---|---|---|
| hash every source | repository | The snapshot rules hash original bytes and never trust mtimes (`command-snapshot.ts`, runtime map "Snapshot/parser"); the command layer hashes the tree before the index and again after it to report edits made during it, and the indexer reads and hashes it once more to capture the one source snapshot. |
| decode each stored record for its hash | repository | The cache check reads each previous record (`getFile`) for its hash, module and version — decoding its whole text and result. The command layer counts those reads as its "inventory" progress. |
| parse | **edit** | Parse results are cached by content hash, module and version. |
| write parsed files | **edit** | Only parsed files are written. |
| read analysis input | repository | `analyze` is a whole-program phase: it receives every file of its module. Before this change each module also decoded every other module's files. |
| language analysis | repository | TypeScript builds every program (one per owning `tsconfig`) from scratch and extracts every file whenever any file changed (reuse only when every changed file is a known failure): hono 24 programs and 965 extractions for a one-line comment; trpc 55 and 1,347. Go's `analyze` runs the whole resolver (`linkNotes`) over every package to find overflow, builtin, failure and library notes. Rust's `analyze` runs `resolveRust` over every crate for the same kind of notes. |
| write changed analysis results | edit, widened | Only results that changed are written — but TypeScript keys some declarations by source offset (`function@4610`), so a body edit that moves later declarations changes the stored link facts of every file that links to them: 17 files (12,672 link rows) on hono, 44 files (23,928 rows) on trpc. A comment appended at the end moves nothing and writes 1–7 files. |
| read resolver input | repository | `resolve` receives every file (all modules), every symbol and all of its module's parsed links, decoded afresh for each module (C-2 forbids keeping them between modules). Before this change, modules with no files read them too. |
| language resolution | repository | Go and Rust resolve every link of the project again (the second whole-project run after `analyze`'s); TypeScript maps its recorded facts to ids for every link. |
| validate resolution | repository | Every link of the module is decided and validated. |
| compare and write links | repository compare, edit write | The store compares every link of the module with the new result and writes only the rows that differ (`writeTargets`, a diff since C-6) — but before this change it first re-read every link with its candidate and library rows and derived the whole result again. |
| report, checkpoint | repository | Row counts, and a checkpoint that holds the whole inventory. |

So the store write is already a diff (rows written follow the edit: 40 link
rows and 9 target rows for a restic edit); the cost was in reading and
re-deriving what it compares. The big costs are the whole-program language
phases, and the per-module reads around them.

### Where the time went in the two slowest cases

- **trpc body edit (94 CPU s):** TypeScript program construction and
  extraction (53 s); writing the 44 files whose link facts moved (12 s; the
  profile shows 29 s inside per-file write transactions on a busy disk);
  reading and writing links (16 s).
- **cli/cli body edit (83 CPU s):** the profile's single largest frame is
  the store's link read, `selectLinks`: 25 s of 72 s sampled, three reads of
  217,000 links with their candidate and library sub-queries; decoding
  every file record 7 s; Go's two whole-project resolutions 13 s + 12 s.

## Part 2 — after

The largest cost a one-file edit pays is whole-program language analysis
(TypeScript's program rebuild, Go's and Rust's two whole-project
resolutions). It cannot be made edit-proportional soundly in one pull
request (sketch below), and the TypeScript module is being changed by two
other pull requests. The largest repository-proportional cost that can be
removed without changing what any phase computes is the shared layer's
repeated reads of every link and record around the resolver; that is what
this change removes. For Go it was the largest single cost of an edit
(cli/cli: 17.3 s compare-and-write + 16.0 s resolver input, against 25.6 s
of Go analysis and resolution).

## Equality proof

The soundness rule: after any edit, the incremental store must be identical,
row for row, to a cold index of the edited tree. The comparison
(`scripts/reindex/dump.mjs`) takes every row of `graph_files` (each file's
whole result: symbols, links, reasons, data), `graph_contexts`,

## Warm ≠ cold with installed dependencies

**The report.** On trpc with dependencies installed, the sweep's warm graph
(a re-index with no edit after the cold index) had about 660 fewer proofs
than expected — 545 `expect-type` member calls unresolved and 115 left at a
unit — and two warm runs on two installs differed by 305 gains and one
withdrawal, while cold counts reproduced (C-23, tRPC controls).

**Not reproduced in isolation.** On a fresh pnpm install of trpc (the
sweep's own install settings, `scripts/reindex/install.mjs`), cold → warm →
warm stores were identical row for row, and so were hono installed and the
bare pins. So the difference needs something outside the checkout.

**Cause.** `DependencyInputs` (C-20) records a stamp for each installed
file it probes — device, inode, mode, size, mtime and **ctime** — from the
run's first `lstat`, cached for the run. `read()` then compared the open
file's `fstat` with that stamp and, on any difference, returned *undefined*:
the declaration was treated as absent. pnpm installs package files as hard
links into a content store, and the sweep's installed mode gives all its
parallel pins one store (`--store-dir` under the shared scratch). When
another pin's install links the same store file, the inode's ctime changes
and its bytes do not. A declaration probed before that moment and read
after it vanished for the rest of the run. `expect-type` is installed by
every vitest-using pin, so it is exactly the package whose store files
other installs keep linking. Whether the cold or the warm index was hit
depended on timing: correctness depended on machine speed.

**Reproduced, deterministically in effect.** The trpc installed store from a
cold index; then a warm re-index while a loop adds and removes a second
hard link to each `expect-type` declaration file — inode metadata only
(`scripts/reindex/link-churn.sh`, diagnosis only). On main's code the warm
store differs from cold in 72 files, 729 links and 729 → 151 library
targets: `expect-type` targets 771 → 42, `vitest` 16,210 → 16,361 (sites
falling back to vitest's re-export of the unit). That is the reported
pattern and size.

**Fix** (`src/graph/dependency-inputs.ts`, shared layer; no TypeScript
module file changes). Whether an installed file changed is decided by its
**content**, never by metadata alone. `read()` reads through its own
handle; if the handle's stamp moved during the read (ctime, nlink — what a
link added and removed by another install does), the file is read again and
its bytes compared by hash: the same bytes are used, different bytes mean
it is being written, so it is tried once more and then treated as absent.
Between runs the stamp stays the cheap first check, and the stored content
hash breaks the tie: a recorded file whose stamp moved but whose bytes hash
the same is unchanged, and its record takes the stamp it now has (the one a
cold index would record).

*Corrected after the second review.* The first two versions compared stamps
only, so a link added and removed between the read and the handle's last
`fstat` on both attempts still dropped an unchanged declaration. A test now
moves the file's metadata during every read (a wrapped `readFileSync`, no
timing): the file is read, recorded as usable, and a later metadata-only
change is no change for the next run; a file whose bytes change during
every read is treated as absent.

*Cost of the tie-breaker:* after another project's install links the same
store files, each recorded installed file that this project **read** has a
moved stamp and is hashed once more on the next run (files only probed,
never read, have no hash and count as changed, as before). On trpc
installed that is up to 9,922 of its 48,410 recorded installed inputs
(63 MB) hashed once — a fraction of a second of SHA-256 on this server — and
the 38,488 probed-only inputs whose stamps moved still force one full
TypeScript analysis, as on main. Verified on trpc installed with link churn
on every `expect-type` declaration during a warm re-index: links, symbols
and library targets identical to cold (only the 14 stamps observed during
the churn differ), and the next plain re-index equals a fresh cold index row
for row.

*Corrected after review.* The first version of this fix re-read a file
whenever its stamp had moved and recorded only the last read's stamp. Two
programs of one run could then analyse different bytes of one declaration
(the first the old bytes, the second the new) while the stored stamp
matched the new bytes, so the next re-index noticed nothing and the store
stayed unlike a cold index for good — worse than main, which treated the
file as absent and recovered on the next run. Now:

- within one run every read of an installed file returns the bytes of its
  first read (kept for the run by location; `package.json`, read both for
  module resolution and by `library.ts`, included);
- the record holds those bytes' content hash and the stamp taken from the
  handle that read them;
- at the end of the run (`records()`), a file whose stamp on disk is no
  longer the one of the bytes used is recorded with a stamp no file can
  have, so the next run sees the input as changed and analyses again.

The review's reproduction is a test: two `tsconfig` programs over one
installed `kit/index.d.ts`, whose mode changes before the run's first read
and whose bytes change after it (a hook on the read, no timing). On the
previous version both programs saw different texts and the next re-index
did not equal a cold index; now both see one text and one more re-index
equals a cold index of the changed tree.

**After the fix** (measured with the first version; the correction keeps
this behaviour: churn changes no bytes, so the first read's bytes are the
bytes on disk). The same churned warm re-index stores files, symbols,
links, candidates and library targets identical to cold; the only
differing rows are the 14 dependency stamps of the churned files. The next
plain re-index then equals a fresh cold index of the tree row for row,
stamps included.
Tests: `test/graph-dependency-inputs.test.mjs` (a metadata-only change
between probe and read — fails on main, passes now; a content change; an
absent file) and the installed fixture in the equality harness.

**What it means for C-23's figures:** the ordinary sweep's warm tRPC graph
was taken while other pins were installing; the controlled same-install
replays were not. The difference between them is this race, not a warm
path in the TypeScript module. Re-running the installed sweep with this fix
should make the ordinary and controlled tRPC figures agree.

## A killed or crashed index leaves no stale graph

**Found in review, present on main.** A re-index killed after its first
analysis write and before its last left files whose records matched their
source hashes but carried a mix of old and new analysis. The next normal
re-index found every file unchanged, the TypeScript module reused the
stored analysis ("unchanged snapshot"), and the store stayed unlike a cold
index while reporting itself complete; a second re-index did not help. Go
and Rust were not affected in practice (their analysis reruns in full every
time), but nothing in the store said a run was cut short.

**Fix** (`src/graph/store.ts`, `src/graph/indexer.ts`). The run's mark
(`graph_meta` key `index-run`, with the removal of the completion record)
is written in the same commit as the run's first write (`beginIndexRun`
arms it; the store's first transaction writes it) and cleared in the run's
last commit (`finishIndexRun`, after resolution) — only if it was written,
so an index that changes nothing still writes nothing and leaves the file's
bytes and journal mode as they were (C-6). A store's commits survive a crash
only as a prefix (C-6), so any write of the run that survives has the mark
with it.

*Owned, after the third review.* Two index runs on one store could defeat
a shared mark: run A analysed a tree with an export removed and paused; the
export was restored; run B completed and cleared the mark; A resumed, wrote
stale caller data and was killed; the next re-index reported complete with
`src/b.ts` keeping an unresolved call a cold index resolves. Now the mark
carries the identifier of the run that wrote it:

- a run begins (`beginIndexRun`) before it reads the store, noting the
  store's data version; a mark found then belongs to a run that did not
  finish or is still running, so this run takes it over at once (writing its
  own identifier) and treats everything as changed;
- its first write first checks, inside the same transaction, that no other
  connection has committed since it began (the connection's own switch to
  the write-ahead log aside) and that no mark appeared; each later commit
  checks that the mark is still its own; if not, the run stops without
  writing and throws `GraphIndexTakenOver` ("Another graph index run
  started on this store and took it over …");
- it clears the mark only if it still owns it;
- a completion record is written only if no other connection committed
  since the run's last commit (or, for a run that wrote nothing, since it
  began); a direct write by another connection between two of the run's
  commits lets the run finish but publish no completion.

So of two overlapping runs at most one writes after the other starts, and a
store becomes complete only through a run that started from a state it
fully read. Two `graph index` commands at once (from the CLI or MCP jobs,
which use the same command path): the second to write stops with that
message instead of the old UNIQUE-constraint error. Tests
(`test/graph-index-runs.test.mjs`, interleavings forced by gates in the
TypeScript analysis, no timing): the reviewer's exact case; A paused before
writing, B completes, A resumes and writes nothing; A paused, B starts and
pauses, A resumes and stops, B finishes and equals a cold index; two
command-path cold indexes at once. On the previous head the reviewer's
case, the two-paused case and the two-commands case fail. A run that finds the mark
(`unfinishedIndexRun`) counts every claimed file and every context file as
changed: no module reuses stored analysis, and parse results stay cached,
since each is complete for its content hash. `graphCommandState()` returns
nothing while the mark is set, so `graph status` is never complete then.
The rule chosen is the simplest sound one — after an unfinished run, every
module is analysed in full once — rather than a per-file record of the
snapshot each analysis came from. **Cost:** per run that writes, two
statements in its first commit and one extra commit at the end, plus the
mark and data-version reads at the start and at each commit. Re-measured on the six pins (final build,
`evidence/c-22/final/`): every count and every report identical to the
earlier "after" run except SQL statements, +7 per index that writes (+11 and
+14 on the cli/cli and hono cold indexes) and +2 on a no-edit re-index that
writes nothing; every reverted edit again equal to cold. After a crash one full
analysis, which is what any context-file change already costs.

**Tested** (`test/graph-reindex-kill.test.mjs`, with
`test/graph-reindex-kill-child.mjs`, C-6's technique): for a Go, a Rust and
a TypeScript fixture, an index, then an edit that changes other files'
analysis, then for each n a copy of the project re-indexed by a child
process that kills itself (SIGKILL) right after the n-th committed store
write — every write boundary of the run: 7 for TypeScript, 6 for Go, 7
for Rust — and then one
normal re-index. After every kill, `graph status` is not complete (unless
the kill came after the completion record), and the one re-index equals a
cold index of the edited tree row for row. On the code before this fix the
TypeScript case fails at the third of its 7 writes.

## A no-edit `graph index` writes nothing

The direct `indexProject` call was byte-stable, but `graph index` through
the command path removed the completion record before every run and wrote
it again after, changing the database bytes on a no-edit run. The command
path no longer removes it up front (the run's first write removes it in the
same commit), writes it only when it would differ, and removes it at the
end of a run that does not complete. A writable connection that writes
nothing but finds a write-ahead log left by a killed run still returns the
store to its at-rest journal on close. Test: two command-path indexes of an
unchanged project leave the database file byte for byte as it was (fails on
the previous head).

## What still makes a one-file edit slow (after this change)

Ranked by the CPU time they cost a body edit on these pins; the estimate is
what an edit-proportional version would leave.

1. **TypeScript program rebuild and full extraction** — hono 65 s, trpc
   57 s. Every program is built and every file extracted on every change.
   *Estimate:* in a long-lived process (MCP, Studio) reusing the old program
   and re-extracting only affected files: a few seconds; in the CLI, with
   on-disk per-file extraction keyed by dependency signatures, program
   construction remains (≈30–40% of today's analysis).
2. **Rust whole-project resolution, twice** — helix 23 s + 26 s, ripgrep
   6 s + 7 s. *Estimate:* per-crate invalidation with an exported-surface
   fingerprint: an edit that keeps a crate's surface re-resolves that crate
   only (helix: a few seconds); one run instead of two halves what is left.
3. **Go whole-project resolution, twice** — cli/cli 13 s + 11 s, restic
   5 s + 3 s. *Estimate:* as Rust, per package.
4. **TypeScript offset-keyed declarations** — hono 5 s and trpc 16 s to
   rewrite the files whose link facts name a moved declaration (17 and 44
   files). *Estimate:* keys anchored to the declaration (name and scope)
   would make a body edit write one file.
5. **Resolver input** — every file record (with its source text), every
   symbol and the module's links, decoded per module: cli/cli 8.6 s, helix
   4.4 s, trpc 3.9 s. *Estimate:* resolvers that declare the fields they
   read (Rust already drops text before its worker) could skip most of it.
6. **Hashing every source three times** — 0.3–3.4 s. The command layer's
   two inventories and the indexer's capture could share one hash pass of
   the same bytes; mtimes stay untrusted.
7. **Decoding each stored record for its hash** — 0.3–1.5 s; a summary
   query would do, but the command layer's progress counts these reads.
8. **Validation reads, process start, store open, checkpoint** — 2–10 s.

## What the big one needs (design sketch)

Whole-program language analysis is the largest cost and the one that makes
an edit repository-proportional. Making it edit-proportional needs, in
order:

1. **An exported-surface fingerprint per file**, computed by each module
   from exactly the facts other files' resolution reads: Go — the file's
   `FileFact` (package, imports, build constraint, filename platform) and
   its symbols without ranges, plus its embedding and type-position links;
   Rust — items, `use` trees, `mod` declarations, `macro_rules` and exported
   macros, `cfg` attributes and `Cargo.toml`; TypeScript — the file's
   declaration signatures (what a `.d.ts` emit holds) and module kind. The
   proof obligation, per module: every cross-file read in the resolver goes
   through fingerprinted data. A body or comment edit then has an unchanged
   fingerprint unless it moves something keyed by position (see 4 above).
2. **A partial result in the indexer contract.** `analyze`/`resolve` may
   return "these files' links re-decided; every other stored decision
   stands", and the store writes those files' links. Unchanged fingerprint ⇒
   only the edited file; changed fingerprint ⇒ the edited file plus its
   reverse-dependency closure (importers of the package, crate dependents,
   files whose program contains it); a changed manifest ⇒ the whole module,
   as today. Global facts must be in the fingerprint or force the fallback:
   Go's implementer sets and candidate caps, Rust's glob and macro scopes,
   Go's package-level shadowing of predeclared names.
3. **Global indexes rebuilt cheaply or kept.** The Go and Rust resolvers
   build whole-project indexes before resolving any link. Rebuilding them
   from stored facts is linear but cheap next to resolution; persisting
   them needs a key over every fingerprint.
4. **TypeScript:** reuse needs the program. Across CLI processes nothing
   compiler-side can persist; per-file extraction results can, keyed by the
   module version, compiler options and the fingerprints of every file the
   file's program reaches (TypeScript's builder computes the same affected
   set from signature hashes). A long-lived process can keep programs and
   pass `oldProgram`.
5. **Proof:** this chunk's harness applies unchanged; each module adds a
   randomised run per pin in its own pull request.

Estimated size: Go one pull request (fingerprint, partial result, package
closure); Rust one or two; TypeScript two (offset keys first, then reuse).

## Found, not built

- TypeScript symbol keys that contain source offsets (`function@4610`): an
  unrelated insertion above a declaration changes the key recorded in other
  files' link facts. Besides the cost above, it is worth checking against
  the stable-identity rule for requirement links.
- The Go standard-library table is read from
  `src/graph/languages/go/stdlib/table.txt.gz` relative to `dist/`. A copy
  of `dist/` without it (an early measurement build of this chunk) silently
  resolved 4,018 fewer library members on restic instead of failing.
- trpc never reaches a complete graph (`complete: false`: six failed files
  are retried on every run), so even a re-index with no edit rebuilds all 55
  programs and rewrites 12 files.

node scripts/reindex/fetch.mjs "$PYM_SCRATCH" restic/restic cli/cli honojs/hono trpc/trpc BurntSushi/ripgrep helix-editor/helix
